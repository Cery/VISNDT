# VISNDT 媒体中心批量上传 / 批量删除 / 产品媒体批量上传 实施方案

## Context（背景与目标）

媒体资源当前管理存在操作闭环缺口：媒体中心（`/media`）只读浏览，无法批量上传、无法批量删除；产品/能力媒体只能单个上传。用户要求补齐三项能力，同时必须规避两个数据完整性问题：

1. **`batchDelete` 是"裸删除"**：直接 `deleteMany`，不删 S3 对象、不校验引用 → 会残留存储、删除被引用文件触发 FK 错误。
2. **孤儿判定只校验 `ProductMedia` 引用**：`findOrphans`/`cleanupOrphans` 不覆盖 ContentMedia / ContentCoverImage / SupplierProductMedia 引用 → 存在误删"已被内容引用"文件的真实风险。
3. **NestJS 上传默认 1MB**：所有现有端点是裸 `FileInterceptor('file')`，后端默认 `fileSize=1MB`，与 `validateFile` 声明的 10MB 不符，>1MB 文件实际会被 multer 拒绝。

目标：媒体中心支持"带归属的多选批量上传 + 多选批量删除"；产品媒体支持"多选批量上传"；并一并加固孤儿判定与引用校验（用户已确认「一并加固」）。

**约束：不改 Prisma schema / 不做 migration；复用现有 service 方法；全部仅 ADMIN。**

## 一、后端改动

### 1A. 加固 `batchDelete`（批量删除安全语义）
文件：`apps/api/src/file-asset/file-asset.service.ts`（方法现于 L290）

- 重构 `batchDelete(ids)`，返回结构改为：`Promise<{ deleted: number; failed: { id: string; reason: string }[] }>`。
- 新增私有帮助方法：
  ```ts
  private async canDeleteSafely(id: string): Promise<{ ok: boolean; reason?: string }>
  ```
  - `findUnique({ where: { id }, include: { _count: { select: { media, contentMedia, contentCoverImages, supplierProductMedia } } } })`。
  - 不存在 → `{ ok:false, reason:'NOT_FOUND' }`。
  - 任一 count>0 → reason 分别映射 `REFERENCED_BY_PRODUCT_MEDIA` / `REFERENCED_BY_CONTENT_MEDIA` / `REFERENCED_BY_CONTENT_COVER` / `REFERENCED_BY_SUPPLIER_PRODUCT_MEDIA`。
- `batchDelete` 用 `for...of` 编排（借鉴现有 `cleanupOrphans` 的逐条模式 L235），通过则复用现有 `delete(id)`（DB+S3 原子，L167），累计 `deleted`；失败项进 `failed`。

### 1B. 加固孤儿判定与清理（用户已确认）
文件：`apps/api/src/file-asset/file-asset.service.ts`

- `findOrphans()`（L208）：查询条件由现状 `entityId: PLACEHOLDER_ENTITY_ID AND media none` 改为 **`entityId: PLACEHOLDER_ENTITY_ID AND organizationId: null AND media none AND contentMedia none AND contentCoverImages none AND supplierProductMedia none`**。使"带归属批量上传"（有 organizationId）的文件不再落入孤儿列表，避免被孤立清理误删。
- `cleanupOrphans()`（L235）逐条再校验的 `_count` 由 `{ media: true }` 扩展为同样覆盖 `contentMedia / contentCoverImages / supplierProductMedia`，命中任一即 `failed` 并给出原因。

### 1C. 带归属批量上传端点 `POST /files/batch-upload`
文件：`apps/api/src/file-asset/file-asset.controller.ts`、`file-asset.service.ts`、新增 `apps/api/src/file-asset/dto/batch-upload.dto.ts`

- Controller 新增（ADMIN only，注意置于 `:id` 路由逻辑之前无冲突，放在 `batch-delete` 附近）：
  ```ts
  @Post('batch-upload')
  @UseGuards(JwtAuthGuard, RolesGuard) @Roles(Role.ADMIN)
  @ApiConsumes('multipart/form-data')
  @UseInterceptors(FilesInterceptor('files', 10, { limits: { fileSize: MAX_FILE_SIZE } }))
  async batchUpload(@UploadedFiles() files, @Req() req, @Body() dto: BatchUploadDto)
  ```
  - import `UploadedFiles, FilesInterceptor`。
- **必须**给 `FilesInterceptor` 显式 `limits.fileSize = 10MB`（匹配 `validateFile`），否则 >1MB 被 multer 层拦截。
- `BatchUploadDto`：`fileType?: FileType`（`@IsOptional @IsEnum`）、`organizationId?: string`（`@IsOptional @IsUUID`）、`entityType?: FileEntityType`（`@IsOptional @IsEnum`，默认 `PRODUCT`）。
- Service 新增：
  ```ts
  async batchUploadWithOwnership(files, userId, opts: { fileType?; organizationId?: string | null; entityType? }):
    Promise<{ created: FileAsset[]; failed: { fileName: string; reason: string }[] }>
  ```
  - 逐文件 `validateFile(file)`，失败进 `failed` 不中断整体。
  - `entityId` 保持 placeholder；`organizationId` = opts.organizationId（显式写入，不从登录用户派生）；`fileType` = opts.fileType ?? `mapMimeTypeToFileType(mime)`；`status: ACTIVE`。
  - 单个 DB `create` 失败则 `storage.deleteObject(key)` 回滚（参考 `product-media.service.ts` `createWithUpload` 回滚语义）。

### 1D. 产品媒体批量上传端点 `POST /products/:productId/media/batch-upload`
文件：`apps/api/src/product-media/product-media.controller.ts`、`product-media.service.ts`

- Controller 新增（复用现有 `POST /media/upload` 的守卫/注解模式，L65-83）：
  ```ts
  @Post('batch-upload')
  @UseGuards(...) @Roles(Role.ADMIN) @ApiConsumes('multipart/form-data')
  @UseInterceptors(FilesInterceptor('files', 10, { limits: { fileSize: MAX_FILE_SIZE } }))
  async createWithUploadBatch(@Param('productId') productId, @UploadedFiles() files, @Body() dto, @Req() req)
  ```
- Service 新增 `createWithUploadBatch(productId, files, dto, userId)`：`for...of` 逐文件复用 `createWithUpload`（原有子上传+建 ProductMedia+回写 entityId+回滚，L100-159），`displayOrder` 按 `当前产品 max(displayOrder)+1 + idx` 递增；聚合返回 `{ created: ProductMedia[]; failed: { fileName; reason }[] }`，单个失败不中断。

## 二、前端改动

### 2A. 类型与 API 封装
文件：`apps/admin/src/types/file-asset.types.ts`、`apps/admin/src/api/file-asset.service.ts`、`apps/admin/src/api/product-media.service.ts`

- 新增类型：`BatchDeleteResult { deleted; failed:{id,reason}[] }`、`BatchUploadResult { created: FileAsset[]; failed:{fileName,reason}[] }`。
- `fileAssetService.batchDelete` 返回类型改为 `Promise<BatchDeleteResult>`。
- 新增 `fileAssetService.batchUpload(files: File[], opts: { fileType?; organizationId?; entityType? })`：FormData 逐个 `append('files', f)` + `append('fileType'/'organizationId'/'entityType')`，`headers: { 'Content-Type': 'multipart/form-data' }`。organizationId 省略时不 append（后端落 null）。
- 新增 `productMediaService.createWithUploadBatch(productId, files, metadata)`：FormData `files` + 元数据，POST `products/:id/media/batch-upload`。

### 2B. MediaList 批量删除
文件：`apps/admin/src/pages/MediaList.tsx`

- 新增 `selectedRowKeys` state；`Table` 加 `rowSelection`，`getCheckboxProps` 基于 `productMediaCount/contentMediaCount`（`FileAssetListItem` 已有）**禁用被引用行**并 `title:'文件被引用，无法删除'`。
- 工具栏「孤立文件清理」按钮旁（L447 附近）加「批量删除」`Button danger`，`disabled={selectedRowKeys.length===0}`。
- 点击 → `Modal.confirm` → `fileAssetService.batchDelete(ids)` → 用返回 `failed` 生成明细（成功 N / 失败 M + 原因）→ 清空选择并 `fetchData()`；异常用 `extractErrorMessage`。

### 2C. MediaList 带归属批量上传
文件：`apps/admin/src/pages/MediaList.tsx`

- 工具栏加「批量上传」按钮 → 打开 `Modal`：
  1. `Upload.Dragger multiple`（`beforeUpload` 收集 File[] 并返回 false，沿用 `ProductMediaCreate.tsx` 模式）。
  2. `fileType` `Select`（复用 `FILE_TYPE_OPTIONS`，默认 `IMAGE`）。
  3. `organizationId` `Select`（复用 `organizations`/`orgOptions`，默认第一个组织）。
- 确认 → `fileAssetService.batchUpload(files, { fileType, organizationId })` → 失败明细提示 → 关闭并 `fetchData()`。

### 2D. ProductMediaList 批量上传
文件：`apps/admin/src/pages/product-media/ProductMediaList.tsx`

- 标题栏「添加媒体」旁加「批量上传」`Button` → `Modal`：`Upload.Dragger multiple` + `mediaType` `Select`（复用媒体类型选项，默认 `IMAGE`）。
- 确认 → `productMediaService.createWithUploadBatch(productId, files, { mediaType })` → 成功/失败提示 → 清空并 `fetchData()`（列表与 `mediaStats` 自动刷新）。

## 三、元数据/默认策略（不改 schema）

| 场景 | 字段 | 策略 |
|---|---|---|
| 媒体中心批量上传 | `fileType` | 前端下拉显式 → 后端 `?? mapMimeTypeToFileType` |
| 媒体中心批量上传 | `entityType` | 默认 `PRODUCT` |
| 媒体中心批量上传 | `organizationId` | 必由前端下拉显式传（默认第一组织）→ 后端强制写入 |
| 媒体中心批量上传 | `entityId` | 保持 placeholder（后续经 ProductMedia create 回写） |
| 产品媒体批量上传 | `mediaType` | 一次批量共用同一下拉值（必填，默认 `IMAGE`） |
| 产品媒体批量上传 | `displayOrder` | service 内 `当前 max + 1 + idx` 递增 |
| 产品媒体批量上传 | `isPrimary/title/description` | 批量统一默认（不改 schema 的最小集合） |

## 四、Multer 大小限制修复（必做）

- 新端点（1C/1D）`FilesInterceptor` 显式 `{ limits: { fileSize: 10MB } }`。
- **顺带统一**：现有 `FileInterceptor('file')`（`file-asset.controller.ts:65`、`product-media.controller.ts:72`、`content-media.controller.ts:69`、`supplier-products-self-service.controller.ts:152`）同样补 `{ limits: { fileSize: 10MB } }`，使它们与 `validateFile` 的 10MB 声明一致（低风险纯增量。若用户希望最小范围，则至少保证新端点配置，现有端点列为说明）。

## 五、验证方案（end-to-end）

前置：`apps/api`（MinIO 就绪）+ `apps/admin` 运行，浏览器 `http://localhost:3001`，账号 `admin@visndt.com` / `admin123456`（已重置）。

1. **批量删除语义**：媒体中心选中一个"未引用"文件 + 一个"被 ProductMedia 引用"文件 → 批量删除 → 断言返回 `{deleted:1, failed:[引用原因]}`；被引用行 checkbox 前端禁用。数据库/MinIO 核对：未引用文件已删，被引用文件仍在且可下载。
2. **带归属批量上传**：媒体中心「批量上传」多文件 + fileType=SPEC_SHEET + 指定组织 → 列表出现多条，所属组织=所选、类型=规格书、所属实体=能力、entityId=placeholder；且 `GET /files/orphans` **不含**这些文件（加固后效果）。
3. **产品媒体批量上传**：某产品媒体页「批量上传」多图 + mediaType=IMAGE → 表格多条，`displayOrder` 递增，`entityId` 已回写为对应 ProductMedia.id（非孤儿）。
4. **孤儿加固**：确认"被 ContentMedia 引用"的文件不会再出现在孤儿列表、不会被 `cleanupOrphans` 清理。
5. **负向**：单文件 >10MB 或非白名单 MIME → 该条进 `failed`，整体不 500。

浏览器端用 `webapp-testing`/`agent-browser` 做登录后逐点 E2E 并截图；配合后端 `FileAssetService`/`ProductMediaService` logger 与 MinIO 对象列表核对。
