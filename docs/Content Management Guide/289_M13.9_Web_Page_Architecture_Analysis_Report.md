## 2. 静态页面分析

### 2.1 静态页面清单

| 页面 | 路由 | 内容来源 | 硬编码项目数 |
|------|------|----------|-------------|
| 解决方案 | `/solutions` | 组件内 `SOLUTIONS` 常量数组 | 5 个行业 |
| 知识中心 | `/knowledge` | 组件内 `SECTIONS` 常量数组 | 4 个分类，16 个条目 |
| 商务合作 | `/business` | 组件内 `SECTIONS` 常量数组 | 3 个合作类型 |
| 关于我们 | `/about` | 组件内 JSX 硬编码 | 4 个信息区块 |

此外，首页组件 `SolutionsSection.tsx` 中也硬编码了 4 个解决方案条目，与 `/solutions` 页面的内容部分重复但独立维护。

### 2.2 各页面详细分析

#### 2.2.1 解决方案页 (`/solutions`)

**当前内容**: 5 个行业解决方案卡片，每个包含标题、描述、应用场景。

```typescript
// 数据来源: 组件内硬编码
const SOLUTIONS = [
  { title: '航空航天检测', description: '...', scenario: '...' },
  { title: '汽车检测',       description: '...', scenario: '...' },
  { title: '管道检测',       description: '...', scenario: '...' },
  { title: '电子检测',       description: '...', scenario: '...' },
  { title: '制造检测',       description: '...', scenario: '...' },
];
```

**为什么是静态的**: 当前开发阶段，解决方案内容作为展示性信息直接写在组件中，避免了数据库设计和 API 开发的工作量。这是一种MVP阶段的快速实现方式。

**缺失的功能**:
- 无行业详情页 (如 `/solutions/aerospace`)
- 无关联产品推荐 (每个解决方案应展示相关检测设备)
- 无案例/白皮书下载
- 无CMS后台管理入口 (Admin 后台完全没有"解决方案管理"菜单)

#### 2.2.2 知识中心页 (`/knowledge`)

**当前内容**: 4 个分类 (检测指南、技术文章、应用案例、选型指南)，每个分类下有 4 个条目，共 16 个条目以纯文本列表形式展示。

```typescript
const SECTIONS = [
  { title: '检测指南', items: ['视觉检测入门', '理解内窥镜规格参数', ...] },
  { title: '技术文章', items: ['高清与标清内窥镜对比', ...] },
  { title: '应用案例', items: ['航空航天：涡轮叶片检测', ...] },
  { title: '选型指南', items: ['如何选择探头直径', ...] },
];
```

**为什么是静态的**: 同解决方案页，为快速上线而采用硬编码实现。条目仅作为标题列表展示，未实现真正的文章内容。

**缺失的功能**:
- 无文章详情页 (如 `/knowledge/articles/visual-inspection-intro`)
- 无富文本内容 (所有条目只有标题，没有正文)
- 无分类筛选/搜索
- 无CMS后台管理 (Admin 后台完全没有"知识中心管理"菜单)
- 无阅读量/点赞/收藏等互动功能
- 无SEO优化 (每篇文章应有独立的 meta 信息)

#### 2.2.3 商务合作页 (`/business`)

**当前内容**: 3 个合作类型 (制造商、技术合作伙伴、行业合作)，每个类型包含描述和 4 个亮点。

**为什么是静态的**: 商务合作信息属于低频变更的企业信息，硬编码在初期是合理的。但随着业务发展，合作类型、权益说明等内容可能需要灵活调整。

**缺失的功能**:
- 无合作申请表单 (用户无法在线提交合作意向)
- 无合作详情页
- 无CMS后台管理

#### 2.2.4 关于我们页 (`/about`)

**当前内容**: 使命、服务内容 (4 个卡片)、服务行业、联系方式。全部以 JSX 硬编码。

**为什么是静态的**: 企业基本信息变更频率极低，这是最适合静态化的页面。但联系方式、地址等信息的变更仍需修改源码。

**缺失的功能**:
- 无CMS后台管理 (联系方式修改需改代码)
- 无团队介绍/发展历程等扩展区块

### 2.3 静态页面共同问题

| 问题 | 影响 |
|------|------|
| 内容更新需修改源码并重新构建部署 | 运营效率低，非技术人员无法操作 |
| 无二级详情页 | 信息密度低，SEO 效果差 |
| 无搜索/筛选功能 | 用户体验差，信息查找困难 |
| 无CMS管理后台 | 内容管理完全依赖开发团队 |
| 内容与首页组件重复且独立维护 | 维护成本高，容易出现不一致 |

## 3. 内容管理现状

### 3.1 当前内容管理方式

```
运营需求 → 提给开发 → 修改源码 → 提交代码 → 构建 → 部署 → 上线
```

**所有非产品类内容** (解决方案、知识文章、商务合作、企业信息) **均以硬编码方式写在 React 组件源码中**。内容更新流程完全依赖开发人员介入，周期长、成本高。

### 3.2 当前 CMS 覆盖情况

| 内容类型 | 是否有 CMS | 管理方式 | 所处系统 |
|----------|-----------|----------|----------|
| 产品信息 | **有** | Admin 后台 CRUD | Admin |
| 产品分类 | **有** | Admin 后台 CRUD | Admin |
| 技术参数/参数组 | **有** | Admin 后台 CRUD | Admin |
| 用户/组织 | **有** | Admin 后台 CRUD | Admin |
| 需求/询价/RFQ | **有** | Admin 后台管理 | Admin |
| 通知 | **有** | Admin 后台管理 | Admin |
| **解决方案** | **无** | 修改源码 | - |
| **知识中心** | **无** | 修改源码 | - |
| **商务合作** | **无** | 修改源码 | - |
| **关于我们** | **无** | 修改源码 | - |
| 首页展示内容 | **无** (部分) | 修改源码 | - |

### 3.3 理想的内容管理架构

理想情况下，内容管理应遵循以下模式:

```
                    ┌─────────────────┐
                    │   CMS 管理后台   │
                    │  (Admin 系统)   │
                    └────────┬────────┘
                             │ 内容编辑/发布
                             ▼
                    ┌─────────────────┐
                    │   后端 API 服务  │
                    │  (内容存储/检索) │
                    └────────┬────────┘
                             │ 数据接口
                             ▼
                    ┌─────────────────┐
                    │   Web 前台展示   │
                    │  (动态渲染内容)  │
                    └─────────────────┘
```

当前只有"产品信息"这条链路走通了完整流程，其他内容类型仍停留在"直接写死在 Web 前台"阶段。

## 4. 二级页面缺失分析

### 4.1 当前有二级页面的路由

Web 前台中，仅有以下路由具备二级页面能力:

| 一级路由 | 二级路由 | 实现方式 |
|----------|----------|----------|
| `/products` | `/products/[slug]` | 动态路由，按 slug 获取产品详情 |
| `/workspace/demands` | `/workspace/demands/[id]` | 动态路由，按 ID 获取需求详情 |
| `/workspace/rfqs` | `/workspace/rfqs/[id]` | 动态路由，按 ID 获取询价详情 |

Home 首页 (`/`) 没有独立的二级页面，其内容通过 Sections 组件平铺展示。

### 4.2 应该但缺失二级页面的路由

#### 4.2.1 知识中心 (`/knowledge`) -- 优先级: 最高

**当前状态**: 16 个条目以纯文本 `<li>` 列表展示，点击无任何反应。

**应有结构**:
```
/knowledge                          ← 知识中心首页 (分类导航 + 最新文章)
/knowledge/[category]               ← 分类列表页 (如 /knowledge/guides)
/knowledge/[category]/[article-slug] ← 文章详情页 (富文本正文)
```

**缺失影响**:
- 16 个条目只有标题，无正文内容，用户无法获取任何实质性知识
- 无独立文章URL，SEO 几乎为零
- 无内容深度，无法建立行业专业形象

**示例**: 条目"视觉检测入门"应导向 `/knowledge/guides/visual-inspection-intro`，包含完整的图文教程、相关产品推荐、相关文章链接等。

#### 4.2.2 解决方案 (`/solutions`) -- 优先级: 高

**当前状态**: 5 个行业卡片，点击无跳转。

**应有结构**:
```
/solutions                          ← 解决方案总览页
/solutions/[industry]               ← 行业详情页 (如 /solutions/aerospace)
```

**行业详情页应包含**:
- 行业痛点与挑战
- 检测方案详解 (技术路线、设备选型)
- 典型案例展示
- 推荐产品列表 (关联产品 API)
- 相关文章/白皮书
- 咨询/询价 CTA

#### 4.2.3 商务合作 (`/business`) -- 优先级: 中

**当前状态**: 3 个合作类型卡片，无进一步交互。

**应有结构**:
```
/business                           ← 商务合作总览页
/business/[type]                    ← 合作类型详情页 (如 /business/manufacturer)
/business/apply                     ← 合作申请表单页
```

#### 4.2.4 分类 (`/categories`) -- 优先级: 中

**当前状态**: 分类卡片仅链接到 `/products?categoryId=xxx`，无独立分类页。

**应有结构**:
```
/categories                         ← 分类总览页 (当前已有)
/categories/[slug]                  ← 分类详情页 (展示该分类下的产品列表)
```

### 4.3 二级页面缺失汇总

| 一级页面 | 缺失的二级页面类型 | 缺失数量 (估算) | SEO 影响 |
|----------|-------------------|----------------|----------|
| `/knowledge` | 分类列表页 + 文章详情页 | 4 分类 + 16+ 文章 | 严重 |
| `/solutions` | 行业详情页 | 5 行业 | 严重 |
| `/business` | 合作类型详情页 + 申请页 | 3 类型 + 1 表单 | 中等 |
| `/categories` | 分类详情页 | 动态数量 | 中等 |

## 5. 改进建议

### 5.1 短期改进方案 (1-2 周，低成本)

**目标**: 在不引入数据库/CMS 的前提下，提升内容展示质量和 SEO。

**具体措施**:

1. **为知识中心创建静态文章详情页**
   - 使用 Next.js 的 `generateStaticParams` 为每个文章条目生成独立路由
   - 在 `/knowledge/[category]/[slug]` 下创建 `page.tsx`
   - 文章内容以 Markdown 文件 (`.mdx`) 形式存放在 `content/knowledge/` 目录
   - 使用 `next-mdx-remote` 或 `@next/mdx` 渲染
   - 优点: 无需数据库，内容通过 Git 管理，可版本控制，支持 PR 审核

2. **为解决方案创建行业详情页**
   - 使用 `generateStaticParams` 为 5 个行业生成独立路由
   - 内容以 Markdown 文件存放在 `content/solutions/` 目录
   - 每个行业详情页关联推荐产品 (通过 API 按分类筛选)

3. **目录结构示例**:
   ```
   content/
   ├── knowledge/
   │   ├── guides/
   │   │   ├── visual-inspection-intro.mdx
   │   │   ├── borescope-specs.mdx
   │   │   └── ...
   │   ├── articles/
   │   ├── cases/
   │   └── selection/
   └── solutions/
       ├── aerospace.mdx
       ├── automotive.mdx
       └── ...
   ```

**成本估算**: 约 3-5 人天 (创建 Markdown 文件 + 路由 + 渲染组件)

**局限性**: 仍需要开发人员通过 Git 提交来更新内容，但比改 JSX 源码更友好，且支持 Markdown 编辑器预览。

### 5.2 中期改进方案 (2-4 周，CMS 集成)

**目标**: 引入轻量级 CMS，实现非技术人员可管理内容。

**方案 A: 使用 Headless CMS (推荐)**

推荐使用 **Strapi** (开源) 或 **Contentful** (SaaS):

- 创建内容类型 (Content Types):
  - `Article`: 文章 (标题、分类、正文、封面图、SEO 元数据、状态)
  - `Solution`: 解决方案 (行业名称、描述、痛点、方案、案例、关联产品)
  - `BusinessCooperation`: 合作类型 (名称、描述、权益、申请链接)
  - `AboutPage`: 关于页面 (各区块内容，支持富文本)

- Web 前台改为从 CMS API 获取数据 (SSR/ISR)
- 内容更新后通过 Webhook 触发 Next.js 重新验证 (ISR revalidate)

**后端改动**:
- 在 Admin 后台添加内容管理菜单:
  - 知识中心管理 (文章 CRUD)
  - 解决方案管理 (行业 CRUD)
  - 商务合作管理 (合作类型 CRUD)
  - 页面内容管理 (关于我们等页面区块)

**方案 B: 扩展现有 Admin 系统**

在现有 NestJS 后端中新增内容管理模块:

- 新增数据库表: `articles`, `solutions`, `business_cooperations`, `page_contents`
- 在 Admin 前端新增对应的管理页面
- 在 Web 前台通过 API 获取内容

**推荐**: 方案 A (Headless CMS) 对于内容管理场景更成熟，提供富文本编辑器、媒体管理、版本控制等开箱即用的功能。方案 B 适合团队有充足开发资源且希望完全掌控的场景。

**成本估算**: 约 10-15 人天 (CMS 搭建 + 内容类型定义 + 前端对接)

## 6. 总结

### 6.1 核心发现

1. **内容管理能力严重不均衡**: VISNDT 平台在产品管理方面已具备完善的 CRUD 能力 (Admin 后台 41 个路由覆盖产品、分类、参数、用户、订单等全生命周期管理)，但在内容管理方面几乎为零 -- 4 个关键展示页面 (`/solutions`, `/knowledge`, `/business`, `/about`) 全部为硬编码静态页面。

2. **二级页面大量缺失**: 知识中心有 16 个条目但无任何文章详情页，解决方案有 5 个行业但无行业详情页。这导致:
   - 信息密度极低，用户无法获取深度内容
   - SEO 效果差，搜索引擎无法收录实质性内容页面
   - 无法支撑内容营销策略

3. **内容更新依赖开发部署**: 所有非产品内容的修改都需要经过完整的开发→构建→部署流程，运营效率低，无法支撑快速迭代的内容运营需求。

4. **首页与独立页面内容重复**: `SolutionsSection` 组件与 `/solutions` 页面各自维护独立的解决方案数据，存在不一致风险。
