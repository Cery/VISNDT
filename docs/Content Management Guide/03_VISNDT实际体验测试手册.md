| 项目 | 内容 |
|------|------|
| **测试目标** | 验证 NestJS API 服务正常启动 |
| **前置条件** | 数据库已启动，环境变量已配置 |

**操作步骤:**

1. 进入 API 目录并启动:
   ```bash
   cd apps/api
   pnpm dev
   ```
2. 等待控制台输出启动成功日志
3. 验证健康检查接口:
   ```bash
   curl http://localhost:4000/api/v1/health
   ```
4. 验证 API 文档（如有 Swagger）:
   ```bash
   curl http://localhost:4000/api/v1/docs -o /dev/null -w "%{http_code}"
   ```

**预期结果:**

- [ ] 控制台输出 "Nest application successfully started"
- [ ] 健康检查接口返回 200 OK
- [ ] API 日志无报错信息
- [ ] 端口 4000 未被占用

**常见问题与解决:**

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 端口 4000 被占用 | 其他进程占用 | `netstat -ano \| findstr :4000` 查看并终止进程 |
| 数据库连接失败 | 数据库未启动或配置错误 | 检查 .env 中数据库连接字符串 |
| 模块加载失败 | 依赖未安装 | 运行 `pnpm install` |
| JWT 密钥缺失 | 环境变量未配置 | 检查 .env 中 JWT_SECRET |

### 1.6 服务启动一键检查脚本

在项目根目录执行以下 PowerShell 命令进行一键验证:

```powershell
# 检查各端口占用情况
Write-Host "=== 端口检查 ===" -ForegroundColor Cyan
@(3000, 3001, 4000, 5432) | ForEach-Object {
    $conn = Get-NetTCPConnection -LocalPort $_ -ErrorAction SilentlyContinue
    if ($conn) { Write-Host "端口 $_ : 已占用 (PID: $($conn.OwningProcess))" -ForegroundColor Green }
    else { Write-Host "端口 $_ : 未占用" -ForegroundColor Red }
}

# 检查 API 健康
Write-Host "`n=== API 健康检查 ===" -ForegroundColor Cyan
try {
    $res = Invoke-WebRequest -Uri "http://localhost:4000/api/v1/health" -UseBasicParsing -TimeoutSec 5
    Write-Host "API 状态: $($res.StatusCode)" -ForegroundColor Green
} catch {
    Write-Host "API 不可达: $_" -ForegroundColor Red
}

# 检查 Web 前台
Write-Host "`n=== Web 前台检查 ===" -ForegroundColor Cyan
try {
    $res = Invoke-WebRequest -Uri "http://localhost:3000" -UseBasicParsing -TimeoutSec 5
    Write-Host "Web 状态: $($res.StatusCode)" -ForegroundColor Green
} catch {
    Write-Host "Web 不可达: $_" -ForegroundColor Red
}

# 检查 Admin 后台
Write-Host "`n=== Admin 后台检查 ===" -ForegroundColor Cyan
try {
    $res = Invoke-WebRequest -Uri "http://localhost:3001" -UseBasicParsing -TimeoutSec 5
    Write-Host "Admin 状态: $($res.StatusCode)" -ForegroundColor Green
} catch {
    Write-Host "Admin 不可达: $_" -ForegroundColor Red
}
```

## Part 8: 删除操作问题诊断专项

> **背景**: 当前测试中发现 Admin 后台多个模块（产品、分类、参数、报价、询价等）删除操作提示"失败"但原因不明。本专项旨在系统化排查所有删除操作，明确每个删除失败的具体原因。

### 8.1 删除操作通用检查清单

| 检查项 | 说明 | 操作 |
|--------|------|------|
| 删除前确认弹窗 | 是否显示确认弹窗？弹窗内容是否明确？ | 每个删除操作前观察 |
| 删除操作 HTTP 请求 | 是否发送了 DELETE / POST 请求？方法是否正确？ | 打开浏览器 Network 面板监视 |
| 后端响应状态码 | 返回 200 / 400 / 404 / 500？ | 检查 Network 面板响应 |
| 后端响应体内容 | 返回的具体错误信息是什么？ | 检查 Response body |
| 前端错误提示 | 前端显示什么提示文案？是后端返回的原文还是前端自己写的？ | 观察 UI 提示 |
| 前端成功假象 | 是否弹窗提示"成功"但数据未删除？ | 删除后刷新页面确认数据状态 |
| 删除后列表刷新 | 删除后页面是否自动刷新？刷新后数据是否消失？ | 观察列表变化 |
| 事务回滚验证 | 如果删除失败，是否有部分数据已被删除的情况？ | 检查关联数据完整性 |

**通用诊断步骤:**

1. 打开浏览器 DevTools → Network 面板，勾选 "Preserve log"
2. 执行删除操作
3. 找到对应的 DELETE/POST 请求
4. 检查：
   - **Request URL**: 是否正确
   - **Request Method**: 是否是 `DELETE` 或 `POST /batch-delete`
   - **Status Code**: 200=成功, 4xx=客户端错误, 5xx=服务端错误
   - **Response**: 查看具体错误信息
   - **Request Headers**: 是否包含 `X-CSRF-Token`（如需）
5. 刷新页面，确认数据状态

## Part 12: 工作流与状态流转测试

> **背景**: 业务实体（需求、RFQ、报价、询价、匹配）都有各自的生命周期状态机。状态非法跳跃会导致数据不一致和业务流程错误。本部分测试所有状态流转的合法性。

### 12.1 需求状态流转

| 项目 | 内容 |
|------|------|
| **测试目标** | 验证需求（Demand）的状态机：DRAFT → PUBLISHED → CLOSED / CANCELLED |
| **前置条件** | 登录 Web 前台 Buyer 账号 |

**状态机定义:**
```
DRAFT ──→ PUBLISHED ──→ CLOSED
  │                        │
  └──→ CANCELLED ←─────────┘
```

**合法流转:**
- DRAFT → PUBLISHED（发布需求）
- PUBLISHED → CLOSED（关闭需求）
- DRAFT → CANCELLED（取消草稿）
- PUBLISHED → CANCELLED（取消已发布需求）

**非法流转（应被阻止）:**
- PUBLISHED → DRAFT（已发布不能回到草稿）
- CLOSED → DRAFT（已关闭不能回到草稿）
- CLOSED → PUBLISHED（已关闭不能重新发布）
- CANCELLED → 任何状态（已取消不能变更）

| 2 | DRAFT → PUBLISHED | 在草稿需求上点击"发布" | 状态变为 PUBLISHED，出现在活跃需求列表 | [ ] |
