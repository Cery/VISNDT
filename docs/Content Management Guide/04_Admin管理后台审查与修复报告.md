## 2. 产品管理

### 2.1 问题1：产品删除400错误

#### 问题描述
点击"删除"按钮时，弹窗显示 `Request failed with status code 400`，控制台输出 `DELETE http://localhost:3001/api/v1/products/{id} 400 (Bad Request)`。

#### 根因分析
后端 `products.service.ts` 的 `remove()` 方法在删除前会检查产品是否有关联数据：

```typescript
// products.service.ts (L135-L161)
async remove(id: string) {
  const product = await this.prisma.product.findUnique({
    where: { id },
    include: { offers: true, demandMatches: true },
  });

  if (product.offers.length > 0) {
    throw new BadRequestException(
      'Cannot delete product with existing offers. Remove offers first.',
    );
  }
  if (product.demandMatches.length > 0) {
    throw new BadRequestException(
      'Cannot delete product with existing demand matches. Remove matches first.',
    );
  }
  // ... 事务删除
}
```

**结论**: 这不是Bug，而是数据完整性保护机制。当产品存在关联的Offer（报价）或DemandMatch（需求匹配）时，系统拒绝删除以防止数据不一致。

#### 已修复内容
- 前端 `ProductList.tsx` 已使用 `extractErrorMessage()` 来显示后端返回的具体错误信息，而非通用的"请求失败"
- 后端 `extractErrorMessage` 函数已添加到 `client.ts`

#### 建议改进
- 在删除确认弹窗中显示具体的错误原因（如"此产品存在关联的报价记录，请先删除报价再删除产品"）
- 考虑添加"级联删除"选项，允许管理员在确认后删除所有关联数据

### 2.2 问题2：批量删除未实现功能

#### 问题描述
选择多个产品后点击批量删除，弹窗提示"删除成功"，但实际并未删除。

#### 根因分析
批量删除调用了 `POST /products/batch-delete`，后端使用 `Promise.allSettled` 遍历调用 `remove()` 方法。如果某个产品有关联数据，`remove()` 抛出异常，但 `Promise.allSettled` 会捕获异常并继续执行，最终返回的 `count` 可能小于请求删除的数量。

#### 已修复内容
- 前端 `handleBatchDelete` 已改为检查 `result.count` 实际删除数量
- 当 `result.count !== ids.length` 时，显示警告信息提示部分删除失败

#### 修复后代码
```typescript
const result = await productService.batchDelete(ids);
if (result.count === ids.length) {
  message.success(`成功删除 ${result.count} 个产品`);
} else {
  message.warning(`成功删除 ${result.count} / ${ids.length} 个产品（部分因有关联数据无法删除）`);
}
```

| 密码 | ✅ 已有 | 创建时必填，编辑时可留空 |
| 组织ID | ✅ 已有 | 可选，输入组织UUID |
| 状态(编辑模式) | ✅ 已有 | 编辑时可修改状态 |

#### 问题分析

当前User模型的设计（基于Prisma Schema）：
```prisma
model User {
  id             String     @id @default(uuid()) @db.Uuid
  email          String     @unique
  passwordHash   String
  name           String?
  status         UserStatus @default(ACTIVE)
  organizationId String?    @map("organization_id") @db.Uuid
  ...
}
```

**关键问题**:
1. **User模型没有角色字段** - 用户的角色是通过 `OrganizationMember` 模型的 `role` 字段来定义的，但创建用户时无法直接设置角色
2. **组织ID使用原始UUID输入** - 用户体验差，应该改为选择下拉框
3. **缺少姓名字段** - 创建用户时不能设置姓名

#### 建议改进

1. **创建用户表单增加"姓名"字段**
2. **"组织ID"改为组织选择下拉框** - 从API获取组织列表供选择
3. **增加"角色"选择** - 在创建用户时同时创建OrganizationMember记录
4. **考虑User模型增加role字段** - 简化角色管理

## 11. 需求/RFQ/询价/报价关系分析

### 11.1 业务概念定义

| 术语 | 英文 | 定义 | 创建者 | 目标 |
|------|------|------|--------|------|
| **需求** | Demand | 采购方发布的需求信息 | 采购方(BUYER) | 描述需要采购的产品/服务 |
| **RFQ** | Request for Quotation | 基于需求生成的报价请求 | 系统/采购方 | 向供应商征求报价 |
| **询价** | Inquiry | 访客对产品的询价咨询 | 访客(未登录) | 咨询产品信息和价格 |
| **报价** | Offer | 供应商对产品的报价 | 供应商(SUPPLIER) | 向采购方提供价格 |

### 11.2 业务流程关系图

```
                    ┌─────────────┐
                    │  访客(Inquiry) │  ← 前台提交，无需登录
                    └──────┬──────┘
                           │ 关联产品
                           ▼
                    ┌─────────────┐
                    │   产品目录   │  ← 全局产品目录
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
       ┌──────────┐  ┌──────────┐  ┌──────────┐
       │  需求    │  │  报价    │  │  询价    │
       │ (Demand) │  │ (Offer)  │  │(Inquiry) │
       └────┬─────┘  └──────────┘  └──────────┘
            │
            │ 生成
            ▼
       ┌──────────┐
       │  RFQ    │  ← 向供应商征求报价
       └────┬─────┘
            │
            ▼
       ┌──────────┐
       │RFQ响应   │  ← 供应商响应报价请求
       └──────────┘
```

### 11.3 关系分析

| 关系 | 说明 |
|------|------|
| 需求 → RFQ | 一个需求可以生成一个RFQ，RFQ是需求的具体化询价请求 |
| RFQ → RFQ响应 | 供应商对RFQ的响应，包含报价信息和产品 |
| 报价 → 产品 | 报价关联到具体产品，由供应商创建 |
| 询价 → 产品 | 访客对产品的询价咨询，独立于需求和RFQ |
| 匹配 → 需求+产品 | 匹配引擎将需求与产品进行匹配 |

### 11.4 关键区别

**需求 vs RFQ vs 询价 vs 报价**:

| 维度 | 需求(Demand) | RFQ | 询价(Inquiry) | 报价(Offer) |
|------|-------------|-----|---------------|-------------|
| 发起方 | 采购方 | 采购方 | 任意访客 | 供应商 |
| 是否需要登录 | 是 | 是 | 否 | 是 |
| 面向对象 | 内部 | 供应商 | 平台管理员 | 采购方 |
| 生命周期 | 草稿→已发布→处理中→已关闭 | 草稿→开放→响应中→已关闭 | 新建→处理中→已回复→已关闭 | 草稿→已提交→已接受/已拒绝/已撤回 |
| 关联产品 | 通过匹配 | 通过需求 | 直接关联 | 直接关联 |
| 用途 | 描述采购需求 | 向供应商询价 | 访客咨询 | 供应商报价 |

### 11.5 建议

1. **RFQ和询价名称混淆**：已修复，RFQ管理页面明确使用"RFQ管理"而非"询价管理"
2. **Admin后台应该显示所有模块**：需求、RFQ、询价、报价四个模块在Admin后台都有独立管理页面
3. **建议在页面添加简要说明**：在每个管理页面顶部添加简短的功能说明，帮助管理员理解用途

### 12.1 平台参与权限

| 角色 | 需求 | RFQ | 询价 | 报价 | 匹配 |
|------|------|-----|------|------|------|

```

    ↓
生成RFQ → 供应商响应RFQ → 采购方审核响应
    ↓

```

### 12.3 建议优化

1. **简化流程**：考虑将需求发布后自动生成RFQ作为可选流程
2. **状态联动**：需求关闭时，关联的RFQ自动关闭
3. **通知集成**：RFQ发布后自动通知相关供应商
4. **匹配结果整合**：在需求详情页直接展示匹配产品，并支持一键生成RFQ
