### 3.2 Architecture Verdict

当前架构更接近：

`Demand -> 自动匹配 -> Buyer 手动创建 Demand 级 RFQ -> 所有 Supplier 可见并提交 Response`

而不是：

`Demand -> 选择 Match -> 面向特定 Match / Supplier 发起 RFQ -> Supplier Response -> Buyer 决策闭环`

因此，`M14.3` 的真正工作重点不是补页面，而是补齐 **流程约束、权限边界、数据关联**。

## 4. Risk List

### High

1. **RFQ 未与 Match 建立强关联，主链条在 Match -> RFQ 处断开**
   - `RFQ` 模型仅关联 `demandId`，且 `demandId` 为唯一字段，未记录 `sourceMatchId` / `targetOrganizationId`。证据：`VISNDT/database/prisma/schema.prisma:547-560`
   - Buyer 侧创建 RFQ 仅提交 `demandId`，未从已接受 Match 发起。证据：`VISNDT/apps/web/src/app/workspace/rfqs/create/page.tsx:44`、`VISNDT/apps/api/src/rfqs/rfqs.service.ts:131`
   - Supplier 可通过 `/rfqs/available` 获取所有 `OPEN/RESPONDING` RFQ，而不是仅获取与自身匹配相关的 RFQ。证据：`VISNDT/apps/api/src/rfqs/rfqs.controller.ts:29-33`、`VISNDT/apps/api/src/rfqs/rfqs.service.ts:80-107`

2. **Buyer 无法完成 Response 审核决策闭环**
   - Buyer RFQ 详情页仅展示响应列表，没有接受/拒绝/标记已阅动作。证据：`VISNDT/apps/web/src/app/workspace/rfqs/[id]/page.tsx:88-127`
   - `RFQResponse.update()` 的权限校验明确限制为“响应所属组织”，即 Supplier 自己；这与 `ACCEPTED/REJECTED` 应由 Buyer 决策的业务语义冲突。证据：`VISNDT/apps/api/src/rfq-responses/rfq-responses.service.ts:233-272`
   - 现有 `RFQResponseStatus` 包含 `VIEWED / ACCEPTED / REJECTED`，但当前对外能力无法由 Buyer 驱动完成。证据：`VISNDT/database/prisma/schema.prisma:49-54`

### Medium

3. **Match Workspace 与后端状态机存在契约不一致**

   - 后端允许的迁移是 `PENDING -> MATCHED -> REVIEWED -> ACCEPTED/REJECTED`，并不允许 `MATCHED -> REJECTED`。证据：`VISNDT/apps/api/src/demands/demands.service.ts:26-33,664-706`

4. **MatchingModule 已有内部状态方法，但外部闭环实际走的是 Demand 模块状态更新**

### 5.2 Match -> RFQ

## 7. API / Database Planning Verdict

### 7.1 是否需要新增 API

结论：**需要**。

最小必要 API 能力：

1. **Match 驱动 RFQ 创建能力**
   - 目标：从已审阅 / 已接受 Match 发起 RFQ，而不是从 Demand 直接发起
   - 建议形态：
     - `POST /rfqs/from-match`
     - 或 `POST /demands/:id/matches/:matchId/create-rfq`

2. **Buyer 侧 Response 决策能力**
   - 目标：让 Buyer 能执行 `VIEWED / ACCEPTED / REJECTED`
   - 建议形态：
     - `POST /rfq-responses/:id/view`
     - `POST /rfq-responses/:id/accept`
     - `POST /rfq-responses/:id/reject`
   - 也可收口成一个 `PATCH /rfq-responses/:id/decision`

3. **可选：Match Workspace 后端聚合接口**
   - 当前不是主阻塞项，但若 M14.3 继续扩展筛选/排序/批量动作，建议新增 buyer 侧聚合接口，替代前端 fan-out

4. **可选：Workflow Timeline / Notification 跳转辅助接口**
   - 当前不是闭环硬阻塞项
   - 可优先复用现有 `workflow-events` 与 `notifications`，只在确实需要过滤/映射时扩展

### 7.2 是否需要新增数据库字段

结论：**需要，且仅加字段可能还不够**。

最小必要数据能力：

1. **RFQ 与 Match 的来源关联**
   - 建议至少补一个来源关系：
     - `RFQ.sourceMatchId`
   - 目的：保证 RFQ 来自哪条 Match 可追踪

2. **RFQ 的目标主体约束**
   - 若业务要求“一个 RFQ 面向一个目标 Supplier”
     - 需要 `RFQ.targetOrganizationId`
   - 若业务要求“一个 Demand 面向多个匹配 Supplier 发起 RFQ”
     - 当前 `demandId @unique` 将成为结构性阻塞
     - 仅加字段不够，更合理的是引入 `RFQRecipient` / `RFQTarget` 关系表，或取消当前单 RFQ-per-demand 约束

3. **RFQResponse 的 Buyer 决策审计信息**
   - 当前只有 `status / createdAt / updatedAt`
   - 若 M14.3 要求正式闭环，建议补：
     - `reviewedBy`
     - `reviewedAt`
     - `decisionNote` 或 `decisionReason`

### 7.3 哪些能力可以优先复用现有模型 / API

- Supplier Offer 绑定能力优先复用现有 `Offer` 模型，不建议引入新报价模型。证据：`VISNDT/database/prisma/schema.prisma:479-500`
- Notification Center 继续复用现有 `Notification` 模型，不建议新建消息系统
- Workflow trace 优先复用现有 `WorkflowEvent` 模型，不建议另起一套审计流

## 8. Recommended M14.3 Scope Boundary

建议将 `M14.3 Business Workflow Completion` 明确拆成以下顺序：

1. **M14.3.1 先定稿主业务语义**
   - RFQ 是否必须来源于 Match
   - RFQ 是单目标还是多目标
   - Buyer 的 Response 决策是否要写回正式审计字段

2. **M14.3.2 再定数据模型与 API**
   - 先定 schema，再定接口，再接前端页面

3. **M14.3.3 最后做 Workspace 收口**
   - Match Workspace 变成真正转单入口
   - RFQ Detail 增加 Buyer 决策动作
   - Notification / Timeline 做到可回跳

本次结论不建议直接跳进页面开发，否则会把当前“广播 RFQ”模型继续固化到前端。
