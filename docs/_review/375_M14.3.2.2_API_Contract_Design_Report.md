## 2. Required API Changes

### 2.1 Match -> RFQ

- 必须将 RFQ 创建从“基于 Demand”调整为“基于 ACCEPTED Match”。
- 必须在创建时建立 `sourceMatchId` 与 `targetOrganizationId` 的契约输出。
- 必须在服务层校验 `DemandMatch.status === ACCEPTED`，否则拒绝创建。

### 2.2 Buyer Response Decision

- 必须停止沿用 Supplier 自更新的 `PATCH /rfq-responses/:id` 作为 Buyer 决策入口。
- 必须改为显式 Buyer 动作接口：`view / accept / reject`。
- 必须将权限主体切换为 Buyer Organization，而不是响应所属 Supplier Organization。

### 2.3 Supplier Targeted RFQ Query

- 必须停止使用“公开可报价池”语义。
- Supplier 查询结果必须收敛到 `targetOrganizationId = currentOrganization`。
- 当前 `GET /rfqs/available` 的返回策略与目标模型直接冲突。

### 2.4 RFQ Access Control

- `GET /rfqs/:id` 不能再是公开接口。
- `GET /rfqs/:id/responses` 不能再是公开接口。
- Buyer 侧必须按 `Demand.organizationId` 校验。
- Supplier 侧必须按 `RFQ.targetOrganizationId` 校验。

## 3. Endpoint Design

### 3.1 Recommended Contract

| 目标 | 推荐设计 | 结论 |
| --- | --- | --- |
| Match -> RFQ | `POST /rfqs/from-match` | `RECOMMENDED` |
| Buyer Response Decision | `POST /rfq-responses/:id/view` | `RECOMMENDED` |
| Buyer Response Decision | `POST /rfq-responses/:id/accept` | `RECOMMENDED` |
| Buyer Response Decision | `POST /rfq-responses/:id/reject` | `RECOMMENDED` |
| Supplier Targeted RFQ Query | `GET /supplier/rfqs` | `NOT RECOMMENDED IN THIS ROUND` |
| RFQ Detail Access | `GET /rfqs/:id` + org access check | `REQUIRED` |
| RFQ Response List Access | `GET /rfqs/:id/responses` + org access check | `REQUIRED` |

### 3.2 Match -> RFQ Path Choice

结论：**优先采用 `POST /rfqs/from-match`，不优先采用 `POST /matches/:matchId/rfq`。**

原因：

- 当前已有 [RfqsController](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfqs/rfqs.controller.ts#L18-L20)，在“不新增 Controller”前提下，`/rfqs/from-match` 可以直接落在现有控制器中。
- 当前代码并不存在顶层 `matches` 控制器；现有 Match API 仍挂在 [DemandsController](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/demands/demands.controller.ts#L234-L279) 下。若采用 `POST /matches/:matchId/rfq`，后续实现将引入新的路由边界设计问题。
- `POST /rfqs/from-match` 也更符合“RFQ 是被创建资源”的现有模块归属。

推荐请求体：

```json
{
  "matchId": "uuid",
  "title": "string",
  "description": "string"
}
```

推荐响应最小字段：

```json
{
  "id": "uuid",
  "demandId": "uuid",
  "sourceMatchId": "uuid",
  "targetOrganizationId": "uuid",
  "status": "DRAFT"
}
```

### 3.3 Supplier Query Path Choice

结论：**从业务语义看，`GET /supplier/rfqs` 更清晰；但在本轮冻结约束下，不建议把它作为首发契约。**

原因：

- 现有 [RfqsController](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfqs/rfqs.controller.ts#L18-L20) 以 `rfqs` 为前缀，直接落地 `/supplier/rfqs` 会与“不新增 Controller”约束冲突。
- 当前前端已全面耦合 `GET /rfqs/available`，见 [rfqs.ts:L74-L88](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/lib/api/rfqs.ts#L74-L88) 与 [supplier/rfqs/page.tsx:L37-L55](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/app/workspace/supplier/rfqs/page.tsx#L37-L55)。

因此建议：

1. 本轮先在 `rfqs` 模块内完成 targeted 语义替换
2. 将现有 `GET /rfqs/available` 改造成“仅返回 target supplier 可见 RFQ”的受限查询
3. 若未来允许调整控制器边界，再把外部契约重命名为 `/supplier/rfqs`

### 3.4 RFQ Detail / Response Access

推荐保留现有路径，但补权限：

- `GET /rfqs/:id`
  - Buyer: `rfq.demand.organizationId == currentOrganization`
  - Supplier: `rfq.targetOrganizationId == currentOrganization`
- `GET /rfqs/:id/responses`
  - Buyer: 可看该 RFQ 的全部响应
  - Supplier: 仅可看本组织自己的响应记录

## 5. Permission Model

### 5.1 `POST /rfqs/from-match`

必须同时满足：

1. 当前用户已登录且属于某个组织
2. `match.demand.organizationId == currentOrganization`
3. `match.status == ACCEPTED`
4. `match.offer.organizationId` 可解析为目标 Supplier 组织

### 5.2 `POST /rfq-responses/:id/view|accept|reject`

必须同时满足：

1. 当前用户属于 Buyer Organization
2. 当前 Buyer Organization 拥有该 RFQ 关联的 Demand
3. 该 RFQResponse 属于该 RFQ

不再允许：

- Supplier Organization 通过 [PATCH /rfq-responses/:id](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.controller.ts#L59-L70) 推进 `VIEWED / ACCEPTED / REJECTED`

### 5.3 `GET /rfqs/:id`

- Buyer 可访问：`rfq.demand.organizationId == currentOrganization`
- Supplier 可访问：`rfq.targetOrganizationId == currentOrganization`
- 其他主体：拒绝访问

### 5.4 `GET /rfqs/:id/responses`

- Buyer 可访问全部响应
- Supplier 仅可访问本组织响应
- 在单目标模型下，Supplier 侧通常最多只会看到自己的单条响应

## 9. Recommendation

### 9.1 Final Recommendation

1. **采用** `POST /rfqs/from-match` 作为 `Match -> RFQ` 首选契约
2. **采用** `POST /rfq-responses/:id/view|accept|reject` 作为 Buyer 决策契约
3. **不建议本轮采用** `GET /supplier/rfqs` 作为首发路径；在不新增 Controller 的约束下，应先在现有 `rfqs` 命名空间内完成 targeted 语义替换
4. **必须收紧** `GET /rfqs/:id` 与 `GET /rfqs/:id/responses` 的 JWT 与组织访问控制
5. **复用** Notification / WorkflowEvent 基础设施，不新建通知与流程事件系统

### 9.2 Notification Recommendation

不需要新增通知系统，但需要新增/调整触发规则：

1. RFQ 从 Match 创建成功后：
   - 应通知目标 Supplier Organization 管理员
   - 不应继续只通知 Demand 创建者
2. Supplier 提交响应后：
   - 应通知 Buyer Organization 管理员或 RFQ 所属 Buyer 责任人
3. Buyer 接受/拒绝响应后：
   - 可继续复用当前 `createForOrganization()` 广播 Supplier 组织管理员的逻辑，见 [notifications.service.ts:L195-L232](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L195-L232)

### 9.3 WorkflowEvent Recommendation

结论：**复用现有 WorkflowEvent 即可。**

建议映射：

- RFQ created from match -> `entityType: RFQ`, `action: CREATED`
- RFQResponse submitted -> `entityType: RFQ_RESPONSE`, `action: SUBMITTED`
- RFQResponse viewed -> `entityType: RFQ_RESPONSE`, `action: REVIEWED`
- RFQResponse accepted/rejected -> `entityType: RFQ_RESPONSE`, `action: ACCEPTED / REJECTED`
