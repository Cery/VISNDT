## 4. Prisma Relation Analysis

### 4.1 ProductMedia Model

```prisma
model ProductMedia {
  id           String    @id @default(uuid()) @db.Uuid
  productId    String    @map("product_id") @db.Uuid
  fileAssetId  String?   @map("file_asset_id") @db.Uuid  // ← NULLABLE
  mediaType    FileType  @map("media_type")
  // ...
  product   Product    @relation(fields: [productId], references: [id])
  fileAsset FileAsset? @relation(fields: [fileAssetId], references: [id])
  //                                 ↑ OPTIONAL (nullable FK)
}
```

### 4.2 FileAsset Model

```prisma
model FileAsset {
  id         String         @id @default(uuid()) @db.Uuid
  entityType FileEntityType @map("entity_type")
  entityId   String         @map("entity_id") @db.Uuid
  // ...
  media ProductMedia[]  // ← One-to-many (no onDelete defined here)
}
```

### 4.3 Foreign Key Constraints (from Migration SQL)

| Constraint | Table | SQL |
|---|---|---|
| Product → ProductMedia | `product_media` | `ON DELETE RESTRICT ON UPDATE CASCADE` |
| **FileAsset → ProductMedia** | `product_media` | `ON DELETE SET NULL ON UPDATE CASCADE` |

```sql
-- product_media_file_asset_id_fkey
ALTER TABLE "product_media" 
  ADD CONSTRAINT "product_media_file_asset_id_fkey" 
  FOREIGN KEY ("file_asset_id") REFERENCES "file_asset"("id") 
  ON DELETE SET NULL ON UPDATE CASCADE;
```

### 4.4 Cascade Behavior Summary

| Operation | Effect on ProductMedia | Effect on FileAsset | Effect on S3 |
|---|---|---|---|
| **Delete ProductMedia** | Row deleted | ⚠️ **No effect** (orphan) | ⚠️ **No effect** (orphan) |
| **Delete FileAsset** | `fileAssetId` → NULL | Row deleted | File deleted ✅ |
| **Delete Product** | `ON DELETE RESTRICT` (blocked if media exists) | No effect | No effect |

**Key Insight:** The `ON DELETE SET NULL` constraint is on the **product_media** table's FK, meaning it only triggers when the **FileAsset** (referenced) is deleted — it sets `product_media.file_asset_id` to NULL. It does NOT trigger when ProductMedia is deleted.

  → FileAsset "fa-001" STILL EXISTS in DB ⚠️

  → Download URL for "fa-001" STILL WORKS ⚠️

There is **no automated cleanup** for orphan FileAssets.

## 6. Found Issues

### Issue #1 (CRITICAL): Orphan FileAsset on ProductMedia Delete

| Attribute | Detail |
|---|---|
| **Severity** | CRITICAL |
| **Location** | `apps/api/src/product-media/product-media.service.ts:62-65` |
| **Type** | Missing cleanup logic |
| **Root Cause** | `ProductMediaService.remove()` only calls `prisma.productMedia.delete()`. It does not delete the associated FileAsset or S3 file. |

**Current Code:**
```typescript
async remove(productId: string, id: string) {
  const media = await this.findOne(productId, id);
  return this.prisma.productMedia.delete({ where: { id: media.id } });
  // ❌ FileAsset not deleted
  // ❌ S3 file not deleted
}
```

**Impact:**
- **Storage Bloat:** Every deleted ProductMedia leaves the file in S3/MinIO permanently
- **Database Bloat:** Every deleted ProductMedia leaves a FileAsset record in the database
- **Security Risk:** Files remain accessible via `GET /files/:id/download` (public endpoint!) even after the ProductMedia is deleted
- **Data Integrity:** Orphan FileAsset records accumulate with no way to trace their origin

**Expected Behavior:**
```typescript
async remove(productId: string, id: string) {
  const media = await this.findOne(productId, id);
  // Delete associated FileAsset if exists
  if (media.fileAsset) {
    await this.storageService.deleteObject(media.fileAsset.storageKey);
    await this.prisma.fileAsset.delete({ where: { id: media.fileAsset.id } });
  }
  // Then delete ProductMedia
  return this.prisma.productMedia.delete({ where: { id: media.id } });
}
```

### Issue #2 (HIGH): Orphan FileAsset on ProductMedia Create Failure

| Attribute | Detail |
|---|---|
| **Severity** | HIGH |
| **Location** | `apps/api/src/file-asset/file-asset.service.ts:67-97` → `apps/api/src/product-media/product-media.service.ts:28-43` |
| **Type** | Two-step upload-create pattern with no rollback |
| **Root Cause** | File upload and ProductMedia creation are two separate API calls. If the second call fails, the FileAsset from the first call is orphaned. |

**Impact:**
- Same storage/database/security issues as Issue #1
- Worse because the user may not even realize the orphan exists (create failed silently)
- EntityId is always placeholder (`00000000-0000-0000-0000-000000000000`), so orphaning is the norm, not the exception

**Note:** The admin frontend `ProductMediaCreate.tsx` first uploads the file, then creates the ProductMedia with the returned `fileAssetId`. If the second step fails, the file is orphaned. The frontend has no cleanup logic for this scenario.

## 7. Risk Assessment

### 7.1 Risk Matrix

| Risk | Likelihood | Impact | Severity |
|---|---|---|---|
| Storage bloat from orphan S3 files | **High** (every delete) | Medium | **HIGH** |
| Orphan DB records accumulation | **High** (every delete) | Low | **MEDIUM** |
| Deleted product files still accessible | **High** (every delete) | **High** | **CRITICAL** |
| S3 cost increase (unbounded growth) | **High** (over time) | Medium | **HIGH** |
| GDPR/data retention violation | Medium | **Critical** | **HIGH** |
| Orphan from create failure | Medium | Low | **MEDIUM** |

### 7.2 Security Risk Detail

The most critical risk is that `GET /files/:id/download` is a **public endpoint** (no JWT auth). Once a file is uploaded:
1. The download URL is accessible to anyone who knows the FileAsset ID
2. Deleting the ProductMedia does NOT revoke access
3. The file remains accessible forever unless manually deleted via `DELETE /files/:id`

This means:
- A user who bookmarks a download URL can access the file indefinitely
- There is no access control tied to ProductMedia lifecycle
- Deleting a product image does not actually remove it from the system

## 8. Recommendation

### 8.1 Immediate (M13.2.7.2 — Fix Critical Issues)

**Priority: CRITICAL**

1. **Fix ProductMediaService.remove()** to cascade-delete FileAsset:
   ```typescript
   async remove(productId: string, id: string) {
     const media = await this.findOne(productId, id);
     if (media.fileAsset) {
       await this.storageService.deleteObject(media.fileAsset.storageKey);
       await this.prisma.fileAsset.delete({ where: { id: media.fileAsset.id } });
     }
     return this.prisma.productMedia.delete({ where: { id: media.id } });
   }
   ```
   - Requires: Inject `StorageService` into `ProductMediaModule`
   - Files affected: `product-media.service.ts`, `product-media.module.ts`

2. **Add `GET /files/:id/download` access control**:
   - Consider adding JWT auth to prevent unauthorized access to deleted files
   - Or: validate that the FileAsset is still linked to an active ProductMedia

### 8.2 Short-term (M13.2.7.3 — Data Integrity)

**Priority: HIGH**

3. **Add orphan cleanup API**:
   - `GET /files/orphans` — list FileAssets with no associated ProductMedia
   - `POST /files/cleanup` — batch delete orphan FileAssets (DB + S3)

4. **Fix entityId population**:
   - After ProductMedia is created, update the FileAsset's `entityId` to the ProductMedia ID
   - Or: remove the `entityType`/`entityId` pattern entirely and rely on the ProductMedia relation

### 8.3 Long-term (M13.3+)

5. **Atomic upload-create endpoint**:
   - Combine file upload and ProductMedia creation into a single transaction
   - `POST /products/:productId/media/upload` — accepts file + metadata in one call
   - If any step fails, rollback the entire transaction

6. **Scheduled orphan cleanup job**:
   - Cron job that periodically scans for orphan FileAssets and S3 files
   - Safe deletion with configurable grace period
