## Database Schema Audit

### Notification Model

Location: `database/prisma/schema.prisma:568-586`

```prisma
model Notification {
  id            String             @id @default(uuid()) @db.Uuid
  userId        String             @map("user_id") @db.Uuid
  type          NotificationType
  status        NotificationStatus @default(UNREAD)
  title         String
  message       String
  referenceType String?            @map("reference_type")
  referenceId   String?            @map("reference_id") @db.Uuid

  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  user User @relation(fields: [userId], references: [id])

  @@index([userId, status])
  @@index([type])
  @@index([createdAt])
  @@map("notification")
}
```

## Permission Model Audit

### Notification Data Isolation

The Notification model uses `userId` as the owner field:

| Property | Behavior |
|----------|----------|
| Ownership | Single user (via `userId`) |
| Organization scope | Not directly — derived via user's organization |
| ADMIN scope | Admin can view all notifications (pattern from Users/Organizations) |

### Access Pattern

| Role | Scope | Notes |
|------|-------|-------|
| `ADMIN` | All notifications | Admin-level view of all system notifications |
| `ORG_ADMIN` | Own notifications | Organization context via user |
| `MEMBER` | Own notifications | Personal notifications only |

### Security Considerations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Cross-user notification access | **Medium** | Backend must validate `userId` from JWT for non-ADMIN roles |
| Notification content exposure | **Low** | Title/message may contain business info; RBAC filtering needed |
| `referenceType`/`referenceId` | **Low** | Links to internal entities; validate access before exposing |

## Risk Assessment

| Risk | Severity | Description | Mitigation |
|------|----------|-------------|------------|
| Backend解冻 scope creep | Medium | Risk of expanding beyond notification module | Strict scope: only `notifications/` module + app.module.ts |
| Existing module conflicts | Low | New module, no existing code to conflict | Notification module is standalone |
| Performance | Low | Notification queries on indexed columns | `[userId, status]`, `[type]`, `[createdAt]` indexes exist |
| Security regression | Low | New endpoints must follow existing RBAC | Pattern from Users/Organizations, JWT + @Roles guard |
| No notification data | Low | No existing notification creation logic | List/detail will show empty state; data population is separate concern |

### Technical Debt Risk

| Concern | Level | Notes |
|---------|-------|-------|
| No notification creation mechanism | **Low** | Backend has no triggers to create notifications. List/detail pages will show empty data until notification creation is implemented. This is acceptable for V1 — the infrastructure is being laid. |
| Admin-only notification visibility | **Low** | Backend service must filter by user; ADMIN role can see all. This is consistent with existing patterns. |

## Final Recommendation

### Backend解冻 Required — Proceed with Minimal Backend Enhancement

**Rationale**:

1. **Database is ready**: Notification model, enums, indexes, and FK constraints are all in place from the initial migration
2. **No existing code to modify**: Zero notification code exists in Backend or Frontend — no risk of regression
3. **Minimal Backend scope**: 1 new module, 5 REST endpoints, 1 app.module.ts import line
4. **Follows established patterns**: Same architecture as Users/Organizations/Settings modules
5. **No new dependencies**: Uses existing PrismaService, JwtAuthGuard, RolesGuard, ApiResponse wrapper
6. **Frontend follows M10.1 pattern**: NotificationList/NotificationDetail matching UserList/UserDetail

**Recommendation**: Proceed with M10.2.1 Backend Notification Module as the first step, then implement Frontend pages following the established M10.1 pattern.
