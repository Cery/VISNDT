## 3. Search Discovery Final Decision

### 3.1 Architecture Decision Record

**Decision:** VISNDT Search = **Unified Industrial Inspection Discovery Layer**

**Rationale:**

VISNDT is not a general-purpose search engine or an e-commerce product catalog. It is an **Industrial Inspection Capability Discovery Platform**. The search experience must reflect this:

| User searches... | Discovers... |
| --- | --- |
| Detection requirement | Matching Products |
| Equipment name | Product Specifications |
| Professional terminology | Knowledge Explanations |
| Application scenario | Solutions + Related Products |
| Technical question | Knowledge Articles + Parameter Guidance |

### 3.2 Unified Discovery Architecture

```
┌─────────────────────────────────────────────────────────┐
│           Industrial Inspection Discovery Layer           │
│                                                           │
│  GET /search?q=超声检测                                    │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐ │
│  │              Unified Discovery API                    │ │
│  │                                                       │ │
│  │  Single Endpoint → Single Response Contract           │ │
│  │                                                       │ │
│  │  UnifiedDiscoveryResponse {                           │ │
│  │    query: string,                                     │ │
│  │    products: ProductDiscoveryResult[],                │ │
│  │    knowledge: KnowledgeDiscoveryResult[],   ← Entry   │ │
│  │    content: ContentDiscoveryResult[],       ← Article │ │
│  │    solutions: SolutionDiscoveryResult[],    ← Solution│ │
│  │    suppliers: SupplierDiscoveryResult[],    ← Offer   │ │
│  │  }                                                    │ │
│  └─────────────────────────────────────────────────────┘ │
│                                                           │
│  Retrieval Strategy per Entity:                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐│
│  │ Product   │ │Knowledge │ │Content   │ │Supplier      ││
│  │ name/model│ │Entry     │ │Article   │ │Offer         ││
│  │ description│ │title/   │ │title/body│ │organization  ││
│  │ params    │ │summary/  │ │          │ │+ product     ││
│  │           │ │structBody│ │          │ │              ││
│  └──────────┘ └──────────┘ └──────────┘ └──────────────┘│
└─────────────────────────────────────────────────────────┘
```

### 3.3 Current vs. Target

| Aspect | Current (Fan-out) | Target (Unified) |
| --- | --- | --- |
| API | 4 separate endpoints | 1 unified endpoint |
| Response | 4 different shapes | 1 unified contract |
| Knowledge | Content(KNOWLEDGE) | KnowledgeEntry |
| Aggregation | Client-side Promise.allSettled | Server-side |
| Semantic | NOT integrated | Future enhancement |
| Ranking | Per-entity | Cross-entity unified |

### 3.4 Desktop Experience Decision

```
Search Input (GlobalSearchBar)
    ↓
Unified Result Page (/search)
    ├── Category Navigation (SearchTypeTabs: All / Product / Knowledge / Content / Supplier)
    ├── Filter Panel (domain, category, parameter range, content type)
    ├── Sort (relevance, date, parameter match)
    └── Result Cards
          ├── ProductResultCard (image, name, model, key params, supplier)
          ├── KnowledgeResultCard (domain badge, title, summary, category)
          ├── ContentResultCard (type badge, cover, title, read time, tags)
          └── SupplierResultCard (org name, offer count, product categories)
```

**Decision:** Single-page unified discovery — NOT multiple independent search entry points.

## 4. Mobile Discovery Architecture Decision

### 4.1 Current State (Code Evidence)

The codebase uses responsive Tailwind CSS patterns:
- `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3` (product grid)
- `sm:px-6 sm:py-6` (search page)
- `lg:flex-row` (filter sidebar)
- `PublicHeader` with hamburger menu

**Assessment:** The application is **responsive** but not **mobile-optimized** for industrial field use. It is a desktop-first design that adapts to mobile, rather than a mobile-first discovery experience.

### 4.2 Mobile Discovery Decision

**Decision:** Mobile is a **First-Class Discovery Experience** — not a desktop shrink-down.

```
Mobile Discovery Flow:

Search Box (full-width, prominent)
    ↓
Category Quick Tabs (horizontal scroll, touch-friendly)
    ↓
Filter Drawer (slide-up, not sidebar)
    ↓
Compact Result Cards (single column, key info first)
    ↓
Detail Page (full-width, optimized reading)
    ↓
Action: Inquiry / RFQ / Contact (prominent CTA)
```

### 4.3 Mobile Information Priority

Mobile displays data in priority order for field workers:

| Priority | Information | Why |
| --- | --- | --- |
| 1 | Equipment name + model | Immediate identification |
| 2 | Key parameters (3-5 critical) | Quick capability assessment |
| 3 | Equipment type / category | Context |
| 4 | Knowledge summary (1-2 sentences) | Understanding |
| 5 | Next action (Inquiry / RFQ) | Workflow continuation |

### 4.4 Mobile Field Use Cases

| Scenario | Supported? | Gap |
| --- | --- | --- |
| Quick equipment lookup | Partially | No dedicated mobile search flow |
| Parameter understanding | No | No parameter explanations |
| Find technical documentation | Partially | Knowledge-base works but not optimized |
| Submit RFQ/Inquiry | Yes | Workspace available |
| Offline access | No | No PWA offline strategy |

**Result: NEED OPTIMIZATION — Responsive but not mobile-first**

## 5. Insight / Parameter Knowledge Boundary Decision

### 5.1 Current State (Code Evidence)

**Content(INSIGHT):**
- Flat content article type (`ContentType.INSIGHT`)
- Rendered via `MarkdownRenderer` on `/insights/[slug]`
- Listed on `/insights` page with ContentCard
- Searchable via `GET /content/public?type=INSIGHT&keyword=`
- **NOT** a dedicated parameter knowledge system

**ParameterDefinition:**
- Fields: `name, code, dataType, unit, required, sortOrder, options`
- **NO** `description` or `explanation` field
- **NO** link to KnowledgeEntry
- **NO** link to Content(INSIGHT)

**KnowledgeEntry:**
- Fields: `title, slug, summary, structuredBody, seoTitle, seoDescription, seoKeywords`
- **NO** link to ParameterDefinition
- Can be used to explain technical terms (e.g., "IP67防护等级", "景深原理")

### 5.2 Boundary Decision

| Concept | Belongs To | Current State | Decision |
| --- | --- | --- | --- |
| "IP67" explanation | KnowledgeEntry | NOT implemented | Future: KnowledgeEntry under "参数指导" domain |
| "景深" explanation | KnowledgeEntry | NOT implemented | Future: KnowledgeEntry under "检测方法" domain |
| "视场角" explanation | KnowledgeEntry | NOT implemented | Future: KnowledgeEntry under "参数指导" domain |
| Parameter encyclopedia articles | Content(INSIGHT) | EXISTS | KEEP (content articles) |
| Parameter value + unit | ParameterDefinition + ProductParameterValue | EXISTS | KEEP |
| Parameter explanation | KnowledgeEntry | NOT implemented | Future — NOT in M22.4 |

### 5.3 Insight Freeze Decision

```
Content(INSIGHT) = Content Publishing Type (KEEP)
Parameter Knowledge = Future KnowledgeEntry Domain (NOT in M22.4)

M22.4 Boundary:
├── Content(INSIGHT): KEEP as-is, searchable via unified search
├── Parameter explanation: NOT in M22.4
└── Parameter-Knowledge link: NOT in M22.4
```

**Decision: Parameter Knowledge is FROZEN — not in M22.4 scope. Future independent planning.**
