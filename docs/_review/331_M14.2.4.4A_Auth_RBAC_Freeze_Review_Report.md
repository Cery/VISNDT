## 3. Backend Auth Review

### 3.1 登录流程

检查对象：

- `POST /auth/login`
- `POST /auth/register`
- `POST /auth/refresh`

旧结构：

- Cookie 写入 token
- 前端主要消费 `ApiResponse.data.user`
- 用户对象以基础字段为主：`id / email / name / organizationId`

新结构：

- 仍由后端写入 Cookie
- 返回包体仍是 `ApiResponse.ok(...)`
- `user` 扩展为：
  - `organization`
  - `organizationMember`
  - `workspaceRole`

兼容性：

- 对当前仓库内 Web 调用链，兼容性为**基本兼容**
- 原因：`apps/web/src/services/auth.service.ts` 仍按 `res.data.user` 读取
- 主要问题不在运行时，而在 Swagger / DTO 仍把响应描述成直接含 `accessToken` 的 JSON 结构

判断：

- Backend Auth 扩展方向本身可用
- 但对外契约描述不准确，不能视为冻结区可直接提交状态

## 4. /auth/me Contract Review

检查对象：

- `GET /auth/me`

当前返回：

- 实际返回为 `ApiResponse.ok(user)`
- `user` 当前可能包含：
  - `id`
  - `email`
  - `name`
  - `organizationId`
  - `organization`
  - `organizationMember`
  - `workspaceRole`

兼容性判断：

- 对当前仓库内前端：**兼容**
- 对公开接口契约：**不完全兼容**

原因：

1. 新字段是增量扩展，现有前端读取已对齐
2. 但 Swagger 仍把 `/auth/me` 标成 `AuthUserDto`，遗漏统一 `ApiResponse` 包装层
3. 这会让外部调用方或后续生成代码误解真实返回结构

风险等级：

- **Medium**

## 5. JWT Context Review

检查对象：

- `auth-request.interface.ts`
- `auth.service.ts`

新增字段：

- `organization`
- `organizationMember`
- `workspaceRole`

审核结论：

1. 这些字段均为可选或可空上下文，接口层没有把它们声明为强制非空
2. `validateUser()` 已统一通过 `buildAuthUser()` 构造上下文，初始化路径相对集中
3. 在本次审查范围内，未发现新增字段直接破坏 `JwtAuthGuard` 的证据
4. 但 `workspaceRole` 的计算逻辑不稳定：`organizationType !== 'SUPPLIER'` 时会统一落成 `BUYER`

稳定性判断：

- JWT 用户上下文本身：**Medium**
- `workspaceRole` 派生结果：**High**

## 6. Frontend RBAC Review

检查对象：

- `RoleGuard.tsx`
- `AuthProvider.tsx`
- `apps/web/src/app/workspace/supplier/**`

旧逻辑：

- `RoleGuard` 实质上按固定 `BUYER` 处理

新逻辑：

- `RoleGuard` 改为读取 `user.workspaceRole`

分析：

1. 当前确实存在两层角色体系并存：
   - 组织成员角色：`ADMIN / MEMBER`
   - 工作区角色：`ADMIN / SUPPLIER / BUYER`
2. 本次未发现“直接权限绕过”证据
3. 未登录用户仍走 fallback，不构成新的越权问题
4. 真正问题在于 `workspaceRole` 缺失或误判时，前端默认回退 `BUYER`

结果：

- RBAC 风险等级：**High**

原因：

- 一旦后端把供应侧组织误判成 `BUYER`，Supplier 页面守卫会直接拒绝访问
- 这不是文档误差，而是真实运行行为偏差

## 7. Workspace Navigation Review

检查对象：

- `WorkspaceSidebar.tsx`

目标模型核对：

- `BUYER`
  - `Dashboard`
  - `Demand`
  - `RFQ`
- `SUPPLIER`
  - `Supplier Workspace`
  - `RFQ Response`
- `ADMIN`
  - `Admin`

审核结论：

1. 导航配置表本身符合业务模型，没有直接加入 Supplier 商城、独立店铺或在线交易入口
2. `SUPPLIER` 配置仅承接供应商工作台、RFQ 响应、通知、设置，方向上正确
3. `ADMIN` 配置仅暴露管理后台相关入口，方向上正确
4. 风险点不在导航表本身，而在 `user?.workspaceRole ?? 'BUYER'`

逐项判断：

- Supplier 看到 Buyer 入口：**可能发生**
- Buyer 看到 Supplier 入口：**当前未见直接证据**
- 普通用户看到 Admin 入口：**当前未见直接证据**

原因：

- 供应侧用户在 `workspaceRole` 为空或被错误映射时，会被前端按 `BUYER` 导航处理

## 10. Commit A Recommendation

最终判断：

- **C. REJECTED**

拒绝原因：

1. `workspaceRole` 推导与开放式组织类型模型不兼容
2. 前端把未知角色静默回退为 `BUYER`
3. Auth 契约文档与真实响应结构不一致
4. 当前改动仍位于 Auth / RBAC 冻结敏感区

重新提交前至少应满足：

1. 明确 `organization.type` 与 `workspaceRole` 的映射规则
2. 去掉前端对未知角色的 `BUYER` 静默回退，改为显式异常或待补全态
3. 对齐 `Controller / DTO / Swagger / 前端服务` 的真实契约描述

## 11. Final Conclusion

本次 `M14.2.4.4A` 只读冻结审查结论如下：

1. Auth 上下文扩展不是本次最危险的问题，最危险的是新增 `workspaceRole` 后映射规则不完整

4. RoleGuard 与 WorkspaceSidebar 的新逻辑会把后端角色误判放大成真实访问与导航问题
5. 因为问题已进入 Auth / RBAC / Workspace 冻结边界，**本次不建议进入 Commit A**
