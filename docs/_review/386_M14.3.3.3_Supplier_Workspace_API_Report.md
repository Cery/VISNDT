## 2. API Changes

本次新增 Supplier Workspace 只读聚合接口，全部挂载在 `/workspace/supplier/*`：

- `GET /workspace/supplier/overview`
  - 返回当前 Supplier 组织的 `RFQ / RFQResponse / Notification / DemandMatch` 聚合摘要
- `GET /workspace/supplier/rfqs`
  - 返回当前 Supplier 组织收到的 Targeted RFQ 列表
  - 字段包含：`id`、`title`、`reference`、`status`、`createdAt`、`updatedAt`、`buyerOrganization`
- `GET /workspace/supplier/responses`
  - 返回当前 Supplier 组织提交的 RFQResponse 列表
  - 字段包含：`id`、`status`、`createdAt`、`updatedAt`、`rfq`、`demand`、`buyerOrganization`

实现原则：

- 仅在 `WorkspaceController` + `WorkspaceService` 内实现
- 仅使用 Prisma 只读查询
- 未修改 `RFQService`、`RFQResponseService`、`DemandService`、`MatchingService`

## 3. Permission Validation

三个 Supplier Workspace API 全部复用现有：

- `JwtAuthGuard`
- `@CurrentUser()`
- `AuthRequest['user']`

在 `WorkspaceService` 内统一执行 Supplier 权限前置校验：

1. `workspaceRole === 'SUPPLIER'`
2. `organizationId` 必须存在

任一条件不满足时，接口抛出 `ForbiddenException`，不会返回跨组织数据。

## 4. Prisma Query Scope

所有查询均严格收敛到当前登录用户的 `organizationId`：

- `RFQ`
  - `where: { targetOrganizationId: currentOrganizationId }`
- `RFQResponse`
  - `where: { organizationId: currentOrganizationId }`
- `Notification`
  - `where: { status: UNREAD, user: { organizationId: currentOrganizationId } }`
- `DemandMatch`
  - `where: { offer: { organizationId: currentOrganizationId } }`

Supplier RFQ / Response 列表中的 Buyer 组织摘要仅通过既有关系只读回查：

- `RFQ -> Demand -> Organization`
- `RFQResponse -> RFQ -> Demand -> Organization`

因此本次实现没有放宽任何领域 API 的数据边界，也没有复用宽口径的 `GET /rfqs/available` 作为 Workspace 数据源。

## 8. Risk

- 当前 RFQ 实体没有独立业务 `reference` 字段，本次 `/workspace/supplier/rfqs` 与 `/workspace/supplier/responses` 中的 `reference` 采用 `rfq.id` 作为稳定标识，`title` 取自关联 `Demand.title`。若后续产品需要专门的人类可读 RFQ 编号，应作为独立契约任务评估，不能在 Workspace 层自行发明新业务字段。
- Buyer 组织摘要依赖 `Demand.organization` 现有关系；若历史脏数据存在空组织场景，接口会返回 Buyer 摘要空字段，但不会越权回退到其他数据源。
