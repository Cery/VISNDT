## 3. Required Schema Changes

### 3.1 RFQ Schema Design

#### 3.1.1 Demand -> 多 RFQ

结论：**当前 schema 不支持，需要调整。**

原因：

- `Demand.rfq RFQ?` + `RFQ.demandId @unique` 将关系硬编码为 `1 Demand : 0..1 RFQ`。
- 373 冻结语义要求一个 `Demand` 可以对多个 `ACCEPTED Match` 分别生成多个 `Targeted RFQ`。

#### 3.1.2 `RFQ.demandId @unique` 是否需要删除

结论：**需要删除。**

建议：

- 将 `demandId @unique` 改为普通 FK + 普通索引。
- 同时新增 `@@index([demandId])` 以维持按 Demand 聚合查询能力。

原因：

- 多 RFQ 模型的唯一来源应从 `demandId` 转移为 `sourceMatchId`。
- 真正应保持唯一的是“一个 `ACCEPTED Match` 只能产生一个正式 RFQ”，因此唯一约束应落在 `sourceMatchId`，而不是 `demandId`。

#### 3.1.3 `RFQ.sourceMatchId`

结论：**合理，且为必需字段。**

建议设计：

- `sourceMatchId String? @map("source_match_id") @db.Uuid`
- 新增 relation 到 `DemandMatch`
- 目标状态下应升级为唯一约束：`@unique`

设计理由：

- 它把 RFQ 明确绑定到一个 `ACCEPTED Match`，与 373 冻结语义一致。
- 它是后续权限、来源追溯、RFQ 替代关系判断的锚点。

迁移建议：

- 第一阶段先允许 `NULL`，用于承接历史 RFQ。
- 数据回填完成后，再考虑收紧为物理必填。

#### 3.1.4 `RFQ.targetOrganizationId`

结论：**合理，且为必需字段。**

建议设计：

- `targetOrganizationId String? @map("target_organization_id") @db.Uuid`
- 新增 relation 到 `Organization`
- 新增 `@@index([targetOrganizationId, status])`

设计理由：

- Supplier 查询和详情访问控制不能继续依赖公开 `available` 列表。
- 虽然理论上可从 `sourceMatch -> offer -> organizationId` 推导，但显式存储目标组织更利于：
  - 权限过滤
  - 查询性能
  - 历史一致性
  - 降低跨表推导复杂度

约束建议：

- 创建 RFQ 时应保证 `targetOrganizationId == sourceMatch.offer.organizationId`
- 该一致性优先由服务层校验，必要时再补数据库约束策略

#### 3.1.5 是否需要新增 `RFQRecipient / RFQTarget` 关系表

结论：**当前冻结模型下不需要。**

原因：

- 373 已冻结为“单 RFQ 单 Supplier”，不是广播 RFQ。
- 引入关系表会把单目标模型提升为多接收方模型，超出本次冻结范围。

### 3.2 RFQResponse Schema Design

#### 3.2.1 `reviewedBy / reviewedAt / decisionNote` 是否合理

结论：**合理。**

建议设计：

- `reviewedBy String? @map("reviewed_by") @db.Uuid`
- `reviewedAt DateTime? @map("reviewed_at")`
- `decisionNote String? @map("decision_note")`
- `reviewer User? @relation(fields: [reviewedBy], references: [id])`

#### 3.2.2 Nullability

建议：

- `reviewedBy`: 初始应为 nullable
- `reviewedAt`: 初始应为 nullable
- `decisionNote`: 保持 nullable

原因：

- `SUBMITTED` 阶段尚未经过 Buyer 查看，天然没有 reviewer / reviewedAt。
- 历史数据同样缺少这两个字段，直接物理非空会使 migration 高风险。
- 业务约束应表达为：
  - 当状态进入 `VIEWED / ACCEPTED / REJECTED` 时，`reviewedBy / reviewedAt` 必填
  - 当状态进入 `REJECTED` 时，`decisionNote` 建议必填

#### 3.2.3 Relation

建议：

- `reviewedBy -> User.id` 足够，不需要再直接挂 Buyer Organization FK
- Buyer 组织归属可从 reviewer 用户现有组织上下文和 RFQ.demand 反向校验

#### 3.2.4 Index

建议：

- 新增 `@@index([reviewedBy])`
- 新增 `@@index([rfqId, status])`

说明：

- 现有 `@@unique([rfqId, organizationId])` 在单目标模型下仍成立，可继续保留。
- 若未来需要兼容“同组织多版本响应”，才需要重审该唯一约束；本次冻结不需要。

#### 3.2.5 Audit 意义

- `reviewedBy / reviewedAt / decisionNote` 解决的是“Buyer 决策主体和时间不可追溯”的问题。
- 它们与 `WorkflowEvent` 不是重复关系：
  - `RFQResponse` 字段存放当前决策结果的主事实
  - `WorkflowEvent` 存放过程事件流

### 3.3 DemandMatch Schema Design

#### 3.3.1 当前状态是否满足业务

结论：**状态枚举本身满足业务，不需要新增状态。**

- 现有枚举：`PENDING / MATCHED / REVIEWED / ACCEPTED / REJECTED / EXPIRED`
- 与 373 冻结语义一致，见 [373 report:L501-L504](file:///F:/Desktop/VISNDT/docs/_review/373_M14.3.1_Business_Semantics_And_Workflow_Decision_Audit_Report.md#L501-L504)

#### 3.3.2 Rematch 历史保存方案

结论：**当前 schema 不能完整保留 append-only 历史。**

现状阻塞点：

- 当前 rematch 直接 `deleteMany` 删除旧记录，见 [demands.service.ts:L445-L457](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/demands/demands.service.ts#L445-L457)。
- 当前 `@@unique([demandId, productId])` + matching `upsert`，见 [schema.prisma:L540-L543](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L540-L543) 与 [matching.service.ts:L175-L201](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/matching/matching.service.ts#L175-L201)，更适合“覆盖当前态”，不适合“保留多轮历史”。

建议方案：

- 若 M14.3.2 需要真实保留 rematch 历史，`DemandMatch` 应增加批次标识，例如：
  - `matchBatchId` 或 `matchRound`
- 并将唯一约束从 `[demandId, productId]` 调整为可区分批次的组合唯一键
- 同时建议增加：
  - `expiredAt DateTime?`
  - `expireReason String?`

#### 3.3.3 是否需要删除行为调整

结论：**需要。**

建议：

- rematch 时不要再物理删除旧 Match
- 应改为：
  - 未进入 RFQ 链路的旧候选 -> 标记 `EXPIRED`
  - 已 `ACCEPTED` 且已产生 RFQ 的 Match -> 禁止被 rematch 清理

#### 3.3.4 是否需要增加字段

最小推荐：

- `matchBatchId` 或 `matchRound`: `REQUIRED`，用于历史分代
- `expiredAt`: `RECOMMENDED`
- `expireReason`: `RECOMMENDED`

不建议在本轮强加：

- `reviewedBy / decisionBy` 到 `DemandMatch`

原因：

- 当前项目已有 [WorkflowEvent](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L593-L610) 可承接 Match 审批过程审计，数据库最小化更稳妥。

## 4. Relation Design

推荐关系模型：

1. `Demand`
   - `rfqs RFQ[]`
   - 保留与 RFQ 的聚合关系，便于 Buyer 从 Demand 视角查看派生 RFQ

2. `DemandMatch`
   - `rfq RFQ?` 或 `generatedRfq RFQ?`
   - 通过 `sourceMatchId` 建立一对一正式下游关系

3. `RFQ`
   - `demand Demand`
   - `sourceMatch DemandMatch`
   - `targetOrganization Organization`
   - `responses RFQResponse[]`

4. `RFQResponse`
   - `rfq RFQ`
   - `organization Organization`
   - `offer Offer?`
   - `reviewer User?`

关系结论：

- `RFQ -> DemandMatch` 应新增 relation
- `RFQ -> Organization(target)` 应新增 relation
- `RFQResponse -> User(reviewer)` 应新增 relation
- `RFQRecipient / RFQTarget` 独立关系表当前不建议引入

删除策略建议：

- `RFQ.sourceMatchId`：推荐 `onDelete: Restrict`
- `RFQ.targetOrganizationId`：推荐 `onDelete: Restrict`
- 原因是 RFQ 一旦形成正式业务记录，不应因上游对象删除而级联消失

## 5. Migration Risk

### 5.1 当前已有 RFQ 数据如何迁移

结论：**不能只靠结构迁移自动完成。**

原因：

- 历史 RFQ 只有 `demandId`，没有 `sourceMatchId`
- 同一个 Demand 可能有多个历史 Match，无法从数据库结构中唯一推导 RFQ 来源 Match

建议：

- 需要一次 data migration / backfill 流程
- 但该流程不能盲目自动绑定，必须区分：
  - 可确定来源的 RFQ
  - 无法确定来源的 RFQ

### 5.2 删除 `demandId unique` 的风险

- 数据库层面风险较低，本质是放宽约束
- 业务层面风险较高：
  - 若 API / 页面仍按“一个 Demand 只有一个 RFQ”写死，放宽后会出现多条数据但 UI / API 只取一条的逻辑偏差

### 5.3 `sourceMatchId` 数据来源问题

结论：**历史数据存在不可回填风险。**

可回填前提：

- 该 RFQ 能唯一匹配到一个 `ACCEPTED DemandMatch`
- 且该 Match 的 `offer.organizationId` 与历史响应/目标语义不冲突

高风险点：

- 当前 rematch 会删除旧 Match，导致历史 RFQ 可能根本找不到原始 Match
- 当前 RFQ 原本允许绕过 Match 直接创建，见 [apps/web/src/app/workspace/rfqs/create/page.tsx:L29-L57](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/app/workspace/rfqs/create/page.tsx#L29-L57)

### 5.4 `targetOrganizationId` 数据填充问题

结论：**历史数据同样不能稳定自动填充。**

原因：

- 当前 RFQ 是公开可响应模型，不存在正式目标组织字段
- 若 RFQ 没有任何 Response，则几乎无法推断历史 intended target
- 若 RFQ 有 Response，只能推断“实际响应组织”，不能 100% 等同于“原目标组织”

### 5.5 是否需要 data migration script

结论：**需要。**

但要区分两类动作：

- schema migration:
  - 新增字段
  - 调整索引 / 唯一约束
- data migration script:
  - 回填 `sourceMatchId`
  - 回填 `targetOrganizationId`
  - 标记无法自动判定的历史 RFQ

推荐落地顺序：

1. 新字段先 nullable
2. 发布 backfill script
3. 补人工核查清单
4. 最后再决定是否收紧为 not null / unique

## 9. Final Recommendation

### 9.1 Final Verdict

`M14.3.2.1 Schema Design Audit: PASS WITH RISKS`

### 9.2 Required Decisions Before Implementation

1. `RFQ.demandId @unique` 应删除，并改由 `sourceMatchId` 承担唯一来源约束
2. `RFQ.sourceMatchId`、`RFQ.targetOrganizationId` 应纳入正式 schema 设计
3. `RFQResponse.reviewedBy / reviewedAt / decisionNote` 应纳入正式 schema 设计
4. `DemandMatch` 若要求保存 rematch 历史，必须补充批次/历史字段并重审唯一约束

### 9.3 Implementation Guidance

- 业务必填不等于首版物理非空
- 对历史数据和状态机中间态，优先采用：
  - nullable 字段
  - backfill script
  - 应用层状态校验
  - 最后再收紧数据库约束

### 9.4 Blocking Risks

#### High

1. `RFQ.demandId @unique` 与多 RFQ 冻结模型直接冲突
2. 历史 RFQ 的 `sourceMatchId` 无法稳定自动回填
3. 历史 RFQ 的 `targetOrganizationId` 无法稳定自动回填
4. `DemandMatch @@unique([demandId, productId])` 会阻碍真实 rematch 历史沉淀

#### Medium

5. Buyer / Supplier 现有 API 和页面都按旧模型耦合，放松约束后易出现返回结构与权限语义错位
6. `RFQResponse.reviewedBy / reviewedAt` 若直接做物理非空，会与 `SUBMITTED` 状态及历史数据冲突

### 9.5 Recommendation

- 可以进入后续实现设计，但应先完成：
  - 详细字段定义冻结
  - backfill 规则设计
  - DemandMatch 历史策略定稿
- 本任务到此停止，不进入 `M14.3.2.2`
