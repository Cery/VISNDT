## 三、决策结论（三项，已定稿）

### 决策 1（D1）：跨端 Design Token 单一事实源 → 共享 JSON token 文件

**采用**：在 pnpm monorepo 下新建 `VISNDT/packages/design-tokens/`，以 `tokens.json` 为唯一事实源（Single Source of Truth），Web 与 Admin 各自消费该 JSON。

**消费策略**：

| 端 | 消费方式 |
|----|---------|
| Web（Next + Tailwind） | 由 `tokens.json` 生成 `globals.css` CSS 变量 + `tailwind.config.ts` 映射（`tokens:build` 脚本；生成物入库，运行时零额外依赖） |
| Admin（Vite + antd） | 直接 `import tokens.json`，`tokens.ts` 收敛为「JSON → TS 导出」薄适配层，`AppProvider.tsx` 的 antd `ConfigProvider` 读取同一份值 |

**否决方案**：
- 「Web 对齐 Admin tokens.ts」→ 否决：仍是无跨端共享的 TS 文件，无法被 Tailwind/Next 直接消费，未真正建立单一事实源。
- 「仅统一 primary 色值」→ 否决：只治 G4，不动 G1/G2，无法支撑平台化地基。

### 决策 2（D2）：图标体系 → Web 采用 lucide-react，Admin 保留 @ant-design/icons

**采用**：Web 引入 `lucide-react`（轻量、tree-shaking、与 Tailwind 生态契合、中性工业风格），替换 77 处 emoji；Admin 继续使用 `@ant-design/icons`（已成熟，无需更换）。

**范围约束**：跨端不强制图标库统一（两端技术栈不同），但统一**图标语义命名约定**（如 `Search` / `Filter` / `Empty` / `ArrowRight`），保证两端视觉语义一致。

**否决方案**：
- `@ant-design/icons` 引入 Web → 否决：体积大、风格偏 AntD、与 Tailwind 体系违和。
- 本地 SVG 组件自建 → 否决：维护成本高，收益不匹配当前阶段需求。

### 决策 3（D3）：原子组件层 → Web 自建 `ui/` 原子层

**采用**：在 Web 建 `apps/web/src/components/ui/` 原子组件层，承接设计 token，覆盖 Button / Input / Card / Badge / Tag / Table / Pagination / Empty / Loading / Error。Admin 已具备成熟组件层（`operation/` + `design-system/`），仅做 token 对齐，不重建。

**范围约束**：不引入 shadcn/ui（避免新增 Radix 依赖与模式迁移，规避冻结边界风险）。

**否决方案**：
- 引入 shadcn/ui → 否决：引入新依赖 + 新范式，违反 V3.2.3 §0「Small Scope + Clear Boundary」。
- 暂缓组件层 → 否决：631 确认 Web 无原子层是 G3 硬伤，必须纳入 M24.6 主线。
