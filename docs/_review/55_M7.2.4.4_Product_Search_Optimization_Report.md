## 2. Current Query Architecture

### 2.1 查询入口

```
GET /products
  ├── keyword          → name/model/description CONTAINS (OR)
  ├── categoryId       → 精确匹配
  ├── status           → 精确匹配
  ├── parameterFilters → parameterValues.some (AND)
  ├── sortBy/sortOrder → 白名单排序
  └── page/pageSize    → offset pagination
```

### 2.2 Prisma where 结构

```typescript
{
  categoryId: "...",     // 直接字段过滤
  status: "ACTIVE",      // 直接字段过滤
  AND: [
    { OR: [
        { name: { contains: "keyword" } },
        { model: { contains: "keyword" } },
        { description: { contains: "keyword" } },
      ]
    },
    // 每个 parameterFilter 生成一个 AND 条件
    { parameterValues: { some: { parameterDefinitionId: "X", value: "Y" } } },
    { parameterValues: { some: { parameterDefinitionId: "Z", value: "W" } } },
  ],
}
```

### 2.3 当前索引覆盖

| 表 | 索引 | 覆盖查询 |
|----|------|----------|
| Product | `@@index([categoryId])` | categoryId 过滤 |
| Product | `@@index([status])` | status 过滤 |
| Product | `@@index([name])` | keyword name contains |
| Product | `@@index([model])` | keyword model contains |
| ProductParameterValue | `@@unique([productId, parameterDefinitionId])` | upsert 唯一约束 |
| ProductParameterValue | `@@index([parameterDefinitionId])` | 单字段过滤 |
| ProductParameterValue | `@@index([parameterDefinitionId, value])` | **本次新增** — 参数筛选 |

## 3. Performance Analysis

### 3.1 查询复杂度分解

| 查询条件 | Prisma 操作 | 索引支持 | 复杂度 |
|----------|-------------|----------|--------|
| keyword (name) | `contains` | ✅ B-tree index scan | O(log n) + 扫描 |
| keyword (model) | `contains` | ✅ B-tree index scan | O(log n) + 扫描 |
| keyword (description) | `contains` | ❌ 无索引 | O(n) 全表扫描 |
| categoryId | 等值 | ✅ B-tree index | O(log n) |
| status | 等值 | ✅ B-tree index | O(log n) |
| parameterFilters | `some` 子查询 | ✅ 复合索引 (新增) | O(log n) per filter |
| sort | `ORDER BY` | 视字段而定 | O(n log n) worst case |
| count | `COUNT(*)` | 复用 WHERE 索引 | O(log n) |

### 3.2 规模评估

| 产品数量 | 参数值/产品 | 总参数值行数 | 无复合索引 | 有复合索引 |
|----------|------------|-------------|-----------|-----------|
| 100 | 10 | 1,000 | < 5ms | < 2ms |
| 1,000 | 10 | 10,000 | ~10ms | < 5ms |
| 10,000 | 10 | 100,000 | ~50ms+ | < 15ms |

### 3.3 潜在慢查询点

1. **description contains**：无索引，全表扫描。对于 10,000+ 产品可能成为瓶颈。
   - 缓解：description 通常较短，且 keyword 搜索通常结合其它条件缩小范围
   - 未来：考虑 PostgreSQL `pg_trgm` 扩展（GIN index on description）

2. **多参数 AND 嵌套子查询**：3 个以上 parameterFilter 会产生嵌套 `some` 子查询
   - 缓解：复合索引 `[parameterDefinitionId, value]` 已优化每个子查询
   - PostgreSQL 优化器会合并多个 EXISTS 条件

3. **count 查询**：与 findMany 使用相同的 WHERE，PostgreSQL 需要额外扫描
   - 缓解：在合理数据量下（< 100,000）可接受
   - 未来：考虑缓存 count 结果

## 4. Index Evaluation — Composite Index

### 4.1 决策

**已执行：新增 `@@index([parameterDefinitionId, value])` 复合索引。**

### 4.2 分析

| 维度 | 评估 |
|------|------|
| **查询模式匹配** | `parameterValues.some({ parameterDefinitionId, value })` 精确匹配复合索引前两列 |
| **索引选择性** | `(parameterDefinitionId, value)` 组合选择性高，查询效率好 |
| **写入开销** | 每次 INSERT/UPDATE ProductParameterValue 需维护一个额外索引，开销极低 |
| **存储开销** | 每行约 40-50 bytes（UUID + VARCHAR），100,000 行约 4-5 MB |
| **风险** | 无风险 — 纯增量索引，不影响现有查询和数据 |

### 4.3 Migration

```sql
CREATE INDEX "product_parameter_value_parameter_definition_id_value_idx" 
ON "product_parameter_value"("parameter_definition_id", "value");
```

- **Migration 名称:** `20260718174748_add_parameter_value_composite_index`
- **影响:** 纯增量，无破坏性变更

### 5.1 当前返回结构

```json
{

    {
      "id": "...",

    }
  ],
  "total": 100,
  "page": 1,
  "pageSize": 20,
  "totalPages": 5
}
```

### 5.2 includeParameters 评估

| 维度 | 不包含参数值（当前） | 包含参数值（includeParameters=true） |
|------|---------------------|--------------------------------------|
| 查询 JOIN 数 | 1 (Product JOIN Category) | 1 + N (Product JOIN ParameterValues) |
| 响应大小 | ~2KB / 20 products | ~8KB / 20 products (10 params each) |
| 适用场景 | 列表浏览、搜索 | 需要展示参数对比的列表 |
| 推荐 | 保持当前默认 | 作为可选参数未来添加 |

**结论：** 当前不增加 `includeParameters`。推荐在 M7.3 中实现为可选查询参数 `includeParameters=true`，需评估 N+1 风险并使用 Prisma `include` 处理。

### 5.3 关于 description 字段

当前 `findAll` 结果直接返回 `description` 字段。对于搜索列表，建议考虑：
- 保持当前行为（返回完整 description）
- 未来可考虑返回截断的 description（如 200 字符）以优化响应大小

## 6. Range Query Future Design

### 6.1 问题描述

当前 `ProductParameterValue.value` 为 `String` 类型，范围查询（如 `镜头直径 <= 3mm`）无法原生支持。

### 6.2 方案对比

| 方案 | 描述 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A: valueNumber 字段** | 新增 `valueNumber Float?` 字段 | 原生支持数值比较；索引友好；实现简单 | 需要迁移；仅支持数值 | ⭐⭐⭐⭐⭐ |
| **B: dataType 转换** | 查询时 CAST(value AS NUMERIC) | 无需迁移 | 无法使用索引；性能差；类型不安全 | ⭐⭐ |
| **C: JSONB 参数** | 将参数存储为 JSONB | 灵活 | 需要重构数据模型；索引复杂 | ⭐⭐ |
| **D: 独立搜索引擎** | Elasticsearch / Meilisearch | 全文搜索+范围查询 | 运维成本高；MVP 过度设计 | ⭐ |

### 6.3 推荐方案：A — valueNumber 字段

**设计：**

```prisma
model ProductParameterValue {
  // ... 现有字段 ...
  value       String
  valueNumber Float?  @map("value_number")  // 新增
}
```

**优势：**
- 数值参数存储 `valueNumber`，字符串参数保持 `value`
- 范围查询直接使用 `valueNumber: { gte: 3.0 }`
- 可创建 `@@index([parameterDefinitionId, valueNumber])` 索引
- 向后兼容：现有字符串参数不受影响

**实施阶段：** M7.3.1 Parameter DataType Enhancement
