```
│  └────────────────────────────┘  │

│  └────────────────────────────┘  │

│  │  · 分辨率: 1920×1080       │  │     (e.g., resolution, accuracy, range)
│  │  · 精度: ±0.01mm           │  │     Configurable via ParameterGroup priority
│  └────────────────────────────┘  │
│  ┌────────────────────────────┐  │
│  │  Supplier Count            │  │  ← "N 家供应商" with link
│  └────────────────────────────┘  │
└──────────────────────────────────┘
```

**Data Source**: `Product` + `ProductMedia` (IMAGE, primary) + `ProductParameterValue` (top 3 sorted by `ParameterDefinition.priority` or `displayOrder`)

**New Component**: `ProductCard` (enhanced, no new file). Add `showCompare` prop, `onCompareToggle` callback, `selectedForCompare` state.

**API**: Existing `GET /products` (need to include `media` and `parameterValues` in response — if not already included, this is a **Future Candidate** requiring API audit). If product list already includes media and parameterValues, no API change needed.

**Constraint Check**: Include `media` and `parameterValues` in list response is a backend concern. If not present, the enhancement must either:
- (a) Fetch per-product detail on card render (N+1, not recommended)
- (b) Mark as Future Candidate: "Product list API include media + key parameters" — requires separate audit
- (c) Use placeholder for key parameters (client-side compute from existing data)

**Decision**: Option (c) for M20.1.1 — key parameters preview is a Future Candidate. Product card image can use existing `ProductMedia` if list API includes it; otherwise, serve placeholder and mark image display as Future Candidate.

**Revised Scope**: Card visual hierarchy enhancement (name/model/category/description layout) is frontend-only. Key parameters preview and actual image display depend on API data availability — mark as Future Candidate if not in current list response.

### 4.3 Product Comparison Architecture

#### 4.3.1 Comparison Page (`/products/compare`)

**URL**: `/products/compare?ids=id1,id2,id3`

**Page Component**: `app/products/compare/page.tsx` (Client Component)

**Data Flow**:
```
ComparePage
  └── useSearchParams() → ids[]
  └── useQuery(['compare-products', ids]) → Promise.all(ids.map(getProduct))
  └── CompareTable
        ├── CompareHeader (product names, images, remove button)
        ├── CompareRow (parameter name → values for each product)
        └── CompareActions (clear, add more, back to search)
```

**Comparison Rules**:
- Max 4 products
- If > 4 IDs in URL, take first 4
- If < 2 IDs, show "Select products to compare" empty state
- Products from same category are compared directly; cross-category shows all parameters

**Parameter Matrix**:
```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ Parameter    │ Product A    │ Product B    │ Product C    │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 分辨率       │ 1920×1080    │ 2048×1536 ▲  │ 1280×720     │
│ 精度         │ ±0.01mm      │ ±0.02mm      │ ±0.01mm      │
│ 重量         │ 2.5kg        │ 3.1kg        │ 1.8kg ▼      │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

**Difference Highlighting**:
- Parameters with different values across products: subtle background highlight
- Best value (NUMBER with min/max semantics): green text
- Worst value: red text
- All same: no highlight

**State Management**:
- Compare selection: `useState<string[]>` in ProductsPage (or React Context for cross-page persistence)
- Compare page: URL params (`/products/compare?ids=...`)
- No Redux/Zustand needed

**Constraint Verification**:
- No `ProductComparison` model in database
- No `ComparisonSnapshot` table
- No `ComparisonTemplate` table
- All data from existing `GET /products/:id` (called N times for compare)
- Client-side matrix computation
