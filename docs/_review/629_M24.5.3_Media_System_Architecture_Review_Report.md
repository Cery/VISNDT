## 2. Current Media Architecture

### 2.1 FileAsset（存储实体）

[schema.prisma L702-724](file:///f:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L702-L724)

```
id / entityType (FileEntityType) / entityId / fileType (FileType)
fileName / storageKey / mimeType / fileSize / uploadedBy (+ createdAt / updatedAt)
```

- 6 个 `FileEntityType`：`PRODUCT / ORGANIZATION / DEMAND / RFQ / RFQ_RESPONSE / CONTENT`。
- 4 个 `FileType`：`IMAGE / DOCUMENT / CERTIFICATE / OTHER`。
- 关系：`uploader(User)`、`media(ProductMedia[])`、`contentCoverImages(Content[])`、`contentMedia(ContentMedia[])`。
- 索引：`@@index([entityType, entityId])`、`@@index([uploadedBy])`。

**观测到的语义问题（Ownership Model）**：
- 平台上传接口 [file-asset.controller.ts](file:///f:/Desktop/VISNDT/VISNDT/apps/api/src/file-asset/file-asset.controller.ts) 调用 `service.upload(file, user.id)`，未传 `entityType`，`entityId` 落为占位符 `00000000-...`。
- 绑定后 `entityId` 语义不一致：
  - ProductMedia 绑定 → `entityId` 被更新为 **ProductMedia 行 id**（entityType 仍为 PRODUCT）；
  - ContentMedia 绑定 → `entityType=CONTENT` 且 `entityId` 更新为 **ContentMedia 行 id**；
  - Content 封面图 → `entityType=CONTENT` 且 `entityId=content.id`。
- 即 `entityType`/`entityId` 并非稳定指向"终极业务实体"，而是有时指绑定行、有时指内容 id、原始上传为占位符——**所有权模型功能可用但语义不一致**。

### 2.2 ProductMedia（产品媒体绑定）

[schema.prisma L367-386](file:///f:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L367-L386)

```
productId / fileAssetId? / mediaType(FileType) / title? / description? / isPrimary / displayOrder
```

- 提供产品媒体绑定 + 主图标记（isPrimary）+ 排序（displayOrder），`onDelete: Cascade`。
- 绑定能力：**PARTIAL PASS**（无 version/archive；fileAssetId 可空允许内联媒体与 FileAsset 引用并存）。

### 2.3 ContentMedia（内容媒体绑定）

[schema.prisma L823-841](file:///f:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L823-L841)

```
contentId / fileAssetId? / type(ContentMediaType) / caption? / altText? / sortOrder
```

- 提供内容嵌入媒体 + 正文说明（caption）+ SEO alt 文本（altText）+ 排序（sortOrder），SEO 能力具备。
- Content 另有 `coverImageId → FileAsset` 封面图关系。

### 2.4 Storage Relationship / API

- 存储底层：S3 Compatible（MinIO 开发 / 生产 S3），`storageKey = uploads/{timestamp}-{uuid}.{ext}`。
- 上传校验：MIME 白名单 + 上限 10MB（[file-asset.service.ts L8-58](file:///f:/Desktop/VISNDT/VISNDT/apps/api/src/file-asset/file-asset.service.ts#L8-L58)）。
- API：`POST /files/upload`、`GET /files/orphans`、`POST /files/orphans/cleanup`、`GET /files/:id/download`、`POST /files/batch-delete`、`DELETE /files/:id`，统一 `@Roles(ADMIN)`。
- Web 消费：`lib/media.ts` 生成 `GET /files/:id/download` 签名直链；开发态使用本地 SVG data-URI 占位（`placeholderImageUrl`）。

### 2.5 下载权限边界（Permission Boundary）

- 仅对 `entityType=CONTENT` 的 FileAsset：`download` 校验所属 Content 必须 `PUBLISHED`（[file-asset.service.ts L124-137](file:///f:/Desktop/VISNDT/VISNDT/apps/api/src/file-asset/file-asset.service.ts#L124-L137)）。
- 其余类型（PRODUCT/ORGANIZATION/DEMAND/RFQ/RFQ_RESPONSE）文件只要有 id 即可通过签名 URL 访问——产品为公开 Global Catalog 符合预期，但对 ORGANIZATION/DEMAND/RFQ 类文件缺少相应公开/私有门控，存在潜在越权访问风险（GAP）。

## 3. Architecture Evaluation Dimensions

| Dimension | Evaluation | 说明 |
|-|-|-|
| Asset Ownership | **GAP（语义不一致）** | `entityType/entityId` 指向不稳定（绑定行/内容id/占位符），无组织级所有权 |
| Organization Isolation | **GAP** | FileAsset 无 `organizationId`；无法按组织隔离/检索/授权媒体 |
| Media Classification | **PARTIAL** | `FileType` 4 元粗分类；无文件夹/标签/目录结构 |
| Lifecycle Management | **GAP** | FileAsset 无生命周期状态（无 processing/archive/expired），与业务实体生命周期无联动 |
| Soft Delete | **GAP** | 仅硬删除（S3 + DB `delete`/`deleteMany`），无软删/回收站/恢复 |
| Version Control | **GAP** | 无 version / media revision / 回滚；仅 Content 文本有 revision，媒体文件无版本 |
| Permission Boundary | **PARTIAL（GAP）** | 仅 CONTENT 门控 PUBLISHED；ORGANIZATION/DEMAND/RFQ 类文件无访问门控 |
| Operational Search | **GAP** | 仅按 placeholder 判定 orphan + 基础列表；无媒体检索（类型/尺寸/时间/实体的组合筛选） |
| Content Asset Reuse | **PARTIAL** | 存储层共享（一个 FileAsset 可被 ProductMedia/ContentMedia 引用），但无去重/复用登记，Orphan 检测仅看 ProductMedia 引用，忽略 ContentMedia/coverImage 引用 |

### 3.1 能力缺口汇总

- **P0 类缺口**：Organization Isolation（无 organizationId，多组织场景无法落地）。
- **P1 类缺口**：Lifecycle State、Soft Delete、Version Control、Operational Search。
- **P2 类缺口**：Media Classification（Folder/Tag）、Permission Boundary 细化、Content Asset Reuse 登记。

## 4. Architecture Decision

### 4.1 Current Status

媒体体系可满足当前 CRUD 运营与内容/产品展示需求（4.5/10，与 625 审计一致），但作为运营中心与未来多组织/供应商能力资产的基础明显不足。

### 4.2 Future Requirement

- 多组织隔离（供应商资料 / 组织文档需要 org 级 scoping）。
- 运营中心需要的媒体检索、孤儿清理、生命周期治理。
- 高质量内容运营需要的版本/回滚与软删恢复。

### 4.3 Implementation Decision

**Decision B — FUTURE EVOLUTION REQUIRED（需演进，实施延后）**

- 依据：上述 9 项评估中多项 GAP，满足"需要 Schema Evolution"判断标准；
- 同时受"Media Schema Evolution Proposal 未批准 / 本任务零码实施"冻结约束，不做任何改动；
- 必须先行产出正式 **Media Schema Evolution Proposal** 并经架构批准后才能实施。

### 4.4 Migration Decision

- 本次：**Migration: NONE**（不落地任何 schema/migration）。
- 未来：演进提案通过后，按独立 phase 落地（涉及 `FileAsset` 扩展列 + 新结构化表 + 可能的新 migration）。

## 5. Future Evolution Roadmap（提案路径，非本次实施）

### Phase 1 — Ownership & Governance Foundation

```
Ownership Isolation   : FileAsset 增加 organizationId（供应商/组织级 scoping）
Lifecycle State       : FileAsset 增加 status（PENDING/ACTIVE/ARCHIVED/EXPORTABLE）
Soft Delete           : FileAsset 增加 isDeleted/archivedAt + 回收站/恢复
Folder / Tag          : 新增 MediaFolder / MediaTag（运营检索分类基础）
```

### Phase 2 — Version & Permission Enhancement

```
Version History       : FileAssetVersion（或 media revision）记录历史版本
Rollback              : 恢复指定版本到主档
Advanced Permission    : 按 organization/role 的媒体级读写门控，覆盖 ORGANIZATION/DEMAND/RFQ 访问边界
```

> 演进优先级建议：Phase 1 的 Ownership Isolation 与 Lifecycle/Soft Delete 是运营与多组织能力的前置；Version 与 Advanced Permission 可在其收敛后跟进。
