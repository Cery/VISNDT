## 三、供应商「分开管理」实现方式（零迁移派生）

- **按文件类型分组**：复用现有 `FileType` 枚举（IMAGE 图片 / DOCUMENT 文档 / CERTIFICATE 资质证书 / OTHER 其他）。
- **按供应商（组织）过滤**：经 `FileAsset.uploadedBy → User → Organization` 只读派生 `organizationId / organizationName / organizationType`，不落列、不加表。
- **资质证书单独管理**：`fileType = CERTIFICATE` 现有枚举即可分组过滤。
- **规格书 / 插图细分**：当前 `FileType` 无 `SPEC_SHEET` / `ILLUSTRATION` 枚举，属 B.2 改库门禁，本轮**不改**（遵用户「仅零迁移，暂不改库」）。

## 五、已知非阻断技术债（记录，不在本轮修复）

**「前后端认证 token 契约不一致」**（P1，非阻断）：

- 后端 `POST /auth/login` 仅写入 HttpOnly cookie（`access_token`/`refresh_token`），响应体只返回 `{ user }`；
- admin 前端 `auth.service.ts` 仍从 `body.data.accessToken` 读取 token，得到 `undefined`；
- 实际认证由后端 JwtStrategy「cookie 优先、Bearer 兜底」承接，故功能可用（cookie 兜底），但 `authStore.accessToken` 恒为空，依赖 Cookie 会话，刷新/过期/持久化语义存在隐患。

**处理建议**：作为独立的「前后端认证契约一致性」任务在 M24.7 后续单独审计处理，**不在媒体中心任务内改动认证逻辑**（属安全敏感区，避免与媒体收口耦合）。
