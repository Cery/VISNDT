#### 3.2.1 Controller 层代码事实

#### 3.2.2 Service 层代码事实

[rfqs.service.ts L54-L78](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfqs/rfqs.service.ts#L54-L78):

```typescript
async findMine(organizationId: string, page = 1, pageSize = 20) {
  const skip = (page - 1) * pageSize;
  const [data, total] = await Promise.all([
    this.prisma.rFQ.findMany({
      where: {
        demand: {
          organizationId,
        },
      },
      skip,
      take: pageSize,
      orderBy: { createdAt: 'desc' },
      include: { demand: true, createdByUser: true },
    }),
    this.prisma.rFQ.count({
      where: {
        demand: {
          organizationId,
        },
      },
    }),
  ]);

  return { data, total, page, pageSize, totalPages: Math.ceil(total / pageSize) };
}
```

#### 3.2.3 语义分析结论

| 项目 | 实际情况 | 是否满足 Supplier RFQ Workspace |
|---|---|---|
| **Swagger 注释声明** | "Get RFQs for current supplier organization" | 声明是 Supplier 语义 |
| **实际 where 条件** | `demand.organizationId == user.organizationId` | ❌ **Buyer 视角**：返回"我组织的 Demand 对应的 RFQ" |
| **Supplier 真实需要** | 所有 OPEN/RESPONDING 状态、我可以报价的 RFQ | ❌ 完全没有这个过滤条件 |
| **状态过滤** | 无（DRAFT / CANCELLED / CLOSED 也会返回） | ❌ 缺少状态过滤 |

**核心问题**:
> `/rfqs/mine` 虽然 Swagger 注释写着 "supplier"，但代码实现完全是 **Buyer 视角**（查找本组织作为发布方的 RFQ）。  
> Supplier Workspace 需要的是"所有可以报价的公开询价单"，与 `demand.organizationId == 我组织` 完全相反。  
> 这个接口不能支撑 `/workspace/supplier/rfqs` 页面。

## 5. Prisma 模型分析

### 5.1 RFQ 模型

[schema.prisma L547-L565](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L547-L565):

```prisma
model RFQ {
  id          String    @id @default(uuid()) @db.Uuid
  demandId    String    @unique @map("demand_id") @db.Uuid
  createdBy   String    @map("created_by") @db.Uuid
  status      RFQStatus @default(DRAFT)
  publishedAt DateTime? @map("published_at")
  closedAt    DateTime? @map("closed_at")
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  demand        Demand        @relation(fields: [demandId], references: [id])
  createdByUser User          @relation(fields: [createdBy], references: [id])
  responses     RFQResponse[]

  @@index([createdBy])
  @@index([status])
  @@map("rfq")
}
```

关键点：
1. **没有 organizationId 字段**：RFQ 的 Buyer 归属是**间接**通过 `demand → Demand.organizationId` 确定的
2. **没有 targetSupplierId**：当前 RFQ 是公开发布模式，不对特定 Supplier 定向
3. **demandId unique**：一个 Demand 只能对应一个 RFQ（1:1 关系）
4. status 枚举：DRAFT / OPEN / RESPONDING / CLOSED / CANCELLED

### 5.2 RFQResponse 模型

## 7. 权限风险分析

### 7.1 风险清单（按严重度排序）

#### RISK-01: `/rfqs/mine` 语义完全错位（High）

- **位置**: [rfqs.service.ts L54-L78](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfqs/rfqs.service.ts#L54-L78)
- **问题**: Swagger 注释声明 Supplier 视角，实际 where 条件是 Buyer 视角（`demand.organizationId == 我组织`）
- **影响**:
  - 如果前端直接在 `/workspace/supplier/rfqs` 调用此接口，Supplier 用户将看到"我组织作为 Buyer 发布的需求的询价"
  - Supplier 无法看到任何他组织发布、可供自己报价的询价单
  - 等于 Supplier RFQ 页面完全不可用
- **建议**: 明确区分 Buyer `findMyPublishedRfqs()` vs Supplier `findAvailableRfqsForQuote()`，不要复用同一个 `/rfqs/mine` 路由

#### RISK-02: 公开 `/rfqs` 接口默认状态不过滤（Medium）

- **位置**: [rfqs.service.ts L26-L52](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfqs/rfqs.service.ts#L26-L52)
- **问题**: `status` 参数可选。不传时，DRAFT 草稿 RFQ 也会出现在公开列表里
- **影响**: Buyer 未发布的内部询价草稿可能被所有访客（含未登录）看到
- **建议**: 不加显式参数时默认只返回 `status in [OPEN, RESPONDING]` 的 RFQ

#### RISK-03: RFQ Response 详情 / 列表 无权限 / 无组织隔离（Medium）

- **位置**:
  - [rfq-responses.controller.ts L17-L22](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.controller.ts#L17-L22) (`/rfqs/:id/responses`)
  - [rfq-responses.controller.ts L48-L53](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.controller.ts#L48-L53) (`/rfq-responses/:id`)
- **问题**: 两个接口均无 JWT 保护、无组织隔离检查
- **影响**: 任何人（未登录 / 竞争对手 Supplier）可以按 ID 或 RFQ ID 查询到所有响应，包括报价 offer（含价格）和商务 message
- **建议**:
  - `/rfqs/:id/responses` 至少限制到：RFQ 的 Buyer 组织 或 响应自己的 Supplier 组织 或 公开仅返回脱敏字段
  - `/rfq-responses/:id` 加 JWT + 组织归属检查（Buyer of RFQ 或 Owner of Response）

#### RISK-04: RFQ Response create 未校验组织成员关系（Medium / RC-06 重复）

- **位置**: [rfq-responses.service.ts L63-L104](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.service.ts#L63-L104)
- **问题**: 只判断 `user.organizationId` 存在，不查询 `OrganizationMember` 确认该用户确实属于此组织
- **影响**: 如果 user.organizationId 被篡改（JWT 未改但数据库 membership 已移除），用户仍可能以该组织身份创建响应
- **建议**: create 时追加 `OrganizationMember` 存在性校验，或在 Controller 加 `RolesGuard`（允许 MEMBER 即可，因为普通成员也该能提交响应）

#### RISK-05: `/rfq-responses/mine` 无分页可能导致响应数据量不可控（Low-Medium）

- **位置**: [rfq-responses.controller.ts L37-L46](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.controller.ts#L37-L46)
- **问题**: Controller 未接收分页参数，Service 一次性返回全部；当 Supplier 响应积累到上百条后，前端列表加载和渲染压力变大
- **影响**: 列表页首屏慢、数据传输冗余；前端类型定义期待 PaginatedResponse 也会报错
- **建议**: Controller 补 `@Query() pagination: PaginationDto`，Service 补 skip/take + 返回 totalPages
