| **数值范围** | 管径 3-6mm → 产品 4mm | ✅ 完全支持 | 低 — `valueMin <= valueNumber <= valueMax` |
| **枚举匹配** | 光源: LED / 激光 | ✅ 完全支持 | 低 — 字符串比较 |
| 布尔匹配 | 防水: true/false | ✅ 完全支持 | 低 — 字符串比较 |

#### 2.3.3 缺失能力分析

| 缺失能力 | 影响 | 优先级 | 解决方案 |
|----------|------|--------|----------|
| 模糊文本匹配 | 无法匹配 "内窥镜" ↔ "工业内窥镜" | P2 | 暂不实现，后续可引入 NLP |

| 参数权重配置 | 无全局权重模板 | P1 | 使用 `DemandParameter.priority` 字段，已存在 |
| 匹配阈值 | 无法配置最低匹配分数 | P1 | 在 MatchingService 中硬编码默认值，后续可配置化 |

## 3. Matching Algorithm Design

### 3.1 算法总览

```
输入:  Demand (含 DemandParameter[])
       Product Candidates (含 ProductParameterValue[])

输出:  DemandMatch[] (含 matchScore, matchDetails)
```

### 3.2 匹配公式

```
单个参数得分:

  score(param) = 
    ┌─ 100                        if 精确匹配 且 value 相等
    ├─ 100                        if 数值范围 且 valueNumber ∈ [valueMin, valueMax]
    ├─ 100                        if 枚举匹配 且 value 相等
    ├─ 0                          if 不匹配
    └─ 0                          if 产品缺少该参数定义

总得分:

  totalScore = Σ (score(i) × weight(i)) / Σ weight(i)

  where:
    weight(i) = DemandParameter.priority  (默认 1)
    score(i)  ∈ [0, 100]

  如果 required 参数不匹配:
    totalScore = 0  (硬过滤)
```

### 3.3 匹配策略详解

#### 策略 1: 精确匹配 (Exact Match)

```typescript
// 当 ParameterDefinition.dataType === 'STRING' | 'BOOLEAN'
// DemandParameter.value !== undefined && DemandParameter.valueMin === undefined

function exactMatch(demandValue: string, productValue: string): number {
  return demandValue.toLowerCase().trim() === productValue.toLowerCase().trim()
    ? 100
    : 0;
}
```

**适用场景：** 镜头视向、光源类型、接口标准、认证标识

#### 策略 2: 数值范围匹配 (Numeric Range Match)

```typescript
// 当 ParameterDefinition.dataType === 'NUMBER'
// DemandParameter.valueMin !== undefined || DemandParameter.valueMax !== undefined

function rangeMatch(
  valueMin: number | null,
  valueMax: number | null,
  productValue: number
): number {
  const min = valueMin ?? -Infinity;
  const max = valueMax ?? Infinity;
  
  if (productValue >= min && productValue <= max) {
    return 100; // 完全在范围内
  }
  
  // 计算偏离度（可选：部分得分）
  if (productValue < min) {
    return Math.max(0, 100 - ((min - productValue) / min) * 100);
  }
  if (productValue > max) {
    return Math.max(0, 100 - ((productValue - max) / max) * 100);
  }
  
  return 0;
}
```

**适用场景：** 管径、工作长度、分辨率、视场角

#### 策略 3: 枚举匹配 (Enum Match)

```typescript
// 当 ParameterDefinition.dataType === 'ENUM'
// 本质是精确匹配，但 value 必须是 ParameterOption 中定义的值
// 可选：从 ParameterOption 表查询以验证合法性

function enumMatch(demandValue: string, productValue: string): number {
  return demandValue.toLowerCase().trim() === productValue.toLowerCase().trim()
    ? 100
    : 0;
}
```

**适用场景：** 光源类型 (LED/激光/卤素)、探头类型 (直视/侧视/双视)

### 3.4 特殊情况处理

| 场景 | 处理方式 |
|------|----------|
| 需求参数在产品中无对应值 | `score = 0`，如果 `required = true` 则 `totalScore = 0` |
| 产品有额外参数（需求未提） | 不参与计分，不扣分 |
| 参数值均为 null | `score = 0` |
| 需求无任何参数 | `totalScore = 100`（仅产品可用性匹配） |

## 5. Workflow Design

### 5.1 匹配触发时机

```
触发方式 A: 同步触发（推荐 V1）
  POST /demands/:id/publish
  └── DemandsService.publish()
      ├── 更新 status → PUBLISHED
      ├── 创建 WorkflowEvent (OPENED)
      └── 调用 MatchingService.match(demandId)  ← 同步触发

触发方式 B: 异步触发（V2 优化）
  POST /demands/:id/publish
  └── DemandsService.publish()
      ├── 更新 status → PUBLISHED
      ├── 创建 WorkflowEvent (OPENED)
      └── 发送匹配事件到消息队列
          └── MatchingWorker 异步处理

触发方式 C: 手动触发（可选）
  POST /demands/:id/rematch
  └── MatchingService.match(demandId)
```

**V1 推荐：** 方案 A（同步触发），简单可靠。方案 B 适用于产品数量 > 10,000 的场景。

### 5.2 匹配执行流程

```
Demand.publish()
    │
    ▼
MatchingService.match(demandId)
    │
    ├── Step 1: 加载 Demand
    │   └── SELECT demand + demandParameters (with ParameterDefinition)
    │
    ├── Step 2: 发现候选产品 (Candidate Discovery)
    │   └── SELECT products WHERE:
    │       ├── status = 'ACTIVE'
    │       └── EXISTS (Offer WHERE status = 'ACTIVE')
    │       └── (可选) categoryId 匹配
    │
    ├── Step 3: 加载候选产品参数
    │   └── SELECT productParameterValues WHERE productId IN (candidates)
    │       └── INCLUDE parameterDefinition
    │
    ├── Step 4: 参数匹配 (Parameter Matching)
    │   └── FOR EACH candidate:
    │       └── FOR EACH demandParameter:
    │           ├── 查找 productParameterValue (by parameterDefinitionId)
    │           ├── 根据 dataType 选择匹配策略
    │           └── 计算 score
    │       └── 加权汇总 totalScore
    │       └── 如果 totalScore < MIN_MATCH_SCORE → 丢弃
    │
    ├── Step 5: 批量创建 DemandMatch
    │   └── UPSERT DemandMatch (by @@unique([demandId, productId]))
    │       ├── matchScore
    │       ├── matchDetails (JSON)
    │       ├── matchStatus = MATCHED
    │       ├── offerId → 选择最佳 Offer
    │       └── matchedAt = now()
    │
    └── Step 6: 返回匹配结果
        └── { matched: number, skipped: number, elapsed: number }
```

### 5.3 候选产品发现策略

```typescript
// 发现策略：优先匹配同分类产品，再扩展
async function discoverCandidates(demand: Demand): Promise<Product[]> {
  // 如果 Demand 关联了 category（通过 DemandParameter 推断）
  // 第一步：同分类产品
  // 第二步：全量产品（降级）
  
  return prisma.product.findMany({
    where: {
      status: 'ACTIVE',
      offers: {
        some: { status: 'ACTIVE' }  // 必须有活跃 Offer
      }
    },
    include: {
      parameterValues: {
        include: { parameterDefinition: true }
      },
      offers: {
        where: { status: 'ACTIVE' },
        orderBy: { createdAt: 'asc' }
      }
    }
  });
}
```

### 5.4 Offer 选择策略

一个 Product 可能有多个 Offer（不同供应商），匹配时需要选择最佳 Offer：

```typescript
// 策略：选择第一个 ACTIVE Offer（按创建时间）
function selectBestOffer(offers: Offer[]): Offer | null {
  return offers.find(o => o.status === 'ACTIVE') || null;
}
```

## 7. Security Consideration

### 7.1 安全分析

| 风险 | 等级 | 防护 |
|------|------|------|
| 匹配结果泄露跨组织数据 | 🟡 中 | matchDetails 不包含敏感字段（如 contactEmail） |
| 匹配结果被未授权用户查看 | 🟢 低 | 通过 Demand/Getsuppliers/:id/matches 的 JWT + 所有权验证 |
| 恶意参数导致匹配膨胀 | 🟡 中 | MAX_MATCHES_PER_DEMAND 限制 |
| 匹配算法被逆向工程 | 🟢 低 | matchDetails 公开化，不隐藏算法 |
| SQL 注入 | 🟢 低 | 使用 Prisma ORM 参数化查询 |

### 7.2 数据访问控制

| 操作 | 权限 | 说明 |
|------|------|------|
| 触发匹配 | 仅 Demand 创建者/管理员 | 通过 publish() 间接触发 |
| 查看匹配结果 | Demand 创建者 + 供应商 | 通过 demand/:id/matches 和 suppliers/:id/matches |
| 更新匹配状态 | Demand 创建者/管理员 | 已有 M7.7 实现 |
| 手动重新匹配 | 仅 Demand 创建者/管理员 | V2 阶段实现 |

1. **零 Schema 变更：** 现有 `DemandParameter`、`ProductParameterValue`、`DemandMatch` 三个模型完全满足 V1 匹配需求。

2. **三种匹配策略：** 精确匹配、数值范围匹配、枚举匹配，覆盖所有 `ParameterDataType`。

3. **加权评分：** 利用 `DemandParameter.priority` 作为权重，`required` 参数不匹配时 totalScore = 0。

4. **同步触发：** V1 采用 Demand publish() 同步触发匹配，简单可靠。

5. **模块化设计：** `matching/` 独立模块，通过 `DemandsModule` 集成，不侵入现有代码。

6. **匹配明细：** 使用 `DemandMatch.matchDetails` JSON 存储完整匹配过程，可追溯、可审计。

## 12. Appendix: 匹配算法伪代码

```
ALGORITHM match(demandId):
  INPUT:  demandId
  OUTPUT: MatchResult

  // 1. 加载需求
  demand = LOAD demand WITH parameters, parameterDefinitions
  IF demand.parameters.length == 0:
    RETURN { matched: 0, reason: "No parameters defined" }

  // 2. 发现候选产品
  candidates = FIND products WHERE:
    status = 'ACTIVE'
    AND EXISTS Offer WHERE status = 'ACTIVE'

  // 3. 加载候选产品参数（批量）
  productParams = LOAD productParameterValues WHERE:
    productId IN candidates.ids
    WITH parameterDefinition

  // 4. 参数匹配
  matches = []
  FOR EACH product IN candidates:
    score = CALCULATE_SCORE(demand.parameters, product.parameterValues)

    IF score.totalScore < MIN_MATCH_SCORE:
      CONTINUE

    offer = SELECT_BEST_OFFER(product.offers)

    matches.push({
      demandId: demand.id,
      productId: product.id,
      matchScore: score.totalScore,
      matchStatus: 'MATCHED',
      matchDetails: score.toJSON(),
      offerId: offer?.id,
      matchedAt: now()
    })

  // 5. 批量创建/更新
  UPSERT DemandMatch (UNIQUE demandId + productId)
    SORT BY matchScore DESC
    LIMIT MAX_MATCHES_PER_DEMAND

  // 6. 返回结果
  RETURN { matched: matches.length, elapsed: ... }
```
