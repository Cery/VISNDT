## 3. Current Workflow Architecture Review

### Content 生命周期（当前实现，`content.service.ts`）

| 方法 | 状态迁移 | WorkflowAction | 说明 |
| --- | --- | --- | --- |
| `create` | → DRAFT | `CREATED` | 创建草稿，`metadata.to=DRAFT` |
| `update` | DRAFT / REVIEW 可编辑 | —（未发事件） | 仅 DRAFT / REVIEW 可修改正文与 SEO |
| `submit` | DRAFT → REVIEW | `SUBMITTED` | 提交审核 |
| `review` | REVIEW → PUBLISHED | `REVIEWED` | 审核通过 |
| `publish` | REVIEW → PUBLISHED | `OPENED` | 直接发布（REVIEW 态） |
| `archive` | PUBLISHED → ARCHIVED | `CLOSED` | 归档 |

- **WorkflowEvent 使用**：`emitEvent()` 以 `entityType=CONTENT`、`entityId`、`action`、`metadata={to}` 写入 WorkflowEvent，operator 为操作者。
- **字段**：`publishedAt`（PUBLISHED 时写入）、`archivedAt`（ARCHIVED 时写入）。

### 关键发现（规划基线）

1. **WorkflowEvent 组织约束冲突**：`WorkflowEventsService.create()` 要求 `operator.organizationId` 存在，否则抛 `ForbiddenException`；而 Content 域按 **author/user** 维度操作（非组织维度）。`content.service.ts` 的 `emitEvent()` 用 `try/catch` 吞掉了该错误，导致 **Content 工作流事件可能被静默丢弃**。这是 M18.4 Implementation 必须修复的可靠性问题。
2. **AuditLog 未接入 Content**：Content 生命周期目前**未**通过 `AuditLogService.log()` 记录系统行为审计（仅依赖 WorkflowEvent，且可能被吞）。AuditLog 与 WorkflowEvent 职责边界现状：WorkflowEvent 记录业务状态流转，AuditLog 记录系统行为（old/new value）。
3. **Notification 无 CONTENT 类型**：`NotificationType` 仅 `SYSTEM / DEMAND_UPDATE / RFQ_UPDATE / RESPONSE_UPDATE`，内容审核相关通知不在当前能力内（M18.4 不新增类型，仅记录）。
4. **无版本历史 / 无定时发布 / 无审核人员显式记录**：当前 Content 仅保留「当前内容」，无历史快照；`content` 字段为覆盖式更新。

## 4. Revision History Design Evaluation

### 候选方案

| 维度 | 方案 A：ContentRevision 独立历史表 | 方案 B：AuditLog 承担版本历史 | 方案 C：Content.content JSON snapshot |
| --- | --- | --- | --- |
| 数据完整性 | ✅ 每次保存快照独立行，版本语义清晰；可做 diff / 恢复 | ⚠️ `newValue` Json 可存快照，但无版本号/顺序语义，内容被覆盖丢失 | ❌ 覆盖式更新，旧内容不保留，无历史 |
| 查询效率 | ✅ 按 `contentId` 索引 + `version` 排序，专表高效 | ⚠️ AuditLog 混合系统审计与业务快照，查询需过滤大表 | ❌ 无历史可查 |
| 审计能力 | ✅ 版本记录独立，与系统审计解耦 | ⚠️ 混入 AuditLog 破坏「审计 vs 业务」边界 | ❌ 无 |
| 未来扩展 | ✅ 可加 version 自增、diff、restore、草稿分支 | ⚠️ 受 `AuditAction` 枚举约束，扩展受限 | ❌ 无法扩展 |
| 边界符合 | ✅ 与 WorkflowEvent（流转）/ AuditLog（系统审计）职责分离 | ❌ 违反「不得混用」边界 | ❌ — |

### 推荐方案

**方案 A — ContentRevision 独立历史表**。

理由：
- 版本历史是**业务数据**（内容快照），与「系统行为审计（AuditLog）」及「业务状态流转（WorkflowEvent）」是三类不同职责，独立建模最清晰。
- 专表索引 + 版本号，查询/差异/恢复/未来扩展均最优。
- 避免污染 AuditLog 边界（符合任务约束「不得混用」）。

候选模型（冻结设计，**Implementation 阶段才落地**）：
`ContentRevision(id, contentId, version, title, summary, content, seoTitle, seoDescription, seoKeywords, coverImageId, snapshot Json, createdBy, createdAt)`
- 每次 `create` / `update` 写入一个递增 `version` 快照。
- 保留「谁在何时保存了什么」。

## 5. Scheduled Publish Design Evaluation

### 现状
`Content.status ∈ {DRAFT, REVIEW, PUBLISHED, ARCHIVED}`，`publishedAt` 在进入 PUBLISHED 时写入当前时间，无「预设定时」能力。

### 设计决策

| 问题 | 决策 |
| --- | --- |
| 是否新增字段 | ✅ 新增 `Content.scheduledPublishAt DateTime?`（仅 Content 上，不建独立 Schedule 模型） |
| 是否新增 Schedule Model | ❌ MVP 不新增独立 Schedule 表（保持 Content 单模型，避免 CMS Scheduler 复杂度） |
| 是否复用 WorkflowEvent | ✅ 定时触发后复用既有 transition + WorkflowEvent（`OPENED`，`metadata` 标记 `scheduled=true` / `scheduledAt`） |
| 是否需要后台任务 | ✅ 需要轻量后台轮询任务（非 CMS Scheduler 系统） |

### 方案
- 在 Content 增加 `scheduledPublishAt` 字段。
- 后台轻量任务（如 `@nestjs/schedule` cron 分钟级轮询）：扫描 `status ∈ {REVIEW}` 且 `scheduledPublishAt <= now()` 的内容，执行既有 `publish()` 过渡（写 `publishedAt` + 发 `OPENED` 事件）。
- 定时设为「审核通过但延后发布」用途：操作者设置 `scheduledPublishAt` 后，内容保持 REVIEW 等待定时发布；未设定时则即时发布。
- **禁止**：引入新的 CMS Scheduler 系统、不新增 `WorkflowAction`（沿用 `OPENED`，语义经 metadata 区分）。

## 6. Reviewer Record Design Evaluation

### 约束
优先复用 User / Organization / WorkflowEvent / AuditLog；**禁止新增 Reviewer 表**。

### 方案
- **审核人员 = WorkflowEvent.operatorId**（`action=REVIEWED` 时 operator 即审核人）。
- 通过 `WorkflowEvent.operator` 关联 User 获取姓名/邮箱展示。
- 无需独立 Reviewer 表；审核记录即「REVIEWED 工作流事件」。
- 若需组织维度审计，可经 User.organizationId 推导（当前 Content 为 author/user 维度，组织为可选增强）。

### 结论
审核人员记录完全复用 `WorkflowEvent.operatorId` + `User`，**不新增表**，符合约束 ✅。

## 7. Approval History Boundary Analysis

### 职责边界（必须保持不混用）

| 载体 | 职责 | Content 场景 |
| --- | --- | --- |
| **WorkflowEvent** | 业务流程状态变化（谁在何时把内容从什么状态转换到什么状态） | CREATED / SUBMITTED / REVIEWED / OPENED / CLOSED 形成**审核时间线（Approval Timeline）** |
| **AuditLog** | 系统行为审计（操作前后值的记录，含 old/new value / IP） | CREATE / UPDATE / STATUS_CHANGE 记录系统级变更痕迹 |
| **Notification** | 待办/通知回流 | 审核待办通知（当前 Content 未接入，M18.4 不新增类型） |

- **Approval Timeline（审核历史）→ WorkflowEvent**：面向业务用户展示「提交→审核→发布」时间线。
- **AuditLog → 系统审计**：面向运维/合规记录每一次数据变更的 old/new value。
- 二者**不得混用**：WorkflowEvent 不做系统级 old/new 审计；AuditLog 不承担业务时间线查询。

### 关键整改项（规划结论，Implementation 落地）
- 修复 Content 域 WorkflowEvent 因组织约束被吞的问题（确保审核时间线可靠记录）。
- 为 Content 生命周期补充 `AuditLogService.log()`（STATUS_CHANGE / UPDATE），补齐系统审计（当前缺失）。

- **对 Content 影响**：Content 本体不变（保持单模型），仅新增可空字段与独立历史表，不影响现有公开读写投影。

## 13. Security Impact

| 项 | 分析 |
| --- | --- |
| 权限 | 版本/定时/审核管理均为 ADMIN 侧，沿用 JwtAuthGuard + RolesGuard + ADMIN；不新增 Role/Permission |
| 审核记录 | 审核人来自 WorkflowEvent.operatorId（User 引用），无新增 PII 载体；公开投影不含审核数据 |
