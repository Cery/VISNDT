### 3.2 Final Semantic Decision

#### 3.2.1 一个 Demand 是否允许产生多个 DemandMatch？

允许。

最终语义：

- 一个 `Demand` 可以产生多个候选 `DemandMatch`
- 每个 `DemandMatch` 对应一个候选供应来源（当前实现上是 `product + offer` 组合）
- 同一 `Demand` 可存在多个 `ACCEPTED` Match，但每个 `ACCEPTED Match` 后续只允许产生一个正式 RFQ

#### 3.2.2 Formal Lifecycle

推荐冻结为以下正式状态机：

| Status | Meaning | Allowed From | Allowed To |
|---|---|---|---|
| `PENDING` | 系统已生成候选记录，但尚未完成对 Buyer 可见化收口 | system create only | `MATCHED` |
| `MATCHED` | 系统确认该候选可供 Buyer 审阅 | `PENDING` | `REVIEWED` |
| `REVIEWED` | Buyer 已完成审阅，准备决策 | `MATCHED` | `ACCEPTED`, `REJECTED` |
| `ACCEPTED` | Buyer 接受该 Match，可据此创建 Targeted RFQ | `REVIEWED` | terminal |
| `REJECTED` | Buyer 拒绝该 Match | `REVIEWED` | terminal |
| `EXPIRED` | 旧 Match 因 rematch 或业务失效而作废 | `PENDING`, `MATCHED` | terminal |

#### 3.2.3 Trigger Semantics

- 系统自动匹配产生什么状态：
  - 推荐：内部先写 `PENDING`，匹配批次完成后推进到 `MATCHED`
  - 若实现上不需要双阶段，M14.3.2 也可直接在落库时写 `MATCHED`
- Buyer 查看后产生什么状态：
  - `MATCHED -> REVIEWED`
- Buyer 接受后产生什么状态：
  - `REVIEWED -> ACCEPTED`
- Buyer 拒绝后产生什么状态：
  - `REVIEWED -> REJECTED`
- 是否允许 `MATCHED -> REJECTED`：
  - **最终语义：不允许**
  - 原因：任何正式拒绝都应留下“已审阅”语义；当前前端一键拒绝只是 UI 便捷，不应成为正式状态机
- 是否允许 `REJECTED -> MATCHED`：
  - **不允许**
  - 原因：同一条 Match 一旦被拒绝，应视为终态
- rematch 后旧 Match 如何处理：
  - **最终语义：旧未决 Match 应标记为 `EXPIRED`，而不是回流**
  - 当前代码直接 `deleteMany` 删除旧 Match，见 [demands.service.ts:L451-L457](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/demands/demands.service.ts#L451-L457)
  - M14.3.2 应把“删除旧 Match”改为“保留历史并失效化”

### 4.2 Final Decision

#### 4.2.1 RFQ 是否必须来源于一个 DemandMatch？

**必须。**

最终冻结语义：

- 新建 RFQ 必须来源于一个 `ACCEPTED DemandMatch`
- `RFQ.sourceMatchId` 应成为正式业务关系
- `Demand -> RFQ` 直接创建路径不再是 M14.3 正式语义

#### 4.2.2 一个 ACCEPTED Match 是否只能产生一个 RFQ？

**是。**

最终语义：

- 一个 `ACCEPTED Match` 对应一个正式 RFQ
- 若后续需要“重新询价”，应关闭/取消旧 RFQ 后再创建替代 RFQ；替代关系可在 M14.3.2 作为可选元数据处理

#### 4.2.3 一个 Demand 是否允许对多个 ACCEPTED Match 分别发起多个 RFQ？

**允许。**

这正是推荐模型的核心。

#### 4.2.4 是否允许一个 RFQ 同时面向多个 Supplier？

**M14.3 正式语义：不允许。**

原因：

- 当前业务目标是把 `Match` 变成 `RFQ` 的严格来源
- 一个 `Match` 当前本质上已经是一个候选供应来源
- 若一个 RFQ 再面向多个 Supplier，则 `sourceMatchId` 语义会失真

### 4.3 Recommended Model

推荐模型：**B**

`一个 Demand -> 多个 Match -> 多个 RFQ -> 每个 RFQ 一个 Supplier`

理由：

1. 与当前 `DemandMatch` 多候选结构一致，见 [matching.service.ts:L171-L203](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/matching/matching.service.ts#L171-L203)
2. 能把 `sourceMatchId` 变成清晰的来源关系
3. 能把 Supplier 可见范围限制到“被定向发送的 RFQ”
4. 能避免“一个 RFQ 多 Supplier”带来的额外 recipient 关系复杂度
5. 与当前 `RFQ.demandId @unique` 冲突，因此该唯一约束必须取消

| Status | Meaning | Allowed From | Allowed To | Operator |
|---|---|---|---|---|
| `SUBMITTED` | Supplier 已提交正式响应 | create only | `VIEWED` | Supplier create |
| `VIEWED` | Buyer 已查看该响应 | `SUBMITTED` | `ACCEPTED`, `REJECTED` | Buyer |

#### 6.2.1 Supplier 谁可以修改？

最终语义：

- 只有响应所属组织可以创建
- 若允许编辑，只允许在 `SUBMITTED` 且 Buyer 尚未 `VIEWED` 前编辑内容
- Supplier 不得修改 `VIEWED / ACCEPTED / REJECTED`

#### 6.2.2 Buyer 谁可以修改？

- Buyer 组织内具备 RFQ 管理权限的用户可以执行：
  - `VIEWED`
  - `ACCEPTED`
  - `REJECTED`

#### 6.2.3 VIEWED 谁触发？

**Buyer 触发。**

推荐语义：

- 由 Buyer 打开“某一条 Response 详情”或显式执行“标记已阅”触发
- 不建议在 RFQ 列表页批量自动触发全部 `VIEWED`

#### 6.2.4 ACCEPTED / REJECTED 谁触发？

**Buyer 触发。**

#### 6.2.5 Buyer 是否可以修改已经 ACCEPTED 的 Response？

**不允许。**

`ACCEPTED` 为终态。

#### 6.2.6 一个 RFQ 是否允许多个 Response 同时 ACCEPTED？

**最终语义：不允许。**

在本次冻结模型下，一个 RFQ 只面向一个 Supplier，理论上最多一条正式 Response。

为兼容历史广播模型，仍冻结以下原则：

- 同一个 RFQ 最多只能有一个 `ACCEPTED Response`
- 若未来存在多个 Response，则接受其中一个后，其余未决响应应自动 `REJECTED`

#### 6.2.7 是否需要记录 reviewedBy / reviewedAt / decisionNote？

- `reviewedBy`: **REQUIRED**
- `reviewedAt`: **REQUIRED**
- `decisionNote`: **OPTIONAL**
  - 拒绝时建议必填
  - 接受时可选

### 7.2 Final Decision

本次冻结结论：**当前 RFQ 状态集合足够，不新增状态。**

正式语义：

| Status | Meaning | Allowed From | Allowed To |
|---|---|---|---|
| `DRAFT` | Buyer 已基于 Match 生成 RFQ，但尚未发出 | create only | `OPEN`, `CANCELLED` |
| `OPEN` | Targeted RFQ 已发布，等待 Supplier 响应 | `DRAFT` | `RESPONDING`, `CLOSED`, `CANCELLED` |
| `RESPONDING` | 已收到至少一条正式 Response，等待 Buyer 决策 | `OPEN` | `CLOSED`, `CANCELLED` |
| `CLOSED` | RFQ 已终结 | `OPEN`, `RESPONDING` | terminal |
| `CANCELLED` | RFQ 已取消 | `DRAFT`, `OPEN`, `RESPONDING` | terminal |

补充冻结规则：

- Supplier 第一次成功提交 Response 后：`OPEN -> RESPONDING`
- Buyer 接受 Response 后：RFQ 自动 `CLOSED`
- RFQ `CLOSED` 后，Supplier 不可再响应

## 10. Final End-to-End Workflow

### 10.1 Frozen Workflow

`Demand`
-> `Matching`
-> `DemandMatch`
-> `Buyer Review`
-> `Accepted Match`
-> `Targeted RFQ`
-> `Supplier Response`
-> `Buyer Review`
-> `Accepted / Rejected`
-> `Notification / WorkflowEvent`

### 10.2 Step-by-Step Semantic Closure

1. Buyer 发布 Demand
2. 系统生成多个 Match
3. Match 从 `PENDING` 收口到 `MATCHED`
4. Buyer 审阅 Match，进入 `REVIEWED`
5. Buyer 接受部分 Match，进入 `ACCEPTED`
6. 每个 `ACCEPTED Match` 生成一个 `Targeted RFQ`
7. RFQ 发布后，仅目标 Supplier 可见
8. 目标 Supplier 提交 Response
9. Buyer 查看 Response，进入 `VIEWED`
10. Buyer 接受或拒绝 Response
11. 若接受，则 RFQ 自动关闭
12. Notification 与 WorkflowEvent 同步记录关键节点

### 18.1 Final Verdict

### 18.2 Frozen Semantics

本次正式冻结的业务语义如下：

1. 一个 `Demand` 允许产生多个 `DemandMatch`
2. `DemandMatch` 正式状态机为：
   - `PENDING -> MATCHED -> REVIEWED -> ACCEPTED/REJECTED`
   - `EXPIRED` 用于 rematch 后旧候选失效
3. 新建 RFQ 必须来源于一个 `ACCEPTED Match`
4. 推荐正式模型为：
   - **B：一个 Demand -> 多个 Match -> 多个 RFQ -> 每个 RFQ 一个 Supplier**
5. Buyer 不允许绕过 Match 直接创建新 RFQ
6. RFQ 必须有唯一 `Target Organization`
7. Response 的正式决策主体是 Buyer，而不是 Supplier
8. RFQ 接受 Response 后自动关闭
9. Notification / WorkflowEvent 继续复用现有模型
