## 2. Current Product Domain Reality

基于真实代码 + Schema，**不做假设**：

- **Product = 平台全球目录（Global Catalog）**：`Product` **无 `organizationId` / 无 `ownerId`**；`createdById` 仅审计字段；`@Roles(ADMIN)` 才能 `POST/PATCH /products`；CreateProductDto 无组织/拥主字段。
- **Supplier Capability = Product + Supplier Offer（Model B）**：`Offer(organizationId, productId)` 带 `@@unique(organizationId, productId)`，供应商只能对既有目录产品创建 Offer（organizationId 服务端由 `user.organizationId` 派生，DTO 不可传）。
- **Product 身兼多职**（详见 §5 Responsibility Map）：平台标准模型 + 展示对象 + SEO 对象 + 搜索对象 + 报价对象 + （经 Offer.indirect）供应商能力载体。
- **约束冻结**（既有决策）：`Product.organizationId / ProductFamily / ProductModel / SupplierOffering` 禁止、Supplier 店铺化禁止、Product 不属于 Organization、VISNDT=工业检测能力发现平台非商品商搜。

## 3. Database Model Analysis

| 对象 | 现状 | 说明 |

| `Offer` | 供应商能力声明 | `@@unique(organizationId, productId)`；`OfferStatus` 枚举（DRAFT/ACTIVE/INACTIVE/SUBMITTED/ACCEPTED/REJECTED/WITHDRAWN） |

结论：当前库即「Global Catalog Product × Offer」二维模型，无第三条 Supplier 产品维度。

## 4. Code Reality Scan

- **API**：`apps/api/src/products` 全部写操作 `@Roles(ADMIN)`；`apps/api/src/offers` 组织 id 服务端派生；`matching/search/media/content` 均与 Product 强绑定。
- **Web**：`apps/web/src/app/workspace/supplier/offers/new/page.tsx`——供应商只能从既有产品 `<ProductSearchSelect>` 选产品建 Offer：`handleProductSelect` 仅写 `productId`；`workspace/supplier/display` 聚合 offers→能力统计；`ProductDetail` + `ManufacturerInfo` 取首个 ACTIVE/SUBMITTED offer 的 organization。
- **Admin**：`ProductForm.tsx` 集中 Admin 创建/编辑（name/model/categoryId/status/description + 参数 + 媒体）；无组织/拥主字段。

审计确认：全栈（API/Web/Admin）当前=Model B，不存在 Model C 的第三条维度代码。

## 6. Hybrid Model C Evaluation（对比矩阵）

| 维度 | Model A 供应商自有产品 | Model B 现状（平台产品×Offer） | **Model C 目标（平台产品×供应商×Offer）** |
|---|---|---|---|
| SEO | ❌ 重复 URL/权重稀释 | ⚠️ 全局唯一，但品牌=首个 Offer 可能偏差 | ✅ 全局权威 + 供应商变体降权避免稀释 |
| 供应商吸引力 | ✅ 强 | ⚠️ 能力表达受限于 Offer | ✅ 自己的系列/型号/图片/参数，快乐表达 |
| Search | ❌ 搜索结果混入供应商副本 | ✅ 单一来源 | ✅ 单一来源 + 变体聚合 |
| 数据治理 | ❌ 重复/冲突 | ✅ 集中治理 | ✅ 集中治理 + 供应商提交需审批 |
| Admin 工作量 | ⚠️ 少但失控 | ✅ 少 | ⚠️ 需审批流（可控） |
| 买家体验 | ❌ 混乱 | ⚠️ P1 无 Offer 产品无制造商展示 | ✅ 能力完整展示 |
| 迁移风险 | ❌ 破坏式 | — | ⚠️ 需定义派生机制（条件项） |

**Model C 定义（限定版）**：不新增「供应商自有目录」。`Platform Product`（全局权威）= 现状 Product；`Supplier Product` = **派生供应商变体**（在 Offer 上表达供应商专属系列/型号/图片/参数/SEO），非顶层新实体。→ **合规于冻结架构**（不触碰 Product.organizationId / SupplierOffering / 店铺化禁止）。

## 7. Product Governance Workflow

- **创建权威（推荐）**：Admin 仍为唯一创建/编辑 Platform Product 者（保全局目录 / 分类 / 参数 / SEO 单一来源）；Supplier 提交「供应商变体草稿」，不经全局目录。
- **状态流评估**：`DRAFT→SUBMITTED→REVIEWING→APPROVED→PUBLISHED→REJECTED` 方向适用，放在**变体/Offer 层**而非全库 Product（因 `Product.status` 现为 String、全局目录不做供应商提交流）。
- **推荐**：供应商能力声明走 Offer 既有审查语义 + 新增「变体提交/审核」读侧治理视图；全局 Product 仍 Admin 治理。

## 8. Migration Strategy

| 策略 | 评估 |
|---|---|
| A 直接替换 Product→SupplierProduct | ❌ 破坏式，违反全局目录冻结 |
| B 新增 SupplierProduct 渐进迁移 | ⚠️ 若顶层实体=违背冻结；若只读派生=可 |
| C 双轨 Legacy+New Product Domain | ❌ 重复来源，治理/搜索成本高 |
| **D 兼容演进（推荐）** | ✅ 保留现有 Product=Platform Product + 在 Offer 上派生 Supplier 变体 + 过渡层；零破坏 |

**推荐：Strategy D（兼容演进）**。本阶段零 Schema/API/前端变更，机制细节（变体存 Offer 内嵌字段 vs 最小变体表 vs 只读派生）延迟至 660 架构设计冻结。

**Decision Blocking Items（供 660 架构设计解封）**：

1. **定义「Supplier Product」为派生供应商变体**：存储机制三选一并冻结（Offer 内嵌字段 / 最小变体表 / 只读派生）——红线：不新增顶层供应商产品目录、不触碰 Product.organizationId/SupplierOffering、不做店铺化。
2. **确定 Offer 绑定**：保持 Option A（Offer 绑定 Platform Product），供应商专属系列/型号/图片/参数/SEO 落到变体层。
3. **治理审批流措辞**：DRAFT→SUBMITTED→REVIEWING→APPROVED→PUBLISHED 落在变体层；全局 Product 维持 Admin 治理，避免状态流污染全局目录。
4. **SEO/品牌权威**：消除 659 列出的 P1（无 Offer 产品制造商「暂未公开」/ JSON-LD brand 偏差），明确变体 URL 与 canonical 权重下沉、防止稀释。
