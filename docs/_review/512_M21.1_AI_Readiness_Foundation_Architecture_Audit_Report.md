## 2. Current Data Architecture Assessment

### 2.1 Prisma Schema Overview

| Domain | Models | Enums | Key AI-Relevant Fields |
|--------|--------|-------|----------------------|
| Identity | 5 (User, RefreshToken, Organization, UserInvitation, OrganizationMember) | 2 | email, name, role, status |

| System | 5 (Notification, WorkflowEvent, AuditLog, FileAsset, Inquiry) | 7 | entityType, action, oldValue, newValue, message |

**Total**: 29 Models, 17 Enums, comprehensive indexing on all query paths.

### 2.2 Search Implementation Audit

| Entity | Search Method | Implementation |
|--------|-------------|---------------|
| Content | `contains` + `mode: 'insensitive'` | Prisma query on `title` + `summary` |
| Product | `contains` + `mode: 'insensitive'` | Prisma query on `name` + `model` |
| Demand | Standard findMany | Category filter |
| Organization | Standard findMany | Name filter |

**Finding**: No PostgreSQL full-text search (`tsvector`), no external search engine, no semantic search. Current search is basic `LIKE`-style string matching at the Prisma layer.

### 2.3 Matching Algorithm Audit

**Implementation**: `ScoringService` (rule-based weighted scoring)

| Data Type | Match Method | Scoring |
|-----------|-------------|---------|
| STRING | Exact match (case-insensitive, trimmed) | 100 or 0 |
| BOOLEAN | Exact match | 100 or 0 |
| ENUM | Exact match (same as STRING) | 100 or 0 |
| NUMBER | Range match (valueMin-valueMax) | 100 (in range) or partial (deviation-based) |

**Key Characteristics**:
- Weighted scoring: `priority` field as weight, default weight from `DEFAULT_MATCH_CONFIG`
- Hard fail: Required parameter → score 0 → total = 0
- Category filter: Demand category → filter candidates
- Candidate filter: `status: ACTIVE` + `has ACTIVE offer`

**AI Enhancement Potential**: Current rule-based scoring can be enhanced with AI-based similarity matching (e.g., embedding-based semantic comparison for STRING parameters, ML-based range optimization for NUMBER parameters).

## 7. Vector Architecture Evaluation

### 7.1 Options Comparison

| Dimension | Option A: pgvector | Option B: External Vector DB |
|-----------|-------------------|------------------------------|
| **Technology** | PostgreSQL extension | Milvus / Qdrant / Weaviate / Pinecone |
| **Integration** | Native SQL, same DB | Separate service, API calls |
| **Deployment** | Single service | Additional infrastructure |
| **Operations** | Minimal overhead | New monitoring, backup, scaling |
| **Performance** | Good for <10M vectors | Better at scale (>10M) |
| **Cost** | Zero additional cost | Infrastructure + licensing |
| **Complexity** | Low | Medium-High |
| **Current Fit** | ✅ Excellent | ⚠️ Overkill |

### 7.2 Recommendation

**Recommendation**: **Option A — PostgreSQL + pgvector**

**Rationale**:
1. **Current Scale**: VISNDT data volume is small (industrial NDT equipment, niche market). pgvector handles millions of vectors efficiently.
2. **Infrastructure Simplicity**: No additional service to deploy, monitor, backup, or scale.
3. **Transactional Consistency**: Vectors stored alongside business data in the same database.
4. **Cost**: Zero additional infrastructure cost. pgvector is a PostgreSQL extension.
5. **Migration Path**: If scale exceeds pgvector capacity, migration to external vector DB is straightforward.

**Implementation Path** (M21.2 Design):
```
1. Enable pgvector extension on PostgreSQL
2. Add embedding vector column to Content model (via Prisma @db.Vector)
3. Create embedding generation pipeline (scheduled/triggered)
4. Implement semantic search using pgvector cosine similarity
```

### 7.3 Embedding Model Recommendation

| Model | Dimension | Language | Suitability |
|-------|-----------|----------|-------------|
| `text-embedding-3-small` (OpenAI) | 1536 | Multilingual | Commercial, high quality |
| `bge-large-zh-v1.5` (BAAI) | 1024 | Chinese-optimized | Open-source, self-hosted |
| `multilingual-e5-large` | 1024 | Multilingual | Open-source, balanced |

**Recommendation**: `bge-large-zh-v1.5` for Chinese content (primary language of VISNDT). Self-hosted, no API cost, optimized for Chinese technical text.

## 10. Final Architecture Decision

### 10.1 Data Quality Assessment Summary

| Domain | Text Quality | Structure | SEO | Search | AI Readiness |
|--------|-------------|-----------|-----|--------|-------------|
| Product | 65% (no SEO) | 90% (params) | 0% (missing) | 40% (LIKE) | 65% |
| Content | 90% (full text) | 85% (tags) | 90% (complete) | 40% (LIKE) | 85% |
| Business | 75% (descriptions) | 80% (match) | N/A | 30% (basic) | 70% |

### 10.2 Decision

**Decision**: **512_M21.1_AI_Readiness_Foundation_Architecture_Audit — PASS**

**Key Findings**:

1. **Content is AI-ready (85%)**: Full text, complete SEO, structured tags, version history. Content is the **best candidate for first AI enhancement** (Semantic Search, Embedding, RAG).

2. **Product is partially ready (65%)**: Excellent parameter system, but missing SEO fields and slug. Product SEO enhancement is a **prerequisite** for product semantic search.

3. **Business is AI-ready (70%)**: Structured matching with rule-based scoring. AI can enhance the ScoringService without replacing it.

4. **pgvector is the recommended vector infrastructure**: Zero additional infrastructure, native PostgreSQL integration, sufficient for current scale.

5. **UserEvent model is needed for future recommendation**: Current AuditLog only tracks mutations, not user behavior.

6. **M21.2 Data & Analytics Infrastructure is the natural next step**: Enable pgvector, create Content embedding, implement UserEvent model, build semantic search MVP.
