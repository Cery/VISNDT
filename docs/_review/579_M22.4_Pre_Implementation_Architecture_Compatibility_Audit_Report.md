### 2.4 Search Architecture Audit

**Audit Method:** Direct inspection of `search.service.ts` (web), `SearchPageContent.tsx`, `products.service.ts`, `content.service.ts`, `knowledge.service.ts`, `semantic/unified-search.service.ts`

**Current Implementation (code evidence):**

```typescript
// apps/web/src/services/search.service.ts:187-215
export async function unifiedSearch(params): Promise<UnifiedSearchResults> {
  const settled = await Promise.allSettled([
    searchProducts(q, page, pageSize),      // GET /products?keyword=
    searchKnowledge(q, page, pageSize),      // GET /content/public?type=KNOWLEDGE&keyword=
    searchSolutions(q, page, pageSize),      // GET /content/public?type=SOLUTION&keyword=
    searchSuppliers(q, page, pageSize),      // GET /offers?keyword=
  ]);
  // Manual aggregation...
}
```

**Critical Finding 1: KnowledgeEntry NOT in search**

`searchKnowledge()` calls `GET /content/public?type=KNOWLEDGE` — this searches Content (type=KNOWLEDGE), NOT KnowledgeEntry (Knowledge Base). The Knowledge Base's KnowledgeEntry model is completely absent from the unified search. This is the same gap identified in the 578 architecture reassessment.

**Critical Finding 2: Semantic Search NOT integrated**

`UnifiedSearchService` (semantic module) is internal-only. It does NOT integrate with the public search page. The public search is purely keyword-based `contains` on database fields.

**4 Distinct Search Endpoints:**

| Endpoint | Entity | Access |
| --- | --- | --- |
| `GET /products?keyword=` | Product | PUBLIC |
| `GET /content/public?type=&keyword=` | Content (ARTICLE/KNOWLEDGE/SOLUTION/INSIGHT) | PUBLIC |
| `GET /offers?keyword=` | Offer (Supplier) | PUBLIC |
| `GET /knowledge/public/entries` | KnowledgeEntry | PUBLIC (NOT in search) |

**Response Structure:** 4 different response shapes, no unified interface. Client-side aggregation with `Promise.allSettled`.

**Result: NEED OPTIMIZATION — 2 critical gaps**

| Question | Finding | Verdict |
| --- | --- | --- |
| Fan-out or unified? | Fan-out, 4 parallel calls | NEED OPTIMIZATION |
| KnowledgeEntry in search? | NO — Content(KNOWLEDGE) used instead | NEED OPTIMIZATION |
| Semantic integrated? | NO — internal-only | NEED OPTIMIZATION |
| Distinct endpoints? | 4 (not counting KnowledgeEntry) | NEED OPTIMIZATION |
| Unified response? | No, 4 different shapes | NEED OPTIMIZATION |
| Frontend aggregation? | Yes, Promise.allSettled | PASS (working) |

### 2.5 Knowledge Architecture Audit

**Audit Method:** Direct inspection of KnowledgeDomain, KnowledgeCategory, KnowledgeEntry, KnowledgeContentRef, KnowledgeRelation models; `knowledge.service.ts`; `apps/web/src/app/knowledge-base/`; `apps/web/src/app/knowledge/`

**Current Knowledge Models:**

```
KnowledgeDomain → KnowledgeCategory → KnowledgeEntry
                                          ↓
                                    KnowledgeContentRef → Content
                                          ↓
                                    KnowledgeRelation
```

**KnowledgeEntry fields:** `title`, `slug`, `summary`, `structuredBody` (JSON), `status`, `authorId`, `publishedAt`, `seoTitle`, `seoDescription`, `seoKeywords`

**Content (type=KNOWLEDGE) vs KnowledgeEntry:**

| Aspect | Content (KNOWLEDGE) | KnowledgeEntry |
| --- | --- | --- |
| Model | `Content` table | `KnowledgeEntry` table |
| Structure | Flat: title, summary, content (Markdown), markdownBody | Structured: title, summary, structuredBody (JSON sections) |
| Classification | Tags only | Domain → Category → Entry hierarchy |
| Relations | None | KnowledgeContentRef → Content, KnowledgeRelation |
| SEO | seoTitle, seoDescription, seoKeywords | seoTitle, seoDescription, seoKeywords |
| Web route | `/knowledge/[slug]` | `/knowledge-base/[slug]` |
| In search | YES (via Content `type=KNOWLEDGE`) | NO (not integrated) |

**Boundary Assessment:**

The two systems COEXIST but serve different purposes:
- **Content (KNOWLEDGE):** Flat content articles, blog-style, tag-based organization
- **KnowledgeEntry:** Structured knowledge, domain-classified, category-organized, with content references and knowledge relations

**No "Searchable Knowledge" vs "Annotation Knowledge" confusion detected.** Both are searchable/readable knowledge. The issue is that KnowledgeEntry is the more structured, domain-classified system but is NOT in search.

**KnowledgeContentRef:** Exists and works — KnowledgeEntry references Content via `SOURCE` / `RELATED` / `SUPPLEMENT` reference types. This is the correct architecture (reference, not copy).

**Result: PASS with optimization note**

| Question | Finding | Verdict |
| --- | --- | --- |
| Content(KNOWLEDGE) vs KnowledgeEntry conflict? | Coexist, overlap, KnowledgeEntry is superset | PASS (needs migration plan) |
| KnowledgeContentRef working? | Yes, 3 reference types | PASS |
| Searchable vs Annotation confusion? | No | PASS |
| Routes distinct? | Yes: /knowledge vs /knowledge-base | PASS |
