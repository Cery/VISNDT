## 2. Inquiry Architecture Verification

目标流（Public Discovery → Buyer Interest → Commercial Request）：

```
Published SupplierProduct（仅 PUBLISHED，来自 661.1 Discovery）
    ↓
Buyer Interest（661.2：Inquiry 携带 supplierProductId + platformProductId）
    ↓
Inquiry RFQ Context（复用现有 Inquiry / Workspace 通知）
    ↓
Existing RFQ Workflow（未改动，供后续 Request 环节复用）
```

- **入口位置**：产品详情「供应商型号」Tab 内，每个已上架供应商型号卡片提供「咨询此型号」按钮。
- **携带上下文**：提交 inquiry 时携带 `supplierProductId` + `platformProductId`（`productId`），并展示 品牌 / 型号 / 能力名（Capability Name）。
- **RFQ 复用**：Inquiry 写入既有 `inquiry` 表，通知经既有 `notificationsService`；RFQ 域零改动，后续 Request 环节沿用既有 RFQ/Response 流程，不引入 Order / Payment。

## 3. SupplierProduct Inquiry Reference（后端）

### 3.1 API Contract Extension

`create-inquiry.dto.ts` 新增**可选**字段：

```ts
@IsUUID()
@IsOptional()
supplierProductId?: string;
```

### 3.2 Validation Rules（`inquiries.service.ts` Step 3.5）

当 `supplierProductId` 提供时，逐项校验：

| 规则 | 实现 | 失败动作 |
| --- | --- | --- |
| SupplierProduct 存在 | `findUnique` | `NotFoundException` |
| **Published status** = `PUBLISHED` | `status !== PUBLISHED` → reject | `ForbiddenException`（DRAFT/SUBMITTED/REVIEWING/APPROVED/REJECTED 一律拒绝进入公网 Inquiry） |
| **Capability binding** | `supplierProduct.platformProductId === dto.productId` | `BadRequestException` |

### 3.3 Context Enrichment

校验通过后：`supplierModelLabel = Brand Series ModelNumber`，写入：
- 接收组织成员的通知消息（`Interest in supplier model: <label>.`）；
- 响应体 `inquiry.supplierProduct = { supplierProductId, supplierModelLabel }` 回显。

### 3.4 Backward Compatibility

- `supplierProductId` **可选**，缺失时行为与既往完全一致（无型号上下文，无额外校验）；
- 不改变既有必填字段契约；不改变 Inquiry 持久化结构（无 schema 字段）。
- **Transport-only reference**：`supplierProductId` 为运行时校验 + 上下文传递，**不新增数据库列**。

## 4. Frontend Inquiry Entry Verification

### 4.1 Entry Location

`SupplierModelsSection`（产品详情「供应商型号」Tab）每个已上架型号卡片，商业可购（有 Offer）时出现「咨询此型号」按钮；点击展开 InquiryForm。

### 4.2 User Flow

```
查看型号卡片 → 点击「咨询此型号」
   → 展示 Buyer 上下文（品牌 / 型号 / 能力名）
   → InquiryForm 提交（携带 productId + offerId + organizationId + supplierProductId）
   → 既有 POST /inquiries 校验 → 供应商接洽
```

### 4.3 Public Exposure Boundary

- 仅展示 **PUBLISHED** 型号（后端 661.1 Discovery 已过滤 + 661.2 Inquiry 再校验）；
- 仅展示 Brand / Series / Model Number / Technical Description / Commercial Availability / Buyer Request 上下文；
- **不展示**：Governance Status / Review Note / Internal Admin Data（后端不下发，前端不渲染）。

## 8. Final Decision

本任务将 **Published SupplierProduct → Buyer Inquiry → 既有 RFQ/Response** 接通：在后端 Inquiry 入口新增 transport-only `supplierProductId` 引用（PUBLISHED + Capability Binding 双校验，非 PUBLISHED 拒绝进公网），在公网供应商型号区块提供「咨询此型号」入口并携带型号上下文，全部复用既有 Inquiry / Notification / RFQ 流程，无 Schema / Migration / RFQ / Matching / Search 改动。

**Status: PASS**

### Risk Assessment

- **Low**：`supplierProductId` 为可选，向后兼容；校验失败仅拒绝该次请求，不影响既有 Inquiry 主流程。
- **Low**：不落库引用，避免因 Schema 变更带来的迁移风风险；代价是型号级引用不持久化（仅通知/响应回显），后续如需持久化可另行评估。

### Next Step Recommendation

- 如需将型号级 Buyer Interest 持久化（入库并进入供应商工作台），需独立评估 Schema/Migration（本任务按约束不引入）。
- 后续可按 roadmap 推进 M28.0 剩余项（Supplier 工作区 / 更深入的商业 Request 编排），均以「RFQ Reuse Before RFQ Rewrite」为原则。
