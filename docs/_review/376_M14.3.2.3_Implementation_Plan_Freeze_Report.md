   - `RFQ @@index([targetOrganizationId, status])`

   - 允许保留新列
   - 回退 API 代码到旧版本

### 5.3 Backend / Frontend Rollback

1. Phase 2 失败：
   - 回退 `rfqs` / `rfq-responses` / `demands` 代码
   - 保留数据库兼容字段
2. Phase 3 失败：
   - 回退前端到旧入口
   - 后端继续保持新权限与新契约
3. Phase 4 失败：
   - 不影响主业务链路上线
   - 允许在不回退主流程的前提下单独修复通知/事件

## 6. Data Migration Strategy

### 6.1 两阶段迁移

1. Stage A: Schema Expand
   - 新增字段全部 nullable
   - 删除 `demandId @unique`
   - 先保证读写不炸
2. Stage B: Backfill
   - 回填 `sourceMatchId`
   - 回填 `targetOrganizationId`
   - 标记无法判定的历史 RFQ
3. Stage C: Constraint Tighten
   - 仅对新生成数据收紧
   - 历史歧义数据处理完成后，再决定是否物理非空

### 6.2 Backfill 分类规则

1. `Deterministic`
   - RFQ 能唯一映射到一个 `ACCEPTED Match`
   - 目标组织与历史响应不冲突
   - 可自动回填
2. `Ambiguous`
   - 同一 Demand 存在多个可疑 Match
   - 或响应组织不能唯一代表目标组织
   - 不自动回填，进入人工核查清单
3. `Orphan`
   - 原始 Match 已因 rematch 删除
   - RFQ 不是从 Match 派生
   - 仅保留旧记录，禁止强行构造虚假来源

### 6.3 迁移冻结规则

1. 不允许用“猜测性匹配”填充 `sourceMatchId`
2. 不允许把“实际响应组织”直接等同于“原始目标组织”而无证据
3. 不允许在 backfill 前先上线强制 `targetOrganizationId` 过滤
