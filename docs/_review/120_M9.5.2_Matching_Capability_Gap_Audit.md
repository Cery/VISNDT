## Current Backend Capability


### 组织隔离验证 (`validateDemandOwnership`)

```typescript
// apps/api/src/demands/demands.service.ts:46-71
private async validateDemandOwnership(id, user) {
  // 1. 用户必须有 organizationId
  if (!user.organizationId) throw BadRequestException('User must belong to an organization');

  // 2. Demand 必须存在
  const demand = await this.prisma.demand.findUnique({ where: { id } });
  if (!demand) throw NotFoundException();

  // 3. 用户必须是创建者 OR 同组织成员
  const isCreator = demand.createdBy === user.id;
  const isSameOrg = demand.organizationId === user.organizationId;
  if (!isCreator && !isSameOrg) throw BadRequestException('No permission');
}
```

**对 Admin 的影响**: 如果 Admin 用户的 `organizationId` 不匹配 Demand 的 `organizationId` 且不是创建者，则无法访问该 Demand 的匹配数据。

## Admin Requirement Analysis

### Admin 运营需求 vs 当前能力

| 需求 | 优先级 | 当前支持 | 差距 |
|---|---|---|---|
| 查看全局匹配总数 | High | ✅ `totalMatches` | 无 |
| 查看匹配状态分布 | Medium | ❌ | 需 `GET /admin/matching/stats` |
| 查看最近匹配列表 | Medium | ❌ | 需全局 Match 列表 API |
| 查看匹配趋势 | Low | ❌ | 需时间序列数据 |
| 按 Demand 查看匹配 | Medium | ✅ Demand Detail | 需逐个点击 |
| 查看匹配评分详情 | Low | ✅ Match Detail | 需逐个点击 |
| 修改匹配状态 | Low | ✅ PATCH | 需 org-scoped |

### Admin 角色限制

Admin 用户访问匹配端点时受 `validateDemandOwnership` 约束:
- 如果 Admin 没有 `organizationId` → 所有 Match 端点返回 400
- 如果 Admin 有 `organizationId` ≠ Demand 的 org → 返回 403
- Admin 只能查看自己组织或自己创建的 Demand 的匹配

**这意味着 Admin 无法获得全局匹配视图。**

## Security Impact

### 当前安全模型

```
Admin 用户
  │
  ├── GET /admin/dashboard/stats  → { matching.totalMatches }  ✅ 可用
  │
  └── GET /demands/:id/matches
      ├── validateDemandOwnership()
      │   ├── require organizationId
      │   └── require: isCreator OR isSameOrg
      └── → 仅返回匹配数据  ❌ 受限于 org-scoped
```

### 安全评估

| 维度 | 当前 | 评估 |
|---|---|---|
| 数据隔离 | org-scoped | ✅ 安全 |
| Admin 全局视图 | 仅 totalMatches | ⚠️ 有限 |
| 越权风险 | 无 | ✅ |
| 敏感数据暴露 | 无（contact info 已保护） | ✅ |

**安全结论**: 当前安全模型是 M8 安全加固的成果，不应弱化。任何 Backend 扩展必须保持 org-scoped 约束。

## Option Analysis

### Option A: Keep Current (推荐)

**策略**: 保持 Backend Freeze，利用现有端点完成 Admin V1。

| 方面 | 评估 |
|---|---|
| 实施成本 | 零 |
| 安全风险 | 零 |
| 功能完整度 | 60% — 有 totalMatches + 按 Demand 查看 |
| 用户体验 | 可接受 — 通过 Demand Detail 查看匹配 |
| 维护成本 | 零 |
| V1 适用性 | ✅ 足以支撑 V1 运营 |

**Admin 运营工作流**:
```
Dashboard → 查看 totalMatches 概览
    ↓
Demand List → 筛选已发布的 Demand
    ↓
Demand Detail → 查看该 Demand 的具体匹配
```

### Option B: Backend Extension

**策略**: 解冻 Backend，新增 `/admin/matching/stats` 和 `/admin/matches`。

| 方面 | 评估 |
|---|---|
| 实施成本 | 中 — 1-2 个 session |
| 安全风险 | 中 — 需绕过 org-scoped，需额外审计 |
| 功能完整度 | 90% — 全局统计 + 列表 |
| 用户体验 | 好 — 一站式匹配概览 |
| 维护成本 | 低 |
| V1 必要性 | ❌ 非必需 |

**新增端点**:
```
GET /admin/matching/stats  → { totalMatches, statusDistribution, averageScore, recentMatches }
GET /admin/matches          → { data: Match[], total, page, pageSize }
```

## Final Recommendation

### 结论: Option A — Keep Current ✅

**理由**:

1. **V1 阶段无需全局匹配视图**: Admin 的核心职责是管理 Product、Demand、Organization，而非监控匹配引擎。匹配监控是 V2/V3 的运营需求。

2. **现有端点已满足基本需求**: `totalMatches` 统计 + Demand Detail 逐项查看覆盖了 V1 的匹配监控场景。

3. **安全模型保护**: 当前的 org-scoped 隔离是 M8 安全加固的核心成果，不应为次要功能弱化。

4. **Backend Freeze 的价值**: 保持 Freeze 避免回归风险，专注于 Admin 前端其他模块（User Management、Organization Management）。

5. **M9 优先级**: User Management 和 Organization Management 是 Admin 系统的核心模块，比对 Matching 做全局监控更重要。

### 后续扩展建议 (V2+)

当运营需求明确需要全局匹配监控时:

1. 新增 `GET /admin/matching/stats` — 聚合统计（不暴露单个 Match 敏感数据）
2. 新增 `GET /admin/matches` — 全局匹配列表（仅返回统计级数据，隐藏敏感信息）
3. 保持 org-scoped 约束 — 不暴露 Demand 的 contact info 和内部参数
