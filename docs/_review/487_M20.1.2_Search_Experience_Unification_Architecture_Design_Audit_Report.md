### 4.2 Content Search (Knowledge + Solutions)

**API**: `GET /content/public`

| Parameter | Support | Description |
|-----------|---------|-------------|
| `type` | ✅ | `KNOWLEDGE` / `SOLUTION` / `ARTICLE` / `INSIGHT` |
| `page` | ✅ | Pagination (1-based) |
| `pageSize` | ✅ | Items per page |
| `keyword` | ❌ | **NOT SUPPORTED** — QueryContentDto has no keyword field |

**Frontend Implementation**:
- `apps/web/src/app/knowledge/page.tsx`: Static list of PUBLISHED content of type `KNOWLEDGE`, no search input
- `apps/web/src/app/solutions/page.tsx`: Static list of PUBLISHED content of type `SOLUTION`, no search input
- Both pages: Server Component (async), no client-side search capability

**Gaps**:
1. ❌ No keyword search parameter in backend API
2. ❌ No search input on knowledge/solutions pages
3. ❌ No content type filter on public pages
4. ❌ No sorting beyond default order

**Assessment**: **Insufficient for unified search** — requires frontend-side keyword filtering or backend API enhancement (Future Candidate).

### 4.3 Supplier Capability Discovery

**API Audit**:

| Endpoint | Auth | Description | Keyword Support |
|----------|------|-------------|-----------------|
| `GET /organizations` | ADMIN only | List all organizations | ✅ (keyword parameter) |
| `GET /organizations/:id` | Public | Get single organization | ❌ (by ID only) |
| `GET /offers` | Public | List offers with filtering | ✅ (keyword, organizationId) |

**Organization Type** (`apps/web/src/types/organization.ts`):
```typescript
interface Organization {
  id: string;
  name: string;
  type: string;
  status: string;
  createdAt: string;
  updatedAt: string;
}
```

**Gaps**:
1. ❌ `GET /organizations` is ADMIN-only — no public supplier listing/search
2. ❌ Organization type lacks `description`, `capability`, `industry` fields
3. ✅ `GET /offers` supports keyword search — can discover suppliers via offer titles
4. ❌ No aggregated supplier search by name/capability/industry

**Frontend Implementation**:
- `/suppliers/[id]`: Supplier detail page, accessed via product detail → supplier link
- No supplier listing page (removed per M19.3.2.1 boundary correction)
- Supplier discovery: product-driven only (ProductDetail → offers → organization)

**Assessment**: **Partially sufficient** — Offers API can be used as indirect supplier discovery, but organization-level search requires ADMIN-only endpoint. Frontend-side workaround: use `GET /offers` with keyword, extract unique organizations from results.

### 5.2 Global Search Entry

**Component**: `GlobalSearchBar`

**Location**: `PublicHeader` navigation bar, between nav items and auth section

**Behavior**:
- Desktop: Inline search input (200px min-width, expandable to 400px)
- Mobile: Search icon → expand to full-width overlay
- Input: keyword text (minimum 2 characters for suggestions)
- Type dropdown: All (default) / Products / Knowledge / Solutions / Suppliers
- Submit: navigates to `/search?q=xxx&type=yyy`

**Search Suggestion Dropdown**:
- Trigger: input length >= 2 characters
- Source: existing API data (product names from `GET /products?keyword=xxx&pageSize=5`)
- Display: top 5 matching product names
- Content/supplier suggestions: Future Candidate (no API support)
- No: autocomplete service, AI search, ML ranking

**URL Pattern**:
```
/search?q=industrial+endoscope&type=product
/search?q=3d+scanner&type=all
/search?q=pipeline+inspection&type=knowledge
```

### 5.3 Unified Search Result Page

**Route**: `/search` (new page in `apps/web/src/app/search/page.tsx`)

**Query Parameters**:
| Parameter | Type | Default | Description |

| `q` | string | required | Search keyword |
| `type` | string | `all` | Search domain: `all` / `product` / `knowledge` / `solution` / `supplier` |

## 6. Search Performance Assessment

### 6.1 Data Flow for "All" Type Search

```
/search?q=endoscope&type=all

↓ Parallel API Requests (TanStack Query)

┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ GET /products   │  │ GET /content/   │  │ GET /offers     │
│ ?keyword=       │  │ public          │  │ ?keyword=       │
│ endoscope       │  │ ?type=KNOWLEDGE │  │ endoscope       │
│                 │  │ ?type=SOLUTION  │  │                 │
└─────────────────┘  └─────────────────┘  └─────────────────┘

↓ Client-side processing

Content: filter by keyword (API doesn't support keyword)
Offers: aggregate by organizationId → supplier results
Products: use as-is

↓ Combined result rendering
```

### 6.2 Performance Assessment

| Aspect | Current State | Assessment |
|--------|---------------|------------|
| API Requests | 3-4 parallel requests | ✅ Acceptable for current scale |
| Response Size | Controlled by pageSize (max 50) | ✅ Acceptable |
| Client-side Filtering | Content keyword matching | ⚠️ Acceptable for MVP, not scalable |
| Supplier Aggregation | Offer deduplication by org | ⚠️ Acceptable for MVP |
| API Aggregation | None (backend) | **Future Candidate** |

**Decision**: Client-side parallel requests are acceptable for M20.1.2. Backend API aggregation for cross-domain search is a **Future Candidate** — to be triggered when data volume reaches performance threshold.
