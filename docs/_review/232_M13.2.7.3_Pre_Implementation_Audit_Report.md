## 5. FileAsset Lifecycle

### 5.1 Existing Delete Methods

| Method | Location | Behavior |
|---|---|---|
| `FileAssetService.delete(id)` | `file-asset.service.ts:123-141` | 1. Find FileAsset by ID<br>2. `storage.deleteObject(storageKey)` — S3 ✅<br>3. `prisma.fileAsset.delete()` — DB ✅<br>4. Throws `NotFoundException` if not found |
| `ProductMediaService.remove(productId, id)` | `product-media.service.ts:68-102` | 1. Find ProductMedia (include fileAsset)<br>2. `prisma.productMedia.delete()` — DB ✅<br>3. `prisma.fileAsset.delete()` — DB ✅ (best-effort)<br>4. `storage.deleteObject(storageKey)` — S3 ✅ (best-effort) |

### 5.2 Duplication Analysis

`ProductMediaService.remove()` and `FileAssetService.delete()` both delete FileAsset from DB and S3, but with different implementations:

| Aspect | `ProductMediaService.remove()` | `FileAssetService.delete()` |
|---|---|---|
| Order | ProductMedia → FileAsset → S3 | S3 → FileAsset |
| Error handling | try/catch — logs errors, doesn't throw | Throws `NotFoundException` |
| NotFound behavior | Silent (no FileAsset = skip) | Throws 404 |
| Reusable | ❌ Manual implementation | ✅ Designed as standalone |

**Recommendation:** `ProductMediaService.remove()` should call `this.fileAssetService.delete(fileAssetId)` instead of manually deleting FileAsset from DB and S3. This would:
- Eliminate code duplication
- Ensure consistent error handling
- Reduce maintenance burden

## 8. Risk Assessment

### 8.1 Current Risks

| # | Risk | Likelihood | Impact | Severity |
|---|---|---|---|---|
| R1 | Orphan FileAsset on create failure | High | Medium | **HIGH** |
| R2 | entityId forever placeholder | High | Low | **MEDIUM** |
| R3 | Code duplication (delete logic) | Certain | Low | **LOW** |
| R4 | No atomic upload-create | High | Medium | **HIGH** |
| R5 | entityType/entityId index unused | Certain | Low | **LOW** |

### 8.2 Risk Detail

**R1 — Orphan FileAsset on Create Failure:**
- Frontend uploads file → FileAsset created (DB + S3)
- Frontend calls create ProductMedia → fails
- FileAsset remains orphaned: DB record + S3 file
- No cleanup mechanism exists
- Accumulates over time with each failed create

**R2 — entityId Forever Placeholder:**
- `entityId: '00000000-0000-0000-0000-000000000000'` is never updated
- `entityType: 'PRODUCT'` is always 'PRODUCT' (hardcoded)
- The `@@index([entityType, entityId])` is useless
- Cannot query "all files for a specific product" via FileAsset

**R4 — No Atomic Upload-Create:**
- Two-step process is inherently racy
- Network failure between steps = orphan
- User closing browser between steps = orphan
- No way to guarantee consistency without a combined endpoint

## 9. Recommended Implementation Plan

### 9.1 Solution Evaluation

#### 方案A: 新增事务上传接口 (New Transactional Upload Endpoint)

**Description:** Create a new `POST /products/:productId/media/upload` endpoint that accepts file + metadata in one call, handles upload + ProductMedia creation atomically.

| Aspect | Assessment |
|---|---|
| API Change | ✅ New endpoint (M13 freeze compatible?) |
| Frontend Change | ✅ Must update `ProductMediaCreate.tsx` |
| Migration | ❌ None needed |
| Complexity | MEDIUM |
| Solves R1, R4 | ✅ Yes |
| Solves R2 | ✅ Can update entityId in same call |

**Pros:** Complete solution; eliminates all create-related orphans  
**Cons:** New API endpoint; frontend changes required; may violate freeze rules

#### 方案B: ProductMediaService.create() 增强 (Enhance create() with entityId Update + Rollback)

**Description:** Modify `ProductMediaService.create()` to:
- On success: update `fileAsset.entityId` to `productMedia.id`
- On failure: delete the orphan FileAsset (if `fileAssetId` was provided)

| Aspect | Assessment |
|---|---|
| API Change | ❌ None — same endpoint |
| Frontend Change | ❌ None |
| Migration | ❌ None needed |
| Complexity | LOW |
| Solves R1 | ⚠️ Partial — only handles backend failures, not frontend abandonment |
| Solves R2 | ✅ Yes |

**Pros:** Minimal changes; no freeze rule violations  
**Cons:** Does not solve frontend abandonment (user closes browser between upload and create)

#### 方案C: 定时清理孤儿 (Scheduled Orphan Cleanup)

**Description:** Add a cron job or manual cleanup endpoint to find and delete FileAssets with no associated ProductMedia.

| Aspect | Assessment |
|---|---|
| API Change | ⚠️ New cleanup endpoint(s) |
| Frontend Change | ❌ None |
| Migration | ❌ None needed |
| Complexity | MEDIUM |
| Solves R1 | ⚠️ Reactive, not preventive |
| Solves R2 | ❌ No |

**Pros:** Cleans up existing orphans; useful for maintenance  
**Cons:** Reactive; doesn't prevent orphan creation; orphans exist between cleanup runs

### 9.2 Recommended Approach: 方案B + 方案C (Layered)

**Phase 1 (Immediate): 方案B — Enhance `create()`**
- Lowest risk, no freeze rule violations
- Fixes `entityId` population
- Handles backend-side create failures

**Phase 2 (Follow-up): 方案C — Add cleanup endpoint**
- `GET /files/orphans` — list orphan FileAssets
- `POST /files/cleanup` — batch delete orphans
- Useful for maintenance and existing orphan cleanup

**Phase 3 (Future): 方案A — Atomic upload-create endpoint**
- Requires freeze review / new phase approval
- Complete solution for frontend abandonment

### 9.3 Detailed Implementation: 方案B

```typescript
// product-media.service.ts — proposed create() enhancement
async create(productId: string, dto: CreateProductMediaDto) {
  await this.ensureProductExists(productId);

  try {
    const productMedia = await this.prisma.productMedia.create({
      data: {
        productId,
        fileAssetId: dto.fileAssetId,
        mediaType: dto.mediaType,
        title: dto.title,
        description: dto.description,
        isPrimary: dto.isPrimary,
        displayOrder: dto.displayOrder,
      },
      include: { fileAsset: true },
    });

    // Update FileAsset entityId to point to this ProductMedia
    if (dto.fileAssetId) {
      await this.prisma.fileAsset.update({
        where: { id: dto.fileAssetId },
        data: { entityId: productMedia.id },
      }).catch((err) => {
        this.logger.warn(
          `Failed to update FileAsset entityId: ${(err as Error).message}`
        );
      });
    }

    return productMedia;
  } catch (err) {
    // Rollback: delete orphan FileAsset if create failed
    if (dto.fileAssetId) {
      try {
        await this.fileAssetService.delete(dto.fileAssetId);
      } catch (cleanupErr) {
        this.logger.error(
          `Failed to cleanup orphan FileAsset ${dto.fileAssetId}: ${(cleanupErr as Error).message}`
        );
      }
    }
    throw err; // Re-throw original error
  }
}
```

**Required changes:**
1. Inject `FileAssetService` into `ProductMediaService` constructor
2. Add `FileAssetModule` to `ProductMediaModule` imports
3. Modify `create()` method as above

## 11. Final Recommendation

### 11.1 Priority: 方案B (Enhance create())

**Reasoning:**
- Lowest risk, minimal changes
- Fixes the `entityId` placeholder issue (M13.2.7.1 Issue #3)
- Provides partial orphan prevention for backend failures
- Does NOT violate any freeze rules
- Can be implemented in a single file (`product-media.service.ts` + `product-media.module.ts`)

**Additional Recommendation: Refactor `remove()` to reuse `FileAssetService.delete()`**

The current M13.2.7.2 fix duplicates `FileAssetService.delete()` logic. While both approaches work, reusing `FileAssetService.delete()` would:
- Eliminate code duplication
- Ensure consistent error handling
- Make future changes to delete logic automatically apply to both paths

This requires:
1. Import `FileAssetModule` into `ProductMediaModule`
2. Replace manual FileAsset/S3 delete with `this.fileAssetService.delete(fileAssetId)`
