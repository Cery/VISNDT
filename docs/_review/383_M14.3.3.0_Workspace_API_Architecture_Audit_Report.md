### 审计结论

当前后端已经具备 Workspace 所需的核心事实数据：

- Buyer 侧可拿到 Demand、Match、RFQ、RFQResponse 决策链路
- Supplier 侧可拿到 RFQ、RFQResponse、Notification 链路
- Auth 已提供 `organizationId` 与 `workspaceRole`
- Notification 与 WorkflowEvent 已提供横向支撑能力

当前真正缺少的是：

- Buyer / Supplier 场景化 overview API
- 面向工作台的计数、分组、最近活动聚合
- 更贴近业务链路的 Workflow 时间线查询边界

## 3. Buyer Workspace Architecture Design

### 目标视图

Buyer Dashboard 需要围绕以下业务链路组织数据：

`我的需求`

`↓`

`匹配结果`

`↓`

`发送 RFQ`

`↓`

`收到供应商响应`

`↓`

`待处理决策`

### 现有数据来源

- `Demand`
  - 当前 Buyer 已有 `/demands/my` 与组织隔离能力
- `DemandMatch`
  - 当前 Buyer 已有 `/demands/:id/matches` 与状态流转能力
- `RFQ`
  - 当前 Buyer 已有 `/rfqs/mine`
  - Targeted RFQ 已支持 `sourceMatchId` 与 `targetOrganizationId`
- `RFQResponse`
  - 当前 Buyer 已有 `view / accept / reject`
  - 但 Buyer 组织级待处理响应列表尚未聚合
- `WorkflowEvent`
  - 当前已有留痕写入
  - 但缺少 Buyer 工作台直接消费的筛选视图

### 架构建议

建议在 `M14.3.3` 中引入“工作台聚合层”概念，而不是继续把 Buyer 工作台查询散落在现有领域 Service 中。

建议方向：

1. 采用单独的 Workspace 聚合边界，例如：
   - `WorkspaceService`
   - 或 `WorkspaceQueryService`
2. 该层职责应是：
   - 聚合既有领域数据
   - 做角色和组织边界裁剪
   - 输出 Dashboard 直接可消费的数据结构
3. 该层不应承担：
   - 领域状态机修改
   - RFQ / RFQResponse 决策逻辑
   - Demand / Match 原子操作写入逻辑

### Buyer 侧推荐聚合内容

- 我的需求列表
- 需求状态计数
- 需求下 Match 结果摘要
- 已发送 RFQ 数量与最近 RFQ
- 已收到 RFQResponse 数量
- `SUBMITTED / VIEWED` 维度下的待处理决策数
- 最近 Workflow / Notification 活动

### 设计判断

Buyer Workspace 不建议直接让前端串联多个既有接口拼装 overview。  
更合适的方式是在后端提供 Buyer 视角的聚合 API，由聚合层统一读取 `Demand / DemandMatch / RFQ / RFQResponse / WorkflowEvent / Notification`。

## 4. Supplier Workspace Architecture Design

### 目标视图

Supplier Dashboard 需要围绕以下业务链路组织数据：

`收到 RFQ`

`↓`

`提交响应`

`↓`

`处理中`

`↓`

`已接受 / 已拒绝`

### 现有数据来源

- `RFQ`
  - 当前已有 `GET /rfqs/available`
  - 但该接口更接近“可响应 RFQ 列表”，不等同于“发给当前供应商组织的 Targeted RFQ Inbox”
- `RFQResponse`
  - 当前已有 `GET /rfq-responses/mine`
  - 能够支撑 Supplier 查看自己组织已提交响应及其状态
- `Organization`
  - 当前已有组织详情访问能力，可支撑 Workspace Header / 组织上下文展示
- `Notification`
  - 当前已有通知列表与未读计数，可支撑 Supplier 待办提醒

### 推荐聚合方式

Supplier Workspace 应以“当前组织”为中心聚合，而不是以单一 RFQ 或单一 Response 为中心。

推荐聚合内容：

- 发给当前组织的 Targeted RFQ 列表
- 当前组织已提交 RFQResponse 列表
- 按 `SUBMITTED / VIEWED / ACCEPTED / REJECTED` 的响应状态计数
- 近期 Buyer 决策结果
- 未读通知与最近通知

### 关键审计判断

`GET /rfqs/available` 可以作为 Supplier 发现 RFQ 的基础能力，但不建议直接作为 Supplier Workspace 的主数据源，原因如下：

1. 该接口当前按状态暴露 `OPEN / RESPONDING`，不是专门为 Targeted RFQ Inbox 设计。
2. Workspace 语义要求的是“属于当前组织的 RFQ 任务”，而不是泛化的“可报价列表”。
3. `M14.3.2` 已引入 `targetOrganizationId`，M14.3.3 更适合围绕该字段做 Supplier Workspace 聚合，而不是继续沿用宽口径列表。

## 5. API Boundary Proposal

以下仅为设计建议，不代表本任务已创建任何 Controller。

### Buyer

#### `GET /workspace/buyer/overview`

- 使用角色：
  - `workspaceRole = BUYER`
- 数据来源：
  - `Demand`
  - `DemandMatch`
  - `RFQ`
  - `RFQResponse`
  - `Notification`
  - `WorkflowEvent`
- 返回内容：
  - 我的需求总数与状态计数
  - Match 摘要
  - RFQ 摘要
  - 待处理响应数
  - 最近活动
- 权限要求：
  - 只能读取当前 `organizationId` 下 Buyer 组织的数据

#### `GET /workspace/buyer/demands`

- 使用角色：
  - `workspaceRole = BUYER`
- 数据来源：
  - `Demand`
- 返回内容：
  - Buyer 工作台用需求列表
  - 可包含状态、最近更新时间、关联 Match/RFQ 计数
- 权限要求：
  - 仅当前 Buyer 组织

#### `GET /workspace/buyer/pending-decisions`

- 使用角色：
  - `workspaceRole = BUYER`
- 数据来源：
  - `RFQResponse`
  - `RFQ`
  - `Demand`
- 返回内容：
  - 当前 Buyer 组织待处理的 RFQResponse 列表
  - 包含响应状态、Demand 标题、Supplier 组织信息、最近更新时间
- 权限要求：
  - 仅当前 Buyer 组织

### Supplier

#### `GET /workspace/supplier/overview`

- 使用角色：
  - `workspaceRole = SUPPLIER`
- 数据来源：
  - `RFQ`
  - `RFQResponse`
  - `Notification`
  - `Organization`
- 返回内容：
  - 收到的 RFQ 数
  - 已提交响应数
  - 响应状态分布
  - 最近 Buyer 决策结果
  - 通知摘要
- 权限要求：
  - 只能读取当前供应商组织相关数据

#### `GET /workspace/supplier/rfqs`

- 使用角色：
  - `workspaceRole = SUPPLIER`
- 数据来源：
  - `RFQ`
- 返回内容：
  - 发给当前组织的 Targeted RFQ 列表
  - 状态、发布时间、关联 Demand、是否已响应
- 权限要求：
  - 必须基于当前组织进行过滤，禁止跨组织访问

#### `GET /workspace/supplier/responses`

- 使用角色：
  - `workspaceRole = SUPPLIER`
- 数据来源：
  - `RFQResponse`
  - `RFQ`
- 返回内容：
  - 当前组织提交的响应列表
  - 状态、Buyer 决策结果、decision 时间
- 权限要求：
  - 仅当前供应商组织

### 设计说明

建议将 `workspace/*` 视为“只读聚合 API”边界：

- 负责聚合
- 不改动既有原子写接口
- 不替代 `demands`、`rfqs`、`rfq-responses` 现有领域职责

## 6. Permission Architecture Review

### 当前可复用能力

- `JWT`
  - 已提供认证上下文
- `organizationId`
  - 已作为多数组织隔离查询的基础条件
- `workspaceRole`
  - 已由 `auth` 根据 `organization.type` 推导为 `BUYER / SUPPLIER`
- `RBAC`
  - 已通过 `RolesGuard` 对 ADMIN 级接口做组织成员角色校验

### Buyer 权限判断

Buyer Workspace 应只允许查看当前 Buyer 组织自己的 Demand 链路，包括：

- 自己组织的 `Demand`
- 自己组织 Demand 下的 `DemandMatch`
- 自己组织创建的 `RFQ`
- 自己组织有权决策的 `RFQResponse`

### Supplier 权限判断

Supplier Workspace 应只允许查看当前 Supplier 组织的链路，包括：

- `targetOrganizationId = current organizationId` 的 Targeted RFQ
- `organizationId = current organizationId` 的 RFQResponse
- 当前组织的通知

### 审计结论

现有鉴权基础足够支撑 Workspace API：

1. 用户身份由 JWT 提供
2. 组织边界由 `organizationId` 提供
3. Buyer / Supplier 视角可由 `workspaceRole` 提供
4. 现有领域服务中已大量使用组织隔离校验，可直接复用同类模式

需要补充的是：

- Workspace 聚合 API 自身必须显式落实组织过滤
- 禁止把通用列表接口未经裁剪直接暴露给 Buyer / Supplier 工作台

1. `M14.3.2` 已完成 Targeted RFQ 所需字段扩展：
   - `RFQ.sourceMatchId`

   - `Demand`
   - `DemandMatch`
   - `RFQ`
   - `RFQResponse`
   - `Notification`
   - `WorkflowEvent`
   - `Organization`
3. 当前审计未发现必须新增字段、模型或 migration 才能支撑 M14.3.3 的证据

建议：

`M14.3.3` 优先基于现有模型完成聚合查询；若后续出现性能瓶颈，应作为后续优化议题单独评估，而不是在本阶段先行打开数据库变更范围。

## 8. API Impact Assessment

### 判断

M14.3.3 需要新增聚合 API。

### 对既有 API 的影响

- 不需要修改既有 `demands`、`matching`、`rfqs`、`rfq-responses` 原子接口契约
- 不需要修改 `M14.3.2` 已冻结的 Buyer Decision 与 Targeted RFQ 主流程接口
- 建议以新增只读聚合 API 的方式提供 Workspace 数据

### 审计建议

1. 新增 `workspace` 命名空间比扩写现有领域 Controller 更清晰
2. `workspace` 接口应作为“读模型 / 聚合视图”边界
3. 现有写操作接口继续保留在原有领域模块中

结论：

`M14.3.3` 的 API 影响应为“新增聚合接口，保持既有契约不变”。
