## 5. Cookie Strategy

### Access Token Cookie

| Attribute | Value |
|-----------|-------|
| Name | `access_token` |
| HttpOnly | ✅ `true` |
| Secure | `true` in production, `false` in dev |
| SameSite | `lax` |
| Path | `/` |
| MaxAge | `JWT_EXPIRES_IN` (default: 86400s = 24h) |

### Refresh Token Cookie

| Attribute | Value |
|-----------|-------|
| Name | `refresh_token` |
| HttpOnly | ✅ `true` |
| Secure | `true` in production, `false` in dev |
| SameSite | `lax` |
| Path | `/` |
| MaxAge | `JWT_REFRESH_EXPIRES_IN` (default: 604800s = 7 days) |

### Security Properties

- ✅ **HttpOnly**: Not accessible to JavaScript (XSS-safe)
- ✅ **Secure in production**: Only sent over HTTPS
- ✅ **SameSite Lax**: CSRF protection for most cases
- ✅ **Token Rotation**: Old refresh token revoked on each refresh
- ✅ **SHA-256 hashing**: Refresh tokens stored as hashes in DB

## 6. RefreshToken Flow

### Token Creation (Login / Register)

```
User authenticates
    ↓
Backend generates:
  accessToken  (JWT, 24h)
  refreshToken (crypto.randomBytes(64), 7d)
    ↓
refreshToken → SHA-256 hash → stored in DB
    ↓
Both tokens set as HttpOnly cookies
    ↓
Response: { user } (no tokens in body)
```

### Token Refresh (401 Handling)

```
API returns 401
    ↓
Frontend api-client:
  POST /auth/refresh (credentials: 'include')
    ↓
Backend:
  1. Read refresh_token cookie
  2. SHA-256 hash → lookup in DB
  3. Validate: not revoked, not expired
  4. Revoke old refresh token (rotation)
  5. Issue new access_token + refresh_token
    ↓
Frontend retries original request
    ↓
If refresh fails → throw 401 → caller handles logout
```

### Logout

```
POST /auth/logout (credentials: 'include')
    ↓
Backend:
  1. Read refresh_token cookie
  2. Revoke refresh token in DB (set revokedAt)
  3. Clear access_token + refresh_token cookies
    ↓
Frontend: clear user state, redirect to /login
```
