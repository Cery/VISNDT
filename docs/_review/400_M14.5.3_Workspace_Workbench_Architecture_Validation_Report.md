## 8. Actions API Necessity Assessment

Evaluated targets:

- `/workspace/buyer/actions`
- `/workspace/supplier/actions`

Assessment result:

- `后续阶段建议新增`

Reasoning:

- Buyer already has `pending-decisions`, which covers the clearest Phase 1 action summary
- Supplier already has `overview + rfqs + responses`, which is enough for the current workbench
- Current dashboards can still express `Status + Navigation` without a dedicated actions endpoint
- However, there is not yet a unified cross-domain action queue for either role
- If future phases require prioritized CTA ordering, timeline-style action stream, or cross-domain pending queue abstraction, a dedicated read-only actions API would reduce frontend assembly pressure

Judgment:

- Current phase: no mandatory need to add actions API now
- Future phase: small read-only actions endpoint is reasonable if workbench grows beyond current summary model

## 9. Risk List

### Medium

1. `WorkspaceSidebar`
   - Supplier navigation still contains both `/dashboard/supplier` and `/workspace/supplier`
   - This creates two Supplier entry concepts in parallel
   - Risk: user mental model may drift between `dashboard workbench` and `supplier shell placeholder`

2. `/workspace/supplier`
   - Current page is still a placeholder shell and explicitly states that later capabilities may be added there
   - Risk: future work may accidentally continue expanding this page instead of keeping `/dashboard/supplier` as the canonical workbench

3. Actions abstraction gap
   - Buyer and Supplier currently rely on separate overview/list endpoints rather than a single prioritized action queue
   - Risk: if pending actions become more complex, frontend assembly logic may start spreading across pages

### Low

4. `WorkspaceHeader`
   - Header is currently a pure shell component and does not introduce domain coupling
   - Residual risk is low, but it should remain shell-only to avoid future API coupling

5. workspace shell
   - `/workspace` has already been reduced to a navigation entry page, which is correct
   - Residual risk is low, but it must stay out of summary aggregation to avoid duplicating dashboard responsibility

6. Legacy route
   - `/workspace/dashboard` still exists and redirects to `/dashboard`
   - Risk is low because behavior is harmless and keeps compatibility, but it is still legacy surface area that should remain documented
