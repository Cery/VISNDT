## 一、数据库现状总览

- **Schema 版本**：Prisma Schema v1.0，基于 VISNDT Blueprint v1.0
- **Provider**：PostgreSQL（`DATABASE_URL`，含 `vector(1536)` 扩展用于 embedding）
- **Model 数量**：34 个
- **迁移批次**：Migration 001~016（Identity → Product → Offer/Demand/RFQ → Notification/Audit → Inquiry → Content → Revision → Tagging → Analytics → AI → Knowledge → ProductCategoryKnowledgeMapping）

### 1.1 领域划分与核心模型

| 领域 | 模型 |
|------|------|
| 身份与组织 | User, RefreshToken, Organization, UserInvitation, OrganizationMember |
| 产品 | ProductCategory, Product, ProductMedia, ParameterGroup, ParameterDefinition, ParameterOption, ProductParameterValue, ProductParameterDefinition |
| 报价 | Offer |
| 需求/询价 | Demand, DemandParameter, DemandMatch, RFQ, RFQResponse |
| 工作流/通知 | WorkflowEvent, Notification |
| 文件/审计 | FileAsset, AuditLog |
| 询盘 | Inquiry |
| 内容 | Content, ContentMedia, ContentRevision, ContentTag, ContentTagRelation |
| 分析 | ConversionEvent |
| AI 数据准备 | ContentChunk |
| 知识库 | KnowledgeDomain, KnowledgeCategory, KnowledgeEntry, KnowledgeContentRef, KnowledgeRelation, ProductCategoryKnowledgeMapping |

### 1.2 合理性评估（当前架构的优点）

1. **命名规范统一**：PascalCase Model + snake_case 列（`@map`），主键一律 `uuid()`。
2. **业务术语冻结到位**：Organization（非 Supplier）、Demand（非 Requirement）、RFQ（非 Inquiry）语义一致，符合 TECH_STACK_DECISION。
3. **供应商实体间关系正确**：`Offer` 以 `@@unique([organizationId, productId])` 约束「一供应商一产品一报价」，符合「产品是全平台 Global Catalog、供应商通过 Offer 展示」的冻结架构。
4. **确定性匹配已落地**：`Demand` → `DemandParameter` → `ProductParameterValue` → `DemandMatch(matchScore)` 链路清晰，无 AI/语义替代参数介入。
5. **知识映射确定性**：`ProductCategoryKnowledgeMapping` 承载「产品 ↔ 知识」双向确定性映射，符合 M24 ADR。
6. **内容已有版本**（`ContentRevision`，`version` + `snapshot`），为媒体版本演进提供了同类范式。

## 二、媒体资产域现状与缺失（重点）

### 2.1 现状结构

```
FileAsset（存储实体）
├─ entityType: FileEntityType（PRODUCT/ORGANIZATION/DEMAND/RFQ/RFQ_RESPONSE/CONTENT）
├─ entityId: Uuid
├─ fileType: FileType（IMAGE/DOCUMENT/CERTIFICATE/OTHER）
├─ fileName / storageKey / mimeType / fileSize
└─ uploadedBy: User（→ 可派生 organizationId）

ProductMedia（产品媒体关联）
├─ productId → Product
├─ fileAssetId? → FileAsset
├─ mediaType: FileType, title, description, isPrimary, displayOrder

ContentMedia（内容媒体关联）
├─ contentId → Content
├─ fileAssetId? → FileAsset
├─ type: ContentMediaType（IMAGE/ATTACHMENT）, caption, altText, sortOrder
```

### 2.2 缺失能力对照（相对「分开管理」诉求）

| 能力 | 现状 | 是否需改库 |
|------|------|:---:|
| 图片/文档/资质/其他分类 | ✅ `FileType` 已支持 | 否 |
| 资质证书单独管理 | ✅ `CERTIFICATE` | 否 |
| 规格书 vs 普通文档细分 | ❌ 只有 `DOCUMENT` | **是**（枚举扩展或加列） |
| 供应商组织级隔离（落列） | ❌ 仅能经 `uploadedBy→User` 派生 | **是**（加 `organizationId`） |
| 媒体生命周期状态（草稿/发布/归档） | ❌ 无 `status` | **是** |
| 软删除 / 回收站 | ❌ 无 `deletedAt` | **是** |
| 文件夹 / 标签组织 | ❌ 无 | **是** |
| 版本历史 / 回滚 | ❌ 无（仅内容域有 Revision） | **是**（较大） |

## 三、媒体中心改库选项（供审核选型）

> 三条路径递进，风险与收益成正比。全部**不触碰** Matching/Scoring/AI/Search 等冻结域，仅涉及媒体资产域。

### 选项 1：零迁移（只读派生 + 现有枚举 + 命名约定）【最低风险，推荐先做】

- **做法**：不改 schema。媒体中心前端统一视图；供应商维度经 `FileAsset.uploadedBy → User → Organization` 只读派生；分类复用 `fileType`；规格书用「文件命名/DOCUMENT + 约定」区分。
- **优点**：零迁移、零风险、可立即上线，符合「Runtime Read-side Capability」哲学。
- **缺点**：规格书无法强类型区分；隔离为非落列派生，跨表过滤/权限强制较弱；无生命周期/软删。
- **适用**：作为 B.1 前端收口，先满足「分开管理」展示诉求。

### 选项 2：最小迁移（低风险，针对性补齐）【推荐中期】

- **做法**：在 `FileAsset` 增列 + 增枚举，聚焦用户明确诉求，不改关系模型：
  1. 扩展 `FileType` 枚举：+ `SPEC_SHEET`（规格书）、+ `ILLUSTRATION`（插图）——或新增 `FileCategory` 子分类。
  2. 新增 `organizationId String? @map("organization_id") @db.Uuid`（+ `Organization` 关系/索引），实现供应商落列隔离。
  3. 新增 `status String @default("ACTIVE")`（生命周期）与 `deletedAt DateTime?`（软删）。
- **优点**：精确命中「不同供应商资料/资质/规格书分开管理 + 隔离 + 回收」；改动局部、可回滚。
- **缺点**：需一次 Prisma 迁移 + 数据回填（现有 `uploadedBy` 反查 `organizationId`）；需同步 API/admin 读写。
- **适用**：B.2 门禁阶段的推荐落地范围（对齐 629 Decision B Phase 1）。

### 选项 3：完整演进（629 Decision B 全量）【高风险，远期】

- **做法**：在选项 2 基础上加文件夹/标签（新表）、版本历史（`MediaVersion`/`MediaRevision`）、高级权限。
- **优点**：彻底媒体资产化，接近 DAM 能力。
- **缺点**：新增多张业务表，触碰「不得新增业务表」冻结约束的边界；风险与工期最大。
- **适用**：仅当内容规模起来后（629 判定「未来演进」，Decision B Phase 2），且需重新架构评审。
