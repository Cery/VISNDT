## 2. Current Matching Architecture Audit

### 2.1 Matching Pipeline

```
Demand.publish()
      |
      ↓
MatchingService.match(demandId)
      |
      ├── Step 1: Load Demand + Parameters + ParameterDefinitions
      ├── Step 2: Query Candidate Products (ACTIVE + Category Filter + Active Offers)
      ├── Step 3: Per-Product Scoring via ScoringService.calculateScore()
      │         ├── DemandParameter → ProductParameterValue
      │         ├── Weighted aggregate (priority-based)
      │         ├── Hard fail: required parameter unmatched → score 0
      │         └── Filter: score < minMatchScore (40) → skipped
      ├── Step 4: Sort by descending score, limit to maxMatchesPerDemand (50)
      ├── Step 5: Batch upsert DemandMatch (PENDING)
      ├── Step 6: Create WorkflowEvent + Notification
      └── Return MatchResultDto
```

### 2.2 Scoring Algorithm

**Algorithm**: `weighted_v1` — deterministic parameter-based scoring

| Data Type | Match Strategy | Score |
|-----------|---------------|-------|
| NUMBER | Range compatibility (value within [min, max]) | 0-100 (partial by deviation) |
| ENUM | Exact match (case-insensitive) | 0 or 100 |
| STRING | Exact match (case-insensitive) | 0 or 100 |
| BOOLEAN | Exact match | 0 or 100 |

**Weight Application**: `totalScore = Σ(score × weight) / Σ(weight)`

**Config**: `minMatchScore = 40`, `maxMatchesPerDemand = 50`, `defaultPriority = 1`

### 2.3 Current Architecture State

| Layer | Status | Description |
|-------|--------|-------------|
| Demand Parameters | ACTIVE | Parameterized demand with priority/required |
| Product Parameters | ACTIVE | ProductParameterValue per ParameterDefinition |
| Category Filter | ACTIVE | CategoryHelper filters by demand category |
| Scoring Engine | ACTIVE | `weighted_v1` deterministic scoring |
| DemandMatch | ACTIVE | PENDING → REVIEWED → ACCEPTED/REJECTED |
| Workflow Events | ACTIVE | Match lifecycle event tracking |
| Notifications | ACTIVE | Match creation notification |
| Knowledge Context | ABSENT | No knowledge layer in matching pipeline |
| AI Context | ABSENT | No AI layer in matching pipeline |

### 2.4 Key Observation

The matching pipeline is **purely deterministic**: Demand Parameters → Product Parameters → Score. There is no injection point for Knowledge, AI, or semantic context. This is by design and must be preserved.

### 3.4 Knowledge Context Output Contract

```typescript
interface KnowledgeContext {
  /** Inspection domain context */
  domain: {
    id: string;
    name: string;
    slug: string;
    description: string;
  };

  /** Inspection category context */
  category: {
    id: string;
    name: string;
    slug: string;
    description: string;
  };

  /** Primary knowledge entries for this match context */
  relevantEntries: KnowledgeEntryRef[];

  /** Prerequisite knowledge (must know before understanding this match) */
  prerequisiteKnowledge: KnowledgeEntryRef[];

  /** Related solution articles */
  relatedSolutions: KnowledgeEntryRef[];

  /** Technical reference documents */
  technicalReferences: KnowledgeEntryRef[];
}

interface KnowledgeEntryRef {
  id: string;
  title: string;
  slug: string;
  summary: string;
  domainName: string;
  categoryName: string;
  relationType: 'PRIMARY' | 'PREREQUISITE' | 'RELATED' | 'SUPPLEMENT';
}
```

## 6. Architecture Decision Register

| ADR | Decision | Status | Rationale |
|-----|----------|--------|-----------|
| ADR-016 | Knowledge Context Layer Design | FROZEN DESIGN | Knowledge provides context as companion data alongside match results, without modifying the scoring pipeline |
| ADR-017 | Knowledge ≠ Score Input | FROZEN | Knowledge content must not affect deterministic parameter scoring. Matching remains explainable and stable. |
| ADR-018 | AI ≠ Matching Engine | FROZEN | AI provides explanation, assistance, and decision support — never auto-match, auto-purchase, or auto-selection |
| ADR-019 | Scenario Understanding Future Interface | FUTURE | Interface designed for M23.1+. No runtime implementation. Input: user requirement + inspection scenario. Output: ScenarioContext (not match score). |
| ADR-020 | Matching Deterministic Core Preserved | FROZEN | `weighted_v1` algorithm unchanged. Demand Parameter → Product Parameter → Score pipeline is the sole matching authority. |
| ADR-021 | Knowledge Context as Read-Side Concern | FROZEN DESIGN | KnowledgeContext is computed on match detail read, not stored in DemandMatch. Zero migration impact. |
| ADR-022 | Matching Score Cap = 100 | FROZEN | No bonus points, no knowledge weight, no AI boost. Score is purely parameter compatibility. |

## 7. M23+ Evolution Roadmap

### 7.1 M23.0: Knowledge Context Foundation

**Objective**: Establish Knowledge Context as a companion layer alongside matching.

**Deliverables**:
- KnowledgeContextAdapter: resolve Domain + Category → KnowledgeEntry → Relation
- GET `/matches/:id/knowledge-context` (read-side companion endpoint)
- KnowledgeContext displayed on match detail page (Admin + Web)
- Zero migration, zero scoring change

**Constraints**:
- KnowledgeContext is computed on read, not stored
- No match score modification
- AI remains FROZEN

---

### 7.2 M23.1: Scenario Understanding

**Objective**: Implement Scenario Understanding Layer for demand creation assistance.

**Deliverables**:
- ScenarioUnderstandingService: parse user requirement → resolve ScenarioContext
- ScenarioContext displayed during demand creation
- Recommended product categories from scenario context
- Recommended knowledge references from scenario context

**Constraints**:
- ScenarioContext is advisory only
- No auto-category assignment
- No auto-parameter generation
- AI remains FROZEN (rule-based only)

---

### 7.3 M23.2: Assisted Recommendation

**Objective**: Provide human-readable recommendation context alongside match results.

**Deliverables**:
- Match recommendation explanation (human-readable, not score-based)
- Knowledge-backed parameter explanation (why this parameter matters)
- Industry standard reference links
- Alternative inspection method suggestions

**Constraints**:
- Recommendation is informational, not prescriptive
- No ranking modification
- No score adjustment
- AI DESIGN phase (interface + contract only)

---

### 7.4 M23.3: AI Decision Support Exploration

**Objective**: Explore AI-assisted decision support interfaces.

**Deliverables**:
- AI Explanation Interface design (ADR only)
- AI Assistant Contract (Interface Definition)
- Prompt Engineering Framework (for future AI runtime)
- Decision Support UI Mockups

**Constraints**:
- AI Runtime remains FROZEN (interfaces only)
- No auto-decision-making
- No auto-match acceptance
- Human review gate preserved

---
