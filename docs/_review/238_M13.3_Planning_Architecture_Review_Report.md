## 5. M13.3 Candidate Scope Analysis

### 5.1 Candidate A: Atomic Upload-Create Flow

**Problem:** When a user uploads a file but closes the browser before creating the ProductMedia, the FileAsset is orphaned in DB + S3. M13.2.7.4 made these detectable and cleanable, but doesn't prevent them.

**Current Flow (Two-Step):**
```
POST /files/upload       → FileAsset created (entityId=placeholder)
  ↓ (user creates ProductMedia in separate step)
POST /products/:id/media → ProductMedia created (entityId updated)
```

**Proposed Atomic Flow:**
```
POST /products/:id/media/upload  → FileAsset created + ProductMedia created in one transaction
  OR
  FileAsset created → if ProductMedia fails → FileAsset rolled back
```

**Analysis:**

| Aspect | Assessment |
|---|---|
| **New API needed?** | ✅ Yes — `POST /products/:id/media/upload` (multipart, accepts file + metadata) |
| **Backend changes?** | ✅ Yes — New method in `ProductMediaService` combining upload + create |
| **Frontend changes?** | ✅ Yes — `ProductMediaCreate` page: single upload instead of two-step |
| **Database changes?** | ❌ No — uses existing models |
| **Migration needed?** | ❌ No |
| **Freeze impact?** | 🟡 YELLOW — New endpoint in ProductMediaController; new service method |
| **Value** | **HIGH** — Eliminates the only remaining orphan generation path |
| **Risk** | **LOW** — Well-understood domain; M13.2.7.3 already proved rollback pattern |
| **Effort** | Medium — 1 backend endpoint + 1 service method + 1 frontend page update |
| **Files** | `product-media.controller.ts`, `product-media.service.ts`, `ProductMediaCreate.tsx` |

**Files Expected:**
| # | File | Change |
|---|---|---|
| 1 | `apps/api/src/product-media/product-media.service.ts` | Add `createWithUpload()` |
| 2 | `apps/api/src/product-media/product-media.controller.ts` | Add `POST /products/:id/media/upload` |

### 5.2 Candidate B: Dynamic entityType Support

**Problem:** All FileAssets are created with `entityType = 'PRODUCT'` (hardcoded in `FileAssetService.upload()`). The `FileEntityType` enum already supports `ORGANIZATION`, `DEMAND`, `RFQ`, `RFQ_RESPONSE`, but none are used.

**Current State:**
```typescript
// FileAssetService.upload() — hardcoded
entityType: FileEntityType.PRODUCT  // Always 'PRODUCT'
```

**Proposed Change:**
```typescript
// Accept entityType as parameter
async upload(file, userId, entityType?: FileEntityType) {
  entityType: entityType ?? FileEntityType.PRODUCT  // Default to PRODUCT
}
```

**Is this actually needed for M13.3?** Let's check which entities use FileAssets:

| Entity | Has FileAsset? | Current Usage |
|---|---|---|
| ProductMedia | ✅ Yes | `entityType = 'PRODUCT'` (correct) |
| Organization | ❌ No | No FileAsset created for organizations |
| Demand | ❌ No | No FileAsset created for demands |
| RFQ | ❌ No | No FileAsset created for RFQs |
| RFQResponse | ❌ No | No FileAsset created for RFQ responses |

**Analysis:**

| Aspect | Assessment |
|---|---|
| **New API needed?** | 🟡 Optional — upload endpoint accepts optional `entityType` param |
| **Backend changes?** | 🟡 Minor — `upload()` signature change + caller updates |
| **Frontend changes?** | ❌ No — admin doesn't upload for non-Product entities |
| **Database changes?** | ❌ No — `FileEntityType` enum already has all values |
| **Migration needed?** | ❌ No |
| **Freeze impact?** | 🟡 YELLOW — Service signature change |
| **Value** | **LOW** — No current consumer of non-Product entityType |
| **Risk** | **LOW** — Backward compatible with default |
| **Effort** | Low — 1 method signature change |
| **Files** | `file-asset.service.ts` |

**Verdict:** Defer to M14+ when non-Product entities actually need FileAsset support. The Prisma schema already supports it (enum values exist), only the service code is hardcoded. Adding a parameter now is premature without a consumer.

**Files Expected (if implemented):**
| # | File | Change |
|---|---|---|
| 1 | `apps/api/src/file-asset/file-asset.service.ts` | Add optional `entityType` parameter to `upload()` |

### 5.4 Candidate D: File Download Security

**Problem:** `GET /files/:id/download` is a public endpoint. Anyone who knows a FileAsset ID can download the file. After M13.2.7.2, deleted ProductMedia cascade-deletes FileAssets, so deleted files return 404. But active files remain publicly accessible.

**Current Flow:**
```
GET /files/:id/download → No auth check → 302 redirect to signed S3 URL
```

**Proposed:** Add JWT authentication to the download endpoint.

**Analysis:**

| Aspect | Assessment |
|---|---|
| **New API needed?** | ❌ No — modify existing endpoint |
| **Backend changes?** | ✅ Yes — Add `@UseGuards(JwtAuthGuard)` to download endpoint |
| **Frontend changes?** | ✅ Yes — `fileAssetService.getSignedUrl()` now sends JWT |
| **Database changes?** | ❌ No |
| **Migration needed?** | ❌ No |
| **Freeze impact?** | 🔴 RED — Modifies existing public endpoint behavior. Could break existing consumers. |
| **Value** | **MEDIUM** — Improves security for file access |
| **Risk** | **HIGH** — Breaking change. Any existing external links to file URLs would stop working. |
| **Effort** | Low — 1 line change in controller + 1 line in admin service |

**Verdict:** This is a **breaking change** to a public API. While security improvement is desirable, it requires:
1. Audit of all consumers of the download endpoint
2. Migration plan for existing direct links
3. Freeze review (RED zone violation)

**Recommendation:** Defer for now. The current security posture is acceptable:
- Deleted files are cascade-deleted (M13.2.7.2) — no orphan access
- FileAsset IDs are UUID v4 — not guessable
- If M13.3 implements Candidate A (atomic upload), the orphan window is eliminated

**Files Expected (if implemented):**
| # | File | Change |
|---|---|---|
| 1 | `apps/api/src/file-asset/file-asset.controller.ts` | Add `@UseGuards(JwtAuthGuard)` to download |
| 2 | `apps/admin/src/api/file-asset.service.ts` | Update `getSignedUrl()` to include auth headers |
