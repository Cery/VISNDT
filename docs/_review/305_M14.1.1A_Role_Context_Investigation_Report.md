## 1. 当前认证流程

当前真实认证链路如下：

```text
登录/注册
  ↓
AuthService 读取 User / Invitation
  ↓
生成 JWT（payload: sub/email/name/organizationId）
  ↓
AuthController 写入 HttpOnly Cookie
  ↓
前端 apiClient 使用 credentials: include
  ↓
AuthProvider 启动时调用 /auth/me
  ↓
Workspace / Dashboard / Settings 基于 user 信息渲染
```

### 1.1 登录与 JWT 生成

`apps/api/src/auth/auth.service.ts` 中，登录与注册生成的 JWT payload 只有：

```ts
const accessToken = this.generateToken({
  sub: user.id,
  email: user.email,
  name: user.name,
  organizationId: user.organizationId,
});
```

对应接口定义 `apps/api/src/auth/interfaces/jwt-payload.interface.ts`：

```ts
export interface JwtPayload {
  sub: string;
  email: string;
  name: string | null;
  organizationId: string | null;
}
```

结论：

- JWT 当前只承载 `User` 基础身份与 `User.organizationId`
- JWT **不承载** `OrganizationMember.role`
- JWT **不承载** `Organization.type`
- JWT **不承载** Buyer / Supplier / Admin 这种前端工作台角色标签

### 1.2 前端保存方式

`apps/api/src/auth/auth.controller.ts` 并不是把 token 返回给前端自己存储，而是直接写 Cookie：

```ts
res.cookie('access_token', accessToken, {
  ...cookieOpts,
  maxAge: ...
});
res.cookie('refresh_token', refreshToken, cookieOpts);
```

`apps/web/src/lib/api-client.ts` 明确采用 Cookie 模式：

```ts
const response = await fetch(url.toString(), {
  ...init,
  headers,
  credentials: 'include',
});
```

结论：

- 当前前端“保存认证态”的真实方式是**浏览器 Cookie**
- 不是旧文档里的 `localStorage`
- `AuthProvider` 只保存 `user` 到 React Context，不保存 JWT 字符串

### 1.3 AuthProvider 加载

`apps/web/src/auth/AuthProvider.tsx`：

```ts
useEffect(() => {
  let cancelled = false;
  (async () => {
    const currentUser = await getMe();
    if (!cancelled) {
      setUser(currentUser);
      setIsLoading(false);
    }
  })();
  return () => { cancelled = true; };
}, []);
```

`apps/web/src/services/auth.service.ts` 中 `AuthUser` 当前只有：

```ts
export interface AuthUser {
  id: string;
  email: string;
  name?: string | null;
  organizationId?: string | null;
}
```

结论：

- 前端启动后只从 `/auth/me` 获取 `id/email/name/organizationId`
- 前端上下文里**没有角色字段**
- 因此 `Workspace` 无法基于真实角色做可靠分流

## 2. Backend 角色来源分析

本节回答五个核心问题：

1. 当前登录用户如何确定 `User`
2. 如何确定 `Organization`
3. 如何确定 `OrganizationMember`
4. 当前角色真正来自哪里
5. Workspace 应该依据什么做菜单和权限分流

### 2.1 用户身份（User）来源

当前登录用户身份来自 `User` 表，并在 JWT 中映射为基础用户信息。

证据一：`apps/api/src/auth/auth.service.ts`

```ts
const user = await this.prisma.user.findUnique({
  where: { email: dto.email },
});
```

证据二：`validateUser()` 再次按 `payload.sub` 回查用户：

```ts
const user = await this.prisma.user.findUnique({
  where: { id: payload.sub },
});

return {
  id: user.id,
  email: user.email,
  name: user.name,
  organizationId: user.organizationId,
};
```

结论：

- 当前用户身份真实来源是 `User`
- `/auth/me` 返回的用户对象也是重新基于 `User.id` 查出的结果

### 2.2 所属组织（Organization）来源

当前组织上下文首先来自 `User.organizationId`，而不是从 `OrganizationMember` 动态选择。

证据一：`schema.prisma`

```prisma
model User {
  ...
  organizationId String? @map("organization_id") @db.Uuid
  organization   Organization? @relation(fields: [organizationId], references: [id])
  memberships    OrganizationMember[]
}
```

证据二：JWT payload 只带 `organizationId`：

```ts
organizationId: user.organizationId,
```

证据三：`apps/api/src/auth/interfaces/auth-request.interface.ts`

```ts
user: {
  id: string;
  email: string;
  name?: string | null;
  organizationId?: string | null;
};
```

结论：

- 当前请求上下文中的组织，真实上是“**用户主组织**”
- 当前系统没有前端可切换的 active organization context
- 即使 `User.memberships` 支持多条成员关系，JWT 仍只带一个 `organizationId`

### 2.3 组织成员关系（OrganizationMember）来源

当前 `OrganizationMember` 是真实存在且真实使用的中间关系表，不是摆设。

证据一：注册时创建成员关系  
`apps/api/src/auth/auth.service.ts`

```ts
await this.prisma.organizationMember.create({
  data: {
    organizationId: invitation.organizationId,
    userId: user.id,
    role: invitation.role,
  },
});
```

证据二：邀请时角色写入 `UserInvitation.role`  
`apps/api/src/auth/invitation.service.ts`

```ts
role: dto.role ?? 'MEMBER',
```

证据三：权限校验时按 `(organizationId, userId)` 查询成员关系  
`apps/api/src/auth/guards/roles.guard.ts`

```ts
const membership = await this.prisma.organizationMember.findUnique({
  where: {
    organizationId_userId: {
      organizationId: user.organizationId,
      userId: user.id,
    },
  },
});
```

结论：

- 当前 `OrganizationMember` 是**真实权限来源之一**
- 它不是前端上下文来源，但它是后端受保护接口的真实授权依据

### 2.4 用户角色（Role）真实来源

#### 结论先行

当前“后端受保护接口”的角色来源，真实来自：

> **`OrganizationMember.role`**

而不是：

- 不是 `User` 表字段
- 不是 `Organization.type`
- 不是 JWT payload
- 不是 `/auth/me`

#### 直接证据

`apps/api/src/auth/enums/role.enum.ts`

```ts
export enum Role {
  ADMIN = 'ADMIN',
  MEMBER = 'MEMBER',
}
```

`apps/api/src/auth/guards/roles.guard.ts`

```ts
const hasRole = requiredRoles.some((role) => membership.role === role);
```

这说明：

- 当前后端角色系统只定义了 `ADMIN` / `MEMBER`
- 且对受保护接口的判定完全基于 `OrganizationMember.role`

#### 反向证据

`apps/api/src/auth/interfaces/jwt-payload.interface.ts` 没有 `role`

```ts
export interface JwtPayload {
  sub: string;
  email: string;
  name: string | null;
  organizationId: string | null;
}
```

`apps/api/src/auth/dto/auth-response.dto.ts` 也没有 `role`

```ts
export class AuthUserDto {
  id: string;
  email: string;
  name?: string | null;
  organizationId?: string | null;
}
```

结论：

- 当前“权限角色”来自 `OrganizationMember.role`
- 当前“认证上下文”却没有把这个角色返回给前端
- 所以前端看不到后端真正使用的角色

### 2.5 Organization.type 是否是角色来源

当前 `Organization.type` 存在，但它不是认证/授权角色源。

证据一：`schema.prisma`

```prisma
model Organization {
  ...
  type String @map("organization_type")
}
```

证据二：`apps/api/src/organizations/organizations.service.ts` 中，`type` 只被当作普通组织字段返回：

```ts
select: {
  id: true,
  name: true,
  type: true,
}
```

证据三：`apps/web/src/components/products/ManufacturerInfo.tsx` 中，`organization.type` 仅用于展示：

```tsx
<span className="font-medium">{organization.type}</span>
```

结论：

- `Organization.type` 当前更像“组织业务标签/分类字段”
- 它**没有进入 JWT**
- 它**没有进入 `/auth/me`**
- 它**没有被 RolesGuard 用于授权**

因此当前不能说“真实角色来自 `Organization.type`”

### 2.6 Backend 侧最终结论

当前 Backend 中与角色上下文相关的真实来源如下：

| 项目 | 当前真实来源 | 是否进入 JWT | 是否进入 `/auth/me` | 当前用途 |
|---|---|---:|---:|---|
| `User` | `User` 表 | ✅ | ✅ | 认证身份 |
| `Organization` | `User.organizationId` 指向 `Organization` | ✅ 只带 id | ✅ 只带 id | 主组织上下文 |
| `OrganizationMember` | `OrganizationMember` 表 | ❌ | ❌ | 后端权限校验 |
| `Role` | `OrganizationMember.role` | ❌ | ❌ | 仅后端 ADMIN/MEMBER 授权 |
| `Organization.type` | `Organization.type` 字符串 | ❌ | ❌ | 展示/业务标签 |

## 3. Database 角色模型分析

### 3.1 关键表与关系

当前数据库关系如下：

```text
User
  ↓  (User.organizationId / memberships)
OrganizationMember
  ↓
Organization
```

更准确地说：

```text
User
  ├─ primary organization -> User.organizationId -> Organization
  └─ membership rows -> OrganizationMember(userId, organizationId, role) -> Organization
```

### 3.2 User

`schema.prisma`

```prisma
model User {
  id             String     @id @default(uuid()) @db.Uuid
  email          String     @unique
  passwordHash   String     @map("password_hash")
  name           String?
  status         UserStatus @default(ACTIVE)
  organizationId String?    @map("organization_id") @db.Uuid

  organization   Organization?        @relation(fields: [organizationId], references: [id])
  memberships    OrganizationMember[]
}
```

当前字段用途判断：

- `id/email/passwordHash/name`：基础认证身份
- `organizationId`：当前 JWT 主组织来源
- `memberships`：成员关系扩展，但前端未消费

### 3.3 Organization

`schema.prisma`

```prisma
model Organization {
  id     String             @id @default(uuid()) @db.Uuid
  name   String
  type   String             @map("organization_type")
  status OrganizationStatus @default(ACTIVE)

  members      OrganizationMember[]
  users        User[]
  offers       Offer[]
  demands      Demand[]
  rfqResponses RFQResponse[]
}
```

当前字段用途判断：

- `name`：组织展示名
- `type`：组织类型/业务标签，当前不是授权角色
- `status`：组织状态
- 与 `Offer` / `Demand` / `RFQResponse` 等业务实体有关联

### 3.4 OrganizationMember

`schema.prisma`

```prisma
model OrganizationMember {
  id             String @id @default(uuid()) @db.Uuid
  organizationId String @map("organization_id") @db.Uuid
  userId         String @map("user_id") @db.Uuid
  role           String @default("MEMBER")

  organization Organization @relation(fields: [organizationId], references: [id])
  user         User         @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([organizationId, userId])
}
```

当前字段用途判断：

- `organizationId + userId`：组织成员关系主键组合
- `role`：后端当前真实授权角色字段
- 当前真实值体系围绕 `ADMIN` / `MEMBER`

### 3.5 Role enum 现状

当前 Prisma Schema **没有 Role enum**。  
当前角色枚举存在于后端代码：

`apps/api/src/auth/enums/role.enum.ts`

```ts
export enum Role {
  ADMIN = 'ADMIN',
  MEMBER = 'MEMBER',
}
```

结论：

- 当前数据库层没有强类型 Role enum
- `OrganizationMember.role` 和 `UserInvitation.role` 都是 `String`
- 这也意味着 Buyer / Supplier 不是当前后端已经冻结好的枚举体系

### 3.6 数据库模型结论

当前数据库能明确支持：

- 用户身份：`User`
- 主组织上下文：`User.organizationId`
- 组织成员关系：`OrganizationMember`
- 组织内权限：`OrganizationMember.role`

当前数据库**不能直接证明**：

- Buyer / Supplier 菜单分流已经有统一字段
- Workspace 角色可以直接从单一字段稳定读取

## 5. 当前问题清单

### RC-01 `/auth/me` 不返回角色上下文

- 问题描述：后端权限真实依赖 `OrganizationMember.role`，但 `/auth/me` 只返回 `id/email/name/organizationId`
- 影响范围：`AuthProvider`、`RoleGuard`、`WorkspaceSidebar`、全部角色化页面
- 严重程度：High
- 建议方向：最小补充 `/auth/me` 返回 `organization + membership + workspaceRole`

### RC-02 `RoleGuard` 当前是硬编码 BUYER

- 问题描述：`RoleGuard.tsx` 直接写 `const hasRole = roles.includes('BUYER')`
- 影响范围：全部 Buyer/Supplier/Admin 页面分流
- 严重程度：High
- 建议方向：禁止前端猜角色，改为消费后端明确返回的角色上下文

### RC-03 后端真实角色与前端角色名词体系不一致

- 问题描述：后端角色枚举只有 `ADMIN` / `MEMBER`，前端 `RoleGuard` 设计的是 `BUYER` / `SUPPLIER` / `ADMIN`
- 影响范围：Workspace 导航设计、页面权限判断、后续 M14.1 Supplier 入口
- 严重程度：High
- 建议方向：明确“组织成员权限角色”和“工作台业务角色”两层概念，不要混用

### RC-04 `Organization.type` 存在但没有进入认证上下文

- 问题描述：`Organization.type` 当前仅是字符串字段与展示字段，不在 JWT、不在 `/auth/me`
- 影响范围：Buyer / Supplier 业务分流
- 严重程度：Medium
- 建议方向：若 Buyer/Supplier 需要基于组织类型分流，应通过 `/auth/me` 或专门 context API 返回

### RC-05 Workspace 当前以 `organizationId` 代替角色

- 问题描述：`Workspace`、`Dashboard`、`Settings` 大量使用“有无 organizationId”来表示工作区状态
- 影响范围：导航、标题、统计卡片、后续 Supplier 入口
- 严重程度：Medium
- 建议方向：把 `organizationId` 降级为组织归属字段，不要继续承担角色判断职责

### RC-06 业务动作权限并未统一绑定到成员角色

- 问题描述：例如 `RfqResponsesService.create()` 只要求 `user.organizationId` 存在即可提交响应，没有成员角色限制
- 影响范围：Supplier RFQ Response 入口、组织内权限边界
- 严重程度：Medium
- 建议方向：M14.1 先定义“谁能看到 Supplier 菜单”，M14.2 再决定是否需要更细粒度成员权限

### RC-07 产品详情页的组织/询价上下文缺失

- 问题描述：产品详情页传入 `organization={null}`，且 `InquirySection` 没拿到 `offerId` / `organizationId`
- 影响范围：公开询价入口、组织信息展示
- 严重程度：Medium
- 建议方向：后续单独修复，但本任务只记录问题，不改代码

## 6. 角色来源结论

### 6.1 五个问题的最终答案

#### 1. 用户身份（User）如何确定

来自 `User` 表，JWT 以 `sub/email/name` 形式携带，`validateUser()` 再回查 `User`。

#### 2. 所属组织（Organization）如何确定

当前来自 `User.organizationId`，这是 JWT 与 `/auth/me` 中唯一可见的组织上下文字段。

#### 3. 组织成员关系（OrganizationMember）如何确定

来自 `OrganizationMember` 表：

- 注册时按 `Invitation.role` 创建成员关系
- 受保护接口访问时由 `RolesGuard` 按 `(organizationId, userId)` 查询

#### 4. 用户角色（Role）如何确定

当前真实授权角色来自：

> **`OrganizationMember.role`**

但这个角色只在后端守卫中使用，**没有返回给前端**。

#### 5. Workspace 应该依据什么进行菜单和权限分流

当前**不应该**继续依据以下任一单字段：

- 不能只看 `user.organizationId`
- 不能直接把 `Organization.type` 当成已接入的角色来源
- 不能用前端硬编码 `BUYER`

### 6.2 推荐的分流依据

M14.1 的 Workspace 菜单和权限分流，推荐依据以下组合：

```text
当前登录用户
  + 当前主组织（organization）
  + 当前组织成员关系（organizationMember）
  + 业务工作台角色（workspaceRole）
```

至少应包含：

- `user.id`
- `user.organizationId`
- `organization.id`
- `organization.type`
- `organizationMember.role`
- `workspaceRole`

其中：

- `organizationMember.role` 负责组织内权限，如 `ADMIN` / `MEMBER`
- `workspaceRole` 负责前台业务导航，如 `BUYER` / `SUPPLIER`

如果当前阶段不想额外引入 `workspaceRole` 字段，也至少应返回：

- `organization.type`
- `organizationMember.role`

由前端做**受控映射**，而不是完全硬编码猜测

## 7. M14.1.1 后续改造建议

### 方案 A：仅前端调整

做法：

- 不改 API
- 前端继续只拿 `organizationId`
- 尝试通过页面路由、是否有组织、局部接口数据去推断角色

优点：

- 改动最小
- 不触碰 `apps/api`

缺点：

- 前端没有真实角色来源
- `RoleGuard` 只能继续猜
- 无法稳定区分 Buyer / Supplier / Admin
- 与当前后端真实授权来源脱节

判断：

> **不推荐**

### 方案 B：补充 `/auth/me` 角色上下文

做法：

- 保持现有 JWT 结构不变
- 在 `/auth/me` 基础上补充：
  - `organization`
  - `organizationMember`
  - `workspaceRole` 或最小可映射字段

可选返回形态示意：

```json
{
  "id": "user-id",
  "email": "user@example.com",
  "name": "User",
  "organizationId": "org-id",
  "organization": {
    "id": "org-id",
    "name": "Org",
    "type": "SUPPLIER"
  },
  "organizationMember": {
    "role": "ADMIN"
  },
  "workspaceRole": "SUPPLIER"
}
```

优点：

- 不改 schema
- 不改 JWT payload
- 与当前后端真实授权链兼容
- `AuthProvider` / `RoleGuard` / `Sidebar` 都能直接消费

缺点：

- 需要最小 API 调整
- 需要定义 `workspaceRole` 与 `organization.type` / `membership.role` 的映射规则

判断：

> **推荐方案**

### 方案 C：新增独立 `/auth/context` 或多组织活动上下文方案

做法：

- 保持 `/auth/me` 基础版
- 新增 `/auth/context`
- 未来可扩展 active organization、`X-Organization-Id`、多组织切换

优点：

- 扩展性最好
- 适合后续多组织、多工作台

缺点：

- 对 M14.1 来说偏重
- 会放大 API 与前端接入范围

判断：

> 可以作为中后期方案，但不适合作为 M14.1 第一落点

### 7.4 推荐方案与原因

推荐：

> **方案 B：补充 `/auth/me` 角色上下文**

原因：

1. 最符合当前真实代码结构
2. 不需要改数据库
3. 不需要改 JWT payload
4. 能直接解决 `RoleGuard`、`AuthProvider`、`WorkspaceSidebar` 的数据缺口
5. 能把“后端真实角色来源”和“前端工作台分流”统一起来
