## 1. Executive Summary

VISNDT 已跨越「功能闭环」阶段，进入「平台产品化深化」准备期。三项审计结论（624 回归通过、625 总体 `CONDITIONAL PASS`）表明：

1. **Media Asset Architecture Evolution** — 判定为「未来需演进，当前冻结、分阶段推进」。
2. **Admin Operation Center Evolution** — 判定为「CRUD → Operation Center，以体验层叠加方式推进，不需新增业务表」。
3. **Web Commercial Experience Evolution** — 判定为「详情模板差异化 + 内容商业化关联，前端为主、现有 API 部分支持」。

## 3. Media Architecture Decision

### 3.1 现状评估（prisma 实测）

- `FileAsset`：`entityType/entityId/fileType/fileName/storageKey/mimeType/fileSize/uploadedBy` — **无版本、无状态、无 `organizationId`、无软删、无目录/标签**。
- `ProductMedia`：`productId/fileAssetId/mediaType/isPrimary/displayOrder` — 支持产品图片管理。
- `ContentMedia`：`contentId/fileAssetId/caption/altText/sortOrder` — 支持内容插图与 SEO alt。
- S3 Compatible 存储（MinIO）已接入；上传/绑定/回滚/孤儿清理闭环齐全；仅 Content 下载侧有发布门禁。

### 3.2 决策项

| 能力 | 是否需要 | 决策 |
|---|---|---|
| Asset Ownership（`organizationId` / supplier ownership / permission） | 需要 | **演进必做**（多供应商隔离，当前仅间接推导） |
| Asset Classification（Folder/Tag/Category/Relation） | 需要 | **演进必做**（运营检索/目录） |
| Asset Lifecycle（Draft/Review/Published/Archived/Deleted） | 需要 | **演进必做**（发布审核/回收站） |
| Asset Version（History/Rollback） | 需要（可分阶段） | 演进第 2 期 |
| Asset Usage（文档/证书/规格PDF/供应商附件） | 已部分 | 演进中补齐收口 |

### 3.3 推荐目标模型（未来演进，非当前建表）

```
FileAsset（演进）+ organizationId / status / version / deletedAt
+
MediaFolder    （目录）
MediaTag       （标签）
MediaRelation  （跨实体关联）
MediaVersion   （版本链，可选）
MediaPermission（权限边界）
```

### 3.4 保持现状理由与演进必要性

- **保持现状（本阶段）**：当前媒体能力已达到生产可用下限；上游 Product/Content 闭环稳定，立即改库风险高于收益。
- **演进必要性（后续）**：多供应商隔离、发布审核、软删恢复、分类检索是工业检测平台的**运营硬需求**，不演进将长期限制内容资产化。

### 3.5 实施前置条件

1. 单独立项《Media Schema Evolution Proposal》送架构评审（**本任务不实施**）。
2. 评审通过前不做 `MIGRATION`、不改 schema、不改 API。
3. 演进分期：1 期隔离/状态/目录/标签/软删 → 2 期版本。

### 3.6 决策

```
Media Architecture Decision: FUTURE EVOLUTION REQUIRED（staged, 冻结实施）→ 保持现状, 前置评审
```

## 4. Admin Operation Center Decision

### 4.1 现状评估

- 已是「统一设计系统 + 权限体系 + 运营组件（`FilterPanel/ResponsiveTable/BatchActionBar/PageToolbar/OperationCard/StatusTag`）」的成熟 CRUD 后台。
- 产品/内容/RFQ/需求/组织/用户/审计等模块字段均已业务裁剪，**无全字段平铺**。
- 缺：按运营状态的默认队列、组合筛选快捷入口、批量决策、移动端兜底。

### 4.2 决策项

| 运营维度 | 是否需要 | 决策 |
|---|---|---|
| Product Operation（Pending Review/Featured/Category/Supplier View/Tag） | 需要 | 体验层叠加 |
| Content Operation（Draft/Review/SEO Check/Relation） | 需要 | 体验层叠加 |
| Supplier Operation（Organization Status/Capability Profile/Asset Review/Tracking） | 需要 | 体验层叠加 |
| Business Operation（RFQ Queue/Matching Queue/Conversion/Notification Center） | 需要 | 体验层叠加 |

### 4.3 演进方式判定

- 方向：**CRUD Management → Operation Center**（以“运营待办队列 + 状态分组 + 组合筛选 + 批量动作”为核心）。
- 方式：**以现有 API 组合 + 前端体验层实现为主**，尽量不新增业务表。
- 约束：不新增 Database Model（沿用现有 schema），不改变 RBAC。

### 4.4 决策

```
Admin Operation Center Decision: EVOLVE TO OPERATION CENTER（additive, 体验层优先, 不改库）
```

## 5. Web Commercial Experience Decision

### 5.1 现状评估

- 当前采购决策路径：`Product → Inquiry`（单一 CTA 闭环）。
- 详情页：统一模板（Product/Solution/Knowledge/Supplier 同构）。
- 内容域（Knowledge/Solution）与产品/方案/供应商的转化关联偏弱。

### 5.2 决策项

| 能力 | 是否需要 | 现状 API 支持 |
|---|---|---|
| Product Journey 深化（场景→方案→知识→供应商→需求→匹配） | 需要 | PARTIAL |
| Content Commercialization（关联产品/方案/供应商/需求入口） | 需要 | PARTIAL |
| Detail Template 差异化（Product/Solution/Knowledge/Supplier） | 需要 | PARTIAL |

### 5.3 决策

- 方向：**统一模板 → 差异化详情模板系统**；**内容域 → 商业化转化入口（关联产品/方案/供应商/需求提交）**。
- 实现：以 **apps/web 前端为主**；复用现有 `Content-Category-Product` 确定性映射与询价/需求入口，避免引入 AI/语义匹配。
- 约束：不触碰 Matching 算法、Search 后端、AI（FROZEN）。

### 5.4 决策

```
Web Commercial Experience Decision: EVOLVE COMMERCIAL JOURNEY（前端为主 + 差异化模板 + 内容商业化）
```
