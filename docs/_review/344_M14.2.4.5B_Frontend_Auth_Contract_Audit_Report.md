## 3. 当前 AuthUser 消费状态

### 3.1 类型声明状态

当前前端 `AuthUser` 定义如下：

- `organization?: AuthOrganization | null`
- `organizationMember?: AuthOrganizationMember | null`
- `workspaceRole?: WorkspaceRole`

证据：

- [`auth.service.ts:L23-L30`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/services/auth.service.ts#L23-L30)

与冻结目标对比：

1. `organization` 应为 `AuthOrganization | null`
2. `organizationMember` 应为 `AuthOrganizationMember | null`
3. `workspaceRole` 应为 `'SUPPLIER' | 'BUYER' | null`

结论：**前端类型层尚未完成“必含字段、允许为 null”的冻结，当前仍保留 `undefined` 语义。**

### 3.2 Context 保持原样透传

`AuthProvider` 在 `/auth/me`、`login`、`register` 返回后，直接将 `AuthUser` 写入 Context，未做字段归一或契约校验。

证据：

- [`AuthProvider.tsx:L19-L30`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/auth/AuthProvider.tsx#L19-L30)
- [`AuthProvider.tsx:L36-L50`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/auth/AuthProvider.tsx#L36-L50)

结论：**前端当前完全依赖 `auth.service.ts` 的类型声明；一旦类型允许 optional，消费层就会自然扩散 `undefined` 判断。**

3. 用 `user?.name`、`user?.email`、`user?.id` 做宽松展示

## 5. 发现的问题

### 问题 1：`AuthUser` 关键字段仍为 optional，未满足冻结契约

严重级别：`High`

表现：

1. `organization` 仍为 `organization?: AuthOrganization | null`
2. `organizationMember` 仍为 `organizationMember?: AuthOrganizationMember | null`
3. `workspaceRole` 仍为 `workspaceRole?: WorkspaceRole`

证据：

- [`auth.service.ts:L23-L30`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/services/auth.service.ts#L23-L30)

影响：

- 前端类型层继续接受“字段缺失”，与 `4.4C/5A` 已冻结的后端契约不一致。

### 问题 2：消费端通过 optional chaining / nullish coalescing 吞并 `undefined`

严重级别：`Medium`

表现：

1. `user.workspaceRole ?? null`
2. `user?.workspaceRole ?? null`
3. `user?.organizationId`
4. `user?.name || user?.email`

证据：

- [`RoleGuard.tsx:L21-L23`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/auth/RoleGuard.tsx#L21-L23)
- [`WorkspaceSidebar.tsx:L45-L46`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/components/workspace/WorkspaceSidebar.tsx#L45-L46)
- [`WorkspaceHeader.tsx:L25-L31`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/components/workspace/WorkspaceHeader.tsx#L25-L31)

- [`workspace/settings/page.tsx:L17-L18`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/app/workspace/settings/page.tsx#L17-L18)

影响：

- 当前实现不会错误赋予默认角色，但会继续把“字段缺失”视作正常可兼容状态，削弱契约约束力。

### 问题 3：工作区标题和状态仍以 `organizationId` 判定，而非以冻结后的对象契约判定

严重级别：`Medium`

表现：

1. `WorkspaceHeader` 以 `user?.organizationId` 区分“组织工作区 / 个人工作区”
2. `workspace/page.tsx` 以 `user?.organizationId` 生成欢迎文案和“组织已激活/待处理”
3. `settings/page.tsx` 以 `user?.organizationId` 显示组织状态

证据：

- [`WorkspaceHeader.tsx:L25-L27`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/components/workspace/WorkspaceHeader.tsx#L25-L27)
- [`workspace/page.tsx:L58-L85`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/app/workspace/page.tsx#L58-L85)
- [`workspace/settings/page.tsx:L147-L153`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/app/workspace/settings/page.tsx#L147-L153)

影响：

- 前端尚未真正消费 `organization` / `organizationMember` 冻结对象，只是沿用旧的 `organizationId` 兼容分支。

### 问题 4：未发现旧 RBAC 显式比较残留，但仍需在 5B 中做一次定向收口

严重级别：`Low`

审计结果：

1. 未发现 `role === 'ADMIN'`
2. 未发现 `role === 'BUYER'`
3. 未发现 `role === 'SUPPLIER'`
4. 未发现 `workspaceRole ?? 'BUYER'` 或 `workspaceRole ?? 'SUPPLIER'`
5. 未发现 `Seller` / `StoreOwner` 旧角色判断

说明：

- 当前风险不在“旧角色分支未删净”，而在“optional 字段仍可被宽松消费”。
