## Existing Architecture Analysis

### M9 架构优势

```
Admin Frontend (React + Vite + Ant Design)
    │
    ├── Auth Layer (Zustand + persist + JWT + 3-layer expiry)
    │
    ├── Page Layer (14 components, discriminated union pattern)
    │       ↓
    ├── Service Layer (7 services, unified apiClient)
    │       ↓
    └── Backend (74 APIs, JWT + RBAC + org isolation)
            ↓
        Database (22 models, PostgreSQL)
```

### M9 架构约束

| 约束 | 影响 |
|---|---|
| Backend Freeze | Admin 只能使用已有 74 个端点 |
| Schema Freeze | 不能新增模型/字段，不能修改 relation |
| Auth Freeze | 不能修改权限模型，不能新增角色 |
| 零依赖 | 不能新增 npm 包 |

## Direction B Analysis: Matching Engine Evolution

### Current State

| 组件 | 状态 |
|---|---|
| Matching Engine | 纯 Service 模块，无 Controller |
| Match 端点 | 4 个，全部 org-scoped (`/demands/:id/matches`) |
| Admin 可见 | 仅 `totalMatches` (Dashboard) |
| 匹配触发 | Demand 发布时自动 + 手动 `rematch` |

### Evolution Path

| 阶段 | 功能 | Backend 影响 | Database 影响 |
|---|---|---|---|
| B1 | 匹配评分详情展示 | ✅ 需新 API | ❌ |
| B2 | 全局匹配列表 | ✅ 需新 API | ❌ |
| B3 | 匹配状态分布统计 | ✅ 需新 API | ❌ |
| B4 | 自动评分算法优化 | ✅ 需修改 | ❌ |
| B5 | 推荐算法 (ML-based) | ✅ 需新增 | ⚠️ 可能需新表 |
| B6 | RFQ Workflow | ✅ 需新增 | ✅ 需新表 |
| B7 | Supplier Response | ✅ 需新增 | ✅ 需新表 |

### Impact Analysis

| 维度 | 评估 |
|---|---|
| Backend 解冻 | ✅ 必须 — 所有阶段都需要新 API |
| Database 解冻 | B1-B4 不需要, B5-B7 需要 |
| 安全影响 | High — 需绕过 org-scoped 但不破坏隔离 |
| 开发复杂度 | Medium-High — 涉及核心匹配逻辑 |
| 业务价值 | Medium — 当前 V1 阶段需求不紧迫 |

### Risk Assessment

| 风险 | 严重度 | 说明 |
|---|---|---|
| org-scoped 绕过 | High | Admin 全局匹配列表需绕过组织隔离 |
| 安全模型退化 | High | 可能弱化 M8 安全加固成果 |
| 匹配逻辑回归 | Medium | 修改核心算法可能引入 Bug |
| 性能影响 | Medium | 全局查询可能在大数据量下变慢 |

### Recommendation

**推荐**: Direction B 作为 M11 Priority。

**理由**:
- 需要 Backend 解冻，应独立规划
- 安全风险较高，需要充分审计
- M9 已确认 V1 阶段无需全局匹配视图
- 应在 Admin Enhancement 完成后再评估

## Direction C Analysis: Customer Platform

### Current State

```
apps/web/          ← Next.js frontend (customer-facing)
    状态: Dormant (M8 后未开发)
```

### Scope Assessment

| 功能 | 优先级 | 复杂度 |
|---|---|---|
| 产品浏览 (列表) | High | Low |
| 产品搜索 (关键词+参数) | High | Medium |
| 产品详情 | High | Low |
| 用户注册 (已有邀请机制) | High | Medium |
| 发布需求 | High | High |
| 供应商响应 | Medium | High |
| 撮合入口 (RFQ) | Medium | High |
| 通知系统 | Low | High |

### Architecture Options

#### Option C1: Reuse Backend + New Frontend (推荐)

```
apps/web (Next.js)
    │
    ├── Public API: GET /products, GET /products/:id
    ├── Auth API: POST /auth/login, POST /auth/register
    └── Demand API: POST /demands, GET /demands
```

| 维度 | 评估 |
|---|---|
| Backend 解冻 | ❌ 不需要 — 已有 74 个端点 |
| 新增 Frontend | ✅ 需要 — Next.js 页面 |
| 开发复杂度 | Medium — 需熟悉 Next.js |
| 与 Admin 隔离 | ✅ 独立项目，无冲突 |

#### Option C2: New Full Stack

| 维度 | 评估 |
|---|---|
| Backend 解冻 | ❌ 不需要 |
| 新增 API | ✅ 需要 |
| 开发复杂度 | Very High |
| 与 Admin 隔离 | ✅ 完全独立 |

### Recommendation

**推荐**: Direction C 作为 M12 Priority，采用 Option C1。

**理由**:
- Backend 74 个端点已覆盖大部分需求
- 复用 JWT Auth + org-scoped 安全模型
- Next.js 独立项目，不影响 Admin
- 应在 Admin 完成后再启动
