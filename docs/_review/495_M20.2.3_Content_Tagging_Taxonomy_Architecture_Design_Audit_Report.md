## 3. ContentTag Model Design

### 3.1 Model Definition

```
ContentTag {
  id          String    @id @default(uuid()) @db.Uuid
  name        String                                    // 显示名称
  slug        String    @unique                         // URL slug
  type        ContentTagType                            // 标签分类
  description String?                                   // 标签描述（SEO）
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  relations   ContentTagRelation[]
}
```

### 3.2 Field Rationale

| Field | Type | Purpose |
|-------|------|---------|
| `id` | UUID | Primary key, auto-generated |
| `name` | String | Human-readable display name (e.g., "超声检测") |
| `slug` | String (unique) | URL-safe identifier (e.g., "ultrasonic-testing"), used in `/tags/[slug]` |
| `type` | ContentTagType | Categorizes the tag itself (TOPIC/INDUSTRY/APPLICATION/TECHNOLOGY) |
| `description` | String? | Optional SEO description for the tag landing page |
| `createdAt` | DateTime | Auto-set on creation |
| `updatedAt` | DateTime | Auto-updated on modification |

### 3.3 Design Decisions

| Decision | Rationale |
|----------|-----------|
| No parent-child hierarchy | Flat tag model; avoids complexity of tree structures |
| Slug as unique identifier | Enables clean URLs (`/tags/ultrasonic-testing`) |
| No status field | Tags are always active; no lifecycle complexity |
| No color/icon | Visual properties are frontend concerns, not data model |
| No order field | Tag ordering is determined by usage count or alphabetical, not hardcoded |
| No organization scope | Tags are global, not per-organization; Content is identity-neutral |

## 4. ContentTagRelation Design

### 4.1 Model Definition

```
ContentTagRelation {
  id        String    @id @default(uuid()) @db.Uuid
  contentId String    @db.Uuid
  tagId     String    @db.Uuid
  createdAt DateTime  @default(now())

  content   Content   @relation(fields: [contentId], references: [id], onDelete: Cascade)
  tag       ContentTag @relation(fields: [tagId], references: [id], onDelete: Cascade)

  @@unique([contentId, tagId])
  @@index([tagId])
  @@index([contentId])
}
```

### 4.2 Field Rationale

| Field | Type | Purpose |
|-------|------|---------|
| `id` | UUID | Primary key, auto-generated |
| `contentId` | UUID (FK → Content) | Which content is tagged |
| `tagId` | UUID (FK → ContentTag) | Which tag is applied |
| `createdAt` | DateTime | When the tag was applied |

### 4.3 Index Strategy

| Index | Type | Purpose |
|-------|------|---------|
| `@@unique([contentId, tagId])` | Unique constraint | Prevent duplicate tag on same content |
| `@@index([tagId])` | B-tree index | Fast lookup: "find all content with this tag" |
| `@@index([contentId])` | B-tree index | Fast lookup: "find all tags on this content" |

### 4.4 Cascade Strategy

| Action | Behavior |
|--------|----------|
| Content deleted | `onDelete: Cascade` → Related ContentTagRelations deleted |
| Tag deleted | `onDelete: Cascade` → Related ContentTagRelations deleted |

This ensures referential integrity: no orphaned relation records.

### 4.5 Design Decisions

| Decision | Rationale |
|----------|-----------|
| No weight/order field | Simple is better; tag display order is alphabetical or by usage |
| No addedBy field | Tags are content metadata, not user-attributed; simpler model |
| Cascade delete | Orphan cleanup is automatic; no manual cleanup needed |
| Composite unique | One tag can only be applied once per content |

## 5. TagType Taxonomy Design

### 5.1 Enum Definition

```
ContentTagType {
  TOPIC         // 主题标签
  INDUSTRY      // 行业标签
  APPLICATION   // 应用标签
  TECHNOLOGY    // 技术标签
}
```

### 5.2 Type Semantics

| TagType | Semantics | Example (中文) | Example (English) |
|---------|-----------|---------------|-------------------|
| `TOPIC` | What the content is about | 超声检测, 射线检测, 目视检测 | ultrasonic-testing, radiographic-testing, visual-inspection |
| `INDUSTRY` | Which industry it applies to | 航空航天, 汽车制造, 能源 | aerospace, automotive, energy |
| `APPLICATION` | What inspection scenario | 焊缝检测, 腐蚀检测, 厚度测量 | weld-inspection, corrosion-detection, thickness-measurement |
| `TECHNOLOGY` | What technical method | 相控阵, TOFD, DR | phased-array, tofd, digital-radiography |

### 5.3 Type Usage Mapping

```
Content Type → Tag Type Mapping

KNOWLEDGE (知识文章):
  → TOPIC: "超声检测原理"
  → INDUSTRY: "航空航天"
  → TECHNOLOGY: "相控阵"

SOLUTION (解决方案):
  → TOPIC: "发动机检测方案"
  → INDUSTRY: "航空航天"
  → APPLICATION: "叶片检测"

ARTICLE (通用文章):
  → TOPIC: "行业动态"
  → INDUSTRY: "汽车制造"

INSIGHT (参数百科):
  → TOPIC: "探头参数"
  → TECHNOLOGY: "相控阵探头"
```

### 5.4 Design Decisions

| Decision | Rationale |
|----------|-----------|
| Four types, not more | Covers all content classification needs without over-engineering |
| No MISC/OTHER type | Forces explicit classification; better for SEO |
| Type is on Tag, not on Relation | A tag has a fixed type; consistent classification |
| No hierarchy within types | Flat within each type; simplicity |
| Tag can be any type | The same tag can't be both TOPIC and INDUSTRY; choose one |

### 5.5 Future AI Readiness

The four-type taxonomy is intentionally aligned with future AI capabilities:

| TagType | AI Use Case |
|---------|------------|
| TOPIC | Content clustering, topic modeling |
| INDUSTRY | Industry-specific recommendations, vertical search |
| APPLICATION | Use-case matching, product recommendation |
| TECHNOLOGY | Technical capability matching, supplier discovery |

## 6. Tag Lifecycle Design

### 6.1 Tag Lifecycle States

```
Tags are SIMPLE entities with no lifecycle states:

CREATE → ACTIVE (always)
         ↓
       DELETE (admin only)
```

**Rationale:**
- Tags are metadata, not content — no editorial workflow
- No DRAFT/REVIEW/PUBLISHED cycle needed
- Tags are immediately usable upon creation
- Deletion is admin-only (cascade cleans up ContentTagRelations)

### 6.2 Tag Creation

| Scenario | Behavior |
|----------|----------|
| Admin creates tag | Direct creation via Admin API; tag immediately available for assignment |
| Content editor assigns tag | Select from existing tags or create new (inline) |
| Duplicate tag name | Rejected by unique slug constraint |
| Tag with no content | Allowed; tags can exist without content (pre-created taxonomy) |

### 6.3 Tag Usage Tracking

```
Tag usage count = COUNT(ContentTagRelation WHERE tagId = X)
```

Usage count is computed on-the-fly, not stored. This avoids:
- Data inconsistency between usage count and actual relations
- Additional write overhead on tag assignment/removal
- Complex synchronization logic

### 6.4 Tag Deletion

| Action | Impact |
|--------|--------|
| Admin deletes tag | Cascade deletes all ContentTagRelations for that tag |
| Content affected | Tag is removed from all content that had it |
| Tag pages | `/tags/[slug]` returns 404 for deleted tag |
| SEO | Sitemap removes deleted tag pages |

### 9.2 Admin API (CRUD)

| Endpoint | Method | Purpose | Phase |
|----------|--------|---------|-------|
| `POST /content/tags` | POST | Create new tag | M20.2.3 |
| `PATCH /content/tags/:id` | PATCH | Update tag (name, description, type) | M20.2.3 |

### 9.3 API Design Notes

| Design Decision | Rationale |
|-----------------|-----------|
| Tags under `/content/` namespace | Tags belong to Content domain |
| Public tag list without auth | Tags are public metadata |
| Content relation via `/content/:id/tags` | RESTful; nested under content resource |
| Batch assignment not in v1 | Single tag assignment is simpler; batch can be added later |
| No pagination on tag list | Expected tag count is < 200; no pagination needed |

### 9.4 Backward Compatibility

```
GET /content/public (existing)           → No change when tag is absent
GET /content/public?keyword= (M20.2.2)   → No change
GET /content/public?tag= (NEW)            → Optional filter; backward-compatible

| Cascade delete | **APPROVED** | Automatic orphan cleanup |

```
Audit Result: PASS

- ContentTag model design is clean, minimal, and aligned with Tag-First principle
- ContentTagRelation provides standard many-to-many with proper indexes and cascade
- TagType taxonomy (4 types) covers all content classification needs
- Flat tag model avoids hierarchy complexity while enabling SEO discovery
- API design follows RESTful conventions under /content/ namespace
- Frontend impact is additive (new pages) with no breaking changes
- Schema migration risk is low (isolated models, no existing data migration)
- M20.1 Search remains frozen; no search interference
- No AI infrastructure, no search infrastructure, no schema expansion beyond scope
- All decisions defer explicit relation models (ContentRelation, ContentProductRelation) to M20.3
