## 2. Current Database Reality（Database Reality Audit）

基于 `schema.prisma` + `migrations/` 真实扫描：

**Product Domain：**
- `Product`：`categoryId` 必填、`status String @default("DRAFT")`（非枚举）、`slug @unique`、`seoTitle`、`embedding vector(1536)`、`createdById` 仅审计、**无 organizationId/ownerId** → 平台全球目录。
- `ProductCategory`：分类树（parentId/children），slug 唯一。
- `ProductMedia`：`productId + fileAssetId? + mediaType + isPrimary + displayOrder`，级联删除。
- `ProductParameterValue`：`@@unique(productId, parameterDefinitionId)` → 平台参数实例。
- `ParameterDefinition/ParameterGroup/ParameterOption`：平台级全局参数目录（code 唯一）。

**Supplier Domain：**
- `Organization`/`OrganizationMember`：组织本体与成员，无产品归属。
- `Offer`：`@@unique(organizationId, productId)`，**绑定 Product（非供应商实体）**；`OfferStatus` 枚举；含 `price/currency/title/description/createdBy`。
- `FileAsset`：**已含 `organization_id` + `status FileAssetStatus` + `deleted_at` 软删**（Migration `add_file_asset_isolation_and_file_type_taxonomy`），`entityType(FileEntityType)` + `entityId`。

**Commercial Domain：**
- `Demand`/`DemandParameter`：需求侧，`categoryId?`。
- `DemandMatch`：`@@unique(demandId, productId)`，**依赖 `Product.productId`**。
- `RFQ`/`RFQResponse`：依赖 `sourceMatchId→DemandMatch`、`targetOrganizationId`、`offerId` → **间接依赖 Product（经 DemandMatch/Offer）**。
- `Content`/`ContentMedia`/`ContentTagRelation` + `FileEntityType.PRODUCT/ORGANIZATION/CONTENT`。

**结论**：当前 Model B 数据承载（Offer→Product），`FileAsset` 已具备 organization 归属分层基础（利好 Media 架构演进）。

## 3. Future Schema Architecture Design

### 3.1 SupplierProduct Entity Design（未来设计，评估新增）

主字段（设计草案，非落库）：

```
SupplierProduct {
  id                  UUID @id
  organizationId      UUID            // belongsTo Supplier Organization
  platformProductId   UUID            // belongsTo Platform Product
  brand               String
  series              String?
  modelNumber         String
  description         String?
  status              SupplierProductStatus @default(DRAFT)
  seoTitle            String?
  slug                String? @unique @db.Uuid   // 供应商型号 URL（可选）
  createdAt / updatedAt
  @@index([organizationId])
  @@index([platformProductId])
  @@index([organizationId, platformProductId])
}
```

生命周期（复用治理冻结，落本实体层、不污染 Platform Product）：

```
DRAFT → SUBMITTED → REVIEWING → APPROVED → PUBLISHED
                            ↘ REJECTED
```

关系（必须明确）：
- `SupplierProduct.belongsTo PlatformProduct`（N:1，能力节点）
- `SupplierProduct.belongsTo Organization`（N:1，供应商）

**红线**：不触碰 `Product.organizationId`；Platform Product 维持无属主全局目录。

### 3.2 Offer Evolution Design

当前：`Offer(organizationId, productId)`。评估三种方案：

| Option | 模型 | 影响 |
|-|-|-|
| **A** 保持 `Offer→Product` | `productId` 仅绑能力节点 | ❌ 丢失供应商型号/品牌维度（商业绑定过粗，无法区分同一能力的多个供应商型号） |
| **B** 改为 `Offer→SupplierProduct` | `supplierProductId` | ⚠️ 商业精确到型号，但 `DemandMatch`/搜索/SEO 的能力节点聚合需经 SupplierProduct→PlatformProduct 反查，查询多一跳；存量 Offer 数据迁移大 |
| **C 兼容双绑（推荐）** | `productId` + `supplierProductId`（均可选或一旧一新） | ✅ 短中期兼容：能力聚合（Search/SEO/Matching/RFQ）继续用 `productId`，供应商型号能力用 `supplierProductId`；存量 Offer 无需破坏性迁移 |

**推荐理由（Option C）**：
1. 兼容演进（Migration Strategy D 精神），零坏数据迁移。
2. 既保留能力节点聚合（Index/Matching/SEO 读 `productId`），又新增供应商型号维度（供 Detail/Supplier 域用）。
3. 符合 660「Offer != Product，双绑 SupplierProduct + PlatformProduct」架构决策。
4. 为后续 `productId` 可空 / `supplierProductId` 必填的最终态预留过渡。
   - 最终态建议：`supplierProductId` 为商业事实源，`productId` 作为能力节点冗余/聚合点（由 SupplierProduct→PlatformProduct 继承填充）。

### 3.3 Parameter Architecture Design（Parameter Ownership Model，冻结）

```
Platform Parameter（全局，属于 Platform Product）
   ├─ ProductParameterValue（Platform 默认值，绑定 Product）
   │
   ├─ Supplier Product Override（供应商覆盖，绑定 SupplierProduct）
   │    例：Platform Resolution=HD → Supplier=Full HD
   └─ Supplier Product Extension（供应商扩展，绑定 SupplierProduct）
        例：特殊涂层 / 特殊认证 / 特殊附件（DataDefinition：自定义字段，复用 ParameterDefinition? 见下）
```

- **Standard Parameter 归属**：Platform Product（`ParameterDefinition`/`ProductParameterValue`，Admin 治理）。
- **Supplier Override**：`SupplierProductParameterValue`（引用同一 `ParameterDefinition`，绑定 SupplierProduct）。
- **Supplier Extension**：供应商自定义（绑定 SupplierProduct）；设计建议 = 复用 `ParameterDefinition`（`scope=SUPPLIER` 或伪全局）+ `SupplierProductParameterValue`，避免新增难治理的自由键值表。
- **禁止**：供应商修改 Global Parameter Definition。

### 3.4 Media Architecture Design（Media Ownership Architecture，冻结）

解决现状混合问题，按归属分层：

| 媒体类型 | 归属 | 设计落点 |
|-|-|-|
| Platform Media | Platform Product | `ProductMedia`（能力节点配图，Admin 治理） |
| Supplier Product Media | Supplier Product | 新 `SupplierProductMedia`（型号主图/多视图/宣传视频，`FileAsset` 复用） |
| Organization Media | Supplier Organization | `FileType.ORGANIZATION` / `FileAsset.organization_id` |
| Content Media | Content | 既有 `ContentMedia` |

**答案：**
1. **产品图片归属**：能力级归 Platform Product（`ProductMedia`），型号级归 Supplier Product（`SupplierProductMedia`）。
2. **宣传视频归属**：供应商型号演示归 Supplier Product；企业宣传归 Organization。
3. **技术文档归属**：Supplier Product（`SupplierProductMedia`，FileType=SPEC_SHEET/DOCUMENT）。
4. **SEO 展示媒体来源**：Platform Media（能力权威首图）+ Supplier Product Media（型号/品牌图）。

复用 `FileAsset`（已含 `organization_id`），新增关联表承载层级。

### 3.5 Document Architecture Design

供应商技术资料：Manual / Specification / Certificate / Inspection Case。

**评估**：独立实体 `SupplierProductDocument` vs 复用 `FileAsset`。

**推荐 = 复用 `FileAsset` + 关联表（不新增独立 Document 实体）**：
- `FileAsset` 已具备 `entityType + entityId + fileType(SPEC_SHEET/DOCUMENT/CERTIFICATE, ...) + organization_id` → 天然可承载供应商文档。
- 通过 `FileAsset.entityType=SUPPLIER_PRODUCT`（或 SupplierProduct 前扩展 `FileEntityType`）+ `SupplierProductMedia`（documentType 区分 Manual/Spec/Cert/InspectionCase）承载。
- 理由：避免重复元数据表；复用既有 upload/soft-delete/org-isolation；文档为「媒体+类型」组合，非独立业务实体。

> 注：`FileEntityType` 现含 PRODUCT/ORGANIZATION/DEMAND/RFQ/RFQ_RESPONSE/CONTENT，缺 SUPPLIER_PRODUCT——此为 660.1 属主枚举扩展点（交 660.2 实现设计，非本任务落库）。

## 4. Migration Strategy

| Strategy | 评估 |
|-|-|
| A 直接迁移 `Offer.productId→supplierProductId` | ❌ 破坏式；存量 Offer 需全量迁移，丢失能力聚合；DemandMatch/Search/SEO 联动破坏 |
| B 兼容双绑 `productId* + supplierProductId*` | ✅ 推荐；无破坏，逐步加列 |
| **C 渐进双轨**（Legacy Product Offer + New Supplier Product Model） | ⚠️ 可作为 B 的过渡层，非独立终态 |

**推荐 = Strategy B（兼容双绑），配合 C 的渐进节奏**：
1. 阶段0（当前）：不动，Offer→Product（Model B 稳定）。
2. 阶段1：新增 `SupplierProduct` 表 + `SupplierProductMedia/ParameterValue` + `Offer.supplierProductId`（可空）。
3. 阶段2：存量 Offer 逐步回填 `supplierProductId`（数据清洗，投递小批量）。
4. 阶段3：`Offer.productId` 收敛为能力聚合冗余字段（由 SupplierProduct→PlatformProduct 继承），最终 `productId` 仅作能力节点关联。

本任务 **不执行任何迁移**，仅给出策略。

## 6. Final Database Architecture Decision

**Future Database Domain Model（冻结方向）**：

```
PlatformProduct
    1 ────── N
SupplierProduct
    1 ────── N
Offer（productId 能力聚合 + supplierProductId 型号源，Option C）
    N ────── 1
Organization
```

**Parameter Ownership**：Standard=Platform；Override=SupplierProduct（继承同 ParameterDefinition）；Extension=SupplierProduct（自定义）。
**Media Ownership**：Platform Media（ProductMedia）/ Supplier Product Media（SupplierProductMedia）/ Organization（FileAsset.org）/ Content（ContentMedia）。
**Document Ownership**：复用 `FileAsset` + `SupplierProductMedia`（Manual/Spec/Cert/InspectionCase 区分）。

**状态 = AUTHENTICATED PASS（Database Architecture Design Complete）**。设计与冻结仅在文档层；Schema 不落库。

**红线**：NO Product.organizationId / Supplier Store / Marketplace / Payment / Order / ERP。Platform Product 维持无属主全局目录。

**遗留（交 660.2 Schema Implementation Design 锁定落库细节）**：SupplierProduct 精确字段/索引/约束、`FileEntityType` 枚举扩展 SUPPLIER_PRODUCT、Offer 双绑迁移 SQL 规划、SupplierProductParameterValue/Media 表结构。
