## 5. WorkspaceRole隔离检查

检查目标：

- BUYER
- SUPPLIER
- null

检查结论：

1. 前端导航层：
   - `BUYER`：显示 `/workspace/notifications`
   - `SUPPLIER`：显示 `/workspace/notifications`
   - `null`：不显示该入口
2. 后端通知访问层：
   - 未基于 `workspaceRole` 做 BUYER/SUPPLIER 隔离
   - 主要基于 `userId`、`organizationId` 与 `organizationMember.role='ADMIN'` 做访问控制
3. 组织隔离：存在
4. 用户隔离：存在，但并非所有接口都完整遵守

代码证据：

1. [`auth-request.interface.ts:L3-L18`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/auth/interfaces/auth-request.interface.ts#L3-L18) 认证用户结构中包含 `workspaceRole`
2. [`notifications.service.ts:L22-L37`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L22-L37) `getAccessScope()` 仅根据 `organizationMember.role='ADMIN'` 和 `organizationId` 扩大为组织范围，否则仅限当前 `userId`
3. [`notifications.service.ts:L42-L63`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L42-L63) 查询 where 条件使用 `userId` 或 `user.organizationId`
4. [`notifications.service.ts:L150-L170`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L150-L170) `validateAccess()` 仅按本人通知或同组织 ADMIN 访问校验

角色维度结论：

1. `BUYER` 与 `SUPPLIER` 在 Sidebar 层都能看到通知入口，因此前端入口层无角色区分
2. `null` 在 Sidebar 层无入口，但后端通知服务本身并未显式拒绝 `workspaceRole=null`，只要 JWT 用户存在即可按 `userId` 范围访问自己的通知
3. Notification 能力当前不是“WorkspaceRole 隔离模型”，而是“用户/组织范围模型”

额外完整性观察：

1. [`notifications.controller.ts:L35-L39`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.controller.ts#L35-L39) 的 `POST /notifications/batch-delete` 未注入当前用户
2. [`notifications.service.ts:L234-L238`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L234-L238) 直接按传入 `ids` 执行 `deleteMany`
3. [`notifications.ts:L19-L63`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/lib/api/notifications.ts#L19-L63) 当前 Web 客户端未封装 `batch-delete`，但这不改变后端接口已暴露且可被直接调用的事实
4. 该接口未附加 `userId` / `organizationId` / `validateAccess()` 约束，存在跨用户删除任意 notification id 的风险

## 6. 风险列表

### High

1. Sidebar 存在 `/workspace/notifications` 入口，但前端路由文件不存在  
   - 证据：[`WorkspaceSidebar.tsx:L18-L32`](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/components/workspace/WorkspaceSidebar.tsx#L18-L32) 与缺失的 `apps/web/src/app/workspace/notifications/page.tsx`
   - 影响：BUYER/SUPPLIER 点击“通知中心”将进入未实现路由，形成明显导航断链

2. `POST /notifications/batch-delete` 未按当前用户做访问约束  
   - 证据：[`notifications.controller.ts:L35-L39`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.controller.ts#L35-L39)、[`notifications.service.ts:L234-L238`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L234-L238)

### Medium

1. 后端 Notification 能力已完整存在，但前端 Workspace 页面缺失  
   - 证据：[`notifications.controller.ts:L11-L70`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.controller.ts#L11-L70)、[`notifications.service.ts:L13-L240`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L13-L240)、`workspace/notifications/page.tsx` 缺失
   - 影响：前后端能力断层，Sidebar 与后端 API 之间没有可落地的 Workspace 页面承接

2. Notification 访问逻辑未基于 `workspaceRole` 做 BUYER/SUPPLIER 隔离  
   - 证据：[`auth-request.interface.ts:L3-L18`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/auth/interfaces/auth-request.interface.ts#L3-L18)、[`notifications.service.ts:L22-L37`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L22-L37)
