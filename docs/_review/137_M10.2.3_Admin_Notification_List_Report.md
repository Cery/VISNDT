## Page Architecture

### Data Flow

```
NotificationList
    ↓
notificationService.getList({page, pageSize, status?, type?})
    ↓
apiClient → GET /notifications
    ↓
Backend NotificationsController → NotificationsService
```

### PageState Pattern

```typescript
type PageState =
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; data: Notification[]; total: number };
```

| State | UI |
|-------|-----|
| Loading | `<Spin size="large">` centered |
| Error | `<Alert type="error">` + Retry button |
| Success | `<Table>` with pagination |

### Filters

| Filter | Type | Backend Param | Options |
|--------|------|---------------|---------|
| Status | `<Select>` | `status` | All, UNREAD, READ |
| Type | `<Select>` | `type` | All, SYSTEM, DEMAND_UPDATE, RFQ_UPDATE, RESPONSE_UPDATE |
| Reset | `<Button>` | clears all | Resets to page 1 |

**Filtering Strategy**: All filters are backend-driven via `notificationService.getList({status, type, page, pageSize})`. No client-side filtering.

### Pagination

| Feature | Implementation |
|---------|---------------|
| Current page | `query.page` → `TablePaginationConfig.current` |
| Page size | `query.pageSize` → `TablePaginationConfig.pageSize` |
| Total | `pageState.total` |
| Size changer | `[10, 20, 50]` |
| Show total | `"1-20 of 150"` format |
| Page change | `handleTableChange` → `fetchNotifications()` |
