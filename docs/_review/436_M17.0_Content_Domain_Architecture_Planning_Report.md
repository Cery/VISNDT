## 4. Content Domain Architecture Proposal

### 4.1 平台定位

内容系统定位为：**工业检测行业知识内容平台**（技术知识、检测指南、应用案例、行业解决方案）。
它不是：商城 / 广告系统 / 供应商店铺（符合既有商业模型约束，禁止 supplier 店铺化）。

### 4.2 内容实体（统一 Content + type 判别）

推荐**统一单表 + `type` 判别**方案（最小闭环，单后台模块、单 API 面，符合 433 MVP 范围）：

```
Content
  id            String  @id
  type          ContentType   // ARTICLE | KNOWLEDGE | SOLUTION | INSIGHT
  title         String
  slug          String   @unique
  summary       String?
  content       String   // 正文（Markdown/富文本）
  coverImageId  String?  // 关联 FileAsset（复用文件资产能力）
  status        ContentStatus // DRAFT | REVIEW | PUBLISHED | ARCHIVED
  authorId      String   // 关联 User
  publishedAt   DateTime?
  archivedAt    DateTime?
  // SEO 元数据（MVP 内联，未来可拆 SeoMetadata 独立模型）
  seoTitle       String?
  seoDescription String?
  seoKeywords    String?
  createdAt     DateTime
  updatedAt     DateTime
```

### 4.3 字段方向说明

- `title` / `slug` / `summary` / `content` / `status` / `publishedAt` / `author` / SEO metadata 均覆盖。
- `slug` 唯一，用于前台详情页路由与 SEO URL。
- `type` 判别：`KNOWLEDGE`（知识中心）、`SOLUTION`（解决方案）、`ARTICLE`（通用文章）、`INSIGHT`（行业洞察，M17 后期）。
- 封面图复用 FileAsset，不上传逻辑不重复建设。

### 4.4 明确不纳入 MVP（保持范围边界）

标签系统、内容搜索系统、推荐系统、SEO 管理系统、AI 内容生成系统 —— 均不在本设计范围内（设计仅预留扩展位，不实现）。

## 5. Workflow Design

内容生命周期 `DRAFT → REVIEW → PUBLISHED → ARCHIVED` 映射到**现有 WorkflowAction 语义**（不修改 WorkflowAction 枚举）：

| 内容状态 | 迁移动作 | WorkflowAction 映射 | 说明 |
| --- | --- | --- | --- |
| DRAFT（草稿） | 创建 | `CREATED` | 新建内容初始为草稿 |
| REVIEW（审核中） | 提交审核 | `SUBMITTED` | 作者提交审核 |
| REVIEW（审核通过） | 审核通过 | `REVIEWED` | 审核人操作 |
| PUBLISHED（已发布） | 发布 | `OPENED` | 对公开站可见 |
| ARCHIVED（已归档） | 归档 | `CLOSED` | 下线/归档 |

复用现有 `WorkflowEvent` 记录（entityId = contentId，operatorId = 操作人，metadata = { type, status 变更 }），通知回流复用 Notification 架构。

> **治理提示（留待 M17.1 评审决策，本任务不实施）**：现有 `WorkflowEntityType` 枚举仅含 DEMAND/RFQ/RFQ_RESPONSE/OFFER/MATCH，内容事件需新增 `CONTENT` 值以承载 entityType。此为设计建议，需在 M17.1 评审中批准后实施，本任务不改动枚举。

## 6. API Design Proposal

遵循现有 Controller 模式（公开 `@Get` + Admin 变更 `@UseGuards(JwtAuthGuard, RolesGuard)` / `@Roles(Role.ADMIN)` / `@ApiBearerAuth()`）。

### Public（公开，仅 PUBLISHED）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/content?type=KNOWLEDGE&page=1&pageSize=20` | 内容列表（已发布，按 type 过滤、分页） |
| GET | `/content/:slug` | 内容详情（已发布，按 slug） |

### Admin（ADMIN，全部状态）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/content` | 创建草稿（DRAFT） |
| PATCH | `/content/:id` | 更新内容 |
| POST | `/content/:id/submit` | 提交审核（→ REVIEW） |
| POST | `/content/:id/review` | 审核通过（→ REVIEWED） |
| POST | `/content/:id/publish` | 发布（→ PUBLISHED） |
| POST | `/content/:id/archive` | 归档（→ ARCHIVED） |
| GET | `/content` | 后台列表（全部状态） |
| GET | `/content/:id` | 后台详情 |

采用 `POST /:id/action` 生命周期端点（与产品 `batch-status` 风格一致），避免在 body 中携带状态变更请求。

## 7. Frontend Architecture Proposal

### Web（公开站）

遵循 `Web Page → Content Service → API Wrapper → Content API`，禁止 Page 直接 fetch 后端：

| 页面 | 说明 |
| --- | --- |
| `/knowledge` | 知识中心列表（替换静态 `SECTIONS`，接入 API） |
| `/knowledge/[slug]` | 知识详情页（动态 `generateMetadata`，复用 M16.3 SEO 机制） |
| `/solutions` | 解决方案列表（替换静态 `SOLUTIONS`，接入 API） |
| `/solutions/[slug]` | 解决方案详情页（动态 `generateMetadata`） |

### Admin（后台）

| 模块 | 说明 |
| --- | --- |
| Content List | 内容列表（状态/作者/type 过滤） |
| Content Editor | 内容编辑（标题/slug/摘要/正文/封面/SEO） |
| Publish Management | 发布管理（submit / review / publish / archive 操作） |

遵循既有 Admin 列表/详情/表单 + BatchOperations 模式；菜单在 `AdminLayout` 新增内容管理入口、路由在 `router/index.tsx` 新增（M17.1 实现阶段）。
