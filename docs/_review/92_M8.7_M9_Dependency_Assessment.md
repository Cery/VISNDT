## 4. Risk Points

| Risk | Severity | Mitigation |
|------|----------|------------|
| Demand owner vs admin override conflict | Low | Admin demand API is separate from user demand API; no conflict |
| Rate limiting on admin dashboard | Low | Dashboard is a single aggregate query; well within limits |
| Performance under load | Low | Admin APIs use Prisma aggregates; indexed queries |
| Frontend token management | Medium | Ensure JWT refresh/expiry handling in frontend |

## 5. Recommended M9 Implementation Order

### Phase M9.1 — Admin Auth + RBAC + Dashboard

1. Admin login page (consumes `POST /auth/login`, `GET /auth/me`)
2. RBAC route guards (checks `Role.ADMIN` from JWT)
3. Dashboard page (consumes `GET /admin/dashboard/stats`)

### Phase M9.2 — Product + Category + Parameter Management

1. Product list/create/edit (consumes `GET/POST/PATCH /products`)
2. Category list/create/edit (consumes `GET/POST/PATCH /product-categories`)
3. Parameter group/definition management (consumes `GET/POST/PATCH /parameter-groups`, `/parameter-definitions`)
4. Product media management (consumes `/products/:productId/media`)

### Phase M9.3 — Demand Management + Matching Monitor

1. Demand list view (consumes `GET /demands`)
2. Admin demand override (consumes `PATCH /admin/demands/:id`)
3. Matching monitor (consumes `GET /admin/matching/stats`, `GET /demands/:id/matches`)

### Phase M9.4 — User + Organization Management

1. User list/edit (consumes `GET/PATCH /users`)
2. Organization list/create/edit (consumes `GET/POST/PATCH /organizations`)
3. Invitation management (consumes `POST /auth/invitations`)
4. Organization member management (consumes `GET/POST /organizations/:id/members`)
