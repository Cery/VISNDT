## Unfreeze Reason

### Why Backend Unfreeze is Required

The Notification model exists in the database (`prisma/schema.prisma:568-586`) with full schema:

```
model Notification {
  id, userId, type, status, title, message,
  referenceType, referenceId, createdAt, updatedAt
}
```

However, the Backend has **zero code** to expose this data:

- No `notifications/` module directory
- No `NotificationsController` with REST endpoints
- No `NotificationsService` with Prisma queries
- No `NotificationsModule` registered in `app.module.ts`
- No DTOs for request/response validation

**Without Backend unfreeze, M10.2 Notification Center cannot proceed.**

## Security Requirements

### Mandatory Security Controls

| Requirement | Implementation |
|-------------|---------------|
| **JWT Authentication** | All endpoints use `@UseGuards(JwtAuthGuard)` |
| **ApiBearerAuth** | All endpoints include `@ApiBearerAuth()` decorator |
| **User Data Isolation** | Non-ADMIN users can only access their own notifications (`userId` from JWT) |
| **ADMIN Scope** | ADMIN role can list all notifications for monitoring purposes |
| **No client-controlled userId** | `userId` is always derived from `@CurrentUser()` JWT payload |
| **Ownership validation** | `GET/PATCH /notifications/:id` validates `notification.userId === currentUser.id` (non-ADMIN) |

### Security Rules

```
Rule 1: userId always from JWT — never from request body/params
Rule 2: Non-ADMIN: filter by currentUser.id
Rule 3: ADMIN: no user filter (view all)
Rule 4: PATCH operations: validate ownership before mutation
Rule 5: No sensitive data exposure (notification content is app-level)
```
