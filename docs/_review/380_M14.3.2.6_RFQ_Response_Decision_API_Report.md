## 3. API变化

### 新增接口

1. `POST /rfq-responses/:id/view`
   - 作用：Buyer 标记 RFQResponse 已查看
   - 请求体：无
2. `POST /rfq-responses/:id/accept`
   - 作用：Buyer 接受 RFQResponse
   - 请求体：`{ "decisionNote"?: string }`
3. `POST /rfq-responses/:id/reject`
   - 作用：Buyer 拒绝 RFQResponse
   - 请求体：`{ "decisionNote"?: string }`

### 兼容性收口

- 现有 `PATCH /rfq-responses/:id` 不再允许 Supplier 侧按原逻辑直接改状态。
- 若调用方仍传入 `VIEWED / ACCEPTED / REJECTED`，服务端会统一走新的 Buyer 决策流与权限校验。

## 4. 权限校验

- 决策接口必须为已登录用户。
- 调用方必须满足：
  - `workspaceRole === BUYER`
  - `user.organizationId` 存在
  - `RFQResponse.rfq.demand.organizationId === user.organizationId`
- 这保证了只有 Buyer 组织成员，且仅能处理属于自己 Demand 链路下的 RFQResponse。
- Supplier 无法调用 Buyer 决策接口，也无法再通过原 `PATCH` 路径绕过该限制。

## 5. 状态流转

- 保持既有状态机：
  - `SUBMITTED -> VIEWED`
  - `VIEWED -> ACCEPTED`
  - `VIEWED -> REJECTED`
- 决策字段写入规则：
  - `view`: 写入 `reviewedBy`、`reviewedAt`
  - `accept/reject`: 写入 `reviewedBy`、`reviewedAt`、`decisionNote`
- 非法跳转会返回 `BadRequestException`。

## 6. Notification影响

- 复用现有 `notificationsService.createForOrganization()`
- `accept/reject` 时向响应所属 Supplier 组织的 ADMIN 成员发送 `NotificationType.RESPONSE_UPDATE`
- `view` 不新增通知，避免仅查看动作造成额外打扰
- 本次未修改 `apps/api/src/notifications/` 代码

## 7. WorkflowEvent影响

- 复用现有 `workflowEventsService.create()`
- 写入实体类型：`WorkflowEntityType.RFQ_RESPONSE`
- 动作映射：
  - `view -> WorkflowAction.REVIEWED`
  - `accept -> WorkflowAction.ACCEPTED`
  - `reject -> WorkflowAction.REJECTED`
- metadata 包含：
  - `previousStatus`

  - `targetOrganizationId`（若存在）
  - `decisionNote`（若存在）
