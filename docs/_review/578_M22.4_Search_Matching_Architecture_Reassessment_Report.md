# 2. Search Architecture Proposal

## 2.1 Core Question: Product Search vs. Knowledge Search — Merge or Separate?

### Recommendation: **Merge — Unified Industrial Retrieval Layer**

**Rationale:**

VISNDT is an **Industrial Inspection Capability Discovery** platform. The user's search intent is inherently unified:

- A user searching "超声检测" wants: products that do ultrasonic inspection, knowledge about ultrasonic inspection techniques, and solutions for ultrasonic inspection scenarios.
- A user searching "焊缝检测" wants: products for weld inspection, knowledge about weld inspection methods, and solutions for weld inspection scenarios.

**Arbitrary separation** of Product Search and Knowledge Search creates a **fragmented user experience** where the user must manually switch between search domains.

**Proposed Architecture:**

```
┌─────────────────────────────────────────────────┐
│         Unified Industrial Retrieval Layer       │
│                                                   │
│  /search?q=超声检测                                │
│                                                   │
│         ↓                                          │
│  ┌─────────────────────────────────────────────┐ │
│  │       Unified Retrieval Service              │ │
│  │                                               │ │
│  │  ┌──────────┐ ┌──────────┐ ┌──────────────┐ │ │
│  │  │ Product   │ │Knowledge │ │Content       │ │ │
│  │  │ Retrieval │ │Retrieval │ │Retrieval     │ │ │
│  │  │           │ │          │ │              │ │ │
│  │  │ Product   │ │Knowledge │ │Content       │ │ │
│  │  │ name/model│ │Entry     │ │articles/     │ │ │
│  │  │ description│ │title/    │ │insights/     │ │ │
│  │  │ + params  │ │summary/  │ │solutions     │ │ │
│  │  │           │ │structBody│ │              │ │ │
│  │  └──────────┘ └──────────┘ └──────────────┘ │ │
│  │                                               │ │
│  │         ↓ Unified Ranking + Merge             │ │
│  │                                               │ │
│  │  UnifiedSearchResponse {                      │ │
│  │    products: [],                               │ │
│  │    knowledge: [],   ← Knowledge Entry          │ │
│  │    content: [],     ← Content assets           │ │
│  │  }                                            │ │
│  └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

### Boundary

- **Merge**: Search QUERY and RESULT layer — single `/search` endpoint, unified response.
- **Keep Separate**: Entity models, database tables, API routes — Product, KnowledgeEntry, Content remain independent data sources.
- **Unified**: Retrieval coordination, ranking, and response aggregation.

## 2.2 Knowledge Entry vs. Content Knowledge — Resolution

Currently, `/search` searches Content (type=KNOWLEDGE) but NOT KnowledgeEntry.

**Recommendation:** KnowledgeEntry REPLACES Content (type=KNOWLEDGE) in search results.

| Source | Current | Future |
| --- | --- | --- |
| Content (type=KNOWLEDGE) | Included in search | **Deprecated from search** |
| KnowledgeEntry | NOT in search | **Primary knowledge search source** |
| Content (type=ARTICLE) | N/A | Included as "content" |
| Content (type=INSIGHT) | N/A | Included as "content" |
| Content (type=SOLUTION) | Included as "solutions" | Included as "content/solutions" |

**Reason:** KnowledgeEntry is the structured, domain-classified, category-organized knowledge asset. Content (type=KNOWLEDGE) is an earlier content type that can be migrated to KnowledgeEntry through KnowledgeContentRef.

# 4. RFQ Matching Evolution

## 4.1 Current Matching Flow

```
Demand Parameters ──→ Product Parameters ──→ Score ──→ Match
```

Purely parameter-based. No understanding of the inspection scenario.

## 4.2 Knowledge-Enhanced Matching (Future)

**Recommendation:** Knowledge Layer provides SEARCH/REFERENCE context for matching, but does NOT enter the scoring algorithm.

```
Current:
Demand Parameters → Product Parameters → Score → Match

Future (Knowledge Context):
Demand
  │
  ├── Parameters (existing)
  ├── Category (existing)
  └── Knowledge Context (NEW — reference only)
        │
        ├── Related KnowledgeEntries (via category/domain)
        ├── Inspection Scenario Understanding
        └── Reference Products (from KnowledgeEntry → ContentRef)
              │
              ↓ (ADVISORY — not scoring)
        MatchingService
              │
              ↓ (SCORING)
        Product Parameters Match (unchanged)
```

**What Knowledge Context provides:**

| Aspect | Without Knowledge | With Knowledge |
| --- | --- | --- |
| Category Expansion | Direct categoryId only | Knowledge domain → related categories |
| Parameter Understanding | Parameter name only | Knowledge explanation of parameter meaning |
| Scenario Context | None | Inspection scenario classification |
| Product Discovery | Active products only | Knowledge-referenced products |

**What Knowledge Context does NOT provide:**

- Does NOT modify the scoring algorithm
- Does NOT replace parameter-based matching
- Does NOT automatically select products
- Does NOT make autonomous decisions
