### 2.3 API Contract

**Endpoint:** `GET /matches/:id/knowledge-context`

**Auth:** JWT Bearer Token

**Response:**

```typescript
{
  code: 200,
  message: "OK",
  data: {
    domain: {
      id: string;
      name: string;
      slug: string;
    } | null;
    category: {
      id: string;
      name: string;
      slug: string;
    } | null;
    relevantEntries: KnowledgeEntryRef[];
    prerequisiteKnowledge: KnowledgeEntryRef[];
    relatedKnowledge: KnowledgeEntryRef[];
    followupKnowledge: KnowledgeEntryRef[];
  }
}
```

### 2.4 Resolution Flow

```
DemandMatch
  → Product (with ProductCategory)
    → KnowledgeDomain (name-based match: exact → contains name → contains slug)
      → KnowledgeCategory (under domain, name match → first category)
        → KnowledgeEntry (PUBLISHED, in domain/category, max 5)
          → KnowledgeRelation (PREREQUISITE / RELATED / FOLLOWUP, max 5 per type)
            → KnowledgeContext (runtime computed, NOT persisted)
```

### 2.5 Design Decisions

| Decision | Rationale |
|----------|-----------|
| Name-based domain matching | No FK between ProductCategory and KnowledgeDomain. Uses case-insensitive name matching (exact → contains → slug) as pragmatic bridge. |
| `KnowledgeContext` as runtime object | Per ADR-016: Knowledge Context is Read-side Companion Data, not a stored entity. |
| `MAX_RELEVANT_ENTRIES = 5` | Prevent unbounded results. Configurable via service constant. |
| `MAX_RELATION_ENTRIES = 5` | Per relation type. Configurable via service constant. |
| JWT required on endpoint | Knowledge context is authenticated (not public). Protects match data. |
| No Swagger DTO class | KnowledgeContext is internal contract; full Swagger typed response deferred to API stabilization phase. |
