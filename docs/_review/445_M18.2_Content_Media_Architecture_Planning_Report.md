## 3. Current FileAsset Capability Review

### 3.1 当前模型（`database/prisma/schema.prisma`）

```prisma
model FileAsset {
  id         String         @id @default(uuid()) @db.Uuid
  entityType FileEntityType @map("entity_type")
  entityId   String         @map("entity_id") @db.Uuid
  fileType   FileType       @map("file_type")
  fileName   String         @map("file_name")
  storageKey String         @map("storage_key")
  mimeType   String         @map("mime_type")
  fileSize   Int            @map("file_size")
  uploadedBy String         @map("uploaded_by") @db.Uuid
  // relations: uploader, media(ProductMedia[]), contentCoverImages(Content[])
}

enum FileEntityType { PRODUCT ORGANIZATION DEMAND RFQ RFQ_RESPONSE }
enum FileType { IMAGE DOCUMENT CERTIFICATE OTHER }
```

- **Content 关联现状**：`Content.coverImageId → FileAsset`（单封面，`contentCoverImages` 反向关系），`Content` 模型无 `media` 反向关系。

### 3.2 当前能力（`apps/api/src/file-asset/` + `storage/` + `product-media/`）

| 能力 | 现状 | 说明 |
| --- | --- | --- |
| 图片 | ✅ | `FileType.IMAGE`，MIME 白名单含 png/jpeg/webp/gif |
| 附件 | ✅ | `FileType.DOCUMENT`，含 pdf/word/excel/ppt |
| PDF | ✅ | `application/pdf` 白名单 |
| 下载文件 | ✅ | `GET /files/:id/download` 生成预签名 URL 重定向 |
| MIME 白名单 | ✅ | `ALLOWED_MIME_TYPES` 校验 |
| 文件大小限制 | ✅ | `MAX_FILE_SIZE = 10MB` |
| Storage Key | ✅ | `uploads/{timestamp}-{uuid}.{ext}`，存于 MinIO/S3 |
| URL 生成 | ✅ | `StorageService.getSignedUrl`（默认 900s） |
| 权限控制 | ⚠️ 部分 | 上传/删除为 ADMIN（RolesGuard）；`GET /files/:id/download` 为**公开**，无鉴权/实体归属校验 |
| 原子上传-create | ✅ | `ProductMedia.createWithUpload` 模式可复用 |
| 孤儿清理 | ✅ | `findOrphans` / `cleanupOrphans` / `batchDelete` |

### 3.3 缺口（Content Media 需求视角）

1. **`FileEntityType` 无 `CONTENT`**：Content 封面目前通过独立的 `contentCoverImages` 反向关系关联，未纳入统一 `entityType` 分类体系。
2. **多图/图文/附件承载缺失**：`Content.coverImageId` 仅单封面，无媒体数组、排序、caption、附件类型区分。
3. **`Content` 无 `media` 反向关系**：无法按内容一次拉取多媒体。
4. **下载端点无归属校验**：`GET /files/:id/download` 公开且仅按 `id` 查找，未校验文件所属实体/实体发布状态，存在安全缺口（详见 §7）。
5. **Admin 响应含 `storageKey`**：`content.service` 的 Admin `findAll`/`findOne`/`findBySlug` 的 `coverImage` 投影含 `storageKey`，为 Admin 内部使用可接受，但需在 Public 投影中彻底排除（当前 Public 投影已排除）。

## 4. ContentMedia Architecture Design

### 4.1 推荐模型（仅设计评估，未创建）

```
Content
   1
   |
   N
ContentMedia      N : 1      FileAsset
```

```prisma
// —— 仅设计基线，不写入 schema ——
enum ContentMediaType {
  IMAGE
  ATTACHMENT
}

model ContentMedia {
  id          String           @id @default(uuid()) @db.Uuid
  contentId   String           @map("content_id") @db.Uuid
  fileAssetId String?          @map("file_asset_id") @db.Uuid
  type        ContentMediaType @default(IMAGE)
  caption     String?
  sortOrder   Int              @default(0) @map("sort_order")

  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  content   Content    @relation(fields: [contentId], references: [id], onDelete: Cascade)
  fileAsset FileAsset? @relation(fields: [fileAssetId], references: [id])

  @@index([contentId])
  @@index([fileAssetId])
  @@map("content_media")
}
```

### 4.2 字段设计说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID | 主键 |
| `contentId` | UUID | 关联 Content（`onDelete: Cascade`，删除内容连带删除媒体关联） |
| `fileAssetId` | UUID? | 关联 FileAsset（可空，兼容外链/占位场景） |
| `type` | `ContentMediaType` | `IMAGE` / `ATTACHMENT`（附件/报告/PDF） |
| `caption` | String? | 图注/说明 |
| `sortOrder` | Int | 排序权重（升序），Admin 拖拽排序 |
| `createdAt` / `updatedAt` | DateTime | 审计时间戳 |

### 4.3 Relation Design

- **Content 1 — N ContentMedia**：`Content.media ContentMedia[]` 反向关系（新增一行 Relation 字段）。
- **FileAsset 侧复用**：`FileAsset` 无需改实体字段，仅新增反向关系 `contentMedias ContentMedia[]`；`CoverImage` 仍走 `Content.coverImageId`（单封面）与 `ContentMedia`（多图/附件）二者并存，互不冲突。
- **`FileEntityType.CONTENT`**：建议新增枚举值，使新上传的 Content 媒体可标 `entityType=CONTENT`（与 Product 模式一致），并复用孤儿清理逻辑。
- **设计原则**：完全复用 `Product → ProductMedia → FileAsset` 成熟模式（含 `createWithUpload` 原子上传-create、删除级联 S3 清理），避免脚手架重造。

### 4.4 Alternative Evaluation

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. `ContentMedia` 中间表 | 与 ProductMedia 一致，支持多图/排序/caption/附件 | ✅ 推荐（一致性最高） |
| B. `Content.content` JSON 内嵌媒体数组 | 简单但无 FK、无级联、排序/caption 需自维护、无法复用 FileAsset 能力 | ❌ 不推荐（破坏统一存储设计） |
| C. 独立模型（ArticleMedia/KnowledgeMedia/SolutionMedia） | 违反单模型约束 | ❌ 禁止 |
| D. 直接 `Content→FileAsset` 多对多（无中间表） | 无排序/caption/类型扩展，无法表达 IMAGE 与 ATTACHMENT 区分 | ❌ 不推荐 |

## 5. API Evolution Plan

### 5.1 Public API 影响

现有：
- `GET /content/public`（列表）
- `GET /content/public/:slug`（详情）

**推荐方案：方案 A（Content API include media）**，而非方案 B（独立 Media API）。

- 详情 `GET /content/public/:slug` 未来在 `publicContentSelect` 中追加：
  ```json
  {
    "content": "...",
    "media": [
      { "id": "...", "type": "IMAGE", "caption": "...", "sortOrder": 0,
        "fileAsset": { "id": "...", "fileName": "...", "mimeType": "..." } }
    ],
    "coverImage": { "id": "...", "fileName": "...", "mimeType": "..." }
  }
  ```
- **关键安全约束**：Public 投影**绝不暴露 `storageKey`**；媒体文件访问通过 `GET /files/:id/download`（预签名 URL）或 `?signed=1` 参数按需生成，禁止直接回传 S3 key。
- 列表 `GET /content/public` 保持轻量（不含 media 数组，避免列表膨胀）；detail 才 include media。
- 兼容性：`media` 为**新增可选字段**，既有字段不变，旧客户端不受影响 → **API Contract 向后兼容**。

### 5.2 Admin API 影响

- 复用 `ProductMedia` 端点范式，未来新增：
  - `POST /content/:id/media` / `POST /content/:id/media/upload`（原子上传-create）
  - `PATCH /content/:id/media/:mediaId`（caption/sortOrder/type）
  - `DELETE /content/:id/media/:mediaId`（删除媒体 + 级联清理 FileAsset + S3）
  - `GET /content/:id/media`（管理端列表，可含 storageKey 供内部使用）
- 全部 `JwtAuthGuard + RolesGuard + Roles(ADMIN)` 保护，与现有 Content ADMIN 端点一致。

### 5.3 推荐结论

**方案 A（`GET /content/public/:slug` include media）为主**，理由：
1. Web 详情页一次请求即可获取正文 + 媒体画廊 + 附件，减少往返；
2. 与现有 `publicContentSelect` 投影模式一致，安全边界清晰；
3. 不新增公开端点，**不扩大 Public API 攻击面**。

## 7. Security Review

| 关注点 | 现状 | 规划要求 |
| --- | --- | --- |
| 文件公开策略 | `GET /files/:id/download` 公开 | 需按实体发布状态约束：仅 **PUBLISHED 内容** 关联的媒体可公开下载；DRAFT/REVIEW/ARCHIVED 媒体拒绝 |
| 未发布内容隔离 | Public Content API 已强制 `status=PUBLISHED` | 媒体下载端点需同样以「文件→ContentMedia→Content.status」链路校验发布状态，杜绝侧信道泄露未发布媒体 |
| storageKey 保护 | Admin 投影含、Public 投影不含 | Public 投影**永不**含 storageKey；Web 仅经预签名 URL 访问，不直接接触 S3 key |
| Public API 字段投影 | `publicContentSelect` 已剔除内部字段 | 扩展 media 时沿用投影模式，仅暴露 id/type/caption/sortOrder/fileName/mimeType，不含 storageKey/entityId/uploadedBy |
| 私有附件访问控制 | N/A（当前无私有附件概念） | 若未来存在私有附件（如仅登录用户下载），需在下载端点加入「实体发布状态 + 登录态」双重校验；当前 MVP 全部为公开发布内容 |
| 文件上传 | ADMIN 保护 + MIME 白名单 + 10MB 限制 | 保持，ContentMedia 上传复用同一 FileAssetService.validateFile |

**结论**：当前最大安全缺口为 `GET /files/:id/download` 无「实体 → 发布状态」归属校验，需在 M18.2 Implementation 落地媒体下载校验，其余边界（Public 投影、上传白名单、大小限制）已稳固。
