## 4. ConversionEvent Architecture Proposal

### 4.1 Purpose & Boundary

```
┌─────────────────────────────────────────────────────────────────┐
│                    EVENT ARCHITECTURE                            │
│                                                                   │
│  L1: User Behavior Event                                         │
│      ConversionEvent ─── 用户行为追踪（浏览/点击/搜索/咨询）       │
│      Purpose: Analytics / Conversion Funnel / Product Discovery  │
│      Scope: Frontend → API → PostgreSQL                          │
│      ─────────────────────────────────────────                   │
│  L2: Business Workflow Event                                      │
│      WorkflowEvent ─── 业务状态流转（创建/提交/打开/回复/关闭）    │
│      Purpose: Business Process Tracking / Workflow Monitoring    │
│      Scope: Backend → PostgreSQL                                 │
│      ─────────────────────────────────────────                   │
│  L3: System Change Event                                          │
│      AuditLog ─── 数据变更审计（创建/更新/删除/状态变更）         │
│      Purpose: Data Governance / Compliance / Security            │
│      Scope: Backend → PostgreSQL                                 │
│      ─────────────────────────────────────────                   │
│  L0: User Notification Event                                      │
│      Notification ─── 用户通知（系统/需求/询价/响应）             │
│      Purpose: User Communication                                 │
│      Scope: Backend → PostgreSQL                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Boundary Principle**:
- ConversionEvent ≠ WorkflowEvent（行为事件 ≠ 业务事件）
- ConversionEvent ≠ AuditLog（行为追踪 ≠ 数据审计）
- ConversionEvent 聚焦用户行为分析，WorkflowEvent 聚焦业务流程状态，AuditLog 聚焦数据变更合规

### 4.2 Event Identity Design

| Field | Type | Purpose | Required |
|-------|------|---------|----------|
| `id` | UUID | 事件唯一标识 | Yes |
| `event` | String / Enum | 事件类型（见 4.3） | Yes |
| `createdAt` | DateTime | 事件发生时间 | Yes |

### 4.4 Data Model Recommendation

#### Prisma Schema Candidate

```prisma
// ===========================================
// Migration 009: Analytics Event Domain
// ===========================================

enum ConversionEventType {
  PAGE_VIEW
  PRODUCT_VIEW
  CONTENT_VIEW
  SEARCH
  PRODUCT_FILTER
  CTA_CLICK
  INQUIRY_START
  INQUIRY_SUBMIT
}

model ConversionEvent {
  id             String              @id @default(uuid()) @db.Uuid
  event          ConversionEventType
  userId         String?             @map("user_id") @db.Uuid
  organizationId String?             @map("organization_id") @db.Uuid
  sessionId      String?             @map("session_id")
  entityType     String?             @map("entity_type")
  entityId       String?             @map("entity_id") @db.Uuid
  source         String?             // 触发来源：路由/组件名
  metadata       Json?               @db.JsonB
  createdAt      DateTime            @default(now()) @map("created_at")

  user         User?         @relation(fields: [userId], references: [id])
  organization Organization? @relation(fields: [organizationId], references: [id])

  @@index([event])
  @@index([userId])
  @@index([organizationId])
  @@index([sessionId])
  @@index([entityType, entityId])
  @@index([createdAt])
  @@index([event, createdAt])
  @@map("conversion_event")
}
```

#### Field Justification

| Field | Justification | Data Source |
|-------|--------------|-------------|
| `id` | 事件唯一标识，UUID 保证分布式唯一性 | Auto-generated |
| `event` | Enum 类型确保事件类型可控，支持类型安全查询 | Frontend/Backend |
| `userId` | 关联已登录用户，支持用户行为分析 | Auth Context |
| `organizationId` | 关联用户所属组织，支持供应商/Buyer 行为分析 | Auth Context |
| `sessionId` | 关联匿名会话，支持漏斗分析和会话归因 | Frontend session |
| `entityType` | 关联实体类型（Product/Content/Inquiry/Demand），支持跨实体聚合 | Event context |
| `entityId` | 关联实体 ID，支持实体级分析 | Event context |
| `source` | 触发来源（路由/组件名），支持来源分析 | Frontend |
| `metadata` | JsonB 扩展字段，支持自定义属性（如搜索关键词、筛选条件） | Event context |
| `createdAt` | 事件时间戳，支持时序分析 | Auto-generated |

#### Field Comparison with Existing Models

| Field | ConversionEvent | WorkflowEvent | AuditLog |
|-------|:---:|:---:|:---:|
| id | ✓ | ✓ | ✓ |
| event/action | ✓ (Enum) | ✓ (Enum) | ✓ (Enum) |
| userId/operatorId | ✓ (optional) | ✓ (required) | ✓ (required) |
| organizationId | ✓ (optional) | — | — |
| sessionId | ✓ | — | — |
| entityType | ✓ (String) | ✓ (Enum) | ✓ (String) |
| entityId | ✓ | ✓ | ✓ |
| source | ✓ | — | — |
| metadata | ✓ (JsonB) | ✓ (JsonB) | — |
| oldValue/newValue | — | — | ✓ (JsonB) |
| ipAddress | — | — | ✓ |
| createdAt | ✓ | ✓ | ✓ |

**Responsibility Separation**:
- ConversionEvent: 用户行为 → 分析用途（可匿名、可延迟、可批量）
- WorkflowEvent: 业务状态 → 业务流程（必须登录、必须即时、必须精确）
- AuditLog: 数据变更 → 合规审计（必须登录、必须即时、必须完整）

### 4.5 Entity Relationships

| Entity | Relationship | Required | Justification |
|--------|:-----------:|:--------:|--------------|
| User | Optional 1:N | No | 未登录用户也需要追踪（匿名浏览） |
| Organization | Optional 1:N | No | 未登录用户无组织归属 |
| Product | Optional N:1 | No | 通过 entityType="PRODUCT" + entityId 关联 |
| Content | Optional N:1 | No | 通过 entityType="CONTENT" + entityId 关联 |
| Demand | Optional N:1 | No | 通过 entityType="DEMAND" + entityId 关联 |
| RFQ | Optional N:1 | No | 通过 entityType="RFQ" + entityId 关联 |
| Inquiry | Optional N:1 | No | 通过 entityType="INQUIRY" + entityId 关联 |

**Design Decision**: 使用 `entityType` + `entityId` 模式而非 Prisma FK 关系。原因：
1. 避免与所有业务 Model 建立 FK（会导致 Schema 膨胀）
2. 与 WorkflowEvent / AuditLog / FileAsset 的设计模式一致
3. 支持未来扩展新实体类型而无需修改 Schema

## 5. Storage Strategy Review

### 5.1 Storage Engine

```
Storage: PostgreSQL（与现有基础设施一致）
Table: conversion_event
Engine: Standard PostgreSQL，无需 TimescaleDB 或 ClickHouse
```

### 5.2 Index Strategy

| Index | Pattern | Purpose |
|-------|---------|---------|
| `@@index([event])` | 按事件类型查询 | 统计各类事件数量 |
| `@@index([userId])` | 按用户查询 | 用户行为分析 |
| `@@index([organizationId])` | 按组织查询 | 供应商/Buyer 行为分析 |
| `@@index([sessionId])` | 按会话查询 | 会话漏斗分析 |
| `@@index([entityType, entityId])` | 按实体查询 | 实体级分析（如产品热度） |
| `@@index([createdAt])` | 按时间查询 | 时序分析、定期清理 |
| `@@index([event, createdAt])` | 复合查询 | 事件趋势分析（最常见查询模式） |

### 5.3 Query Patterns

| Query | Use Case | Index Used |
|-------|----------|------------|
| `WHERE event = 'product_view' AND createdAt > NOW() - INTERVAL '7 days'` | 周产品浏览量 | [event, createdAt] |
| `WHERE userId = ? AND createdAt > NOW() - INTERVAL '30 days'` | 用户月行为轨迹 | [userId] |
| `WHERE entityType = 'PRODUCT' AND entityId = ?` | 产品热度 | [entityType, entityId] |
| `WHERE organizationId = ? AND event = 'inquiry_start'` | 供应商咨询入口量 | [organizationId] + [event] |
| `WHERE sessionId = ? ORDER BY createdAt` | 会话漏斗 | [sessionId] |

### 5.4 Retention Strategy

| Tier | Retention | Action |
|------|-----------|--------|
| Hot (0-30 days) | 保留全部 | 用于实时分析和 Dashboard |
| Warm (30-90 days) | 保留全部 | 用于月度报表和趋势分析 |
| Cold (90-365 days) | 聚合后保留 | 按天聚合 event count，删除原始事件 |
| Archive (>365 days) | 仅保留聚合数据 | 删除原始事件，保留年度统计 |

**建议**: M21.3.2 阶段仅实现 Hot/Warm（不实现自动清理），M21.3.3 BI Foundation 阶段实现 Cold 聚合，M21.3.5 后实现 Archive 策略。

### 5.5 Estimated Data Volume

| Metric | Estimate | Assumption |
|--------|----------|------------|
| Events per page view | ~3-5 | page_view + product_view + cta_click |
| Daily active users | ~100-500 | 早期阶段 |
| Daily events | ~500-2,500 | 保守估计 |
| Monthly events | ~15,000-75,000 | |
| Storage per event | ~200 bytes | 含 metadata JsonB |
| Monthly storage | ~3-15 MB | 可忽略 |

**结论**: PostgreSQL 足以承载当前和未来 12-24 个月的事件量，无需引入专用时序数据库或 OLAP 引擎。

### 6.1 API Endpoint Proposal

**Request Body**:

### 6.2 API Design Principles

| Principle | Implementation |
|-----------|---------------|
| **Batch Write** | 接受数组，单次请求写入多个事件（减少 HTTP 往返） |
| **Fire-and-Forget** | 客户端不等待写入结果，异步处理 |
| **No Read API** | M21.3.2 阶段仅实现写入，读取在 M21.3.3 BI Foundation 实现 |
| **No Auth Required** | 匿名事件允许（userId/organizationId 为 optional） |
| **Rate Limiting** | 简易速率限制（防止滥用），不实现复杂限流 |

## 8. Risk Assessment

| # | Risk | Level | Impact | Mitigation |
|---|------|-------|--------|------------|
| R1 | ConversionEvent 与 WorkflowEvent 职责重叠 | **中** | 同一业务行为（如 inquiry_submit）可能同时触发 ConversionEvent 和 WorkflowEvent，造成数据冗余 | 明确边界：ConversionEvent 记录用户行为（含匿名），WorkflowEvent 记录业务状态变更（含操作人）。允许重叠但用途不同 |
| R2 | 事件写入性能影响 API 响应时间 | **低** | 同步写入可能增加 API 延迟 | 事件写入使用异步队列/批量写入，不阻塞主请求 |
| R3 | 前端事件丢失（用户关闭页面） | **中** | page_view 等事件可能因页面卸载而丢失 | 使用 `navigator.sendBeacon()` 或批量上报策略 |
| R4 | ConversionEvent 表膨胀 | **低** | 长期运行后数据量增长 | 预留 TTL 策略，M21.3.3 实现聚合 |
| R5 | 匿名用户无法关联后续行为 | **中** | 未登录用户 sessionId 无法与登录后行为关联 | sessionId 跨登录保持，登录后将 userId 回填历史事件 |
| R6 | 超出 M21.3.2 范围进入 BI | **高** | 过早实现 Dashboard 或聚合查询 | 严格限定 M21.3.2 仅实现事件写入，禁止读取 API |
| R7 | Schema 变更影响现有 Migration 历史 | **低** | 新增 Model 不会影响现有 Migration | 新建 Migration 009，独立于现有 001-008 |
