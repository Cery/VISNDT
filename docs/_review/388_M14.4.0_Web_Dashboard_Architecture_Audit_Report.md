### Authentication Integration

Web auth is centralized in:

- `src/auth/AuthProvider.tsx`
- `src/auth/AuthGuard.tsx`
- `src/auth/RoleGuard.tsx`
- `src/services/auth.service.ts`
- `src/lib/api-client.ts`

Current mechanism:

1. Root layout mounts `Providers`, which includes both `QueryClientProvider` and `AuthProvider`.
2. `AuthProvider` calls `GET /auth/me` on mount and stores the result in React context.
3. Login/Register call backend auth APIs and rely on backend-set HttpOnly cookies.
4. `apiClient` uses `credentials: 'include'`, auto-refreshes via `/auth/refresh`, and attaches CSRF token for write requests.
5. Protected pages use `AuthGuard`; role-specific pages additionally use `RoleGuard`.

### API Client Structure

Current Web API access is split across:

- `src/lib/api-client.ts`
  - shared fetch wrapper
  - cookie auth
  - refresh retry
  - CSRF support
- `src/lib/api/*.ts`
  - domain-oriented API clients such as `demands.ts`, `rfqs.ts`, `notifications.ts`
- `src/services/*.ts`
  - thin page-facing wrappers over domain API clients

Current finding:

- There is **no dedicated Workspace API client** under `src/lib/api/` or `src/services/`.
- Existing workspace/dashboard pages still read from domain endpoints such as:
  - `GET /demands/my`
  - `GET /rfqs/mine`
  - `GET /rfqs/available`
  - `GET /rfq-responses/mine`
  - `GET /notifications/unread-count`
  - `GET /inquiries/mine`

This does not yet satisfy the M14.4 rule that Workspace API should be the only dashboard aggregation source.

## Auth Integration Review

### Existing Login Flow

Current login flow:

1. User submits `/login`
2. `useAuth().login()` calls `POST /auth/login`
3. Backend sets `access_token` and `refresh_token` as HttpOnly cookies
4. `AuthProvider` stores returned `user`
5. Login page redirects to `/workspace/dashboard`

### Token Storage

Current token model is cookie-based:

- No `localStorage`
- No manual token persistence in Web
- Requests use `credentials: 'include'`
- Expired access token is retried through `/auth/refresh`

This is aligned with keeping auth logic out of dashboard page code.

### User Context

`AuthUser` in Web already includes:

- `id`
- `email`
- `name`
- `organizationId`
- `organization`
  - `id`
  - `name`
  - `type`
- `organizationMember`
  - `role`
- `workspaceRole`

### Role Detection

Role detection is backend-derived, not frontend-invented.

Backend `AuthService` resolves:

- `organization.type = BUYER` -> `workspaceRole = BUYER`
- `organization.type = SUPPLIER | MANUFACTURER | DISTRIBUTOR` -> `workspaceRole = SUPPLIER`

Frontend uses `RoleGuard` and `WorkspaceSidebar` navigation off that `workspaceRole`.

### Organization Information Availability

Audit result:

- Web can identify `BUYER`
- Web can identify `SUPPLIER`
- Web can access `organizationId`
- Web can access organization display data

Conclusion:

The current auth payload is sufficient for dashboard route gating and organization-scoped API selection.

## Dashboard Route Design

This section is design only. No route implementation is performed in this task.

### Proposed Routes

- Buyer Dashboard: `/dashboard/buyer`
- Supplier Dashboard: `/dashboard/supplier`

### Buyer Route Design

Route: `/dashboard/buyer`

- Page responsibility:
  - Present buyer workspace summary only
  - Show demand overview cards
  - Show recent buyer demands
  - Show pending RFQ response decisions
  - Provide navigation entry points to existing buyer workspace detail pages
- API dependency:
  - `GET /workspace/buyer/overview`
  - `GET /workspace/buyer/demands`
  - `GET /workspace/buyer/pending-decisions`
- Permission requirement:
  - authenticated user
  - `workspaceRole = BUYER`
  - valid `organizationId`

### Supplier Route Design

Route: `/dashboard/supplier`

- Page responsibility:
  - Present supplier workspace summary only
  - Show targeted RFQ inbox snapshot
  - Show submitted response tracking snapshot
  - Provide navigation entry points to existing supplier workspace detail pages
- API dependency:
  - `GET /workspace/supplier/overview`
  - `GET /workspace/supplier/rfqs`
  - `GET /workspace/supplier/responses`
- Permission requirement:
  - authenticated user
  - `workspaceRole = SUPPLIER`
  - valid `organizationId`

### Route Planning Notes

Recommended planning principles:

1. Dashboard route should stay presentation-only.
2. Dashboard page should consume workspace aggregation APIs directly.
3. Existing write operations should remain in current domain pages such as demands, rfqs, and responses.
4. Role-based redirect entry can be added later from a neutral `/dashboard` route, but should not duplicate dashboard business logic.

## Frontend Risk Assessment

### 1. Missing Workspace API Client Capability

Risk Level: High

Evidence:

- No `workspace.ts` client exists under `src/lib/api/` or `src/services/`
- Current dashboard/workspace pages aggregate through multiple legacy endpoints

Impact:

- Violates the M14.4 architecture rule that Workspace API is the single aggregation source
- Encourages page-level data stitching and future duplication of backend business semantics

### 2. Existing Dashboard Route Semantics Are Split

Risk Level: High

Evidence:

- `/workspace/dashboard` is buyer-only
- `/workspace/supplier` is supplier-only but not a real dashboard
- `/dashboard` currently redirects only to `/workspace/dashboard`

Impact:

- Route meaning is inconsistent between buyer and supplier
- Future dashboard entry behavior will be ambiguous unless role-based routing is normalized

### 3. Layout Boundary Is Not Isolated

Risk Level: Medium

Evidence:

- Root layout always renders `PublicHeader` and `PublicFooter`
- Workspace shell is page-local instead of being handled by a dedicated nested layout

Impact:

- Dashboard UX may inherit public-site chrome unintentionally
- App-shell consistency and route-level composition are harder to control

### 4. CSR-Heavy Workspace Rendering

Risk Level: Medium

Evidence:

- Workspace pages are client components
- Data is loaded after mount with `useEffect` in several pages

Impact:

- First paint may show loading placeholders before auth/data resolution
- SEO is not a goal for dashboard pages, but perceived performance and route flicker need attention

### 5. Mixed Data Fetching Patterns

Risk Level: Medium

Evidence:

- React Query is available globally
- Workspace pages still mix raw `useEffect + useState` and React Query

Impact:

- Cache behavior, refetch behavior, and error handling are inconsistent
- Dashboard implementation may diverge further without a single fetching convention

### 6. Existing Supplier Pages Use Legacy Domain Views

Risk Level: Medium

Evidence:

- `/workspace/supplier/rfqs` uses `GET /rfqs/available`
- `/workspace/supplier/responses` uses `GET /rfq-responses/mine`

Impact:

- Supplier dashboard may be tempted to reuse generic lists instead of workspace-scoped aggregates
- This weakens the presentation-layer boundary

### 7. Dirty Working Tree During Audit

Risk Level: Low

Evidence:

- Repository currently contains existing modified and untracked files outside this task

Impact:

- Audit conclusions remain valid
- But later implementation should avoid mixing M14.4 changes with unrelated in-flight files

## Conclusion

Current audit conclusion: **ARCHITECTURE READY WITH FRONTEND INTEGRATION GAPS**

Summary judgment:

1. Web already has enough auth context to distinguish `BUYER`, `SUPPLIER`, and `organizationId`.
2. Backend workspace aggregation APIs required by M14.4 already exist and match the planned buyer/supplier dashboard responsibilities.
3. The main gap is in Web integration, not backend capability.
4. Dashboard implementation should add route-level presentation pages that consume only `workspace/*` read APIs.
5. Implementation should avoid reusing legacy dashboard aggregation through `demands`, `rfqs`, `rfq-responses`, and `inquiries` endpoints.
