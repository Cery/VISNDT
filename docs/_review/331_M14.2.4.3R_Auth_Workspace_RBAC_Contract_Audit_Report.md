## 2. Executive Summary

本次双路只读复核后，3 个候选点中有 3 个成立，其中：

- High：1 项

结论不是“文档表述偏差”，而是已经能够落成真实运行行为的代码问题：

1. 后端 `resolveWorkspaceRole` 将所有非 `SUPPLIER` 的组织类型统一映射为 `BUYER`，而数据库与创建入口允许任意字符串类型，已可证明存在 `MANUFACTURER` 这类供应侧类型输入。
2. 前端 `RoleGuard` 与 `WorkspaceSidebar` 对 `workspaceRole` 统一回退到 `BUYER`，会把“角色缺失/未识别”静默转成采购侧体验。
3. Auth 控制器真实返回的是 `ApiResponse.ok(...)` 包装后的 Cookie Auth 响应，但 Swagger/DTO 仍声明 `AuthResponseDto.accessToken` 等非真实 JSON 包体字段，`/auth/me` 也遗漏包装层。

## 4. Findings

### High-1 非 `SUPPLIER` 供应侧组织会被确定性降级为 `BUYER`

严重度：High

证据链：

1. `Organization.type` 在 Prisma 中是普通 `String`，没有枚举约束：`database/prisma/schema.prisma:205-209`
2. 创建组织 DTO 仅做 `@IsString()` 校验，没有类型白名单：`apps/api/src/organizations/dto/create-organization.dto.ts:4-11`
3. 组织创建服务直接 `this.prisma.organization.create({ data: dto })` 持久化输入：`apps/api/src/organizations/organizations.service.ts:98-100`
4. 测试数据脚本实际写入 `MANUFACTURER`：`create_test_data.ps1:64-78`, `83-98`
5. Auth 角色推导只识别 `SUPPLIER`，其余非空组织类型全部回退为 `BUYER`：`apps/api/src/auth/auth.service.ts:249-266`

影响：

1. 只要用户不是组织成员 `ADMIN`，且组织类型不是字面量 `SUPPLIER`，`workspaceRole` 就会被返回为 `BUYER`
2. 这会直接影响 Supplier 页面守卫和侧边导航选择
3. 对供应侧但使用其他类型值的组织，问题是实打实的角色映射错误，不是纯文档问题

边界说明：

- 不能夸大成“所有 `MANUFACTURER` 用户都已错误”，因为 `organizationMemberRole === ADMIN` 时会先短路成 `ADMIN`：`apps/api/src/auth/auth.service.ts:253-255`
- 但可以确认：对任意非 Admin 成员，且组织类型为 `MANUFACTURER` 等非 `SUPPLIER` 值时，该错误必然成立

### Medium-2 前端把缺失/空 `workspaceRole` 静默回退为 `BUYER`

严重度：Medium

证据链：

1. 后端明确允许 `workspaceRole` 返回 `null`：`apps/api/src/auth/auth.service.ts:257-259`
2. 前后端类型也都声明 `workspaceRole` 为可选且可空：
   - `apps/api/src/auth/dto/auth-response.dto.ts:46-51`
   - `apps/api/src/auth/interfaces/auth-request.interface.ts:17`
   - `apps/web/src/services/auth.service.ts:11-35`
3. `RoleGuard` 对已登录用户使用 `user.workspaceRole ?? 'BUYER'`：`apps/web/src/auth/RoleGuard.tsx:21-22`
4. `WorkspaceSidebar` 同样使用 `user?.workspaceRole ?? 'BUYER'` 并回退到采购侧导航：`apps/web/src/components/workspace/WorkspaceSidebar.tsx:49-50`
5. Supplier 页面统一依赖 `RoleGuard roles={['SUPPLIER']}`：
   - `apps/web/src/app/workspace/supplier/page.tsx:21`
   - `apps/web/src/app/workspace/supplier/rfqs/page.tsx:64`
   - `apps/web/src/app/workspace/supplier/responses/page.tsx:79`
   - `apps/web/src/app/workspace/supplier/rfqs/[id]/page.tsx:159`

影响：

1. 当 `workspaceRole` 缺失、为空或被后端错误映射时，前端不会进入“未知角色/待补全上下文”状态，而是直接当成 `BUYER`
2. Supplier 用户会被拒绝访问供应商页面，同时看到采购侧导航
3. 这会掩盖后端契约缺口，使问题表现为“页面走错”而不是“角色上下文缺失”

审查判断：

- 该问题本身不是越权放大，而是错误默认值造成的错误放行方向与错误导航
- 它与 High-1 叠加后，会把后端角色映射错误直接投射到前端体验层

### Medium-3 Auth Swagger/DTO 与真实返回契约不一致

严重度：Medium

证据链：

1. `register/login/refresh` 在控制器中通过 Cookie 写入 token，返回 JSON 仅为 `ApiResponse.ok({ user: result.user }, ...)`：
   - `apps/api/src/auth/auth.controller.ts:74-80`
   - `apps/api/src/auth/auth.controller.ts:89-95`
   - `apps/api/src/auth/auth.controller.ts:104-115`
2. 统一响应包装结构定义为 `{ success, data, message, timestamp }`：`apps/api/src/common/dto/api-response.dto.ts:3-25`
3. 但 `AuthResponseDto` 仍声明 JSON 里存在 `accessToken`：`apps/api/src/auth/dto/auth-response.dto.ts:54-59`
4. `/auth/me` 的 Swagger 类型标为 `AuthUserDto`，但控制器真实返回仍是 `ApiResponse.ok(user)` 包装对象：`apps/api/src/auth/auth.controller.ts:128-136`
5. 前端服务已按包装层读取 `res.data`，说明仓库内真实消费契约是“包裹在 `ApiResponse.data` 里的用户对象”：`apps/web/src/services/auth.service.ts:56-75`, `92-95`

影响：

1. Swagger 与 DTO 会误导调用方认为登录/注册/刷新接口在 JSON 中直接返回 `accessToken`
2. `/auth/me` 的文档也会遗漏统一包装层
3. 该问题当前主要影响接口文档真实性、联调预期和后续生成式客户端，而不是本仓库内前端运行链路

## 8. 审查结论

本次 331 号审查确认：

1. `workspaceRole` 改造并非单纯文档补齐，而是已经引入了真实 RBAC 映射风险
2. 最大的运行时问题在于后端把开放式组织类型模型硬压成 `SUPPLIER / BUYER` 二值
3. 前端 `BUYER` 默认值会把这一后端问题继续放大为导航与页面访问偏差
4. Auth 契约文档当前不能直接代表真实接口返回，应以代码实现为准

因此，本轮审查建议后续收口顺序为：

1. 先修正 `workspaceRole` 推导与组织类型模型的对应关系
2. 再移除前端对未知角色的 `BUYER` 静默回退
3. 最后收口 Swagger / DTO，使接口文档重新与真实包体一致
