## 4. Product Architecture Audit

**Schema 关键模型**：`Product`、`ProductCategory`、`ProductMedia`、`ProductParameterValue`、`ParameterDefinition`、`ParameterGroup`、`ParameterOption`、`ProductParameterDefinition`。

**核心事实**：

- `Product` **无 organizationId**，只有 `createdById` 与 `status`（String，默认 DRAFT）。
- `/products` 系列路由：`GET /products`、`GET /products/:id` 公开；`POST/PATCH/DELETE /products` 均 `@Roles(Role.ADMIN)`，批量删除/批量改状态亦 ADMIN。
- 产品创建/编辑/删除：**仅 ADMIN**（[products.controller.ts](file:///f:/Desktop/VISNDT/VISNDT/apps/api/src/products/products.controller.ts)）。
- 产品状态流转：仅 `batch-status` 直接改 `status` 字符串，**无独立审核工作流**（对比 Content 的 submit/review/publish 流程）。

**当前模式判定：A — 平台标准产品库（Global Catalog）**

- Product 是平台级全局目录，不属于任何 Organization。
- 供应商通过 `Offer`（organizationId + productId，唯一约束 `[organizationId, productId]`）关联到全局产品，表达「哪个供应商提供这款产品」。

**当前真实生命周期**：

| 环节 | 谁 | 说明 |
| --- | --- | --- |
| 创建 | Admin | `POST /products`（ADMIN） |
| 编辑 | Admin | `PATCH /products/:id`（ADMIN） |
| 审核 | 无 | 仅 `batch-status` 改状态，无审核工作流 |
| 发布 | Admin | 状态改 `ACTIVE`（直接字段改动） |
| 删除 | Admin | `DELETE /products/:id`，关联数据保护 + `force` 级联 |
| 展示 | 公开 | `GET /products` / `GET /products/:id` 公开返回 |

## 5. Supplier Capability Audit

**Schema 关键模型**：`Organization`、`OrganizationMember`、`Offer`、`User`、`RFQResponse`、`RFQ`。

**供应商能力矩阵**：

| 能力 | 状态 | 依据 |
| --- | --- | --- |
| 创建产品 | ❌ | Product 创建仅 ADMIN，无 organizationId |
| 编辑产品 | ❌ | 同上 |
| 上传图片 | ⚠️ 仅 Admin 经产品媒体；供应商无产品级上传入口 | ProductMedia 由 Admin 管理 |
| 上传证书 | ⚠️ 同上（FileType.CERTIFICATE 存在，但非供应商自助） | ProductMedia / FileAsset |
| 维护资料 | ⚠️ 基础组织信息（Organization CRUD），无店铺/供应商主页 | organizations 模块 |
| 提交 Offer | ✅ | `POST /offers`（authenticated，org-scoped） |
| 响应 RFQ | ✅ | RFQResponse（SUBMITTED→VIEWED→ACCEPTED/REJECTED） |
| 查看机会 | ✅ | RFQ 定向 + Workspace 供应商 RFQ 页面 |
| 管理组织信息 | ✅ | Organization / OrganizationMember |

**双管理模式评估**：

- 当前实际是「**平台集中管理 + 供应商 Offer 参与**」：管理员维护全局产品目录与发布，供应商只在全局产品上挂 Offer、响应 RFQ。
- 未来若要完整双管理（管理员审核发布 + 供应商自助提交产品/图片/证书/参数），需要：
  - `Product.organizationId`（或将产品归属供应商），或
  - `Product + Offer + SupplierProfile` 混合模型（产品=平台标准，Offer/供应商资料=供应商侧）。
- **本阶段仅做架构评估，不实施**。建议：优先保留「平台标准产品库 + Offer 供应商挂载」的现状，避免为供应商开放产品创建，以维持目录质量与一致性；若业务需要供应商自助，再评估 `Product.organizationId` 或引入 `SupplierProfile`。

## 6. Supplier Product Display Experience Audit

**核心场景**：多个供应商拥有相同基础产品（如「工业视频内窥镜」：手持/6mm/100万像素），但外观图、功能、参数、认证、服务不同。

**当前模型**：

- `Product`（全局标准产品，含共同参数）→ `Offer`（供应商挂载：title/description/price/currency/status）。
- 产品详情页 `findOne` 虽 `include offers → organization`，但页面渲染时 `ManufacturerInfo` 被传 `organization={null}`（[products/[slug]/page.tsx](file:///f:/Desktop/VISNDT/VISNDT/apps/web/src/app/products/[slug]/page.tsx)），即**不展示任何供应商信息**。
- 询价链路仅取「第一个 ACTIVE/SUBMITTED Offer」路由到 `InquirySection`，**不提供多供应商选择/对比**。

**当前支持程度：Low**

- 不支持「产品族(Product Family) → 产品型号(Product Model) → 供应商版本(Supplier Offering)」层级展示。
- 仅能表达「Product + Offer」模式，且前端未把 Offer/供应商版本呈现给用户。

**未来展示模型建议**（仅建议，不实施）：

1. 产品详情页将 `offers`（含 organization）真实渲染为「**供应方 / 报价列表**」，支持按供应商查看参数差异、认证、服务能力。
2. 引入「参数对比」视图：同一 Product 下多个 Offer 的差异参数并排对比。
3. 若需完整产品族，可评估 `ProductCategory` 层级 + 子型号（`Product.model` 已存在，可承载型号维度），供应商版本收敛到 Offer。
4. 询价改为「选择目标供应商」而非自动取第一个 Offer。

## 8. Matching Capability Audit

**链路**：`Demand` → `MatchingService.match` → `Product` → `Offer` → `DemandMatch`。

**关键证据**（[matching.service.ts](file:///f:/Desktop/VISNDT/VISNDT/apps/api/src/matching/matching.service.ts)）：

- 候选：`status=ACTIVE` 且有 `ACTIVE Offer` 的产品，按 Demand 分类过滤。
- 评分：`ScoringService.calculateScore` 加权（`weighted_v1`），基于参数匹配度、required、priority、硬约束（hardFail）。
- **参数共享**：Demand 的 `DemandParameter` 与 Product 的 `ProductParameterValue` 均引用同一 `ParameterDefinition`，**共享参数定义体系** ✅。
- 过滤低分、按分数降序、限量、upsert 到 `DemandMatch`。
- 状态机：PENDING → REVIEWED → ACCEPTED/REJECTED，组织作用域校验。

**Matching 成熟度：Medium**

- 具备可用的规则化加权匹配（结构化参数、共享定义、硬约束、评分明细）。
- 仍属确定性规则匹配，无语义/向量/学习能力。

## 13. Architecture Risks

1. **供应商展示断层**：产品详情不展示供应商/Offer，与「供应商体系」能力脱节，制约转化。
2. **产品无审核工作流**：`status` 直接改动，无提交/审核/发布审计，产品质量控制薄弱（对比 Content 有完整 WORKFLOW）。
3. **搜索能力闲置**：后端参数/范围筛选已实现，前端未消费，形成「后端能力 > 前端体验」缺口。
4. **产品族/型号缺失**：模型无法表达「产品族 → 型号 → 供应商版本」，多供应商同款产品无法对比。
5. **AI 零设施**：为 AI 做好准备的后端数据存在，但无向量/语义基础设施，AI 应用需从零搭建。
6. **未提交状态**：M18.5.3 的 SEO 面板改动尚未提交（多文件 modified/untracked），存在提交遗漏风险。
