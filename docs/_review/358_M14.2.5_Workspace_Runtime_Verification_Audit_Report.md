## 5. API Client Integrity

整体结论：

1. `demands`、`rfqs`、`matches`、`notifications` 相关前端调用未发现已删除接口或明显 404 断链

|Workspace 页面/能力|前端调用路径|后端 endpoint|结论|

|Demands 列表|`services/demand.service.getDemands()` -> `lib/api/demands.getMyDemands()`|`GET /demands/my`|OK|

|Demand 详情|`services/demand.service.getDemand()` / `getDemandMatches()`|`GET /demands/:id` / `GET /demands/:id/matches`|OK|
|RFQ 列表|`services/rfq.service.getRfqs()` -> `lib/api/rfqs.getMyRfqs()`|`GET /rfqs/mine`|OK|
|RFQ 创建|`lib/api/rfqs.createRfq()`|`POST /rfqs`|OK|
|RFQ 详情主体|`services/rfq.service.getRfq()` -> `lib/api/rfqs.getRfq()`|`GET /rfqs/:id`|OK|
|RFQ 详情-响应详情|`services/rfq.service.getRfqResponses()` -> `getMyRfqResponses()` -> `GET /rfq-responses/mine`|后端同时提供 `GET /rfqs/:id/responses`|Risk|

## 7. Risk List

### High

1. `/workspace/rfqs/[id]` 的“响应详情”调用链与后端接口语义不一致
   - 证据：
     - 前端页面在 [rfqs/[id]/page.tsx:L29-L44](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/app/workspace/rfqs/[id]/page.tsx#L29-L44) 调用 `getRfqResponses(1, 50)` 后按 `rfqId` 过滤
     - `getRfqResponses()` 实际在 [rfq.service.ts:L62-L67](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/services/rfq.service.ts#L62-L67) 中别名到 `getMyRfqResponses()`
     - `getMyRfqResponses()` 对应 [rfqs.ts:L184-L193](file:///F:/Desktop/VISNDT/VISNDT/apps/web/src/lib/api/rfqs.ts#L184-L193) 的 `GET /rfq-responses/mine`
     - 后端 `findMine()` 在 [rfq-responses.service.ts:L62-L89](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.service.ts#L62-L89) 按 `organizationId` 查询
     - 后端已存在按 `rfqId` 查询的正确接口 [rfq-responses.controller.ts:L17-L22](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfq-responses/rfq-responses.controller.ts#L17-L22)
   - 影响：
     - RFQ 详情页的响应列表可能不是“当前 RFQ 的全部响应”，而只是“当前组织的响应记录里被前端过滤出来的一部分”
     - 当响应数量超过分页上限或组织语义不匹配时，页面可能展示不完整或错误的数据

### Medium

1. Workspace 路由命名空间与 Sidebar 入口存在不一致

     - 后续若继续按 `/workspace/*` 规则扩展审计或权限控制，容易遗漏 Buyer 仪表盘入口
