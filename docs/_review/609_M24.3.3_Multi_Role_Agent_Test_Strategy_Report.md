## 1. 执行摘要

本任务建立 VISNDT 全平台**多角色 Agent 测试体系**，使系统在 612 / 613 UI 优化完成后，能够从四类视角（Anonymous Visitor / Buyer / Supplier / Admin）系统化验证页面完整性、功能可用性、业务流程闭环、UI/UX 体验、数据完整性、权限边界与架构冻结边界。

核心结论：

1. **测试体系 = 6 个 Agent**（1 Supervisor + 4 Role Agent + 1 Regression Report Agent），遵循「一 Agent 一视角一报告」原则。
2. **四角色严格对齐业务模型**：Visitor = 能力发现；Buyer = 需求管理；Supplier = 能力提供商（`Supplier != Store Owner`）；Admin = 工业运营控制中心（非默认 AntD）。
3. **统一测试报告格式（10 段）** + **统一优先级（P0/P1/P2/P3）**，保证跨角色可比、可汇总。
4. **测试数据依赖已识别**，缺口（测试账号 / 媒体资源 / 产品图片 / 知识关联 / 供应能力 / 业务状态数据）整体移交 611 Test Data Finalization 处理，本任务**只分析不创建**。
5. **架构冻结边界全程生效**：Agent 测试必须把「Product = Global Catalog / Supplier = Capability Provider / Search = Industrial Capability Discovery / AI = Frozen / Matching = Deterministic」作为**验证断言**而非可选检查。

## 4. Agent Architecture（VISNDT Multi-Agent QA System）

```
                         QA Supervisor Agent（编排 / 汇总 / 判定）
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
  Visitor Agent              Buyer Agent                Supplier Agent
  （匿名访客，能力发现）       （需求方工作台，需求闭环）    （能力提供商工作台，供给闭环）
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    │
                             Admin Agent
                       （工业运营控制中心，治理闭环）
                                    │
                          Regression Report Agent
                      （跨角色汇总 / 架构边界审计 / 优先级裁定）
```

### 4.1 职责分工

| Agent | 角色定义 | 核心验证目标 | 输出物 |
|---|---|---|---|
| QA Supervisor Agent | 编排层 | 分配测试范围、合并四角色报告、裁定 P0/P1、输出阶段测试结论 | Phase Test Summary |
| Visitor Agent | Anonymous Visitor | Public Platform Experience（发现 / 导航 / 理解 / 转化入口 / 移动端） | Visitor Test Report |
| Buyer Agent | Buyer | Demand Side Workspace（注册 / 登录 / 需求 / RFQ / 匹配 / 通知 / 询价 / 资料） | Buyer Test Report |
| Supplier Agent | Supplier（Capability Provider） | Capability Provider Workspace（能力展示 / Offer / RFQ 响应 / 询价响应 / 组织 / 通知），验证 `Supplier != Store Owner` | Supplier Test Report |
| Admin Agent | Admin | Industrial Operation Console（12 模块治理） | Admin Test Report |
| Regression Report Agent | 回归层 | 汇总五份报告 → 跨角色数据一致性 + 架构边界 + 优先级裁定 | Regression Report |

### 4.2 Agent 生命周期

每个 Role Agent 遵循统一生命周期，保证可复现、可追踪：

```
Prepare（读取 607 现状 + 608 目标 + 本测试报告范围）
   ↓
Execute（按测试矩阵逐项验证，记录 Evidence）
   ↓
Classify（P0/P1/P2/P3 分类）
   ↓
Report（按 §5 统一 10 段格式输出）
   ↓
Archive（报告归档至 docs/_review，供 Regression Report Agent 汇总）
```

## 5. Role Test Matrix（四角色测试矩阵）

### 5.1 Agent 1 — Anonymous Visitor Agent

| 项 | 值 |
|---|---|
| 验证 | Public Platform Experience |
| 覆盖页面 | Homepage、Product Center（/products）、Category（/categories）、Search（/search）、Solution（/solutions）、Knowledge Center（/knowledge-base、/knowledge）、Business（/business）、About（/about）、Inquiry Entry |
| 关注点 | Discovery Flow、Navigation、Content Understanding、Conversion Entry、Mobile Experience |

验证清单（关键断言）：

1. **首页**：Hero 保留；章节叙事顺序 = 能力分类 → 热门设备 → 解决方案 → 撮合流程 → 知识入口 → 供应能力（Capability Provider，非店铺）→ 需求入口。
2. **产品中心**：表现为 Global Capability Catalog（能力目录），卡片突出「检测能力参数」而非商品属性；无价格/库存/销量/购物车/下单按钮。
3. **搜索**：表现为 Industrial Capability Discovery（五段链：Header → Landing → Result → Facet → 下钻）；结果多实体分区（Product / Knowledge / Solution / Supplier Capability）；Supplier 结果为 Capability Provider 卡片（非店铺卡片）。
4. **转化入口**：仅允许「询价 Inquiry」与「提交需求 Demand」，无任何交易/商城入口。
5. **移动端**：导航 / 筛选 / 卡片 / 触摸目标（44px）在移动断点可用。

### 5.2 Agent 2 — Buyer Agent

| 项 | 值 |
|---|---|
| 验证 | Demand Side Workspace |
| 覆盖 | Register、Login、Workspace Dashboard、Demand、RFQ、Match、Notification、Inquiry、Profile |
| 验证流程 | 需求创建 → 需求管理 → 询价流程 → RFQ 流程 → 通知闭环 |

验证清单（关键断言）：

1. **注册/登录**：注册 → 登录 → Cookie/Refresh 会话保持 → 登出，全链路无 401 误伤。
2. **概览** `/workspace/dashboard`：需求 / RFQ / 匹配状态一览（StatCard），数据与 Demand/RFQ/Match 实际一致。
3. **需求** `/workspace/demands`（create / [id] / edit）：参数化需求表达；创建 → 保存 → 发布 → 匹配联动闭环。
4. **RFQ** `/workspace/rfqs`（[id]）：RFQ 追踪（状态徽章），与 RFQResponse 决策状态一致。
5. **匹配** `/workspace/matches`（[matchId]）：匹配结果 + 分数；Matching 确定性（Demand Parameters → Product Parameters → Score → Match，无 AI/Knowledge 参与评分）。
6. **通知** `/workspace/notifications`：业务通知闭环（触发 → 可见 → 已读）。
7. **设置** `/workspace/settings`：账户/组织信息可读可改。

## 6. Unified Test Report Format（统一测试报告格式）

所有 Role Agent 输出严格遵守以下 10 段格式：

```
1. Current State              当前状态（被测页面/模块的现状基线）
2. Test Scope                 测试范围（页面 / 交互 / 数据 / 权限）
3. Functional Coverage        功能覆盖（逐功能点 PASS / FAIL / SKIP）
4. Page / Interaction Validation  页面与交互验证（布局 / 组件 / 点击 / 状态反馈）
5. Data Validation            数据验证（字段完整性 / 一致性 / 关联正确性）
6. Permission Validation      权限验证（角色边界 / 越权 / 未授权访问）
7. UX Issue List              UX 问题清单（含 Evidence 与复现路径）
8. Architecture Risk          架构风险（是否触碰冻结边界）
9. Improvement Recommendation 改进建议
10. Priority Classification   优先级分类（P0 / P1 / P2 / P3）
```

## 10. Media Strategy（媒体验证策略）

测试体系必须覆盖 Media 生命周期五段：

```
Create → Attach → Display → Fallback → Cleanup
```

| 环境 | Placeholder / Storage 方案 |
|---|---|
| 开发阶段 | `https://picsum.photos/` 作为 Placeholder Provider（占位图，稳定可访问） |
| 生产 | `FileAsset` + `S3 Compatible Storage`（技术栈冻结的存储方案） |

验证断言：

1. **Create**：媒体上传（FileAsset 创建）成功。
2. **Attach**：媒体关联到 Product / Content（如 ProductMedia / ContentMedia）。
3. **Display**：详情页 / 卡片正确渲染真实媒体（`/files/:fileAssetId/download` 或预签名）。
4. **Fallback**：缺图时降级到「暂无图片」空态，不破坏布局。
5. **Cleanup**：媒体删除 / 孤儿文件清理（Admin FileAsset Orphan Cleanup）。

## 12. Improvement Direction（改进方向）

1. **测试执行前置条件**：611 必须先于 614，否则 Agent 测试因缺账号/媒体/业务数据无法执行。
2. **响应式一致性**：Visitor Agent 明确覆盖移动断点，避免桌面 PASS / 移动 FAIL 的遗漏。
3. **跨角色数据一致性**：Regression Report Agent 专项核对「Buyer 看到的需求 == Admin 看到的需求 == Supplier 收到的机会」。
4. **架构断言内置化**：将 §13 冻结边界转化为 Agent 测试的硬断言，而非人工判断。
