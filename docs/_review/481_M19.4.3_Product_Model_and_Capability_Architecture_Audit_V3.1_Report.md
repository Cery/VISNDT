**Product = Global Platform Catalog** — CONFIRMED. Product is not owned by any Organization. `createdById` is an audit trail, not a business ownership relation.

### 4.2 Indirect Supplier Relation

```
Product ──(1:N)──→ Offer ──(N:1)──→ Organization
```

The `Offer` model enforces `@@unique([organizationId, productId])`, meaning:
- One Organization can have **at most one Offer** per Product
- Multiple Organizations can have Offers on the same Product
- Product does NOT know which Organizations offer it (no back-reference in Product to Organization)

**Verified**: Product → Offer → Organization chain is intact. No direct Product → Organization path exists.

### 4.3 Offer Constraint Analysis

The `@@unique([organizationId, productId])` constraint on Offer has important architectural implications:

| Scenario | Supported? | Mechanism |
|----------|------------|-----------|
| Multiple suppliers offer same product capability | ✅ | Each supplier creates one Offer on the Product |
| One supplier offers multiple product variants | ✅ | Each variant = separate Product, each with its own Offer |
| One supplier offers the same product multiple times | ❌ | Blocked by @@unique constraint (desired behavior) |
| Different business users manage same supplier's capability | ✅ | Multiple Users belong to same Organization, share Offer |

**This constraint is architecturally correct**: it prevents duplicate offers and enforces the "one capability offering per supplier per product" model.

### 5.3 Scenario Validation Results

| Requirement | Supported? | Mechanism |
|-------------|------------|-----------|
| **多供应商提供同类产品能力** | ✅ PASS | Multiple Organizations create Offers on different Products in same category |
| **同一供应商存在多个型号** | ✅ PASS | Each model = separate Product, Supplier creates one Offer per Product |
| **不同业务员共享供应商能力** | ✅ PASS | Multiple Users in same Organization share Organization's Offers |
| **避免平台产品重复** | ✅ PARTIAL | `@@unique([organizationId, productId])` prevents duplicate offers; but no unique constraint on (name, model) — Product name duplication is a governance concern, not a schema defect |

### 5.4 Product Deduplication Analysis

The scenario requirement "避免供应商A创建一个产品，供应商B再次创建同名产品" raises a governance concern:

| Concern | Current State | Assessment |
|---------|---------------|------------|
| Product name uniqueness | No DB constraint on (name, model) | Acceptable — Product is platform-managed, Admin creates products, not suppliers |
| Supplier creates product | Not supported — Product.createdById is audit only, no supplier self-service product creation | Correct — Product creation is Admin governance |
| Duplicate product names | Possible at DB level | **Future Candidate**: Add `@@unique([name, model])` if needed, but current Admin governance is sufficient |

**Conclusion**: Product duplication is prevented by the architecture itself — suppliers do NOT create Products. They only create Offers on existing Products. Product creation is Admin-governed. This is the correct architectural separation.

**Assessment**: The parameter system fully supports industrial inspection equipment parameterization. The `value` (String) + `valueNumber` (Float) dual-field design elegantly handles both display and search.
