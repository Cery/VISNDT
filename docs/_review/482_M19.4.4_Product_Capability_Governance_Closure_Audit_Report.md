## 4. Final Architecture Decision

### 4.1 Product: Global Catalog

```
Product = Platform Global Catalog
  ├── category: ProductCategory (tree)
  ├── parameterValues: ProductParameterValue[] (typed, indexed)
  ├── media: ProductMedia[] (FileAsset-backed)
  ├── offers: Offer[] (capability mapping)
  └── demandMatches: DemandMatch[] (matching)

FORBIDDEN:
  Product.organizationId  ❌
  Product.supplierId      ❌
  Product.ownerId         ❌
  ProductFamily           ❌
  ProductModel (entity)   ❌
  SupplierOffering        ❌
```

**Decision**: Product remains Platform Global Catalog. Product ownership is not assigned to any Organization. Product.createdById is audit-only, not business ownership.

### 4.2 Supplier: Capability Provider

```
Supplier = Capability Provider
  ├── identity: Organization (name, type, status)
  ├── capability: Offer[] (productId → Product)
  └── members: OrganizationMember[] (multi-user)

NOT:
  Store Owner
  Marketplace Seller
  Inventory Owner
  Transaction Party
```

**Decision**: Supplier = Capability Provider. Supplier displays its capability through Offers on Platform Products. No Supplier Store, Shop, Catalog, or independent product inventory.

### 4.3 Offer: Capability Mapping Layer

```
Offer = Capability Mapping
  ├── organizationId → Organization (supplier)
  ├── productId → Product (capability)
  ├── title, description (capability expression)
  ├── price, currency (optional reference)
  ├── status: OfferStatus (DRAFT→ACTIVE→...→WITHDRAWN)
  └── @@unique([organizationId, productId])

ROLE:
  Bridge between Product (Global Catalog) and Organization (Supplier)
  One supplier can offer multiple products (1:N)
  Multiple suppliers can offer the same product (N:1)
  One supplier CANNOT offer the same product twice (unique constraint)
```

**Decision**: Offer is the capability mapping layer. It connects Product (what) to Organization (who). The `@@unique([organizationId, productId])` constraint correctly prevents duplicate offerings.

### 4.4 Parameter: Industrial Search Foundation

```
Parameter System:
  ParameterGroup → ParameterDefinition → ProductParameterValue

Data Types: STRING | NUMBER | BOOLEAN | ENUM

Search:
  - Exact match (value)
  - Range query (valueNumber: gte/lte)
  - AND combination (multiple parameterFilters)
  - Composite indexes: [parameterDefinitionId, value] + [parameterDefinitionId, valueNumber]

Coverage:
  固定参数 ✅ | 枚举参数 ✅ | 数值范围 ✅ | 布尔参数 ✅ | 组合能力 ✅
```

**Decision**: Parameter system is the industrial search foundation. 4 data types cover all industrial inspection equipment parameters. Dual-field design (value + valueNumber) supports both display and range search. No ParameterTemplate or SemanticAlias needed at current scale.

### 4.5 Search: Database Query First

```
Search Boundaries (M19.3 CLOSED):
  Product Search: GET /products (keyword + categoryId + parameterFilters)
  Supplier Capability: GET /organizations/:id + GET /offers?organizationId=
  Knowledge Search: GET /content/public (future planning)
  Matching Search: Demand → DemandMatch (RFQ Domain)

Strategy: Database Query First
  No Elasticsearch, Algolia, Meilisearch
  Upgrade only when data scale proves necessary
```

**Decision**: Search architecture frozen per M19.3 CLOSED. Database Query First is sufficient. Four search boundaries are strictly separated.

### 4.6 Matching: Weighted Scoring

```
Matching Flow:
  Demand.publish() → match() → Candidate Products → ScoringService.calculateScore()
  → DemandMatch (matchScore + matchDetails JSONB) → PENDING → REVIEWED → ACCEPTED/REJECTED
  → RFQ (sourceMatchId) → RFQResponse → WorkflowEvent

Scoring: Weighted parameter matching
  - DemandParameter (value/valueMin/valueMax/required/priority)
  - ProductParameterValue (value/valueNumber)
  - Category filter (Demand.categoryId)
  - Active status filter (Product.status='ACTIVE' + Offer.status='ACTIVE')
```

**Decision**: Matching architecture frozen. Weighted scoring is functional. AI scoring enhancement possible by replacing ScoringService implementation without schema change.
