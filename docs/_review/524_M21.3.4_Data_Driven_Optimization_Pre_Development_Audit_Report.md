## 10. Architecture Decision

### 10.1 Date Truncation Strategy

```
Decision: Use Prisma.$queryRaw with PostgreSQL DATE_TRUNC()

Rationale:
  - Prisma groupBy does not support date truncation natively
  - PostgreSQL DATE_TRUNC('day'/'week'/'month', createdAt) is standard
  - $queryRaw is safe with parameterized queries
  - No new dependency needed

Alternative considered: Application-level grouping (current approach)
  Rejected: Does not scale; loads all events into memory
```

### 10.2 Entity Name Resolution Strategy

```
Decision: Read-only JOIN via Prisma include/select

Rationale:
  - Product and Content models already have name fields
  - Use Prisma groupBy + separate findMany for name resolution
  - No new relation fields needed (ConversionEvent.entityId is a plain UUID)
  - Two-step: groupBy for counts → findMany for names

Alternative considered: Add relation fields to ConversionEvent
  Rejected: Would require schema change + migration (violates freeze)
```

### 10.3 Time Range Strategy

```
Decision: Add optional from/to query params to dashboard endpoint

Rationale:
  - Backward compatible (omit params = all-time, current behavior)
  - Enables Admin UI time range picker
  - Reduces query scope for large datasets
  - No new API endpoint needed
```
