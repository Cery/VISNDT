## 1. Executive Summary

VISNDT 从"工业设备展示平台"向"工业检测能力发现平台"的转型在**后端领域模型**层面已基本完成——Product = Platform Capability、SupplierProduct = Capability Model、Offer = Commercial Offer 的三层架构已正确实现，Search Service 和 Discovery Service 的注释与 DTO 均使用 Capability 术语。但**前端 UI 术语和 SEO 元数据**仍存在大量"设备/产品"残留，形成"后端说能力、前端说设备"的认知断层。

**核心判断**：平台已具备 Capability Domain 的正确架构骨架，但尚未完成面向用户的"概念翻译层"——即用户看到的仍是"产品目录/设备列表"，而非"能力发现平台"。后台 Admin 运营能力存在 Offer/Inquiry/RFQ 无编辑页、Product 编辑表单缺 slug/seoTitle 等 CRUD 缺口。

**关键风险**：SEO 元数据 `SITE_DESCRIPTION` 仍然描述为"工业无损检测设备平台"，搜索引擎会将 VISNDT 索引为"设备销售网站"而非"能力发现平台"，这是产品化上线前的 **P0 阻断项**。

## 4. Entity Relationship Audit

### 4.1 实际关系图（代码验证）

```
Product (Platform Capability) ───────────────┐
  │ id (UUID)                                  │
  │ categoryId → ProductCategory               │
  │ name, model, description, status            │
  │                                            │
  ├── ProductParameterValue[] ──→ ParameterDefinition[]
  ├── ProductMedia[] (CASCADE 删除)             │
  ├── SupplierProduct[] (platformProductId) ────┤
  │     │ brand, series, modelNumber            │
  │     │ status: DRAFT→...→PUBLISHED           │
  │     │                                       │
  │     ├── SupplierProductParameterValue[] ──→ ParameterDefinition[]
  │     ├── Offer[] (Restrict 删除)             │
  │     │     price, currency, status            │
  │     └── SupplierProductMedia[]              │
  │                                            │
  ├── Offer[] (productId, Restrict) ────────────┘
  ├── Inquiry[] (productId, NoAction)
  ├── DemandMatch[] (productId)
  └── ProductCategoryKnowledgeMapping[] (间接)
        └── KnowledgeCategory → KnowledgeEntry[]
```

### 4.2 关键发现

| 关系 | 删除策略 | 影响 |
|---|---|---|
| Product → ProductMedia | `Cascade` | ✅ 删除能力时自动清理媒体 |
| Product → ProductParameterValue | `Cascade` | ✅ 删除能力时自动清理参数 |
| Product → SupplierProduct | `Restrict` | ⚠️ 有已发布能力型号时无法删除能力（正确设计） |
| Product → Offer | `Restrict` | ⚠️ 有报价时无法删除能力 |
| SupplierProduct → Offer | `Restrict` | ⚠️ 有报价时无法删除能力型号 |

**Orphan Entities 检查**：
- ❌ **Solution（方案）**：已出现在搜索标签和首页中，但 schema.prisma 中**无独立 Solution 模型**。方案通过 Content（type=SOLUTION）实现，是 Content 子类型，非独立实体。这在架构上合理但**Admin 无方案管理独立入口**（Content 管理列表可筛选 SOLUTION 类型）。
- ✅ 所有其他实体均有明确的 Capability Domain 关联链。

### 4.3 缺少的关联

| 关联 | 状态 |
|---|---|
| Product → Knowledge（直接） | ❌ 不存在 — 通过 ProductCategory → ProductCategoryKnowledgeMapping → KnowledgeCategory → KnowledgeEntry 间接关联（ADM-M24-008/009/010 冻结设计） |
| Knowledge → Product（直接） | ❌ 不存在 — 同上，反向间接关联 |
