### 推荐修复方式

Precheck conclusion:

- `TD-006` requires **A. 页面级调整为主**.
- It is **not** a pure **B. 公共组件级调整** problem.

Reason:

1. `RoleGuard` itself is not executing requests; it only gates render output.
2. The actual leak window comes from page-local composition order: content component mounts before role gating.
3. Simply changing `RoleGuard` without restructuring page entry would not reliably prevent `useEffect` in already-mounted content components.

Recommended implementation shape:

- Keep `AuthGuard` as outer authentication gate.
- Move `RoleGuard` outside Supplier content component mount boundary, matching the Buyer control pattern.
- Prefer page entry wrappers such as:
  - `AuthGuard -> RoleGuard -> SupplierPageContent`
- Do not widen this task into a global guard refactor unless multiple pages can be normalized by a clearly reusable shell abstraction after page-level proof is complete.

## 6 Implementation Split Proposal

### Phase A1: TD-006 Access Boundary

- 修改目标
  - Normalize Supplier page entry composition so role validation happens before protected content mount
  - Cover at least:
    - `supplier/rfqs`
    - `supplier/responses`
    - `supplier/rfqs/[id]`
  - Keep compatibility shell `supplier/page` aligned if touched

- 风险
  - Page structure changes may affect loading state placement, fallback rendering, and shell composition
  - Over-generalizing into shared abstractions too early may widen scope beyond the validated Supplier pages

- 验证方式
  - Static code check: `AuthGuard -> RoleGuard -> PageContent` composition exists at page entry
  - Runtime verification target:
    - wrong-role authenticated user no longer triggers Supplier `useEffect` fetch before denial UI
  - Regression check:
    - Supplier authorized users can still load list/detail/response pages normally

### Phase A2: TD-001 Service Boundary

- 修改目标
  - Normalize the following pages to `page -> service -> api wrapper`
    - `demands/create`
    - `matches`
    - `notifications`
  - Fill service-layer gaps without introducing new business capability

- 风险
  - Service-layer extraction can accidentally mix orchestration, transformation, and UI concerns
  - Notifications is the widest delta because the service file is currently absent
  - Matches needs care to avoid partial normalization where reads and writes still diverge

- 验证方式
  - Import check:
    - target pages no longer directly import business API wrappers for covered actions
  - Static dependency check:
    - page imports service file; service file imports `@/lib/api/*`
  - Regression target:
    - create demand, update/rematch match actions, and notification read actions still resolve through existing API behavior

Recommended execution order inside Phase A:

1. A1 first
2. A2 second

Reason:

- Access-boundary timing is the higher-risk item.
- A1 is more localized and better suited as the first implementation proof.
- A2 can then proceed with cleaner page ownership and reduced scope ambiguity.
