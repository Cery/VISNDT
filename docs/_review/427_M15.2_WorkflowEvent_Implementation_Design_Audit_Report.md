## 4. WorkflowAction Design Proposal

### 4.1 Current State

当前 `WorkflowAction` 只有 9 个枚举值：

- `CREATED`
- `SUBMITTED`
- `OPENED`
- `RESPONDED`
- `ACCEPTED`
- `REJECTED`
- `CLOSED`
- `WITHDRAWN`
- `REVIEWED`

### 4.2 Problem Statement

需要判断这些 Action 是否足以表达：

- `MATCH_CREATED`
- `RESPONSE_CREATED`
- `OFFER_CREATED`
- `REMATCH`

### 4.3 Option Comparison

| 方案 | 描述 | 优点 | 风险 |
| --- | --- | --- | --- |
| 方案 A | 复用现有 `WorkflowAction` | 不需要改 enum；不需要 migration；更符合 M15 最小治理范围 | `rematch` 语义只能通过 metadata 表达，动作本身不够一眼可读 |
| 方案 B | 新增 Action，例如 `REMATCHED` / `PUBLISHED` / `STATUS_CHANGED` 等 | 业务语义更显式；未来跨域可读性更强 | 需要 schema/migration；会扩大 M15.2 范围；还会牵动历史事件命名治理 |

### 4.4 Coverage Evaluation

#### A. `MATCH_CREATED`

可由：

- `entityType = MATCH`
- `action = CREATED`

表达。

#### B. `RESPONSE_CREATED`

可由：

- `entityType = RFQ_RESPONSE`
- `action = CREATED`

表达。

#### C. `OFFER_CREATED`

可由：

- `entityType = OFFER`
- `action = CREATED`

表达。

#### D. `REMATCH`

这是当前唯一不完全适配现有枚举的动作，因为它更像：

- 一次“重新生成匹配结果”的业务触发原因
- 而不是所有实体都共享的稳定生命周期动作

在方案 A 下，`rematch` 只能被表达为：

- 新生成 `MATCH` 的 `CREATED`
- 并通过 `metadata` 标识其触发来源为 `rematch`

在方案 B 下，则可以新增显式 action，例如 `REMATCHED`。

### 4.5 Recommended Option

推荐：

`M15.2 采用方案 A：复用现有 Action，不新增 enum。`

推荐理由：

1. `MATCH_CREATED`、`RESPONSE_CREATED`、`OFFER_CREATED` 都已经可以被 `CREATED` 完整承载。
2. `M15.2` 当前目标是“补齐与收敛”，不是重新设计整个事件词汇表。
3. 新增 Action 会直接引入 schema/migration，不符合当前最小治理路径。
4. `rematch` 从架构上更像“触发原因”而不是跨域通用状态动作，优先作为 metadata 语义保留更稳妥。

补充建议：

- `M15` 内不新增 `WorkflowAction`
- `M16/M17` 若确定 `WorkflowEvent` 将成为 CMS/内容/SEO/运营主审计事实源，再评估是否升级为更显式的动作词表

## 5. Entity Subject Normalization Proposal

### 5.1 Current Conflict

当前 Match 相关事件存在两条主体口径：

- `matching.service.ts` 使用 `entityType = MATCH`：[`matching.service.ts:L363-L378`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/matching/matching.service.ts#L363-L378)
- `demands.service.ts:updateMatchStatus()` 使用 `entityType = DEMAND`：[`demands.service.ts:L723-L739`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/demands/demands.service.ts#L723-L739)

### 5.2 Candidate Comparison

| 候选 | 优点 | 问题 |
| --- | --- | --- |
| 方案 A: `entityType = MATCH` | 与真实发生状态变化的实体一致；便于形成完整 Match 时间线；更适合运营审计与后续跨域查询 | 需要 Demand 侧代码入口统一改口径 |
| 方案 B: `entityType = DEMAND` | 可以把 Match 视为 Demand 的附属子状态 | 会把 Match 生命周期混入 Demand 历史；难以支持后续独立报表、后台查询与跨域审计 |

### 5.3 Semantic Assessment

从业务语义看：

- 被创建、被审核、被接受、被拒绝的是 `DemandMatch`
- `Demand` 是聚合根，但不是本次发生状态变化的直接对象

从未来 CMS / SEO / 运营审计角度看：

- 未来系统实体只会更多，不会更少
- 如果当前允许“子实体状态变化挂在父实体上”，后续内容审核、发布、索引等实体也会复制这种混乱
- 运营侧若要按实体时间线追踪，`MATCH` 必须能被独立筛选、独立回放

### 5.4 Final Recommendation

推荐：

`统一采用方案 A：Match 事件主体统一为 MATCH。`

理由：

1. 事件主体应等于发生生命周期变化的直接实体。
2. `MATCH_CREATED`、`MATCH_REVIEWED`、`MATCH_ACCEPTED`、`MATCH_REJECTED` 可以形成单一时间线。
3. `DEMAND` 仍可在 metadata 中保留 `demandId`，但不应承担 Match 的主体角色。
4. 这也是 `415` Phase B 中 `MATCH event subject normalization` 的唯一稳定方向：[`415_M15.0_Technical_Debt_Governance_Planning_Report.md:L148-L157`](file:///F:/Desktop/VISNDT/docs/_review/415_M15.0_Technical_Debt_Governance_Planning_Report.md#L148-L157)
