## 3. Prisma AuditLog Analysis

### 3.1 Model Definition

```prisma
model AuditLog {
  id         String      @id @default(uuid()) @db.Uuid
  entityType String      @map("entity_type")
  entityId   String      @map("entity_id") @db.Uuid
  action     AuditAction
  operatorId String      @map("operator_id") @db.Uuid
  oldValue   Json?       @map("old_value") @db.JsonB
  newValue   Json?       @map("new_value") @db.JsonB
  createdAt  DateTime    @default(now()) @map("created_at")

  operator   User        @relation(fields: [operatorId], references: [id])

  @@index([entityType, entityId])   // Composite: query by entity
  @@index([operatorId])             // Single: query by operator
  @@index([action])                 // Single: filter by action type
  @@index([createdAt])              // Single: time-based queries
  @@map("audit_log")
}
```

### 3.2 AuditAction Enum

```prisma
enum AuditAction {

  DELETE
  STATUS_CHANGE

}
```

### 5.3 AuditLog Injection Points

Three strategies for automatic audit recording:

| Strategy | Injection Point | Pros | Cons |
|----------|----------------|------|------|
| **A. NestJS Interceptor** | Wrap controller methods | Centralized, non-invasive, captures response | Needs `@UseInterceptors` decorator, doesn't know old value |
| **B. Prisma Middleware** | `prisma.$use()` in PrismaService | Captures ALL mutations automatically, has old/new values | Complex — must filter events, parse Prisma args |
| **C. Service-Level Calls** | `this.auditLogService.log()` in each service | Explicit, controllable, can capture old value | Requires modifying every service (~10 files) |

### 5.4 Recommended Strategy: Hybrid (A + C)

| Component | Strategy | Reason |
|-----------|----------|--------|
| **CREATE events** | Prisma Middleware | Captures `args.data` as `newValue` |
| **UPDATE events** | Service-level | Must fetch old value before mutation |
| **DELETE events** | Service-level | Must fetch old value before deletion |
| **LOGIN events** | Service-level | Not a Prisma mutation — handled in auth.service |
| **STATUS_CHANGE events** | Service-level | May need custom logic |

## 9. Recommendation

### 9.1 Recommended Approach: Phased Implementation

| Phase | Scope | Rationale |
|-------|-------|-----------|
| **M13.2.3.1** | Backend — AuditLog query API only | Read-only, minimal risk, enables Admin page |
| **M13.2.3.2** | Admin — AuditLog List + Detail pages | Frontend-only, uses existing patterns |
| **M13.2.3.3** | Backend — Auto-recording (Prisma middleware) | Most complex, requires careful testing |
| **M13.2.3.4** | Admin — Filters, diff view, date range | Enhancement after recording works |

### 9.2 Decision Matrix

| Option | Pros | Cons |
|--------|------|------|
| **Go: Full Implementation** | Complete audit trail, compliance-ready | ~10h effort, Backend Unfreeze |
| **Go: Query API Only** | Admin page works, low risk | No auto-recording — audits must be manually written |
| **Skip** | No effort, no risk | Missing audit trail, no compliance |

### 9.3 Recommendation

**Go: Query API + Admin Pages (M13.2.3.1 + M13.2.3.2)**

Auto-recording (M13.2.3.3) can be added later in a separate phase. The immediate value is in being able to query existing audit logs if any exist, and being ready for when recording is implemented.

**Justification**:
1. The AuditLog model is already production-ready — no schema changes needed
2. Query API is low risk (read-only, no mutations)
3. Admin pages follow the established PageState pattern
4. Auto-recording can be phased in gradually (start with Products, expand)
5. The `oldValue`/`newValue` JsonB fields enable rich diff displays
