## 1. Executive Summary

M7.1 Organization Context 架构审查完成。核心结论：

- **Organization Context 策略**: MVP 使用 JWT `user.organizationId` (方案 A)，无需额外服务

## 2. Q1: Organization Context Resolution Strategy

### 2.1 方案对比

| 维度 | 方案 A: Direct JWT | 方案 B: Context Service | 方案 C: X-Org-Id Header |
|------|-------------------|------------------------|--------------------------|
| **实现方式** | `@CurrentUser().organizationId` | 新建 `OrganizationContextService` | Header `X-Organization-Id` |
| **复杂度** | 低 | 中 | 中 |
| **DB 查询** | 0 (JWT 自带) | 1 (验证 membership) | 1 (验证 header) |
| **多组织支持** | ❌ 仅 primary org | ✅ 可切换 | ✅ 可切换 |
| **M6 兼容** | ✅ 完全兼容 | ✅ 完全兼容 | ✅ 完全兼容 |
| **安全性** | 中 (JWT payload) | 高 (DB 验证) | 高 (需验证) |
| **MVP 适用** | ✅ **推荐** | ❌ 过度设计 | ❌ 过早 |

### 2.2 Decision: 方案 A (Direct JWT) for MVP

```typescript
// M7.1 Controller Pattern
@Post()
@UseGuards(JwtAuthGuard)
async create(
  @Body() dto: CreateDto,
  @CurrentUser() user: AuthRequest['user'],
) {
  // user.organizationId ← from JWT, no extra query
  return this.service.create(dto, user.organizationId);
}
```

### 2.3 为什么不需要 OrganizationContextService

| 理由 | 说明 |
|------|------|
| JWT 已携带 `organizationId` | `validateUser()` 已从 DB 加载，无需再查 |
| `RolesGuard` 已验证 membership | 到达 Controller 时，用户已通过 `JwtAuthGuard` + `RolesGuard` (if applicable) |
| 无多组织切换需求 (MVP) | 用户只有一个 primary org，无需切换上下文 |
| 避免额外 DB 查询 | 每次请求额外查 `OrganizationMember` 是浪费 |

### 2.4 未来扩展路径

```
MVP (M7.1):  JWT.organizationId → direct use
  │
  ▼
Future (M7.x): OrganizationContextService
  - 支持 X-Organization-Id header
  - 验证 user membership in target org
  - 缓存 active organization context
  - 不破坏 M6 Freeze (仅仅是新增服务)
```

### 4.2 M7.1 安全查询模式

#### 反模式 (当前 — 禁止)

```typescript
// ❌ WRONG: No org scoping
async update(id: string, dto: UpdateOfferDto) {
  await this.findOne(id);  // Finds ANY offer by id
  return this.prisma.offer.update({ where: { id }, data: dto });
}
```

#### 正模式 (M7.1 — 必须)

```typescript
// ✅ CORRECT: Org-scoped query
async update(id: string, dto: UpdateOfferDto, organizationId: string) {
  const offer = await this.prisma.offer.findFirst({
    where: { id, organizationId },
  });
  if (!offer) {
    throw new NotFoundException(`Offer ${id} not found`);
  }
  return this.prisma.offer.update({ where: { id }, data: dto });
}
```

### 4.3 Service 方法签名标准

```typescript

@Injectable()
export class SomeBusinessService {
  
  // Public: no auth needed
  async findAll(pagination: PaginationDto) { ... }
  async findOne(id: string) { ... }

  // Authenticated: needs user context
  async create(dto: CreateDto, user: AuthRequest['user']) {
    // Use user.id, user.organizationId
  }

  // Org-scoped: needs org ownership check
  async update(id: string, dto: UpdateDto, organizationId: string) {
    // Verify ownership before update
  }

  // Org-scoped delete

    // Verify ownership before delete
  }
}
```

## 5. Controller Authentication Patterns

### 5.1 Pattern 1: Public API

```typescript
// No auth required, no user context
@Get()
@ApiOperation({ summary: 'List all items' })
async findAll(@Query() pagination: PaginationDto) {
  return ApiResponse.ok(await this.service.findAll(pagination));
}
```

**适用于**: 产品浏览、目录查看、公开 RFQ 列表

### 5.2 Pattern 2: Authenticated User

```typescript
@Post()
@UseGuards(JwtAuthGuard)
@ApiBearerAuth()
@ApiOperation({ summary: 'Create a new item' })
async create(
  @Body() dto: CreateDto,
  @CurrentUser() user: AuthRequest['user'],
) {
  return ApiResponse.ok(
    await this.service.create(dto, user),
    'Created',
  );
}
```

**适用于**: 创建 Demand、创建 Offer、创建 RFQ

### 5.3 Pattern 3: Organization Admin

```typescript
@Patch(':id')
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(Role.ADMIN)
@ApiBearerAuth()
@ApiOperation({ summary: 'Update item (ADMIN only)' })
async update(
  @Param('id') id: string,
  @Body() dto: UpdateDto,
  @CurrentUser() user: AuthRequest['user'],
) {
  return ApiResponse.ok(
    await this.service.update(id, dto, user.organizationId!),
    'Updated',
  );
}
```

**适用于**: 管理 Offer、管理成员、发布 RFQ

### 5.4 Pattern 对比

| 维度 | Pattern 1: Public | Pattern 2: Authenticated | Pattern 3: Admin |
|------|-------------------|-------------------------|------------------|
| **Guard** | 无 | `JwtAuthGuard` | `JwtAuthGuard` + `RolesGuard` |
| **@CurrentUser()** | ❌ | ✅ | ✅ |
| **@Roles()** | ❌ | ❌ | `@Roles(Role.ADMIN)` |
| **@ApiBearerAuth()** | ❌ | ✅ | ✅ |
| **401 响应** | ❌ | ✅ (no token) | ✅ (no token) |
| **403 响应** | ❌ | ❌ | ✅ (non-ADMIN) |

## 6. Multi-Organization Future Compatibility

### 6.1 Current State

```
User
├── organizationId: Org-A (primary, nullable)
├── memberships[]:
│     ├── Org-A: ADMIN
│     └── Org-B: MEMBER
│
JWT: { sub, email, name, organizationId: "Org-A" }
```

### 6.2 Limitation

| 场景 | 能否支持 | 限制 |
|------|---------|------|
| 在 primary org 操作 | ✅ | `user.organizationId` = Org-A |
| 切换到 Org-B 操作 | ❌ | JWT 只有 Org-A，无法切换 |
| 查看所有 org 成员身份 | ❌ | JWT 不包含 memberships |

### 6.3 M7.1 MVP 决策

**Accept MVP limitation。** 理由：
- 新注册用户尚未加入任何 Organization (`organizationId = null`)
- 用户加入第一个 Organization 后，`organizationId` 被设置
- 大多数 MVP 用户只有一个 Organization
- 未来可以通过 `OrganizationContextService` 扩展，不破坏 M6 Freeze

### 6.4 未来扩展 (不阻塞 M7.1)
