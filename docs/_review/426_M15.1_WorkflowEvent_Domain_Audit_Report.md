## 3. Current WorkflowEvent Architecture

### 3.1 Data Model

当前 `WorkflowEvent` 为通用事件模型：

- `entityType`: `DEMAND | RFQ | RFQ_RESPONSE | OFFER | MATCH`
- `action`: `CREATED | SUBMITTED | OPENED | RESPONDED | ACCEPTED | REJECTED | CLOSED | WITHDRAWN | REVIEWED`
- `operatorId`: 强制记录操作人
- `metadata`: `JsonB` 承载上下文

对应证据：

- [`schema.prisma:L53-L81`](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L53-L81)
- [`schema.prisma:L608-L626`](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L608-L626)

### 3.2 Service Pattern

当前 WorkflowEvent 并不是统一事件总线，而是“由各个业务 Service 在关键动作后自行调用”的写入模式：

- Service 主动调用 `workflowEventsService.create(...)`
- 部分场景直接在事务内 `tx.workflowEvent.create(...)`
- `WorkflowEventsService.create()` 还要求调用用户带有 `organizationId`

对应证据：

- [`workflow-events.service.ts:L42-L53`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/workflow-events/workflow-events.service.ts#L42-L53)
- [`demands.service.ts:L331-L341`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/demands/demands.service.ts#L331-L341)
- [`rfqs.service.ts:L251-L262`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/rfqs/rfqs.service.ts#L251-L262)

### 3.3 Notification / Audit Relationship

当前系统不存在：

- `WorkflowEvent -> Notification` 的统一派发器
- `WorkflowEvent -> AuditLog` 的统一映射器
- `Notification.workflowEventId` 或 `AuditLog.workflowEventId` 之类的显式关联

实际实现是：

- Notification 由业务 Service 直接创建：[`notifications.service.ts:L177-L225`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/notifications/notifications.service.ts#L177-L225)
- AuditLog 由 Prisma 中间件独立记录：[`prisma.service.ts:L21-L41`](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/prisma/prisma.service.ts#L21-L41)

结论：

- `WorkflowEvent`、`Notification`、`AuditLog` 当前是并列体系，不是单一审计总线
- 关系判断：`C. 部分重复`

### 7.2 Biggest Gaps

当前最大缺口按优先级排序为：

1. 缺事件类型 / 缺触发点
   - `MATCH_CREATED`
   - `RESPONSE_CREATED`
   - `RFQ legacy create`
   - `Rematch`

2. 缺统一命名与主体归属
   - Match 状态变化在 `MATCH` 与 `DEMAND` 两个主体之间分裂

3. Notification 绕过 Event
   - 当前是业务 Service 直接发通知

   - 通用 `update()` / `batchStatus()` 仍可绕过专用 transition 语义

5. Cross-domain completeness pattern 已出现
   - Offer 域也复现了 create / generic mutation 缺事件、transition 才写事件的模式
   - 说明当前问题是架构级模式，而不只是单一业务域的遗漏

### 7.3 Database Adjustment Needed?

结论：

`当前 M15.2 若仅补齐现有业务域事件，不强制需要数据库调整。`

原因：

- 现有 `WorkflowEntityType` 与 `WorkflowAction` 已足以表达当前缺失的 `MATCH_CREATED`、`RESPONSE_CREATED` 等事件
- 当前问题主要在“写入时机”和“边界收敛”，不是 schema 无法承载

但从中长期看，数据库模型存在后续扩展压力：

- `Notification` 没有与 `WorkflowEvent` 的显式关联
- `AuditLog` 没有可靠的 before/after snapshot 机制
- `WorkflowEntityType` 尚未覆盖未来 CMS / Content / SEO 等实体

### 7.4 Impact on M16 / M17

结论：

`会影响。`

影响点如下：

1. `CMS 审核流`

2. `内容发布`

3. `SEO 状态`
   - 若后续引入 SEO 发布状态或索引状态，当前 WorkflowEvent/Notification/AuditLog 三套并行机制会增加治理成本
