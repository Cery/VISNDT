## 6. Lifecycle-aware CRUD Audit

### 6.1 Product 生命周期

| 状态 | 描述 | 状态机 |
|---|---|---|
| `DRAFT` | 草稿（创建默认） | → ACTIVE, → INACTIVE |
| `ACTIVE` | 活跃（前台可见） | → INACTIVE, → DRAFT |
| `INACTIVE` | 停用（前台不可见） | → ACTIVE |

**判决**：Product 状态机**过于简单**——缺少 `DEPRECATED`（能力被替代）和 guards。但 `DRAFT/ACTIVE/INACTIVE` 三态覆盖基本生命周期，作为 Capability 长期资产管理**基本满足**当前需求。`DEPRECATED` 是 Future Candidate。

### 6.2 SupplierProduct 生命周期

| 状态 | 描述 | 状态机（Guarded） |
|---|---|---|
| `DRAFT` | 草稿 | → SUBMITTED |
| `SUBMITTED` | 已提交 | → REVIEWING |
| `REVIEWING` | 审核中 | → APPROVED, → REJECTED |
| `APPROVED` | 已通过 | → PUBLISHED |
| `PUBLISHED` | 已发布（前台可见） | 终端状态 |
| `REJECTED` | 已驳回 | 终端状态 |

每个转换都有 guards 检查当前状态。例如 `submit()` 要求 `status === DRAFT`，`approve()` 要求 `status === REVIEWING`。

**判决**：✅ 完整且受保护的状态机。符合 Capability Model 审核流程。

### 6.3 Offer 生命周期

| 状态 | 描述 | 状态机（Guarded） |
|---|---|---|
| `DRAFT` | 草稿 | → SUBMITTED |
| `SUBMITTED` | 已提交 | → ACCEPTED, → REJECTED, → WITHDRAWN |
| `ACCEPTED` | 已接受 | 终端状态 |
| `REJECTED` | 已拒绝 | 终端状态 |
| `WITHDRAWN` | 已撤回 | 终端状态 |

**判决**：✅ 完整且受保护。Offer 是商业报价，不是可随意修改的"商品价格"——这是 Capability Discovery 的正确设计。

### 6.4 Demand 生命周期

| 状态 | 描述 | 状态机（Guarded） |
|---|---|---|
| `DRAFT` | 草稿 | → PUBLISHED |
| `PUBLISHED` | 已发布 | → CLOSED |
| `PROCESSING` | 处理中 | → CLOSED |
| `CLOSED` | 已关闭 | 终端状态 |
| `CANCELLED` | 已取消 | 终端状态 |

**判决**：✅ 完整且受保护。

### 6.5 关于 "Offer/Inquiry/RFQ 无编辑页" 的架构判断

704 将其列为 P1 Defect。本次加强版判断：

- **Offer**：有 `PATCH /offers/:id` 端点（Authenticated），Admin 可以通过 API 编辑。但 Admin UI 的 OfferDetail 是只读的。这是**UI 缺失**，不是 API 缺失。且 Offer 有完整的生命周期操作（submit/accept/reject/withdraw），商业报价的正确编辑方式是状态流转而非直接修改金额。**降级为 P2**。
- **Inquiry**：Inquiry 是 Buyer→Supplier 的询价记录，创建后应为**不可变**（审计要求）。后端无 PATCH 端点，正确。**降级为 Observation**。
- **RFQ**：RFQ 有生命周期操作（publish/close），与 Demand 联动。无独立编辑是**正确的**——RFQ 由 Demand 派生，编辑应通过 Demand 进行。**降级为 Observation**。

## 11. SEO Semantic Fit Assessment

### 11.1 当前 SEO 语义

| 元素 | 当前值 | 搜索引擎理解 |
|---|---|---|
| `<title>` | "VISNDT – 工业检测设备平台" | 设备销售平台 |
| `<meta description>` | "VISNDT是一个专业的工业无损检测设备平台——发现高精度内窥镜、检测相机和测量系统..." | 设备销售 + 具体产品类型 |
| `<meta keywords>` | 工业内窥镜, 无损检测, NDT, 检测设备, 内窥镜, 测量系统, 工业检测, VISNDT | 设备/产品导向，缺"能力" |
| JSON-LD Product | `@type: 'Product'` + name, description, model, brand, category | 电商产品页 |

### 11.2 架构判断

**`@type: 'Product'` 不是本质问题。** Schema.org 的 `Product` 类型是通用 schema，许多非电商平台（如技术文档站、开源项目）也使用它描述"产品/项目"。VISNDT 的 Product 页面确实在描述一个"工业检测能力定义"，使用 `Product` 类型在 schema.org 语义上是**可接受的**。

**真正的问题是 `SITE_DESCRIPTION` 和 `defaultTitle`**——它们用"设备"语言描述平台，导致搜索引擎将整个站点索引为"设备销售网站"。修改这两个字符串即可解决 SEO 语义问题，不需要改 JSON-LD 类型。

**704 的 P2-05 降级为 Observation**。

### 11.3 建议修改（仅文案，非代码变更）

| 元素 | 当前 | 建议 |
|---|---|---|
| SITE_DESCRIPTION | "工业无损检测设备平台——发现高精度内窥镜..." | "工业检测能力发现平台——发现检测能力、能力型号、技术知识与解决方案" |
| defaultTitle | "VISNDT – 工业检测设备平台" | "VISNDT – 工业检测能力发现平台" |
| SITE_KEYWORDS | 缺"能力"关键词 | 增加 "工业检测能力", "能力发现", "capability" |

**NO。** 本次加强版验证了所有关键 Service 的实际查询逻辑：
- Product 不会在运行时降级为"商品"——它没有 price、inventory、SKU 等电商字段

- Search 不会在运行时返回"商品列表"——SupplierProduct 结果携带 `capability` 层级

**数据库说 Product，运行时做 Capability，没有断层。**

### Question 3: Capability Identity 是否贯穿 Search → Inquiry 完整链路？

**YES。** 完整链路验证通过：

```

```

每一步都有 Product.id 的显式传递或后端强制校验。没有断链。
