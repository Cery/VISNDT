## 4. Role Audit

### Buyer（能否完整表达"我要什么"）
- **能表达基础**：title / description / budgetRange / quantity / quantityUnit / expectedDeliveryDate（Web create 表单齐全）。
- **不能表达技术参数**：无任何参数录入入口 → "我要什么"在技术维度完全缺失。
- **不能表达分类**：Web create/edit 无 categoryId 字段（该字段决定 matching 的分类过滤与知识映射）。
- **不能表达联系人**：Web create 无 contactName/Email/Phone/contactVisible，仅 Admin edit 有。
- **能看到"我提出了什么"**：DemandDetail 有工作流时间线、状态、描述、参数（空）。但**联系人信息 Web 详情也不展示**。
- **看不到"供应商如何响应"**：匹配详情页只见单一 score + 前端伪造的 3 个通用因子，看不到后端真实参数级打分。

### Supplier（能否完整理解需求并正确报价）
- **理解需求技术参数：不能**。供应商 RFQ 详情页 `supplier/rfqs/[id]/page.tsx` 读取 `demand.parameters`，因接口恒不返回 → **永远空显示**（用户所报问题根因）。
- **报价表达**：Offer 有 price/currency/status 生命周期，但 **Offer 详情不返回 supplierProduct 绑定**（`offers.service.ts` findOne `include: { organization, product, createdByUser }` 无 supplierProduct）→ 报价无法表达"针对哪个能力型号"。

### Admin（是否拥有完整运营数据视图）
- **Database Admin ≠ Frontend Admin**：Product 有 `slug`/`seoTitle` 后端标量字段，但 Admin `ProductForm.tsx` 表单无这两个字段（仅 name/model/categoryId/status/description），无法创建/编辑/回显。
- 其余核心资源（SupplierProduct 审核、Content SEO、User/Org、Demand 状态流转）Admin 视图相对完整（见 §5-§15）。

### Organization
- `Organization(type/status/members)` + `OrganizationMember(role)` 模型完整；权限边界由后端 `RolesGuard` + 各 Service 的 organizationId 范围检查（`demands.validateDemandOwnership`、`inquiries.getInquiryById`、`offers.*`/`matching.*` 的 `offer.organizationId === user.organizationId`）实现。Web/Admin 权限显示基本一致，**未发现 UI 隐藏但 API 泄密的 P0 级缺口**。

## 29. Root Cause Analysis

统一根因：**"后端数据丰满、前端消费单调"的系统性模式**，表现为三类子根因：

1. **Data Entry Missing（前端录入断点）**：Demand 的参数/分类/联系人在 Web/Admin 表单完全缺失，导致下游字段"有列无值"，从而 matching/RFQ/展示层层空转。这是 P1-1/P1-2/P2-3/P2-4 的共同源头。
2. **API Contract Truncation（`include`/`select` 截断）**：RFQ 不含 `demand.parameters`、Offer 不含 `supplierProduct`、Product `findOne` 不含 `supplierProducts`，导致"后端有但 API 不给"（Type D）。
3. **Type/Consumption Mismatch（前端未对齐后端结构）**：`DemandParameter` 前端扁平 vs 后端嵌套；`matchDetails` 后端丰富 JSON 被前端抛弃并用单 score 伪造成因。

与 711 的关系：711 只看到 Demand/RFQ Parameter 一个切片（根因 1+2 的部分），**未识别出"整个交易链 + 能力 SEO 治理 + 匹配解释"层面的同构问题**。
