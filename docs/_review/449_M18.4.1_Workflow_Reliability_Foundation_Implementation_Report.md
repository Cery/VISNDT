## 4. WorkflowEvent Reliability Fix

### 原问题
Content 生命周期 `emitEvent()` 调用 `WorkflowEventsService.create()` 时，因 `create()` 强制校验 `operator.organizationId`（Content 用户可能无组织），异常被 `try/catch` 静默吞掉，导致 WorkflowEvent 丢失。

### 修复方案
1. **`WorkflowEventsService.create()`**：组织约束改为仅对组织绑定实体生效——`dto.entityType !== WorkflowEntityType.CONTENT` 时才要求 `user.organizationId`；CONTENT 实体豁免。
2. **`ContentService.emitEvent()`**：移除 `try/catch`，直接 `await workflowEventsService.create(...)`，WorkflowEvent 失败时向上抛出，Content 生命周期失败（数据完整性 > 静默成功）。

### 验证结果
- 方案符合「最终方案必须保持 WorkflowEvent 数据完整性 > 静默成功」要求。
- 对所有组织绑定实体（Demand/RFQ/...）原有约束保持不变，未扩大权限。

## 5. AuditLog Integration

### 新增审计记录点

| Content 流程 | AuditLog action | oldValue / newValue |
| --- | --- | --- |
| create | `CREATE` | newValue = `{ title, status, seoTitle, seoDescription, seoKeywords, coverImageId }` |
| update | `UPDATE` | oldValue（更新前）vs newValue（更新后），含 title/status/SEO/coverImageId |
| submit | `STATUS_CHANGE` | oldValue=`{ status: DRAFT }` → newValue=`{ status: REVIEW }` |
| review | `STATUS_CHANGE` | `REVIEW` → `PUBLISHED` |
| publish | `STATUS_CHANGE` | `REVIEW` → `PUBLISHED` |
| archive | `STATUS_CHANGE` | `PUBLISHED` → `ARCHIVED` |

### Audit 内容
- entityType=`CONTENT`，entityId=content.id，operatorId=操作者，action 取 CREATE/UPDATE/STATUS_CHANGE，oldValue/newValue 按上述策略。

### old/new value 策略
- 通过 `auditPayload()` 投影，仅捕获审计要求字段（title、status、SEO 字段、coverImageId），避免冗余与敏感字段。
