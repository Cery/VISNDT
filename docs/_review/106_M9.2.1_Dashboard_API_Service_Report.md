## API Integration

### Service Architecture

```
┌──────────────────────────────────────────────────┐
│  dashboardService.getStats()                     │
│  ┌────────────────────────────────────────────┐  │
│  │  apiClient.get('/admin/dashboard/stats')   │  │
│  │  ┌──────────────────────────────────────┐  │  │
│  │  │  axios instance (src/api/client.ts)  │  │  │
│  │  │  - baseURL: /api/v1                  │  │  │
│  │  │  - Auth header: Bearer {token}       │  │  │
│  │  │  - 401 → clearAuth + redirect        │  │  │
│  │  │  - Response unwrap: response.data    │  │  │
│  │  └──────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────┘  │
│  Returns: DashboardStats (typed)                 │
└──────────────────────────────────────────────────┘
```

### Service Implementation

```typescript
import { apiClient } from './client';
import type { DashboardStats } from '../types/dashboard.types';

interface DashboardStatsResponse {
  success: boolean;
  data: DashboardStats;
  message: string;
  timestamp: string;
}

export const dashboardService = {
  async getStats(): Promise<DashboardStats> {
    const response = (await apiClient.get(
      '/admin/dashboard/stats',
    )) as unknown as DashboardStatsResponse;
    return response.data;
  },
};
```

**Key design decisions**:
- Uses existing `apiClient` (not creating a new Axios instance)
- `as unknown as` cast is necessary because the response interceptor unwraps to `unknown` (Axios type limitation)
- Returns `DashboardStats` directly (extracts `.data` from the ApiResponse envelope)
- Auth header injection is handled transparently by the existing request interceptor

### Usage Example

```typescript
import { dashboardService } from '../api';
import type { DashboardStats } from '../types';

const stats: DashboardStats = await dashboardService.getStats();
// stats.users.total, stats.demands.published, etc.
```

## Type Design

### Type Hierarchy

```
DashboardStats
├── users: DashboardUserStats
│   ├── total: number
│   └── active: number
├── organizations: DashboardOrganizationStats
│   └── total: number
├── products: DashboardProductStats
│   └── total: number
├── demands: DashboardDemandStats
│   ├── total: number
│   └── published: number
└── matching: DashboardMatchingStats
    └── totalMatches: number
```

### Design Principles

| Principle | Applied |
|---|---|
| All fields explicitly typed (`number`) | Yes |
| No `any` usage | Yes |
| No optional fields (all guaranteed by backend) | Yes |
| Extensible — new sub-objects can be added without breaking existing types | Yes |
| Sub-interfaces allow partial consumption (e.g., only `DashboardUserStats`) | Yes |
| Barrel export via `src/types/index.ts` | Yes |

### Extensibility

If backend adds new stat categories (e.g., `rfqs`, `notifications`), the pattern is:
1. Add new sub-interface in `dashboard.types.ts`
2. Add field to `DashboardStats`
3. Update barrel exports

No breaking changes to existing consumers.
