## 6. Security Audit

### 6.1 Authentication & Authorization

All audited write endpoints follow the same security pattern:

```typescript
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles(Role.ADMIN)
@ApiBearerAuth()
```

**Guard Chain**: `JwtAuthGuard` → `RolesGuard`

**JwtAuthGuard** (from `auth/jwt-auth.guard.ts`):
- Extends `AuthGuard('jwt')` from `@nestjs/passport`
- Validates JWT token, extracts user from payload

**RolesGuard** (from `auth/guards/roles.guard.ts`):
- Reads `@Roles()` decorator metadata
- Checks `request.user` exists
- Checks `user.organizationId` exists
- Queries `OrganizationMember` table for membership
- Validates `membership.role` against required roles

**Role Enum** (`auth/enums/role.enum.ts`):
```typescript
enum Role {
  ADMIN = 'ADMIN',
  MEMBER = 'MEMBER',
}
```

### 6.2 Endpoint Security Matrix

| Module | Read Endpoints | Write Endpoints |
|--------|---------------|-----------------|
| ParameterGroup | Public (no guard) | ADMIN only |
| ParameterDefinition | Public (no guard) | ADMIN only |
| ProductCategory | Public (no guard) | ADMIN only |
| ProductMedia | Public (no guard) | ADMIN only |

### 6.3 Organization Isolation

All audited modules are **global catalog** resources — they do not have `organizationId` fields. This is by design:
- Parameters and Categories are shared across all organizations
- No organization isolation is needed for these resources
- Security is enforced via ADMIN role restriction on write operations

### 6.4 Security Findings

| Finding | Severity | Detail |
|---------|----------|--------|
| `as any` cast in ParameterDefinition service | Low | `create()` and `update()` use `as any` on DTO — type safety gap |
| Missing Delete on Parameter/Category | Medium | No delete endpoints for ParameterGroup, ParameterDefinition, ProductCategory — admin cannot remove stale data |
| No audit logging on write | Low | AuditLog model exists but no audit hooks in these modules |

## 9. Recommendation

### 9.1 M13.1 Implementation Strategy

Based on this audit, the recommended implementation order for M13.1 is:

| Priority | Sub-phase | Module | Backend Change | Status |
|----------|-----------|--------|:---:|--------|
| **P0** | M13.1.1 | ParameterGroup Management | ❌ None | ✅ Go |
| **P0** | M13.1.2 | ParameterDefinition Management | ❌ None | ✅ Go |
| **P0** | M13.1.3 | Category Management | ❌ None | ✅ Go |
| **P1** | M13.1.4 | Media/File Management | ⚠️ Partial | ⚠️ Metadata-only |

### 9.2 Recommended Approach for Blocked Features

**ParameterOption Management** (F-03):
- **Option A** (Recommended): Embed option management in ParameterDefinition Edit page — allow inline add/edit/delete of options. This requires:
  - `POST /parameter-definitions/:id/options` (or nested resource)
  - `PATCH /parameter-definitions/:id/options/:optionId`
  - `DELETE /parameter-definitions/:id/options/:optionId`
  - Requires Backend Unfreeze for `parameter-definitions` module
- **Option B**: Defer to M13.2, use ENUM-type parameters without options for now

**File Upload** (F-01):
- **Option A**: Implement full file upload API with S3/multipart — requires significant backend work
- **Option B** (Recommended for M13.1): Implement media metadata management (view, edit, delete existing media) without upload. Defer upload to M13.2+ when S3 infrastructure is finalized
- **Option C**: Use a simple local file storage approach for MVP

**Delete Endpoints** (F-02):
- Low effort, standard pattern — can be added during M13.1 implementation
- Requires Backend Unfreeze for affected modules

### 9.3 Backend Unfreeze Requirements

If M13.1 needs to include any of the blocked features, the following modules need Backend Unfreeze:

| Feature | Module to Unfreeze | Scope |
|---------|-------------------|-------|
| ParameterOption CRUD | `parameter-definitions` | Add option sub-resource |
| Parameter/Category Delete | `parameter-groups`, `parameter-definitions`, `product-categories` | Add DELETE endpoints |
| File Upload | New `file-asset` module | Full upload + storage |
