## 3. 475 Boundary Issue Analysis

### 3.1 Problem

Task 475_M19.3.2 introduced a public supplier listing page at `/suppliers` (via `apps/web/src/app/suppliers/page.tsx`) and a supplier browsing entry in the product listing page header (`/products` → `/suppliers`). This created:

```
/suppliers
├── Supplier A
├── Supplier B
└── Supplier C
```

This flow forms a **Public Supplier Directory**, which violates the VISNDT architecture principle:

> **Supplier = Capability Provider**, not Public Directory Entity / Store Owner / Marketplace Seller.

### 3.2 Why It Violates Architecture

1. **Supplier Directory** enables users to browse suppliers independently, forming a store/marketplace browsing pattern.
2. **Supplier = Capability Provider** means supplier discovery must be **Product-driven**: users find a product first, then discover which suppliers can provide it.
3. The `/suppliers` listing page creates a parallel discovery path that bypasses the Product Global Catalog, undermining the architecture freeze.

### 3.3 Correct Discovery Flow

The architecture-allowed flow is:

```
Product Search → Product Detail → Supplier Capability Section → Supplier Public Profile
```

i.e., **Find Product → Discover Capability Provider**.

### 3.4 Forbidden Flow

The following is explicitly forbidden:

```
Supplier Directory → Browse Suppliers → Choose Supplier
```
