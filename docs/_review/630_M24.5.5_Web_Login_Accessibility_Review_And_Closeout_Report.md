## 3. 排查过程（Diagnosis）

### 3.1 登录链路确认

Web 登录由 [auth.service.ts](file:///f:/Desktop/VISNDT/VISNDT/apps/web/src/services/auth.service.ts#L56-L62) 发起 `POST /auth/login`，经 `lib/api-client.ts` 打到 `http://localhost:4000/api/v1`；登录接口排除在 CSRF 白名单外（[api-client.ts L25](file:///f:/Desktop/VISNDT/VISNDT/apps/web/src/lib/api-client.ts#L25)）。

### 3.2 端口/容器检查

- 初始时 api:4000 **DOWN**，web/api 均无法访问登录接口；Postgres（healthy）、MinIO（:9000）正常运行于 Docker。
- 用户已手动启动 API 后，`/health` 返回 `{"status":"ok","database":"connected"}`，登录链路恢复可达。

### 3.3 账号核查（直查 Postgres）

- 全库与 seed（[seed_demo.ts](file:///f:/Desktop/VISNDT/VISNDT/database/seed_demo.ts#L83-L120)）中**均不存在** `buyer@visndt.com` / `supplier@visndt.com`。
- 现有账号：`demo.buyer.01/02@visndt.local`、`demo.supplier.01/02/03@visndt.local`（密码 `demo123456`）、`admin@vip.com` / `admin@visndt.com`（`admin123456`）。
- 结论：用户指定的两个账号需要**补建**，否则以 `admin123456` 登录必失败。

### 3.4 角色判定模型确认

Web 的 `workspaceRole` 由后端 [auth.service.ts L210-241](file:///f:/Desktop/VISNDT/VISNDT/apps/api/src/auth/auth.service.ts#L210-L241) 依据 `user.organization.type`（BUYER/SUPPLIER）解析，并以 `organizationMember` 返回成员角色。因此账号是否正确落入买家/供应商工作台，取决于**归属组织的 type**。
