# VISNDT M9.5.1 Matching Monitor Architecture Plan

> 生成时间: 2026-07-23

> 类型: Architecture Design — Read Only

## Phase Overview

**目标**: 分析 Backend Matching Domain，设计 Admin Matching Monitor 前端方案。

**结论**: Matching 是嵌入式模块，无独立 API。M9.5 应设计为 **READ-ONLY Matching Statistics Monitor**。

**最终评估**: **PASS** ✅ — 方案明确，可实施。

## Backend Matching Domain Analysis

### 模块结构

```
apps/api/src/
├── matching/              # 匹配引擎（纯 Service 模块，无 Controller）
│   ├── matching.service.ts    # match(demandId): 全量匹配运算
│   ├── matching.module.ts
│   ├── scoring/
│   │   └── scoring.service.ts # 加权评分算法
│   ├── helpers/
│   │   └── category.helper.ts # 分类过滤
│   ├── types/
│   │   ├── match-context.ts   # MatchContext, DEFAULT_MATCH_CONFIG
│   │   └── parameter-score.ts # ParameterScore, ScoreResult
│   └── dto/
│       └── match-result.dto.ts # { matched, skipped, totalCandidates, elapsedMs }
│
├── demands/               # Demand 模块（包含 Match 子端点）
│   ├── demands.controller.ts  # 15 个端点，含 4 个 Match 端点
│   ├── demands.service.ts     # getDemandMatches, getDemandMatchDetail, updateMatchStatus
│   └── dto/
│       ├── query-match.dto.ts        # status, sort, page, pageSize
│       └── update-match-status.dto.ts # status, notes
│
├── admin/                 # Admin Dashboard（已有 totalMatches 统计）
│   ├── admin.controller.ts
│   └── admin.service.ts
```

### 关键发现

| 发现 | 详情 |
|---|---|
| 无独立 Matching Controller | `matching/` 模块是纯服务，通过 `DemandService.rematch()` 调用 |
| Match 端点嵌套在 Demand 下 | `GET/PATCH /demands/:id/matches/:matchId` |
| 所有 Match 端点 org-scoped | `validateDemandOwnership()` 检查 |
| 已有 Dashboard 统计 | `totalMatches` 在 `/admin/dashboard/stats` 中 |
| 匹配引擎触发方式 | `POST /demands/:id/rematch` (rate-limited 10/min) |

## API Inventory

### Match 相关端点 (4 个)

| # | 端点 | Method | 权限 | 返回值 | Admin 可访问 |
|---|---|---|---|---|---|
| 1 | `/demands/:id/matches` | GET | JWT (org) | 分页 Match 列表 | ❌ org-scoped |
| 2 | `/demands/:id/matches/:matchId` | GET | JWT (org) | Match 详情 | ❌ org-scoped |
| 3 | `/demands/:id/matches/:matchId` | PATCH | JWT (org) | 更新状态 | ❌ org-scoped |
| 4 | `/demands/:id/rematch` | POST | JWT (org) | MatchResult | ❌ org-scoped |

### Admin Dashboard 已有数据

| 端点 | Method | 权限 | 返回字段 |
|---|---|---|---|
| `/admin/dashboard/stats` | GET | JWT (ADMIN) | `matching.totalMatches` |

### Match 端点详情

#### `GET /demands/:id/matches`

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| status | DemandMatchStatus | — | PENDING/MATCHED/REVIEWED/ACCEPTED/REJECTED/EXPIRED |
| sort | `'score'` \| `'latest'` \| `'updated'` | `'score'` | 排序 |
| page | number | 1 | 页码 |
| pageSize | number | 20 | 每页条数 |

#### 返回的 DemandMatch 数据结构

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| demandId | UUID | 所属 Demand |
| productId | UUID | 匹配产品 |
| matchScore | Float | 匹配分数 (0-100) |
| matchStatus | DemandMatchStatus | PENDING/MATCHED/REVIEWED/ACCEPTED/REJECTED/EXPIRED |
| matchDetails | Json | 算法参数、参数得分明细 |
| offerId | UUID? | 关联 Offer |
| matchedAt | DateTime? | 匹配时间 |
| reviewedAt | DateTime? | 审核时间 |
| createdAt | DateTime | 创建时间 |
| updatedAt | DateTime | 更新时间 |
| product | Product (include) | 关联产品 |
| offer | Offer? (include) | 关联 Offer |

## Prisma Model Analysis

### DemandMatch 模型

```
model DemandMatch {
  id          String           @id @default(uuid())
  demandId    String           // FK → Demand
  productId   String           // FK → Product
  matchScore  Float            // 0-100 weighted score
  matchStatus DemandMatchStatus // PENDING, MATCHED, REVIEWED, ACCEPTED, REJECTED, EXPIRED
  matchDetails Json?           // { algorithm, parameterScores[], matchRate, ... }
  offerId     String?          // FK → Offer (best ACTIVE offer)
  matchedAt   DateTime?
  reviewedAt  DateTime?
  createdAt   DateTime
  updatedAt   DateTime

  demand  Demand  @relation
  product Product @relation
  offer   Offer?  @relation
}
```

### DemandMatchStatus 枚举

| 值 | 说明 |
|---|---|
| PENDING | 待匹配 |
| MATCHED | 已匹配 |
| REVIEWED | 已审核 |
| ACCEPTED | 已接受 |
| REJECTED | 已拒绝 |
| EXPIRED | 已过期 |

### Match 状态流转

```
PENDING → MATCHED → REVIEWED → ACCEPTED
                              → REJECTED
```

## Admin Requirements

### 约束分析

| 约束 | 对 M9.5 的影响 |
|---|---|
| 无独立 "all matches" API | 无法直接列出所有 Match |
| Match 端点 org-scoped | Admin 不能绕过组织范围 |
| Backend Freeze | 不能新增 API |
| Dashboard 已有 totalMatches | 可复用统计 |

### M9.5 方案决策

**方案 B: Matching Statistics Monitor (READ-ONLY)**

### 数据来源

| 数据 | 来源 | 可用性 |
|---|---|---|
| totalMatches | `/admin/dashboard/stats` | ✅ 已有 |
| 状态分布 | 需新增 API 或聚合 | ⚠️ 需设计 |
| Recent Matches | 需遍历所有 Demand 的 matches | ❌ 不可行 |

### 简化方案

鉴于 Backend Freeze 约束，M9.5 最务实的实现范围:

1. **复用 Dashboard API**: 展示 `totalMatches` 统计卡片
2. **扩展 Dashboard 类型**: 若 Backend 返回更多 matching 字段，则展示
3. **未来扩展**: 待 Backend 解冻后，可新增 `/admin/matching/stats` 端点

### 替代方案: 合并到 Dashboard

考虑到数据可用性，也可以将 Matching Monitor 直接作为 Dashboard 的增强，而非独立页面。这样 `/matching` 路由可重定向到 Dashboard 或展示简化的匹配统计。

## Final Recommendation

### 架构结论

**M9.5 Matching Monitor = READ-ONLY Statistics Page**

Matching 是嵌入式模块，无独立 API。受 Backend Freeze 约束，M9.5 应实现为:
1. 复用 `/admin/dashboard/stats` 的 matching 数据
2. 创建简洁的 MatchingMonitor 页面替换 `/matching` Placeholder
3. 为后续 Backend 解冻后扩展预留空间

### 实施建议

| 优先级 | 任务 | 说明 |
|---|---|---|
| 立即 | M9.5.1 Matching Monitor Page | 1 页面 + 路由替换 |
| 后续 | M9.5.2 Matching List | 需 Backend 新增 `/admin/matching` 端点 |
| 后续 | M9.5.3 Match Detail | 需 Backend 适配 |

### 下一步

**M9.5.1 Matching Monitor Page Implementation** — 创建 MatchingMonitor 页面，替换 `/matching` Placeholder。
