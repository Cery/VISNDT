## 4. EntityType Consistency Review

### 4.1 Canonical enum reality

- Current schema defines `WorkflowEntityType = DEMAND / RFQ / RFQ_RESPONSE / OFFER / MATCH` at [schema.prisma:L77-L83](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L77-L83).
- Current action enum is `WorkflowAction`, not a separate `EventType`, at [schema.prisma:L85-L95](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L85-L95).
- `WorkflowEvent` persistence model stores only `entityType`, `entityId`, `action`, `operatorId`, `metadata` at [schema.prisma:L608-L625](file:///F:/Desktop/VISNDT/VISNDT/database/prisma/schema.prisma#L608-L625).

### 4.2 Domain-by-domain consistency

1. Demand
   - Demand create/publish/close consistently use `entityType = DEMAND`.
   - Publish is expressed as `OPENED`, not `PUBLISHED`, because current action enum has no `PUBLISHED`.

2. RFQ
   - RFQ publish/close and `createFromMatch()` consistently use `entityType = RFQ`.
   - Legacy `create()` path emits no event, so consistency is broken by omission rather than by wrong subject.

3. RFQResponse
   - Decision events consistently use `entityType = RFQ_RESPONSE`.
   - `view()` maps to `WorkflowAction.REVIEWED`, because current action enum has no dedicated `VIEWED`.
   - `CREATE` path emits no event, so lifecycle trace is incomplete.

4. Matching
   - `matching.service.review/accept/reject` consistently use `entityType = MATCH`.
   - `demands.service.updateMatchStatus()` records match state changes under `entityType = DEMAND`, with `matchId` only placed in metadata.
   - This means the same business object has two audit subjects: sometimes `MATCH`, sometimes `DEMAND`.
   - This is the strongest current EntityType inconsistency in the codebase.

### 4.3 Consistency judgment

`PASS WITH RISKS`

Reason:

- `DEMAND / RFQ / RFQ_RESPONSE` are mostly internally consistent where events exist.
- `MATCH` is not consistently treated as the workflow subject.
- Action vocabulary is also semantically stretched: `OPENED` stands in for publish, `REVIEWED` stands in for view.

## 7. Recommended Fix Order

1. Add `RFQResponse CREATE` event on supplier submit path.
   - Highest business value because it closes an end-user initiated mutation gap.

2. Add `MATCH_CREATED` event inside `matching.service.match()`.
   - Make automatic match generation auditable before downstream review and RFQ flows.

3. Canonicalize `MATCH_STATUS_CHANGED` subject to `entityType = MATCH`.
   - Review whether [demands.service.ts:L723-L739](file:///F:/Desktop/VISNDT/VISNDT/apps/api/src/demands/demands.service.ts#L723-L739) should log as `MATCH` instead of `DEMAND`.

4. Normalize RFQ create coverage.
   - Make `create()` and `createFromMatch()` emit the same class of `RFQ CREATED` event, with consistent metadata shape.

5. Decide policy for generic Demand/RFQ status updates.
   - Either forbid lifecycle status mutation in broad update endpoints, or add WorkflowEvent emission there.

6. Optionally review action vocabulary.
   - Decide whether `OPENED` / `REVIEWED` remain the canonical mapping, or whether action semantics need future normalization.
