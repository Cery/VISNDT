### 3.3 Boundary Enforcement

```
Rule 1: Product ≠ Content
  - Product model is separate from Content model
  - Product pages use Product API, not Content API
  - Product parameters are NOT Content.articles

Rule 2: Supplier ≠ Content Owner
  - Content.author is User (platform operator), not Organization
  - No Supplier-authored content model
  - Supplier capability is expressed through Offer + Product, not Content

Rule 3: Content ≠ Marketplace
  - Content is informational, not transactional
  - No price, SKU, cart, or order in Content
  - Content-to-Product linking is informational (discovery), not commercial
```

## 4. Content Relationship Architecture

### 4.1 Relationship Model Design

```
┌──────────────────────────────────────────────────────────────┐
│                   Content Relationship Model                   │
│                                                               │
│  ┌──────────┐     ┌──────────────┐     ┌──────────┐         │
│  │ Product   │     │   Content    │     │ Solution │         │
│  │          │◄───►│  (KNOWLEDGE) │◄───►│          │         │
│  └──────────┘     └──────┬───────┘     └──────────┘         │
│                          │                                    │
│                          │ "related to"                       │
│                          ▼                                    │
│                   ┌──────────────┐                            │
│                   │   Content    │                            │
│                   │  (ARTICLE)   │                            │
│                   └──────────────┘                            │
│                                                               │
│  Relationship Types:                                          │
│  ─────────────────                                            │
│  Content → Product    : "applies to" / "mentions"             │
│  Content → Content    : "related to" / "see also"             │
│  Content → Solution   : "part of" / "used in"                 │
│  Content → Industry   : "relevant to" (via Tag)               │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 Implementation Strategy

**Option A: Tag-Based Relationship (Recommended for M20.2)**

Content relationships are inferred through shared tags, not explicit FK relations.

```
Content A ──tag──▶ "ultrasonic-testing" ◀──tag── Content B
                                         ◀──tag── Product X
```

- **Pros**: No schema change, no migration, flexible, SEO-friendly (tag pages)
- **Cons**: Implicit relationships, no weight/ordering
- **Effort**: Low -- only ContentTag + ContentTagRelation models needed

**Option B: Explicit Relation Model (Deferred to M20.3)**

```
ContentRelation {
  sourceContentId, targetContentId, relationType, weight, sortOrder
}
ContentProductRelation {
  contentId, productId, relationType
}
```

- **Pros**: Explicit, ordered, typed relationships
- **Cons**: Schema change, migration, more complex Admin UI
- **Effort**: Medium -- 2 new models + Admin UI + API

### 4.3 Architecture Decision

| Decision | Verdict | Rationale |
|----------|---------|-----------|
| Content-Content Relationship | **Tag-Based (M20.2)** | Start with tag-based implicit relationships; explicit ContentRelation deferred to M20.3 |
| Content-Product Relationship | **Tag-Based (M20.2)** | Link via shared tags; explicit ContentProductRelation deferred to M20.3 |
| Content-Solution Relationship | **Tag-Based (M20.2)** | Same approach; Solution is a ContentType, shares tag system |
| Explicit Relation Model | **Deferred (M20.3)** | Requires schema change + Admin UI; evaluate after tag system is operational |

**Design Principle**: Tag-First, Relation-Later. Tag system provides 80% of relationship value with 20% of the complexity.

## 5. Taxonomy Architecture

### 5.1 Tag Model Design

```
ContentTag {
  id          String   @id @default(uuid()) @db.Uuid
  name        String                           // "超声检测"
  slug        String   @unique                 // "ultrasonic-testing"
  type        TagType                          // TOPIC | INDUSTRY | APPLICATION | TECHNOLOGY
  description String?                          // Optional description for tag page SEO
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

ContentTagRelation {
  id        String   @id @default(uuid()) @db.Uuid
  contentId String   @db.Uuid                   // FK → Content
  tagId     String   @db.Uuid                   // FK → ContentTag
  createdAt DateTime @default(now())

  @@unique([contentId, tagId])
  @@index([tagId])
  @@index([contentId])
}

TagType enum:
  TOPIC       -- "超声检测", "射线检测", "目视检测"
  INDUSTRY    -- "航空航天", "汽车制造", "能源"
  APPLICATION -- "焊缝检测", "腐蚀检测", "厚度测量"
  TECHNOLOGY  -- "相控阵", "TOFD", "DR"
```

### 5.2 Tag Architecture Benefits

| Benefit | Description |
|---------|-------------|
| Cross-Content Discovery | Related articles via shared tags |
| Content-to-Product Linking | Product tagged with same industry/application |
| SEO Tag Pages | `/tags/ultrasonic-testing` aggregates all related content |
| Filter Enhancement | Tag-based filtering on list pages |
| Low Maintenance | Tags are simple labels, not complex hierarchies |
| No Schema Expansion | Tags are flat, not nested categories |

### 5.3 Tag vs Category Distinction

| Dimension | Category | Tag |
|-----------|----------|-----|
| Purpose | Product classification (hierarchical) | Content classification (flat) |
| Model | Category model (Product domain) | ContentTag model (Content domain) |
| Structure | Tree (parent-child) | Flat list |
| Usage | Product browsing | Content discovery |
| SEO | Category pages | Tag pages |
| Owner | Product domain | Content domain |

### 5.4 Architecture Decision

| Decision | Verdict | Rationale |
|----------|---------|-----------|
| ContentTag Model | **Approved** | Essential for content discovery and SEO |
| ContentTagRelation Model | **Approved** | Many-to-many linking between Content and Tag |
| TagType Enum | **Approved** | TOPIC/INDUSTRY/APPLICATION/TECHNOLOGY provides structured classification |
| Tag Hierarchy | **Rejected** | Flat tags only; hierarchy adds complexity without proportional value |
| Tag → Product Linking | **Deferred** | ProductTagRelation model deferred to M20.3 |
| Implementation | **M20.2.3** | Requires schema change (2 new models + migration) -- separate design review required |

**Design Note**: ContentTag and ContentTagRelation are schema changes. Per architecture constraints, they require dedicated schema design review before implementation.

## 6. Search Integration Architecture

### 6.1 Current Search State

```
/search flow (M20.1):
  User Input → SearchBar → useSearchParams → GET /products?keyword=...&categoryId=...&parameterFilters=...
  Results: ProductCard[] only (no content)
```

**Gap**: Content (KNOWLEDGE/SOLUTION/ARTICLE/INSIGHT) is NOT searchable.

### 6.2 Search Integration Design

**Phase 1: Frontend Aggregation (M20.2.2 -- Recommended)**

```
/search flow (enhanced):
  User Input → SearchBar → useSearchParams
    ├── GET /products?keyword=...  (existing)
    └── GET /content/public?type=...&keyword=...  (NEW -- content search)
  
  Results: Unified result list with type badges
    [Product] Industrial Borescope XYZ-3000
    [Knowledge] 超声检测技术指南
    [Solution] 航空航天发动机检测方案
    [Product] High-Resolution Inspection Camera
```

**Implementation approach:**
- Frontend parallel fetch: products + content
- No backend search aggregation needed
- Content search via existing `GET /content/public` with keyword filter on title + summary
- Result type discrimination via badge (Product vs Knowledge vs Solution)
- Tab filter: All / Products / Knowledge / Solutions

**Phase 2: Backend Aggregation (M20.3 -- Future)**

```
GET /search?q=keyword&type=all
  → Backend aggregates products + content + (future) knowledge
  → Single response with typed results
```

**Phase 3: Full-Text Search (M20.3+ -- Future)**

```
PostgreSQL full-text search (tsvector/tsquery) on:
  Product: name, description
  Content: title, summary, content
```

**Phase 4: Semantic Search (M21+ -- Future)**

```
Vector embedding + semantic similarity
```

### 6.3 Content Search API Design

**Option A: Extend existing GET /content/public (Recommended)**

```
GET /content/public?type=KNOWLEDGE&keyword=ultrasonic&page=1&pageSize=20
```

Add optional `keyword` parameter to QueryContentDto:
- Search against `title` (ILIKE) and `summary` (ILIKE)
- Results ordered by relevance (title match > summary match) then publishedAt desc
- No full-text index needed; ILIKE is sufficient for current data scale

**Option B: New GET /content/search endpoint**

```
GET /content/search?q=ultrasonic&type=KNOWLEDGE
```

Separate search endpoint with dedicated response format.

### 6.4 Architecture Decision

| Decision | Verdict | Rationale |
|----------|---------|-----------|
| Content in Search | **Approved (M20.2.2)** | Essential for content discoverability |
| Search Approach | **Frontend Aggregation (Phase 1)** | No backend changes; extensible |
| Content Search API | **Option A: Extend /content/public** | Minimal change; backward compatible |
| Keyword Search | **ILIKE on title + summary** | Sufficient for current scale; no infrastructure |
| Full-Text Search | **Deferred (M20.3+)** | Requires PostgreSQL tsvector setup |
| Semantic Search | **Deferred (M21+)** | Requires vector database |
| AI Search | **Rejected** | Architecture constraint |

**Design Note**: Adding `keyword` parameter to `QueryContentDto` is a minor API change. Per architecture constraints, this requires separate review before implementation.

```
  - "行业合作" section

/about → Static page (hardcoded content)
  - "我们的使命" section
  - "我们提供什么" section (4 cards)
  - "服务行业" section
  - "联系我们" section
```

### 9.2 Migration Design

**Target**: Both pages become content-managed via the Content system.

**Approach**: Create BUSINESS-type Content entries for each section/page.

```
Migration Steps:

1. Create ContentType.BUSINESS enum value (schema change -- requires review)
2. Create BUSINESS content entries in Admin:
   - "商务合作" (slug: business, covers current /business content)
   - "关于VISNDT" (slug: about, covers current /about content)
3. Update /business page:
   - Fetch CONTENT with slug "business" (type=BUSINESS, status=PUBLISHED)
   - Render via MarkdownRenderer
   - Add dynamic SEO metadata
4. Update /about page:
   - Fetch CONTENT with slug "about" (type=BUSINESS, status=PUBLISHED)
   - Render via MarkdownRenderer
   - Add dynamic SEO metadata
```

### 9.3 Migration Benefits

| Benefit | Description |
|---------|-------------|
| Content Management | Edit without code deployment |
| SEO Enhancement | Dynamic metadata, JSON-LD, OpenGraph |
| Version History | ContentRevision tracks all changes |
| Workflow | Review + publish flow for business content |
| Consistency | Same content system as Knowledge/Solutions |

| /about → Content | **Approved (M20.2.4)** | Content-managed, SEO-enhanced |
