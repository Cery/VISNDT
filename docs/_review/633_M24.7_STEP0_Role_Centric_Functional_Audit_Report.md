### 3.2 Web 编号/ID 一致性关键发现

| # | 问题 | 影响 | 级别 |
|---|------|------|------|
| W1 | 产品列表 `ProductCard` 链接用 `product.id`，详情路由却是 `[slug]`；同一实体两种标识口径并存 | 深层链接失效风险、SEO 与引用不一致 | **P0** |
| W2 | 供应商详情路由 `[id]`，但页面内不显示组织 ID / 统一业务编号 | 供应商侧「我是哪家」身份感弱，对账/客服定位难 | P1 |
| W3 | 列表卡片普遍不展示「业务编号」（如产品型号/需求单号/RFQ 单号），仅靠中文标题区分 | 多条目同名前缀时无法快速锁定 | P1 |
| W4 | Demand/RFQ/Offer 详情链接用 `{id}`（UUID），但页面未向用户暴露可读编号 | 跨页沟通引用困难 | P1 |

### 3.3 Web 角色视角差距

- **buyer**：需求/询价流程字段齐全，但缺「单号/编号」体系与「状态流转时间线」可读性；`/workspace/supplier` 仍是跳转占位（已在 625 记账）。
- **supplier**：Offer 列表缺「关联产品型号/编号」「报价单号」；供应商详情页身份信息（组织类型/资质）展示偏弱。

## 五、媒体中心分步审计（B.0）

### 5.1 现状能力边界（schema 已核）

`FileAsset` 现有：`entityType`（PRODUCT/ORGANIZATION/DEMAND/RFQ/RFQ_RESPONSE/CONTENT）、`fileType`（**IMAGE/DOCUMENT/CERTIFICATE/OTHER**）、`fileName/storageKey/mimeType/fileSize/uploadedBy`。

### 5.2 安全可做（零迁移） vs 需改库（门禁）

| 用户诉求 | 能否零迁移 | 说明 |
|---------|:---:|------|
| 统一媒体中心列表 + 分页/搜索 | ✅ 可 | 前端聚合，复用现有字段 |
| 按文件类型分组（图片/文档/资质/其他） | ✅ 可 | 复用 `fileType` 枚举 |
| 按供应商过滤（不同供应商分开） | ✅ 可 | `FileAsset.uploadedBy → User → Organization` 派生（只读派生，不落列） |
| 资质证书（CERTIFICATE）单独管理 | ✅ 可 | 复用现有 `fileType=CERTIFICATE` |
| **规格书 vs 普通文档细分** | ⚠️ 需改 | `FileType` 只有 `DOCUMENT`，无 `SPEC_SHEET` 区分 |
| **供应商组织级隔离归属（落列）** | ⚠️ 需改 | `FileAsset` 无 `organizationId` 列 |
| **媒体生命周期状态 / 软删 / 回收** | ⚠️ 需改 | 无 `status` / `deletedAt` 字段 |
| 版本历史 / 回滚 | ⚠️ 需改 | 无版本表（629 Phase 2） |

## 七、结论与下一步

**结论：CONDITIONAL PASS（功能/字段/编号/媒体整合尚未达标，需按路线推进）**

零代码审计完成，已产出 Web/Admin 三角色差距清单（P0×2、P1×5、P2×若干）与媒体分步边界。**核心结论：媒体中心「分开管理」的展示/筛选/供应商派生可零迁移先做；但「供应商隔离落列 + 规格书细分 + 生命周期/软删/版本」必须改库，单独门禁处理（详见 634 报告）。**

**Next Step（推荐顺序）**：
1. `A.1~A.5` 设计系统打底（纯前端低风险）
2. `B.1` 媒体中心前端收口（零迁移优先满足「分开管理」诉求）
3. `C.1` 编号/ID/字段规范化（前端修正，先解决 W1/A1 等 P0/P1）
4. `B.2` 媒体 schema 演进（门禁，见 634）
