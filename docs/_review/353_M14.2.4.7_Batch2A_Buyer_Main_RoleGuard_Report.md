## 3. 修改原因

1. Buyer 主页面此前只校验登录态，没有校验 `workspaceRole` 是否为 `BUYER`
2. 这导致 `SUPPLIER` 或 `workspaceRole = null` 的已登录用户理论上可通过直链访问 Buyer 页面
3. 本次仅在页面主体入口补充 Buyer 专属角色守卫，不扩大到 create/detail/matches 页面

## 4. Buyer Access Control变化

修改前：

1. `/workspace/demands` 页面：`AuthGuard -> DemandsContent`
2. `/workspace/rfqs` 页面：`AuthGuard -> RfqsContent`
3. 入口层仅要求“已登录”，未要求 `workspaceRole = BUYER`

修改后：

1. `/workspace/demands` 页面：`AuthGuard -> RoleGuard(roles=['BUYER']) -> DemandsContent`
2. `/workspace/rfqs` 页面：`AuthGuard -> RoleGuard(roles=['BUYER']) -> RfqsContent`
3. 仅当 `workspaceRole` 为 `BUYER` 时，页面主体才继续渲染

## 5. SUPPLIER/null访问行为变化

修改前：

1. `SUPPLIER` 用户只要已登录，即可直接访问 `/workspace/demands`
2. `SUPPLIER` 用户只要已登录，即可直接访问 `/workspace/rfqs`
3. `workspaceRole = null` 的已登录用户也可直接进入上述 Buyer 页面

修改后：

1. `SUPPLIER` 用户会在页面入口被 `RoleGuard` 拒绝，不再继续渲染 Buyer 页面主体
2. `workspaceRole = null` 用户会在页面入口被 `RoleGuard` 拒绝，不再继续渲染 Buyer 页面主体
3. 未新增任何默认角色补偿逻辑
