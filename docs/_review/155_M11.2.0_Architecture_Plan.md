## 1. Architecture Summary

M11.2 目标是在现有 Notification 基础设施上，构建 **Business Event → Notification Trigger → Notification Record → Notification Center** 的完整闭环。

### 核心发现

| 维度 | 现状 | 结论 |
|------|------|------|
| Notification 数据模型 | ✅ 完整 (id, userId, type, status, title, message, referenceType, referenceId) | **无需 schema 变更** |
| Notification API | ✅ 完整 (list, detail, unread-count, mark-read, mark-all-read) | **无需新增 API** |
| Notification Frontend | ✅ 完整 (List/Detail pages, filtering, auto-mark-read) | **无需前端变更** |
| Notification 创建 | ❌ **缺失** — 无 create() 方法 | **核心差距** |
| 业务事件触发 | ❌ **缺失** — 无任何业务事件触发通知 | **核心差距** |
| NotificationType | ⚠️ 4 种 (SYSTEM/DEMAND_UPDATE/RFQ_UPDATE/RESPONSE_UPDATE) | **可用但需扩展** |

### 架构设计原则

```
Backend: Additive-only (仅添加，不修改现有逻辑)
Database: Frozen (0 schema changes)
Frontend: Frozen (0 changes)
Dependencies: Frozen (0 new dependencies)
```

### 2.3 Notification Prisma Model

```
model Notification {
  id            String         @id @default(uuid())
  userId        String         @map("user_id")
  type          NotificationType
  status        NotificationStatus @default(UNREAD)
  title         String
  message       String
  referenceType String?        @map("reference_type")
  referenceId   String?        @map("reference_id") @db.Uuid
  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt

  user User @relation(fields: [userId], references: [id])
  @@index([userId, status])
}
```

**评估:** 模型字段完整，支持所有通知场景。`referenceType` + `referenceId` 可关联业务实体。

## 3. Event Model Design

### 3.1 Event Taxonomy

| 事件 ID | Event Name | 触发位置 | 触发时机 | NotificationType | 标题模板 | 消息模板 |
|:---:|-----------|----------|----------|:---:|---------|---------|
| E1 | RFQ Created | `rfqs.service.ts:create()` | POST /rfqs 成功 | `RFQ_UPDATE` | "New RFQ Created" | "RFQ for demand '{demandTitle}' has been created" |
| E2 | RFQ Status Changed | `rfqs.service.ts:update()` | PATCH /rfqs/:id 成功 | `RFQ_UPDATE` | "RFQ Status Updated" | "RFQ status changed to '{newStatus}'" |
| E3 | RFQ Response Submitted | `rfq-responses.service.ts:create()` | POST /rfqs/:id/responses 成功 | `RESPONSE_UPDATE` | "New RFQ Response" | "Supplier '{orgName}' submitted response to RFQ" |
| E4 | RFQ Response Accepted | `rfq-responses.service.ts:update()` | PATCH /rfq-responses/:id status=ACCEPTED | `RESPONSE_UPDATE` | "Response Accepted" | "RFQ response from '{orgName}' has been accepted" |
| E5 | RFQ Response Rejected | `rfq-responses.service.ts:update()` | PATCH /rfq-responses/:id status=REJECTED | `RESPONSE_UPDATE` | "Response Rejected" | "RFQ response from '{orgName}' has been rejected" |
| E6 | Match Completed | `matching.service.ts:rematch()` | Rematch 流程完成 | `DEMAND_UPDATE` | "Matching Completed" | "{matched}/{candidates} products matched for demand '{demandTitle}'" |
| E7 | Match Status Changed | `demands.service.ts:updateMatchStatus()` | PATCH /demands/:id/matches/:matchId 成功 | `DEMAND_UPDATE` | "Match Status Updated" | "Match status changed to '{newStatus}'" |
| E8 | Offer Created | `offers.service.ts:create()` | POST /offers 成功 | `RESPONSE_UPDATE` | "New Offer Created" | "Supplier '{orgName}' created offer '{offerTitle}'" |

### 3.2 Notification Recipient Logic

| 事件 | 通知对象 | 查询逻辑 |
|------|----------|----------|
| E1 (RFQ Created) | Demand 创建者 | `demand.createdBy` |
| E2 (RFQ Status Changed) | Demand 创建者 + RFQ 创建者 | `demand.createdBy`, `rfq.createdBy` |
| E3 (RFQ Response) | RFQ 创建者 | `rfq.createdBy` |
| E4 (Response Accepted) | Response 提交者 (Supplier) | `response.organizationId` → members |
| E5 (Response Rejected) | Response 提交者 (Supplier) | `response.organizationId` → members |
| E6 (Match Completed) | Demand 创建者 | `demand.createdBy` |
| E7 (Match Status) | Demand 创建者 + 匹配的 Supplier | `demand.createdBy`, `offer.organizationId` → members |
| E8 (Offer Created) | 同组织 Admin 成员 | `offer.organizationId` → members (role=ADMIN) |

### 4.2 Required Backend Changes

#### 4.2.1 NotificationsService — 新增 create() 方法

```typescript
// 文件: apps/api/src/notifications/notifications.service.ts
// 变更: 新增方法（additive）

async create(dto: CreateNotificationDto): Promise<Notification> {
  return this.prisma.notification.create({
    data: {
      userId: dto.userId,
      type: dto.type,
      title: dto.title,
      message: dto.message,
      referenceType: dto.referenceType,
      referenceId: dto.referenceId,
    },
  });
}

async createForOrganization(
  organizationId: string,
  dto: Omit<CreateNotificationDto, 'userId'>,
): Promise<Notification[]> {
  // 查询组织内所有成员
  const members = await this.prisma.organizationMember.findMany({
    where: { organizationId, role: 'ADMIN' },
  });
  
  // 批量创建通知
  const notifications = await Promise.all(
    members.map((member) =>
      this.prisma.notification.create({
        data: {
          userId: member.userId,
          type: dto.type,
          title: dto.title,
          message: dto.message,
          referenceType: dto.referenceType,
          referenceId: dto.referenceId,
        },
      }),
    ),
  );
  
  return notifications;
}
```

## 7. Security Analysis

### 7.1 Notification Creation Security

| 风险 | 缓解措施 | 状态 |
|------|----------|:---:|
| 通知发送给错误用户 | `createForOrganization()` 通过 `organizationId` 查询成员 | ✅ |
| 跨组织通知泄露 | `create()` 以 `userId` 为粒度，结合 `getAccessScope()` 验证 | ✅ |
| 未授权通知创建 | 不暴露 POST /notifications API，仅内部调用 | ✅ |
| 通知数据注入 | 标题/消息内容来源于业务数据，不包含用户输入 | ✅ |

### 7.2 Organization Isolation

现有 `getAccessScope()` 逻辑保持不变:
- **ADMIN** → org-scoped (查看组织内所有成员通知)
- **MEMBER** → user-scoped (仅查看自己的通知)

M11.2 新增的 `createForOrganization()` 方法遵循相同隔离原则。

### 12.2 关键决策
