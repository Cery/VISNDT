### 2.2 数据源矩阵（当前 Relation Strategy）

| 关联 | 路径 | 策略 |
| --- | --- | --- |
| Product → Related Knowledge（KnowledgeEntry） | `GET /products/:id/related-knowledge` | **Backend Managed**（Product → ProductCategory → ProductCategoryKnowledgeMapping → KnowledgeCategory → KnowledgeEntry；ACTIVE/PUBLISHED 过滤 + 按 entry id 去重 + 稳定排序 mapping.sortOrder → publishedAt desc → id） |
| Product → Related Products | `GET /products/:id/related-products` | **Backend Managed**（同 ProductCategory ACTIVE 产品，排除当前，createdAt desc → id asc） |
| KnowledgeEntry → Related Products | `GET /knowledge/public/entries/:slug/related-products` | **Backend Managed**（同一 mapping 反向） |
| Product → Related Solutions | 页面 `GET /content/public?type=SOLUTION` | **Frontend Deterministic**（最新发布优先，prop 注入） |
| Content-KNOWLEDGE 详情 → Related Products / Solutions | 页面 `GET /products` + `GET /content/public?type=SOLUTION` | **Frontend Deterministic**（最新发布优先） |
| Solution 详情 → Related Products / Knowledge / Other Solutions | 页面 `GET /products` + `GET /content/public?type=KNOWLEDGE/SOLUTION` | **Frontend Deterministic**（最新发布优先） |

### 2.3 关键架构事实

- **已存在结构化关联基础**：`ProductCategoryKnowledgeMapping`（M24.1.1 落地）已提供**后端管理的确定性 Product↔Knowledge 映射**，并已被 594/595 接入 Product/Knowledge 详情页。因此"Backend Managed Commercial Relation System"的**基础设施已部分存在**，架构缺口主要是 **Solution 侧（Solution↔Product、Solution↔Knowledge）与 Content-KNOWLEDGE 侧**仍为纯前端最新优先。
- **双"知识"语义并存**：`KnowledgeEntry`（知识域，结构化，走 backend mapping）与 `Content(type=KNOWLEDGE)`（内容域）是两套知识载体，其关联策略不一致。
- **确定性约束保持**：所有当前关联均为确定性排序，无 AI/keyword 语义猜测，符合冻结纪律。

## 3. Business Relation Model Assessment

### 3.1 Product ↔ Solution

**结论：FUTURE REQUIRED**

- 现状：Product 详情的相关解决方案来自 `GET /content/public?type=SOLUTION` 最新优先，Solution 详情的相关产品来自 `GET /products` 最新优先——**无行为化、无运营可控、随内容规模增大而劣化**。
- 判断：MVP/当前数据规模下**短期内不需要**（最新优先 + 人工可控可接受）；当解决方案资产规模化、需要运营精选指定"某产品匹配哪些解决方案"时，需结构化。
- 建议形态：`ProductSolutionRelation`（或复用 ContentCategory↔ProductCategory 映射思路），带 RelationStatus / RelationPriority 运营属性。

### 3.2 Knowledge ↔ Product

**结论：ALREADY ESTABLISHED（已结构化）**

- 现状：`ProductCategoryKnowledgeMapping` + 594/595 端点已提供**后端管理的确定性映射**（Product ↔ KnowledgeEntry 双向），运营可在 Admin 管理。
- 判断：**不需要新增模型**——该关联已是结构化、后端管理、确定性、可运营。
- 注意点：Content(type=KNOWLEDGE) 载体的 Product 关联仍为前端最新优先；未来可评估是否将内容知识统一纳入同一确定性映射，属 **Future 可选**，非缺口。

### 3.3 Parameter Driven Relation（Capability Knowledge Graph）

**结论：FUTURE CAPABILITY**

- 概念：Parameter → Inspection Scenario → Solution → Product 形成能力知识图谱。
- 现状：参数体系为 Product 参数定义（ParameterGroup/ParameterDefinition），已用于搜索筛选；但无参数↔场景↔解决方案的结构化映射。
- 判断：**未来能力而非当前需求**；即便未来实现，也必须**确定性参数映射**（non-AI / non-semantic），符合冻结纪律；M24.5 不实施。

## 5. Relation Model Decision

### 评估三选项

| 选项 | 描述 | 适用 |
| --- | --- | --- |
| **A** Continue Frontend Deterministic Relation | 全前端最新优先 | MVP/规模小，但 Solution 侧无法运营治理 |
| **B** Introduce Commercial Relation Model | 新增 ProductSolutionRelation/ProductKnowledgeRelation/SolutionKnowledgeRelation/ParameterRelation + Priority/Status | 全量结构化，复杂度与运营成本高 |
| **C** Hybrid Evolution | 既有 Backend-Managed 确定性映射保持；Solution/Content 侧继续前端确定性；按需渐进补齐 | 当前最贴合实际（**已处于混合态**） |

### 最终决策：**Decision C — HYBRID EVOLUTION**

- **保留**：已后端管理的 `Product↔Knowledge`（mapping）与 `Product→Product` 确定性关联；
- **维持**：Solution/Content-KNOWLEDGE 侧前端确定性（最新优先 + Props 注入）作为默认策略；
- **不新增**：本任务/M24.5 不引入新的 Relation Model 表；
- **待未来**：当内容规模与运营治理需求明确后，再启动 `Commercial Relation Model` 提案（含 ProductSolution 等），一次性统一映射策略。
