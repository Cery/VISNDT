## 1. Phase Overview

### 1.1 Context

M11.0 Architecture Review 确认平台后端架构完整，但 Admin 前端存在明确的业务操作能力缺口。M11.1 的目标是完成 Admin 端的业务操作闭环，在不修改 Database、不修改 Frozen 模块的前提下，通过 Admin 前端扩展 + 必要的 Backend 补充来覆盖 RFQ 操作、匹配审核、响应管理等核心业务场景。

### 1.2 Scope Summary

| Dimension | M11.0 (Current) | M11.1 (Target) |
|-----------|:---:|:---:|
| **Admin Routes** | 20 | ~28 |
| **Admin Pages** | 20 | ~28 |
| **Frontend Services** | 7 | ~11 |
| **Frontend Type Files** | 6 | ~10 |
| **Backend API Changes** | — | 0 new endpoints (reuse existing) |
| **Database Changes** | — | 0 |
| **Freeze Violations** | — | 0 |

### 1.3 Four Functional Modules

| # | Module | Purpose |
|---|--------|---------|
| **A** | RFQ Operation Center | RFQ List + Detail, lifecycle management |
| **B** | RFQ Response Management | Response List + Detail, status management |
| **C** | Match Review Center | Match List + Detail, review workflow |
| **D** | Notification Trigger Foundation | Auto-trigger notifications on business events |

## 2. Current Architecture Analysis

### 2.1 Backend API Surface (M11.1 Relevant)

#### RFQ Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/rfqs` | Public | List all RFQs (paginated) |
| `GET` | `/rfqs/:id` | Public | Get RFQ by ID (includes demand + creator) |
| `POST` | `/rfqs` | JWT | Create RFQ (demandId required) |
| `PATCH` | `/rfqs/:id` | JWT | Update RFQ (org-scoped, state machine enforced) |

**RFQ State Machine:**
```
DRAFT → OPEN → RESPONDING → CLOSED
                   ↘ CANCELLED
```

#### RFQ Response Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/rfqs/:id/responses` | Public | List responses for an RFQ (paginated) |
| `POST` | `/rfqs/:id/responses` | JWT | Create response (org-scoped) |
| `GET` | `/rfq-responses/:id` | Public | Get response by ID |
| `PATCH` | `/rfq-responses/:id` | JWT | Update response (org-scoped, state machine) |

**Response State Machine:**
```
SUBMITTED → VIEWED → ACCEPTED
                   ↘ REJECTED
```

#### Offer Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/offers` | Public | List all offers (paginated) |
| `GET` | `/offers/:id` | Public | Get offer by ID |
| `POST` | `/offers` | JWT | Create offer (org-scoped) |
| `PATCH` | `/offers/:id` | JWT | Update offer (org-scoped) |

#### Demand Match Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/demands/:id/matches` | JWT | List matches for demand (org-scoped) |
| `GET` | `/demands/:id/matches/:matchId` | JWT | Match detail (org-scoped, includes demand params) |
| `PATCH` | `/demands/:id/matches/:matchId` | JWT | Update match status (state machine, workflow event) |
| `POST` | `/demands/:id/rematch` | JWT | Re-match (rate limited 10/min) |

**Match State Machine:**
```
PENDING → MATCHED → REVIEWED → ACCEPTED
                             ↘ REJECTED
```

#### Supplier Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/suppliers` | Public | List suppliers (keyword search) |
| `GET` | `/suppliers/:id` | Public | Supplier detail (product/offer/match counts) |
| `GET` | `/suppliers/:id/products` | Public | Supplier products (via Offer) |
| `GET` | `/suppliers/:id/matches` | JWT | Supplier matches (org-scoped) |

#### Admin Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/admin/matching/stats` | ADMIN | Matching stats (total, avg score, hard fail, rematch) |
| `GET` | `/admin/dashboard/stats` | ADMIN | Full platform stats |

#### Notification Domain

| Method | Endpoint | Auth | Description |
|--------|----------|:---:|-------------|
| `GET` | `/notifications` | JWT | List (paginated, filterable) |
| `GET` | `/notifications/unread-count` | JWT | Unread count |
| `PATCH` | `/notifications/read-all` | JWT | Batch mark read |
| `GET` | `/notifications/:id` | JWT | Detail |
| `PATCH` | `/notifications/:id/read` | JWT | Mark read |

#### Business Purpose
为 Admin 提供 RFQ 全生命周期管理能力：查看平台所有 RFQ、查看 RFQ 详情（含关联 Demand）、创建 RFQ、管理 RFQ 状态流转。

#### Existing Capability
- ✅ Backend: Full RFQ CRUD API with state machine (`GET/POST /rfqs`, `PATCH /rfqs/:id`)
- ✅ Backend: RFQ state transitions enforced (DRAFT→OPEN→RESPONDING→CLOSED/CANCELLED)
- ✅ Backend: Org-scoped ownership validation on update
- ❌ Frontend: No RFQ pages (no list, no detail, no create)

#### Missing Capability
- ❌ RFQ List page (table with filters)
- ❌ RFQ Detail page (basic info + demand info + response count)
- ❌ RFQ Create UI (select demand → create RFQ)
- ❌ RFQ Status management (status transition buttons)

### 4.4 Module D: Notification Trigger Foundation

#### Business Purpose
在关键业务事件发生时自动创建通知记录，使现有 Notification Center 能够展示有意义的业务通知。

#### Existing Capability
- ✅ Backend: Notification CRUD API (5 endpoints, M10.2)
- ✅ Backend: Notification model with `referenceType`/`referenceId` for cross-entity linking
- ✅ Frontend: NotificationList + NotificationDetail pages (M10.2)
- ❌ Backend: **No notification creation logic** — Notification is only consumed, never produced
- ❌ Backend: WorkflowEvent creation exists but does not trigger notifications

#### Missing Capability
- ❌ Auto-create notification on Match status change (MATCHED → notify demand owner)
- ❌ Auto-create notification on Match review (ACCEPTED/REJECTED → notify)
- ❌ Auto-create notification on RFQ creation (→ notify demand owner)
- ❌ Auto-create notification on RFQ Response submission (→ notify RFQ creator)
- ❌ Notification creation service method

#### Required Backend Changes

| # | Change | Module | Type | Description |
|---|--------|--------|:---:|-------------|
| D1 | `notifications.service.ts` | `notifications/` | **Extend** | Add `create()` method for programmatic notification creation |
| D2 | `demands.service.ts` | `demands/` | **Extend** | Call notificationService.create() on `updateMatchStatus()` |
| D3 | `rfqs.service.ts` | `rfqs/` | **Extend** | Call notificationService.create() on `create()` |
| D4 | `rfq-responses.service.ts` | `rfq-responses/` | **Extend** | Call notificationService.create() on `create()` |

#### Required API Changes
- **None.** No new endpoints. All changes are internal service-to-service calls.

#### Database Impact
- **None.** No schema changes. Notification model already has all required fields.

#### Security Impact
- **Low.** Notification creation is internal (no user-facing API). Uses existing `userId` from JWT context.

#### Freeze Impact
- ⚠️ **Unfreeze Required** — 4 files in 3 modules:
  - `notifications/notifications.service.ts` (M10.2 re-frozen zone)
  - `demands/demands.service.ts` (M8 frozen zone)
  - `rfqs/rfqs.service.ts` (M8 frozen zone)
  - `rfq-responses/rfq-responses.service.ts` (M8 frozen zone)
- **Mitigation:** All changes are additive (new method + new internal call), no existing logic modified.
- **Requires:** M11.1 Backend Unfreeze Approval (separate document, following M10.2/M10.3 precedent).

#### Design

**Notification Trigger Points:**

| Event | Trigger Location | Recipient | Type | Title Pattern |
|-------|-----------------|-----------|------|---------------|
| Match Created | `MatchingService.match()` → `DemandsService.publish()` | Demand creator | `DEMAND_UPDATE` | "New match found for demand '{title}'" |
| Match Reviewed (ACCEPTED) | `DemandsService.updateMatchStatus()` | Match product's offer owner | `DEMAND_UPDATE` | "Match accepted for product '{name}'" |
| Match Reviewed (REJECTED) | `DemandsService.updateMatchStatus()` | Match product's offer owner | `DEMAND_UPDATE` | "Match rejected for product '{name}'" |
| RFQ Created | `RfqsService.create()` | Demand creator | `RFQ_UPDATE` | "RFQ created for demand '{title}'" |
| Response Submitted | `RfqResponsesService.create()` | RFQ creator | `RESPONSE_UPDATE` | "New response to RFQ #{id}" |

**Implementation Pattern:**
```typescript
// In notifications.service.ts (add method)
async create(data: {
  userId: string;
  type: NotificationType;
  title: string;
  message: string;
  referenceType?: string;
  referenceId?: string;
}): Promise<Notification> {
  return this.prisma.notification.create({ data });
}

// In demands.service.ts updateMatchStatus() (add after match update)
await this.notificationService.create({
  userId: offerOwnerUserId,
  type: NotificationType.DEMAND_UPDATE,
  title: `Match ${dto.status.toLowerCase()} for product`,
  message: `...`,
  referenceType: 'DEMAND_MATCH',
  referenceId: matchId,
});
```
