## 1. Authority Model（M34.6 权威保持）

本 Target-State 以 M34.6 CLOSED 状态为唯一后端基线，权威关系**冻结**：

| 对象 | 权威角色 |
|------|---------|
| Product | Capability / Catalog Authority（§1.1） |
| SupplierProduct | Supplier-owned Product Authority（§1.2） |
| Organization(type=SUPPLIER) | Supplier Authority（§1.3 / §1.5） |
| Inquiry | Existing Connection / Inquiry Authority（§1.6 / §16.1） |
| BuyerEvaluation | **Buyer User Evaluation Snapshot（NOT Domain Authority）**（ADR-M34-13 Option B） |

**核心约束（本任务强制保持，不得违反）：**

1. **BuyerEvaluation 不是新 Domain Authority**。权威始终归属被引用对象（Product / SupplierProduct / SUPPLIER Organization）。
2. **Forwarding 单一路径**：`BuyerEvaluation → Connection Context → Existing Inquiry`。不得创建第二套 Inquiry / Connection 权威。
3. **One persistence authority, multiple UX views**：仅一个持久化权威（BuyerEvaluation），Interested / Shortlisted / Comparing / Contacted 均为**同一权威的状态值 + UX 视图**，不是独立模型。

## 2. Evaluation State Architecture（4 状态产品语义）

Schema 中 `EvaluationState` 枚举冻结：

```prisma
enum EvaluationState { INTERESTED  SHORTLISTED  COMPARING  CONTACTED }
```

### 2.1 状态产品语义矩阵

| State | 产品语义 | 是否用户可见 | 是否终态 | 是否可回退 |
|-------|---------|:---:|:---:|:---:|
| INTERESTED | 买家对结果表示「感兴趣」，希望稍后回顾（短名单第一步） | 是 | 否 | 是（用户可删除 → NOT_EVALUATED，或转移到其他状态） |
| SHORTLISTED | 买家已放进「短名单」，形成备选能力集（Candidate Pool） | 是 | 否 | 是（可退回 INTERESTED / 删除） |
| COMPARING | 买家正在多个候选之间对比选型 | 是 | 否 | 是（可退回 SHORTLISTED / INTERESTED / 删除） |
| CONTACTED | 买家已对目标发起 Connection（进入既有 Inquiry flow） | 是 | **次终态（读侧）** | 是（状态本身可回退，但**不反向抹除**已产生的 Inquiry 记录） |

### 2.2 COMPARING — Persistent state 还是 Temporary workspace view？（强制判定）

**结论：COMPARING 是 backend-persistent 状态值（Database 枚举成员），不是临时 UI view。**

- **Schema 已将其持久化**（`EvaluationState.COMPARING` 是数据库枚举，`BuyerEvaluation.state` 可持该值）。
- **UI 必须消费它，而不得创造第二套 comparison state**：
  - Workspace 中 `state == COMPARING` 的评估进入「Comparing 视图」。
  - 该视图展示的是**同一 BuyerEvaluation 权威**的过滤结果（persistence → view filter），**不新增 Comparison 模型 / Comparison 表 / Comparison 状态机**。
- **临时「对比工作台（当前正在对比的一屏）」属于 Frontend transient state**（见 §10 UX State Machine）：
  - 只是「当前在 Comparing 视图内选中哪几个 BuyerEvaluation 以便横向看参数」的 UI 瞬间态；
  - **不写数据库**；刷新后由 `state==COMPARING` 集合 + URL query（如 `?compare=<ids>`）恢复；
  - **禁止**为此引入 `ComparisonAuthorized` / `ComparisonSession` 等持久化对象。
- 边界总结：**persistent = 每个 BuyeEvaluation 的 state 值 COMPARING**；**transient = UI 当前选中哪几个评估来做参数对比**。

### 2.3 状态迁移（合法 Transition）

```
            ┌─────────────────────────────────────────────┐
            │           NOT_EVALUATED (UI 派生，非 DB 值)   │
            └──────────────────┬──────────────────────────┘
                               │ Create (POST /evaluations)
                               ▼
                       ┌───────────────┐
                       │  INTERESTED   │◄─────┐
                       └──────┬────────┘      │ Rollback
                              │ PATCH(state)  │
                       ┌──────▼────────┐      │
                       │  SHORTLISTED  │──────┘
                       └──────┬────────┘
                              │ PATCH(state)
                       ┌──────▼────────┐
                       │   COMPARING   │
                       └──────┬────────┘
                              │ Connection (不直接改 state)
                       ┌──────▼────────┐
                       │   CONTACTED   │   （可由 Connection flow 触发 PATCH(state=CONTACTED)）
                       └───────────────┘

   任意非终态 ← → 其它非终态（Owner 通过 PATCH /evaluations/:id 回退或前移）
   任意状态 → DELETE /evaluations/:id → NOT_EVALUATED
```

- **单调进阶非强制**：允许跳过状态（如直接 CREATE(state=SHORTLISTED) 或 PATCH 从 INTERESTED → CONTACTED），不设严格状态机锁；后端以 `PatchEvaluationDto` 校验合法枚举值为准，不校验「必须逐级」。
- **NOT_EVALUATED 是 UI 派生状态**（当 `GET /evaluations` 未返回该 target 时），**非数据库枚举成员**。

## 3. No Second Evaluation Authority

**强制禁止新增以下任何 Domain Authority / 模型 / 表：**

- ❌ Shortlist model
- ❌ Favorite model
- ❌ Watchlist model
- ❌ Comparison model
- ❌ SavedProduct model
- ❌ SavedSupplier model

**唯一表达结构：**

```
BuyerEvaluation（唯一持久化权威）
       ↓
UI Views（同一权威的派生视图 / Filter）
       ↓
Interested · Shortlisted · Comparing · Contacted
```

**判定原则：** `Evaluation = Authority`；`Shortlist / Compare = Evaluation Views`。短期列表、收藏、对比全是同一 BuyerEvaluation 的状态视图，不得成为独立平行信息架构。

## 4. Buyer Workspace Information Architecture（IA）

### 4.1 现状审计（769 前实际存在）

Web 侧 Buyer 面当前为「/dashboard/buyer（Dashboard 概览）+ /workspace/*（散列功能页）」双轨：

- `/dashboard/buyer`：Buyer Dashboard 概览（业务快照 + 待处理 + 业务导航 DOMAIN_NAV_ITEMS）。
- `/workspace/demands` `/workspace/rfqs` `/workspace/matches` `/workspace/notifications` `/workspace/settings`：Demand / RFQ / Match / 通知 / 设置。
- `WorkspaceSidebar` BUYER 导航项：仪表盘 / 我的需求 / 我的询价请求 / 匹配结果 / 通知中心 / 设置。
- **当前没有** Evaluation 相关的 Buyer 导航项、页面、路由。

> 审计发现：Buyer Workspace 存在「Dashboard 聚合页 + 独立功能页」双轨。M34.7 Target IA 的判定基于「Evaluation 是 Buyer 个人长期状态集」，它有独立聚合价值，故作为**一级导航节点**引入；但**不**为此复制其他功能页为多级 IA（见 4.2/4.3）。

### 4.2 Target IA（M34.7）

```
Buyer Workspace
├── Overview（=/dashboard/buyer 或 Buyer 入口 Overview，聚合概览）
├── Evaluations（=/workspace/evaluations —— 单一 Evaluation 路由）
│   ├── [Filter: all]     ← query/tab
│   ├── [Filter: Interested]   （state=INTERESTED）
│   ├── [Filter: Shortlisted]  （state=SHORTLISTED）
│   ├── [Filter: Comparing]    （state=COMPARING）
│   └── [Filter: Contacted]    （state=CONTACTED）
└── Connections / Inquiry（=既有 Inquiry 权威入口，复用，不新建）
```

### 4.3 IA 判定（哪些是节点 / 哪些是 Filter）

| 候选节点 | 判定 | 依据 |
|---------|------|------|
| Evaluation 一级节点 | ✅ **真实独立 Route** | Evaluation 是 Buyer 长期状态集，有独立聚合与导航价值，且不与现有 Demand/RFQ/Match 语义重叠 |
| Interested / Shortlisted / Comparing / Contacted | ⚠️ **UI Filter / Tab，不是独立 Route** | 它们共属同一 `BuyerEvaluation` 权威，只是 state 过滤；不各自建页面路由 |
| Connections / Inquiry | ✅ **引用入口（复用既有）** | 沿用既有 Inquiry 权威，引入到 Workspace 作 Connection 出口，不新建设置/复制 |
| Overview | ✅ 保持既有 Dashboard 语义 | Buyer 业务概览保持，不重造 |

**结论：** 只引入一个一级 Evaluation Route；四个状态用 **query param / tab / filter** 表达，绝不为每个状态建独立路由。

## 5. Route Architecture Gate

### 5.1 路由契约

| 场景 | Browser URL | 说明 |
|------|------------|------|
| Public Product | `/products/[slug]` | 公开 Catalog 权威（无认证） |
| Public SupplierProduct | 依赖既有公开能力面（Product Detail 内 Supplier 能力 / Supplier 公开对比） | 公开只读 |
| Buyer Evaluations（一级） | `/workspace/evaluations` | 认证 BUYER 私有 |
| Evaluation 状态过滤 | `/workspace/evaluations?state=COMPARING`（query param） | 同一路由，filter 表达 |
| Evaluation 参数对比视图 | `/workspace/evaluations?state=COMPARING&compare=<id1>,<id2>` | transient compare selection（不新增路由） |
| Evaluation → Target | `/products/[slug]` 或公开 Supplier 能力面（deep link） | 从 Evaluation 跳回被评估对象 |
| Evaluation → Connection | → 既有 Inquiry flow（见 §6） | 复用，不新建 |
| Inquiry / Connection 出口 | 既有 Inquiry 入口（Workspace Connection 节点聚合） | 复用 |

**三一律（Browser URL = UI State = Backend Resource Identity）：**

- 每个后端资源（`BuyerEvaluation:id`、target `Product/SupplierProduct`、连接上下文）都有**可深链 URL**。
- **避免 UI-only hidden state**：所有需要「刷新后可恢复」的 UI 状态必须能从 URL 重建（见 §7.1）。
- Evaluation 的选中态（如 `state`、`compare` 选参）以 query param 表达，而非仅存内存。

### 5.2 Route 禁止事项

不得产生以下**新的平行信息架构**，除非经明确架构论证证明必要（本 Target-State 判定为不必要）：

- ❌ `/shortlists`
- ❌ `/favorites`
- ❌ `/watchlists`
- ❌ `/comparisons`
- ❌ `/buyer-evaluation-system`

**默认原则：`Evaluation = Authority；Shortlist / Compare = Evaluation Views`。** 所有短名单/对比都落在 `/workspace/evaluations` 单一权威路由下，以 state / query filter 表达。

## 6. Connection Architecture

### 6.1 现状（M34.6 已证明）

```
BuyerEvaluation → connectionContext（GET /evaluations/:id/connection）→ { target, productId, supplierProductId, orgId, organization.type=SUPPLIER }
```

Connection **不新建第二套 Inquiry**。M34 Contract 已确认 Supplier 发现/接线基于 **PUBLISHED SupplierProduct → Organization(type=SUPPLIER)**（零 Offer 依赖），Inquiry 为既有连接权威。

### 6.2 Connection CTA 唯一入口原则

**原则：Evaluation 不直接创建 Inquiry；Evaluation 进入既有 Inquiry flow。**

- 每个 Evaluate 卡片 / 详情页提供一个 **唯一 Connection CTA**（如「发起询价 Inquiry」）。
- 该 CTA 调用 `GET /evaluations/:id/connection` 解析连接上下文 → **跳转/预填到既有 Inquiry flow**（复用既有 `inquiry` API / 表单）。
- **禁止**在 Evaluation 模块旁另建「创建 Inquiry」逻辑，或绕过既有 Inquiry 权威写入。

### 6.3 必须保持的恒等

```
Evaluation ≠ Inquiry
Evaluation → Connection Context → Existing Inquiry
```

- Evaluation 记录 buyer 对 target 的「评估意图」。
- Inquiry 是**独立既有连接对象**，由既有 Inquiry 权威管理。
- Contacted 状态 = 已发生 Connection 的评估状态标记（PATCH state），不反向承载 Inquiry 数据副本。

## 7. Evaluation UX State Machine

### 7.1 状态归属（Backend vs Frontend transient）

**Backend 决定（持久化）：**
- `BuyerEvaluation.state`（INTERESTED / SHORTLISTED / COMPARING / CONTACTED）— 数据库值。
- `BuyerEvaluation.targetType / targetId` — 评估目标标识。
- `BuyerEvaluation.note` — 备注。
- 拥有权（owner = user.id）与 RBAC（BUYER）。

**Frontend transient state（不写数据库）：**
- 加载 / 错误 / 稳定 的字段（loading / error / ready）。
- UI 动画、瞬时选中（当前 hover / focus / dragging）。
- **参数对比视图的当前选中集合**（`compare=<ids>` query，或组件内 transient selection）——不是持久化 Comparison。
- 输入草稿（未提交的 note / filter）。

**铁律：Frontend transient state 不得写数据库；Backend state 不得由前端本地伪造（必须经 PATCH persist 后反映）。**

### 7.2 状态机 + 场景表

| 场景 | UI 行为 | 归属 |
|------|--------|------|
| Create | `POST /evaluations` → 成功加入列表 / 失败显示错误 | Backend(UserAction) |
| Update | `PATCH /evaluations/:id` → 乐观更新 + 失败回滚 | Backend(UserAction) |
| Delete | `DELETE /evaluations/:id` → 移出列表 / 失败回滚 | Backend(UserAction) |
| Transition | `PATCH state`（INTERESTED↔SHORTLISTED↔COMPARING↔CONTACTED） | Backend |
| Restore | 从 URL（`/workspace/evaluations` + query）重新拉取恢复 UI | URL-state（Frontend + Backend fetch） |
| Refresh | 重新 `GET /evaluations` 同步 | Backend |
| Deep Link | 直接访问单评估 URL / target / connection → 校验 owner，加载对应查看视图 | Backend(owner) |
| Unauthorized | AuthGuard → `/login`；RoleGuard → 拒绝非 BUYER | FRONTEND guard |
| Target Removed | connection / 详情解析不到 target → 显式「目标已移除」状态（非空态、非报错） | Frontend（detect）+ Backend 404 |
| Target Unpublished | 目标不再 ACTIVE/PUBLISHED → 显式「目标已不可访问」状态 | Frontend（detect） |

**NOT_EVALUATED = 派生 UI 状态**：当 `GET /evaluations` 未返回某 target，卡片显示「评估」动作（等价 NOT_EVALUATED），通过 Create 进入持久化。

## 8. Product vs SupplierProduct Display Architecture

| 维度 | Product Evaluation | SupplierProduct Evaluation |
|------|--------------------|-----------------------------|
| 语义 | **Capability / Catalog evaluation**（买家评估「这个能力型号」） | **Specific Supplier-owned supply evaluation**（买家评估「某供应商提供的该型号」） |
| 身份 | targetType=PRODUCT；被评估对象是能力目录项 | targetType=SUPPLIER_PRODUCT；被评估对象是供应商供应的型号 |
| 标题 | Product 名称（Catalog 层） | Product 名称 + 供应商标识（避免 Product=Supplier 误等） |
| 供应商信息 | 不显式展示单一 Supplier（Catalog 层，供应商为多对多） | **必须展示** SupplierProduct.organization（type=SUPPLIER） |
| 状态 | 显示 BuyerEvaluation.state | 显示 BuyerEvaluation.state |
| Connection | Connection Context 解析到该 Product 的**官方 SupplierProduct → Organization**（M34 §10.3） | Connection Context 即该 SupplierProduct → Organization |
| 跳转目标 | Product Detail（公开能力面） | 对应 Supplier 能力面 / Product Detail（Supplier 上下文） |

**强制边界（禁止）：**
- ❌ `Product = Supplier`（Product Evaluation 不得被当作 Supplier 本身）。
- ❌ `Product Evaluation 自动等价 SupplierProduct Evaluation`。两者是不同 targetType 的评估；Workspace 列表须区分「Catalog 评估」与「供应商供应评估」，并按 §8 身份/标题/供应商列展示。

## 9. Supplier Context Architecture

- 保持 `SupplierProduct.organization = Organization(type=SUPPLIER)`。
- 展示 Supplier 上下文时，从 **SupplierProduct → Organization(type=SUPPLIER)** 派生，**不得新增 Supplier Domain**（Organization 即 Supplier Authority）。

- **禁止**为 Workspace 创建独立的 `SupplierProfileView` / `SupplierSummary` 等新实体或表。

## 10. Empty / Error / Loading Architecture

**铁律：`Empty ≠ Error`。** Empty 是「没有数据」的合法状态，Error 是「请求失败」的异常状态；两者的 UX 表现、文案、可恢复动作必须分离。

| 场景 | UX 行为 |
|------|--------|
| No Evaluation | Empty 态：「尚无评估。去发现并评估检测能力。」+ 指向 Discovery / Search 的 CTA。非错误。 |
| Evaluation Loading | 骨架屏 / Loading 指示；不闪空白。 |
| Evaluation Error | Error 态：「加载评估失败」+ 重试。非空态。 |
| Target Missing | 目标已移除 → 显式「该评估的目标已移除」灰态 + 提供删除评估；非 404 报错崩溃。 |
| Target Unpublished | 目标不可访问 → 显式「目标已停用/未发布」灰态；可继续管理评估或删除；不伪造可连接。 |
| Connection Unavailable | Connection CTA 在该 target 不可连接时明确禁用并说明（如无 PUBLISHED SupplierProduct / 非 SUPPLIER org）；非空态。 |
| Unauthorized | AuthGuard 拦截到 /login；RoleGuard 拒绝非 BUYER。 |
| Session Expired | 401 → 自动 refresh；refresh 失败 → 提示登录失效并跳 /login。 |
| Empty Comparison | Comparing 视图无评估 → 「尚无对比项」Empty 态 + CTA。非错误。 |
| Empty Shortlist | Shortlisted 视图无评估 → 「短名单为空」Empty 态 + CTA。非错误。 |

## 11. Desktop + Mobile Architecture

**Mobile = 与 Desktop 同等级架构约束，不得后补。** 要求 `Desktop IA = Mobile IA`（信息架构一致），但**不要求** Desktop Layout = Mobile Layout。

### 11.1 响应式信息层级

- 同一 IA（Overview / Evaluations / Connections）在 Desktop 与 Mobile 一致。
- Mobile 上以「优先信息 → 交互」重组：列表 → 卡片化；Detail 走独立页面/抽屉；避免横向溢出。

### 11.2 响应式交互优先级 / CTA / Card / 对比 / 连接

| 项 | Desktop | Mobile |
|----|---------|--------|
| Evaluation 列表 | 多列表格 / 卡片网格 | 单列卡片流（无水平滚动） |
| 状态 Filter | 顶栏 Tab / 侧栏 Filter | 下拉 / 横向 Tab（可滚动，不溢出） |
| CTA 位置 | 卡片 / 详情中稳定可见 | 底部固定 CTA 或卡片可见大按钮（touch target ≥ 44px） |
| Evaluation Card | 展开含参数摘要 | 精简卡，参数用轻量详情，不横向堆砌 |
| 参数对比视图 | 横向对比表（可横向滚动容器内） | **不可 unbounded 横向表**；改为可切换的纵向卡片对比 / 翻页对比，避免横向溢出与 Desktop-only 交互 |
| Connection | 右侧 CTA | 底部 CTA / 明显按钮 |

### 11.3 Mobile Minimum Requirements

| 能力 | Mobile 行为 |
|------|-------------|
| Evaluation list | 单列卡片，无横向溢出 |
| Evaluation state filter | 可触达的 filter（Tab / 下拉），无溢出 |
| Evaluation detail | 独立视图 / 抽屉，无 desktop-only 操作 |
| Target navigation | 可跳转公开能力面 / Product Detail |
| Connection CTA | 可见、可触达（合理 touch target） |
| Inquiry entry | 复用既有 Inquiry 入口；移动端可用既有表单 |

**COMPARING 窄屏表达：** 窄屏禁止 fellinto unbounded 横向对比表；以「当前选中评估列表 + 逐项卡片对比 / 纵向对比」呈现，保持 same comparing logic（persistence=state），仅 presentation 变换。禁止 Horizontal overflow / Unbounded comparison table / Desktop-only interaction。

## 12. Accessibility / Interaction Architecture（架构要求，不实施）

必须定义（implementation 阶段执行）：
- **Keyboard navigation**：全链路可键盘操作。
- **Focus order**：逻辑顺序，无焦点丢失 / 陷入。
- **Button semantics**：真实 button / link，非 div 冒充。
- **State indication**：非仅 color；补齐文本 / icon / aria。
- **Loading indication**：aria-busy / 明确文案。
- **Error announcement**：live region 宣告。
- **Touch target**：≥ 44px 关键交互。

**禁止 color-only state indication / emoji-only semantic 作为核心交互依赖。**

## 13. API Consumption Contract

基于 M34.6 已实现 API，**禁止新增 / 修改 / 补漏 API**。前端未来消费：

| API | UI Use Case |
|-----|-------------|
| `POST /evaluations` | 创建评估（Create / 卡片「评估」动作） |
| `GET /evaluations` | 列出我的评估（Overview / Evaluations 列表，支持 query=state） |
| `GET /evaluations/:id` | 单评估详情（Evaluation Detail） |
| `GET /evaluations/:id/connection` | 解析 Connection Context → 进入 Inquiry |
| `PATCH /evaluations/:id` | 更新 state / note（Transition / Update） |
| `DELETE /evaluations/:id` | 删除评估（Delete / 移除） |

**API GAP 处理：** 若 M34.7 UI 需要、但现有 API 不支持（如「按 state 过滤分页」是否足够，或需要单个 target 的当前评估查询），**必须记录为 API GAP** 并列为 **Future / Separate Authorization**，**不得在本任务偷偷补 API**。当前判定：`GET /evaluations` 提供分页列表，状态过滤可在前端按返回 `state` 过滤或以 query 驱动；若后端需支持服务端 `state` 过滤，属 API GAP → Future Authorization。
