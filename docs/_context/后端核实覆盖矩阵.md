# VISNDT 后端核实覆盖矩阵

> 用途：追踪每个模块的核实状态，避免"整份文档到底可不可信"这种笼统判断。
> 维护规则：任何工具（Trae/Claude Code/人工）只要真正读过某模块的完整
> 源码并有原始证据（贴代码/贴命令输出），就把对应行更新为「已核实」+
> 日期 + 证据来源；仅凭转述/推测/前端间接证据的，标「未核实」，不要
> 因为"看起来合理"就升级状态。

## 状态定义

- ✅ **已核实**：直接读过完整源码或跑过命令，有据可查
- ⚪ **部分核实**：读过关键片段（如路由清单）但未读完整 service 实现
- ❌ **未核实**：仅依赖转述、前端间接推断，或完全没有信息来源
- 🔴 **已核实且发现真实缺陷**：核实过程中确认存在与文档声明不符的问题

## 专项：e2e 真实业务通过率

- **2026-09-10 真实结果**（环境已通）：**165 个用例，117 通过 / 48 失败；8 个套件失败 / 11 通过**
- 失败套件：`matching/match-flow`、`auth/auth-invitation`、`users/users-security`、`matching/performance-benchmark`、`demands/demand-flow`、`organizations/organizations-security`、`offers/offer-core`、`rfq/rfq-core`
- **已排除环境因素**：Prisma 能连库执行（不再是无数据库的初始化报错），数据库 `migrate status` up-to-date（38 迁移已应用）
- 原始日志：`F:\Desktop\VISNDT\e2e_full_result.log`（171KB，`Test Suites: 8 failed, 11 passed` / `Tests: 48 failed, 117 passed`）
- **两类新发现根因（非环境问题）**：
  1. **审计日志中间件 FK 冲突** — `prisma.service.ts` 的 `$use` 中间件对全部 model 的全部写操作自动写 `AuditLog`，`operatorId` 引用 User；测试清理 `user.deleteMany` 时命中外键 `audit_log_operator_id_fkey` → 清理抛错 → 整套件级联失败。这同时影响 `UsersService.remove` 与用户删除路径。
  2. **Prisma schema 漂移导致测试 fixture 失效** — `Product.categoryId` 已改为非空，但 e2e 的 `createProductWithParams` 仍传 `categoryId: undefined` 且未建 `category` → `PrismaClientValidationError: Argument 'category' is missing`。
  3. 少量真实断言差异，如 auth-invitation Case1「注册无邀请码」测试期望 401，实际 register 抛 `BadRequestException`(400)。
- 推论：由于大量失败是中间件/cascade 触发，**这 48 个失败不能简单归为"业务逻辑真错"**——相当一部分是测试基建缺陷阻断了断言执行；但 `111 通过`说明核心主链路（产品、admin、rematch、category-filter、rate-limit、workflow-permission 等）是真实跑通的。

## 维护方式

每次任何工具真正核实过一个模块，回来更新这张表对应的单元格
（状态 + 日期 + 证据文件名/行号），**不要整份重写**——这样这张表
本身也变成"只追加、可信赖"的记录，而不是又一份可能过时的静态文档。
